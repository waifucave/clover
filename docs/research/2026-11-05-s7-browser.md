**One result changes a [D] (the owner decides).** §12.1 puts headless tabs "in a hidden window that is never shown". Such a tab runs its timers but never draws on any OS: no rAF, no `IntersectionObserver` or `resize`, and no `capturePage`. On Wayland it gives no picture at all. The owner's design holds otherwise: tabs live in the app's own Electron, move without reloading and keep running while every window is closed. What has to change is the window. A tab a bot is working in needs a host window that is **shown but can't be seen or touched** (1×1, transparent where the OS allows, click-through, unfocusable, out of the taskbar and the Dock). A tab nobody is using can rest in the never-shown window, throttled as a background tab in Chrome is. The wording is under "Proposed spec edits", with four [P] edits.

| `windows-latest` | Windows Server 2025 (build 26100), x64 | 4, 16 GB | 1024×768 at 1× | none: software (WARP) |
| `ubuntu-24.04` | Ubuntu 24.04, kernel 7.0, x64 | 4, 16 GB | Xvfb 1920×1080 (X11), or headless Weston 13 (Wayland), or none (Ozone headless) | none: software |
| `ubuntu-24.04-arm` | Ubuntu 24.04, arm64 | 4, 16 GB | none (Ozone headless) | none |

Versions: Electron 45.2.2 (Chromium 156.0.8078.80, Node 24.22.2), Chrome for Testing 156.0.8078.80 (the same Chromium), Bun 1.3.14. These are the latest OSes GitHub offers, one version behind the spec's floor (macOS 27, Windows 11, Ubuntu 26.04): the live gates check the real ones.

The prototype is self-contained: its own `package.json`, one folder below `spikes/` so it is not a workspace member. It has four parts.

* **The probe page.** Every tab loads it. It counts a 10 ms interval, a chained 10 ms timeout and rAF, with the longest gap between ticks. It logs `visibilitychange`, resize, freeze and focus with their times. It keeps state that a reload would lose: a random token made at load, a field's value, `sessionStorage`, a scroll position, and an open server-sent-events stream. It plays a looping VP8 + Opus clip and runs an `AudioContext`.
* **A frame marker.** The probe page draws a strip of 52 black and white cells in its top-left corner, encoding the time it was drawn (ms) and a draw counter, with a checksum. Any picture of the page (`capturePage`, a CDP screenshot or screencast frame, a decoded WebRTC or WebCodecs frame) is decoded back to "when was this drawn". That gives each picture's freshness, and each streamed frame's end-to-end latency, on one machine's clock.
* **The Electron probe** (`src/electron/`). Tabs are `WebContentsView`s, sandboxed, with no Node and no preload, each in its own partition (spec §12.1). The probe puts them in each candidate place and measures them there.
* **The daemon side** (`src/cft/`, `src/pair/`). A pinned Chrome for Testing install with its own zip reader and a CDP client over the DevTools pipe. A minimal Bun daemon and Electron app for the pair, with launchd, `systemd --user` and Task Scheduler login items.

The workflow ran seven times ("rounds"), each fixing what the one before found, and then once more in full on the PR's head (`results/final/`, every job green). Every round's JSON and summary are under `results/`. Caveats that hold throughout:

* Windows and Linux runners have no GPU, so their CPU numbers are for software rendering and software video encoding.
* Every "link" is loopback, so latencies are floors before any network.
* Memory is the best number each OS has: macOS physical footprint (libproc), Linux PSS, and Windows private bytes. A sum of resident sizes counts Chromium's shared pages once per process.

## 1. Moving a tab between headless and shown

**Verdict: works, on all three OSes and every kind of display.** A tab moves by moving its `WebContentsView` out of one window and into another (`removeChildView`, `addChildView`, then `setBounds`). Nothing reloads, from any of the hidden places tried.

**Method.** A probe tab holds everything a reload would lose (see above) and plays its clip. It goes hidden → shown → hidden four times from each hidden place: a view in no window (`detached`), a view in a window that is never shown (`hiddenWindow`), the same with the agent's size forced by CDP (`hiddenWindowFit`), and the two shown-but-unseen host windows of §2 (`invisibleWindow`, `tinyWindow`). Each cycle checks the token, the field, `sessionStorage`, the scroll position, how many times the server saw the event stream open, and how far the clip played. It also times the first fresh picture of the shown tab (polled with `capturePage` from the moment of the move, decoded from the frame marker) and the page's first rAF. Numbers are from round two; round one agreed except for the fresh picture, whose round-one figure (1.5 s) was a measuring bug.

Notes:

* **The layout follows the view,** as Winter's headless lesson says (§12.1): a shown tab lays out at the browser view's size, and its 1280×800 comes back when it goes back to its host. A page in a place that draws nothing sees `innerWidth` change but gets its `resize` event only at its next rendering step (round one).
* **A view in no window is the worst place to show from on macOS** (909 ms at p95), and it draws nothing while there (§2), so it is not a place to keep tabs.
* **The clip kept playing everywhere,** hidden or shown. A page playing sound is exempt from background throttling (§2), so the clip says nothing about the timers of a silent page.


## 2. Hidden tabs: throttling, pictures and cost

**Verdict: works with limits, and not as the spec has it.** A tab in a window that is never shown, or in no window, **draws no frames on any OS.** With `backgroundThrottling: false` its timers run at full speed and the page says it is visible, but rAF never runs, and nothing that waits for a rendering step happens: `resize` events, `IntersectionObserver` (lazy images, infinite scroll), `ResizeObserver`, rAF-driven apps. `capturePage` fails there on every OS, with or without `stayHidden` ("Current display surface not available for capture"). What does work everywhere is a **host window that is shown but can't be seen or touched**: 1×1 pixel, frameless, not focusable, click-through and out of the taskbar. A 1280×800 view inside it draws at the display's rate, and `capturePage` gets the whole 1280×800 picture in 7–29 ms. On CI it kept drawing even under another window.

**Method.** Each configuration is a fresh probe tab in its own partition, measured over 5 s after 2 s to settle. "Throttling" is `webPreferences.backgroundThrottling`. CPU is the whole app's (main, GPU, network and renderer processes), as a percentage of one core. Numbers are from round two unless marked; round three re-ran everything and agreed.

**Timers and frames** (rates in Hz; rAF 0 means the page draws nothing):

* **Sound exempts a page from throttling,** whatever the setting, as in Chrome. Its media plays at 0.84–0.95× in every hidden place (frames decoded at 25–28 fps).
* **Wayland's 40 Hz is the output's rate** under headless Weston; the shown view runs at 40 too.

## 3. Wayland

**Verdict: works with limits.** Under headless Weston the 1×1 host window works as on the other systems. What Wayland changes:

* **A never-shown window gives nothing at all.** On macOS, Windows and X11 a CDP screenshot or one frame of a frame subscription still gets a picture from a never-shown window; on Wayland both time out, and even tab capture (`getUserMedia` of the tab) fails at once, with no message. Any design that leaves working tabs in a never-shown window fails on Wayland first.
* **An app can neither place a window nor make it transparent.** `setOpacity` exists only on macOS and Windows, and the compositor picks every window's position. `skipTaskbar` and always-on-top do nothing either. So the 1×1 host is a real window that the compositor places, a one-pixel dot that can show in its window list and overview.
* **The 1×1 window draws at the output's rate:** rAF 40 Hz, as the shown view does under headless Weston, and `capturePage` takes 22 ms (11 ms old). The screencast runs at 40 fps and WebCodecs at 30 fps (§6). Moving tabs works as on X11 (§1).
* **What headless Weston can't show** is how GNOME (Mutter) and KDE (KWin) treat the dot. Both stop sending frame callbacks to a window that is covered, minimized or on another workspace, and Chromium then stops drawing it. Round three put an opaque full-screen window over the dot under Weston, and it kept drawing at 40 Hz, as expected, since Weston doesn't hold frame callbacks back from covered windows. So this is a live gate (below).
* **The fallback is XWayland.** Started with `--ozone-platform=x11` on a Wayland desktop, the app is an X11 client, which times its own frames and gets the X11 numbers above (rAF 60, `capturePage` 13 ms). It loses fractional scaling (blurry text on scaled screens) and Wayland-native input methods, so it should be a setting, used only if the live gate fails.
* Electron 45 uses Wayland natively on a Wayland session (the default since Electron 38). Its sandbox needs the AppArmor profile on Ubuntu, as on X11 (§5).


## 4. Chrome for Testing where no app runs

**Verdict: works, with the headless shell, sandboxed on every OS.** On Linux the sandbox needs the AppArmor profile, as Electron does (§5). One trap cost four rounds on Linux, and it matters beyond the browser: see "The Linux stall" below.

**Method.** `src/cft/` is a daemon-side installer and driver, in Bun, launching nothing outside CI:

* **Install** (`install.ts`, `unzip.ts`). It downloads the pinned build from Google's `chrome-for-testing-public` bucket and checks the size, the SHA-256 against `pins.json`, and the server's MD5. Then it unpacks with its own zip reader, which handles ZIP64, file modes, symlinks and CRCs, and refuses entries that would escape the folder. The unpack goes into a staging folder that is renamed into `<home>/browsers/cft/<version>/<artifact>-<platform>`, so a half-written install is never used. The version is pinned to **156.0.8078.80, the Chromium in Electron 45.2.2**, so the app's browser and the server's one are the same engine. All eight archives (two kinds × macOS arm64, Windows x64, Linux x64 and arm64) were pinned from round two's downloads and matched in round three.
* **Start** (`cdp.ts`). The browser is started with **`--remote-debugging-pipe`**: no port, so no other local process, a bot's Bash included, can reach it. On macOS and Linux the pipes are two `pipe(2)` pairs made over `bun:ffi` and handed to `Bun.spawn` as fds 3 and 4 (`fdpipe.ts`, Winter's road). On Windows, Chromium wants handle values, so the pipes are inheritable anonymous pipes named with `--remote-debugging-io-pipes` (`winpipe.ts`). A loopback port is kept only as a fallback.
* **The same tab operations as the app's checks:** background timers and rAF, a resize without a reload, JPEG and PNG screenshots, a screencast, one browser per bot with its own `--user-data-dir`, and the cost of a browser, a tab, a browser context and a second bot's browser.

Two artifacts were compared: `chrome-headless-shell` and full Chrome in `--headless` mode. Numbers are from round three for macOS and Windows (round five and six agreed) and round seven for Linux.

Notes:

* **Use the headless shell.** In full Chrome's headless mode, a tab behind another in the same window is hidden and throttled (1.0–1.2 Hz, rAF 0, its media stopped). On macOS, one tab in a window of its own was hidden too. Full Chrome also costs four to six times as much (263–451 MiB a browser, 48–57 MiB a tab). The headless shell has no windows to stack: every tab is visible and draws, and its layout is the agent's exact 1280×800 (full Chrome's window frame took it to 1264×649 and 1280×657).
* **A bot's browser is its own process tree with its own profile folder**, which isolates cookies and storage and keeps them across restarts. A browser context (`Target.createBrowserContext`) costs no more than a tab but keeps nothing on disk, so it suits throwaway work. Each further bot's browser costs another base (44–118 MiB).
* **The pipe is the right transport.** It starts as fast as the port (within 10–20 ms), and no other process can reach it. A Windows reader that looped while bytes were waiting starved every timer during a screencast (round two's 17-minute hang); reading once per tick fixed it.
* **The Linux stall: never start a browser through `node:child_process`'s stdio pipes.** Rounds three to six lost the connection to a Linux browser at arbitrary moments while it kept running: either it could no longer write to us ("Could not write into pipe"), or it read end-of-file from us ("Connection terminated while reading from pipe"). Our own writes had all gone out, and a reader on a worker thread failed the same way, so something closed our descriptors while they were in use. The one Linux-only step before every failure was a fallback start through `node:child_process` with extra stdio pipes, reached because the sandboxed native start fails there without the AppArmor profile; that child crashed at once ("No usable sandbox!"). Round two had already seen the same transport hand the browser an end-of-file. Round seven tried the native pipe unsandboxed before any other transport, and all four Linux runs (x64 and arm64, both readers) passed every step. The likely cause is a late close of a recycled descriptor in Bun's child-process code, though the spike didn't isolate it. For C and every lane that spawns from the daemon, the rule is the same: on Linux, pass extra descriptors to `Bun.spawn` as plain numbers, as `fdpipe.ts` does, and never through `node:child_process`'s extra `"pipe"` slots.
* **On a bare Ubuntu 24.04 server** the headless shell lacks 21 libraries (X11, NSS, ATK, GBM, ALSA, D-Bus, GLib…). Installing 20 packages (143 with their dependencies; the list is in `scripts/ci/cft-deps.sh`) makes it start. The `clover-core` server package should depend on them.
* **Cookies on disk are not encrypted** with `--password-store=basic` and `--use-mock-keychain`, which a server with no keyring needs. The profiles live under the daemon's home, with its permissions.
* Chrome for Testing has no auto-update. The daemon must move the pin itself: with each Electron upgrade, to keep the engines equal, or sooner for a security fix.


## 5. The app and daemon pair

**Verdict: works on all three OSes,** with one Windows fix. Task Scheduler does not restart a crashed task, so the daemon runs under a small supervisor.

**Method.** The prototype has three parts:

* **A minimal daemon** (`src/pair/daemon.ts`, compiled with `bun build --compile`). It holds an OS lock on its home and listens on `<home>/run/core.sock` (on Windows, a named pipe). It starts the app through the OS when none is connected within 2 s. It restarts an app that went away without saying so, after 1, 2, then 4 s, and the start after the third crash in two minutes is in safe mode. On the app's Quit it exits 0.
* **A minimal app** (`src/pair/app-main.ts`). It has no window and a tray menu with Quit, and keeps one instance per user. It starts the daemon through the OS when none answers. When the daemon goes away without saying so, it reconnects every 500 ms and starts the daemon itself after 3 s.
* **The login items** (`src/pair/units.ts`):
  * macOS: a launchd user agent with `RunAtLoad`, `KeepAlive {SuccessfulExit: false}` and `ThrottleInterval` 1.
  * Linux: `systemd --user` units, the daemon's with `Restart=on-failure` and `RestartSec=1`. The app has a unit of its own, which the daemon starts with `systemctl --user start`, so it lives in its own cgroup.
  * Windows: a Task Scheduler task for the daemon with a logon trigger, an interactive token, least privilege, no time limit, not stopped on battery, and normal priority. There is an on-demand task for the app, or the daemon spawns it as a detached child (both were measured).

The runner (`src/pair/run.ts`) installs these, starts the daemon as a login would, and then walks through: a second daemon on the same home, an app crash, a crash loop, two daemon crashes (one with the app's help switched off), the tray's Quit, a user starting the app, and the daemon side's Quit. The numbers below are from two rounds, which agreed within a few ms.

**What lanes E and C need to know**

* **The lock is the kernel's,** so a crashed daemon never leaves a stale one. On macOS and Linux it is `flock(LOCK_EX|LOCK_NB)` on `<home>/run/core.lock`. On Windows it is the lock file opened by `CreateFileW` with no sharing, over Bun's FFI (`src/pair/lock.ts`). A second daemon exits **0**, so its login item does not loop.
* **macOS.**
  * Set `ThrottleInterval` to 1. Without it, launchd waits up to 10 s before restarting a crashed job.
  * `KeepAlive {SuccessfulExit: false}` gives exactly "restart after a crash, not after a Quit".
  * The app starts the daemon with `launchctl kickstart gui/<uid>/<label>`. The daemon starts the app with `open -n -g -a` (`-g`: in the background), so launchd is the app's parent.
  * A signed app should register through `SMAppService.agent`, which Electron 45 exposes as `app.setLoginItemSettings({ type: 'agentService', serviceName })`. CI cannot test it, since it needs the signed bundle with the plist inside, so it goes to the live gates.
  * Use `LSUIElement` to keep the app out of the Dock. The spike called `app.dock.hide()` after start.
* **Windows.**
  * **Task Scheduler's "restart on failure" did not restart a killed task**, as a plain task or with the app started as a detached child. The task should run `clover-core supervise`, a mode of the same binary that runs the daemon as its child. The supervisor restarts the child after a crash, after 0.5, 1, 2, 4 s and so on, and ends when it exits 0 (`src/pair/daemon.ts`). Measured: back in 0.6 s, then 1.2 s, and Quit ends the supervisor, so nothing restarts until the next login.
  * The app's own restart after 3 s (`schtasks /Run`) is the second net.
  * Task XML defaults to override:
    * `ExecutionTimeLimit` defaults to 72 hours, after which the task is stopped. Set `PT0S`.
    * `DisallowStartIfOnBatteries` and `StopIfGoingOnBatteries` default to true, so a laptop on battery would not start the daemon at logon, or would stop it. Set both false.
    * `Priority` defaults to 7, below normal. Set 5.
    * Set `MultipleInstancesPolicy` to `IgnoreNew`.
  * `InteractiveToken` worked on the runner, whose user is logged on. Whether a **standard (non-admin) user** can register a logon-trigger task for themselves is a live gate, since the runner is an administrator.
  * The app lived through the daemon's crash both when it was started by its own on-demand task and as the daemon's detached child. The task is cleaner: the app is then never in the daemon's job object.
  * The named pipe (`\\.\pipe\clover-…`) works with Bun's `node:net`, both serving and dialling.
* **Linux.**
  * The app needs its own unit. Started as the daemon's child, it would sit in the daemon's cgroup, and `KillMode=control-group` would take it down with any daemon restart.
  * The app unit needs the session's `DISPLAY` or `WAYLAND_DISPLAY`. A desktop session imports these into the user manager. The spike did it with `systemctl --user set-environment`.
  * On the runner a user manager existed only after `loginctl enable-linger`. That is right for servers (§3.1) and not needed on desktops.
  * The XDG autostart entry is generated (`xdgAutostart` in `units.ts`), but only a real desktop session can run it, so it is a live gate.
* **Electron's sandbox on Ubuntu 24.04 needs the AppArmor profile** the deb and rpm install (spec §4). Without it Electron aborts at once with exit 133: "The SUID sandbox helper binary was found, but is not configured correctly". With a profile that grants `userns` to the binary (`scripts/ci/apparmor.sh`), it runs sandboxed. The AppImage cannot install one, so on Ubuntu 23.10 and later the spec's fallback package starts sandboxed only after the user installs the profile; otherwise it needs `--no-sandbox`.

## 6. The streamed view on other devices

**Verdict: works, with encoded video rather than pictures.** For a tab that moves, WebCodecs video over the link gives 30 fps at 29–68 ms on loopback for about 2.3 Mbit/s. JPEG pictures, as Winter's phone mirror sends them, give 60 fps for 35–66 Mbit/s, far more than a phone's link should spend. With acks and only the newest picture kept, they would fall to what the link carries, a few frames a second.

**Method.** A tab in a host window, and a viewer page in the same app, joined by a loopback WebSocket that stands for the link. Four roads:

* **CDP screencast:** `Page.startScreencast`, JPEG at quality 70, each frame acked, newest only (Winter's road).
* **`capturePage` polled at 30 fps**, sent as JPEG.
* **WebRTC:** tab capture (`getMediaSourceId`, then `getUserMedia` with `chromeMediaSource: 'tab'`) into an `RTCPeerConnection`, with VP8 or H.264.
* **WebCodecs:** the same tab capture through `MediaStreamTrackProcessor` into a `VideoEncoder` (H.264 or VP8, 2.5 Mbit/s target, a keyframe every 2 s). The encoded chunks go over the link to a `VideoDecoder` in the viewer.

Two contents: the whole page animating (worst case), and a page where only the frame marker changes, twice a second. Latency runs from the marker's draw time to the decoded frame at the viewer, on one clock. Each road ran for 10 s after a warm-up (6 s for WebRTC, 2 s for the rest).

**The whole page animating** (frames per second, latency p50, kbit/s):

| Road and source | macOS | Windows | Linux X11 | Linux Wayland |
| :- | :- | :- | :- | :- |
| Screencast, shown tab | 60 fps, 40 ms, 48 900 | 64 fps, 29 ms, 50 900 | 60 fps, 36 ms, 55 000 | 38 fps, 71 ms, 34 900 |
| Screencast, 1×1 host window | 59 fps, 48 ms, 57 000 | 64 fps, 33 ms, 60 600 | 60 fps, 42 ms, 66 100 | 40 fps, 73 ms, 43 800 |
| Screencast or polled `capturePage`, never-shown window | no frames | no frames | no frames | no frames |
| **WebCodecs H.264, 1×1 host window** | **30 fps, 51 ms, 2240** | **30 fps, 31 ms, 2160** | **30 fps, 34 ms, 2400** | **30 fps, 68 ms, 2380** |
| WebCodecs H.264, never-shown window | 30 fps, 43 ms, 2240 | 30 fps, 29 ms, 2170 | 30 fps, 32 ms, 2400 | fails (no capture) |
| WebCodecs VP8, never-shown window | 30 fps, 62 ms, 2290 | 30 fps, 30 ms, 2180 | 30 fps, 34 ms, 2420 | fails |
| WebRTC VP8, never-shown window | 4 fps, 180 ms, 680 | 26 fps, 38 ms, 2490 | 21 fps, 42 ms, 2520 | fails |
| WebRTC H.264, never-shown window | 13 fps, 201 ms, 2380 | 15 fps, 56 ms, 2500 | 13 fps, 68 ms, 2490 | fails |
| Polled `capturePage`, opacity-0 window | 30 fps, 59 ms, 29 600 | 32 fps, 33 ms, 30 400 | — | — |

**Only the marker changing:** every encoded road sends what changes and nothing else: 1–2 fps, 8–113 kbit/s, 15–57 ms. WebCodecs H.264 sent 8–34 kbit/s.

**CPU** (% of one core, with no hardware encoder on the Windows and Linux runners): capture and encode 75–113% for WebCodecs, 58–110% for WebRTC and 70–159% for the screencast. The viewer used 10–43%.

Notes:

* **Tab capture makes a never-shown tab draw while it is captured** (the source's rAF went to 60–64 Hz on macOS, Windows and X11), the only thing besides being shown that does. On Wayland it fails.
* **WebRTC is the wrong road here.** Its congestion control starts low and climbs, and in a 6 s warm-up it reached only 4–26 fps. It also wants ICE and STUN, which the link (S1) already does. WebCodecs hands the frames to us, and the link carries them on a stream of its own.
* **The bitrate is ours to set:** WebCodecs takes a target bitrate and keyframes on demand. When the link falls behind, the sender drops frames up to the next keyframe and lowers the target. That keeps "newest only" for video.
* A screenshot for a bot stays a still picture (JPEG or PNG through CDP, or `capturePage`), as today.


## Proposed spec edits

1. **Touches a [D]: the owner decides.** §12.1, the first [D] bullet under "How".
   * Now: "A tab is either headless, in a hidden window that is never shown, or shown in the browser view, and it moves between the two without reloading."
   * Proposed: "A tab is either headless, in a host window the user never sees, or shown in the browser view, and it moves between them without reloading. The host window is shown but can't be seen or touched: 1×1, transparent where the OS allows, click-through, unfocusable, and out of the taskbar and the Dock. A tab no bot is using rests in a window that is never shown."
   * Why: §2 and §3. A never-shown window draws nothing on any OS, and on Wayland nothing can take a picture of it.
2. **[P]** §12.1, "How", the sentence on throttling and screenshots.
   * Now: "Headless tabs are not throttled in the background, and their screenshots are taken without showing them (`capturePage` with `stayHidden`); S7 checks Wayland, where frames can stop anyway."
   * Proposed: "A tab a bot works in has background throttling off and draws at the display's rate in the host window. Its screenshots are `capturePage` of its view, which needs no `stayHidden` there. A tab that no bot has used for a few minutes, and that plays no sound and that no one watches, rests in the never-shown window with throttling on, as a background tab in Chrome does. It goes back to the host before the bot's next command. On Wayland the host can't leave the window list, and whether GNOME and KDE keep drawing it when it is covered is a live gate; the fallback there is XWayland (`--ozone-platform=x11`)."
3. **[P]** §12.1, "From another device".
   * Now: "the view streams pictures over the link, as Winter's phone mirror does (newest picture only, acked, on its own low-priority stream)"
   * Proposed: "the view streams the tab as video over the link: tab capture encoded with WebCodecs (H.264, else VP8) in the app, about 2.3 Mbit/s for 30 fps of full motion and tens of kbit/s for a still page, on its own low-priority stream. When the link falls behind, the sender skips to the next keyframe and lowers the bitrate, so a viewer only ever waits for the newest picture."
4. **[P]** §12.1, "Where no app runs".
   * Now: "the browser is Chrome for Testing or Chromium's headless shell, driven by the daemon"
   * Proposed: "the browser is Chrome for Testing's headless shell. It is pinned to the Chromium of the app's Electron, checked against a SHA-256 pin, and driven by the daemon over the DevTools pipe (no port), with a profile folder per bot. On Linux it needs the AppArmor profile, as Electron does, and the server package's dependencies (S7 lists them)."
5. **[P]** §3.1, the always-on pair, a line for Windows: "On Windows the logon task runs `clover-core supervise`, which runs the daemon as its child and restarts it after a crash: Task Scheduler's restart on failure did not fire for a killed task (S7)."

Nothing else in the spec conflicts with these results. §4 already makes the deb and rpm the main Linux packages because of the AppArmor profile, and S7 confirms why: without the profile, Electron exits at once (status 133) and the headless shell refuses to start sandboxed.


## Risks

1. **The host window on real desktops.** On CI the 1×1 host kept drawing under an opaque window on macOS, Windows, X11 and Weston. Real sessions add more: Spaces and full-screen apps, Stage Manager, the lock screen, a sleeping display and App Nap on macOS; virtual desktops, Win+D and the lock screen on Windows; and on Wayland, compositors that stop frame callbacks to a covered window. If one of these stops the host, its tabs behave like never-shown tabs: their timers run, they don't draw, and a picture is either refused or old. M1's freshness probe (below) must tell the bot so, rather than hand it an old picture. Each case is in the live gates below.
2. **Drawing costs CPU.** A tab that draws costs what a shown tab does (19–30% of a core for an animated page without a GPU), so the rest rule in edit 2 matters on laptops. A bot that watches a busy page keeps one core partly busy.
3. **Two Chromiums to keep equal.** Chrome for Testing has no auto-update, so the daemon's pin must move with every Electron upgrade, and sooner for security fixes. That is a release-pipeline task (lane M).
4. **Wayland's dot.** The 1×1 host shows in the window list and overview of a Wayland desktop. If GNOME or KDE make that ugly or stop drawing it, the XWayland fallback costs fractional scaling.
5. **A stray close in Bun's child-process code on Linux** (§4, "The Linux stall"). Dropping one transport ended the browser's stalls, but the daemon spawns much else (Bash, plugins, agents). If the cause is in Bun, any of the daemon's descriptors can be hit. Lane C should reproduce it on its own, and file it with Bun if it holds.
6. **Windows makes the host 32×31.** A frameless window can't be smaller there, so the host must stay at opacity 0 (round five ran it so, and it drew at 64 Hz). On X11 the host is a visible 1-pixel dot, which a top panel usually covers.
7. **The numbers come from CI runners** with 3–4 vCPUs and no GPU on Windows and Linux. Absolute CPU figures will move on real machines. The verdicts rest on what works and what draws, which won't.
