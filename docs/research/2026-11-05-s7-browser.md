**One result touched a [D], and the owner has decided it (November 5, 2026): design B, with decision 1a's hybrid. Decision 2, whether Clover carries Electron patches, is open, and B is built unpatched as the baseline.** §12.1 puts headless tabs "in a hidden window that is never shown". A plain tab there runs its timers but never draws, on any OS: rAF stops, and so do `IntersectionObserver`, `ResizeObserver` and `resize` events. `capturePage` fails, and on Wayland nothing can take a picture of it at all (§2). Two designs fix it, and both keep what the owner decided (§14.2 item 56: tabs in the app's own Electron, never reloading between headless and shown, and running while every window is closed).
* **B, Winter's viewport (§7), recommended and chosen.** A bot's tab is drawn offscreen, in a window that is never shown, at a rate the app sets. When the person looks, the browser view draws its frames and sends their input back without a reload, as Winter's panel did. No window appears on any OS, Wayland included, except a same-site window a page opens while the person watches, which opens as a real one. So §3.1 stays as written, and so does §12.1's [D] sentence, except for screen-reader users: a screen reader reads nothing in the viewport, and a bot's tab can't become a real view without a reload, which item 56 rules out. How they take over a bot's tab is **decision 1a**: a hybrid (while a screen reader is on, new bot tabs are real views in A's host window), an explicit reload exception, or mirroring the page's accessibility tree (weeks of work). The owner chose the hybrid, so no tab ever reloads, and A's host is built for that case only. B ships on a stock Electron: a page's dialogs are answered at once, a watched tab's frames come as CPU bitmaps so its dropdowns draw, and a same-site window a page opens is a real window while the person watches, and refused or reopened without its opener while a bot is alone. An animating page costs more CPU while watched.
* **A, the host window (§2, §3), not chosen except as the hybrid's host.** A bot's tab is a real view in a window that is shown but that the user isn't meant to see or use. On Windows and X11 the user can't see it or click it, and on macOS sees nothing, or one pixel of the page if M1 picks the cheaper opaque host. On Wayland it is a one-pixel dot the compositor places, which can show in the window list and can take a click. §3.1's "no window" becomes "no window the user can see".
* **Why B:** it puts no window on screen on any OS but that one, and it draws at the app's rate whatever the desktop does, so it doesn't rest on each desktop's occlusion rules. Everything a person does in a page worked through the viewport on all four desktops. A's advantages are the watched tab itself, a real view that a screen reader reads, and staying on Electron's mainstream path, plain views with none of offscreen rendering's edges.
* **Decision 2, open:** whether Clover carries a patched Electron. Patches would only restore what B gives up without them (dialogs offered to the person, same-site windows offscreen, dropdowns with GPU frames). That is one decision for the whole project, with lane E's WebRTC patch.
* **The other roads each give something up:** tab capture fails on Wayland, turning throttling off after creation works only on macOS, a separate headless browser goes against item 56, and Chrome's own headless mode would hide the app's windows too (§7.5).

The decided wording, and the record of what the owner was asked, is edit 1 under "Proposed spec edits", which also has four [P] edits.

Versions: Electron 45.2.2 (Chromium 156.0.8078.80, Node 24.22.2), Chrome for Testing 156.0.8078.80 (the same Chromium), Bun 1.3.14. These are the latest OSes GitHub offers, one version behind the spec's floor (macOS 27, Windows 11, Ubuntu 26.04): the live gates check the real ones. Rounds eight to ten also ran the Electron probe's pictures, cost and shared host at a forced device scale factor of 2 on macOS, Windows and X11 (`--force-device-scale-factor=2`).

The prototype is self-contained: its own `package.json`, one folder below `spikes/` so it is not a workspace member. It has four parts.

* **The probe page.** Every tab loads it. It counts a 10 ms interval, a chained 10 ms timeout and rAF, with the longest gap between ticks. It logs `visibilitychange`, resize, freeze and focus with their times. It keeps state that a reload would lose: a random token made at load, a field's value, `sessionStorage`, a scroll position, and an open server-sent-events stream. It plays a looping VP8 + Opus clip and runs an `AudioContext`. From round eight it also moves and resizes an element twice a second, watched by an `IntersectionObserver` and a `ResizeObserver`, and counts mouse presses.
* **A frame marker.** The probe page draws a strip of 52 black and white cells in its top-left corner, encoding the time it was drawn (ms) and a draw counter, with a checksum. Any picture of the page (`capturePage`, a CDP screenshot or screencast frame, a decoded WebRTC or WebCodecs frame) is decoded back to "when was this drawn". That gives each picture's freshness, and each streamed frame's end-to-end latency, on one machine's clock.
* **The Electron probe** (`src/electron/`). Tabs are `WebContentsView`s, sandboxed, with no Node and no preload, each in its own partition (spec §12.1). The probe puts them in each candidate place and measures them there.
* **The daemon side** (`src/cft/`, `src/pair/`). A pinned Chrome for Testing install with its own zip reader and a CDP client over the DevTools pipe. A minimal Bun daemon and Electron app for the pair, with launchd, `systemd --user` and Task Scheduler login items.

The workflow ran seven times ("rounds"), each fixing what the one before found. It then ran once more in full on `5bae76e66` (`results/final/`), whose prototype the next commit kept, and four more times for the review's experiments and the fixes they led to (`results/round8/` to `round11/`). Round twelve tested Winter's model, offscreen tabs shown through a viewport, in a job of its own on macOS, Windows, X11 and Weston (§7, `results/round12/`), and round thirteen ran everything once more with its conclusions asserted (`results/round13/`). Round fourteen ran the viewport jobs once more, with a cross-site window the page opens (`results/round14/`), and round fifteen with selecting and copying a page's text (`results/round15/`). Every round's JSON and summary are under `results/`.

**What a green job means.** Until round eight every runner exited 0 whatever it found, so a green job meant only that it had run to the end: rounds three to six's Linux Chrome for Testing jobs were green while their pipes stalled. Since round eight each runner checks what this report concludes, and fails its job when a check fails (M1 item 5 lists the checks). In round eight two jobs failed, and both failures were findings: on X11 a click at the 1×1 host's pixel landed on the host (§3), and on Windows at a scale factor of 2 the host's tabs drew nothing (§2). Rounds nine and ten checked the fixes. In round ten (run 41971290499) every job passed, with all 172 of its checks. Round eleven (run 41977985566, on `261732dd5`) added the daemon lock's tests on macOS and Windows and passed every job too: all 172 checks, and the lock's three tests on each OS. Round twelve's viewport job recorded without asserting. Round thirteen (run 42003365006, on `bb8d4e7cd`) asserted round twelve's conclusions and the pair's held lock as well, and passed every job: all 312 of its checks. Round fourteen (run 42014274318, on `b3ce1f852`) ran the unit and viewport jobs again with a cross-site window added (recorded, not yet asserted), and passed every job: all 135 of the viewport's checks. Caveats that hold throughout:

* Windows and Linux runners have no GPU, so their CPU numbers are for software rendering and software video encoding.
* Every "link" is loopback, so latencies are floors before any network.
* Memory is the best number each OS has: macOS physical footprint (libproc), Linux PSS, and Windows private bytes. A sum of resident sizes counts Chromium's shared pages once per process.

## 1. Moving a tab between headless and shown

**Verdict: works, on all three OSes and every kind of display.** A tab moves by moving its `WebContentsView` out of one window and into another (`removeChildView`, `addChildView`, then `setBounds`). Nothing reloads, from any of the hidden places tried.

**Method.** A probe tab holds everything a reload would lose (see above) and plays its clip. It goes hidden → shown → hidden four times from each hidden place: a view in no window (`detached`), a view in a window that is never shown (`hiddenWindow`), the same with the agent's size forced by CDP (`hiddenWindowFit`), and the two shown-but-unseen host windows of §2 (`invisibleWindow`, `tinyWindow`). Each cycle checks the token, the field, `sessionStorage`, the scroll position, how many times the server saw the event stream open, and how far the clip played. It also times the first fresh picture of the shown tab (polled with `capturePage` from the moment of the move, decoded from the frame marker) and the page's first rAF. Numbers are from round two; round one agreed except for the fresh picture, whose round-one figure (1.5 s) was a measuring bug.

| | macOS | Windows | Linux X11 | Linux Wayland | Linux, no display |
| :- | :- | :- | :- | :- | :- |
| Same document, field, `sessionStorage`, scroll; the event stream never reopened | yes, from every place | yes | yes | yes | yes |
| The clip while moving: seconds played per second, frames decoded per second (of 30) | 0.93–0.98, 27.5–28.9 | 0.92–0.97, 27.5–28.8 | 0.92–0.96, 28.1–28.6 | 0.92–0.96, 27.5–28.6 | 0.93–0.96, 27.5–28.6 |
| First fresh picture once shown, p50 (p95) | 30–74 ms (57–97); from no window 43 ms (909) | 21–27 ms (24–60) | 26–31 ms (27–37) | 24–33 ms (29–128) | 22–29 ms (28–35) |
| First rAF once shown, p50 | 3–24 ms | 0–15 ms | 1–13 ms | 1–11 ms | 0–12 ms |
| Layout: hidden → shown → hidden | 1280×800 → 1000×700 → 1280×800 | same | same | same | same |
| The agent's 1280×800 kept while shown (`Emulation.setDeviceMetricsOverride`) | applied in 1–3 ms | 1 ms | 1 ms | 1–2 ms | 1 ms |

Notes:

* **The layout follows the view,** as Winter's headless lesson says (§12.1): a shown tab lays out at the browser view's size, and its 1280×800 comes back when it goes back to its host. A page in a place that draws nothing sees `innerWidth` change but gets its `resize` event only at its next rendering step (round one).
* **A view in no window is the worst place to show from on macOS** (909 ms at p95), and it draws nothing while there (§2), so it is not a place to keep tabs.
* **The clip kept playing everywhere,** hidden or shown. A page playing sound is exempt from background throttling (§2), so the clip says nothing about the timers of a silent page.
* **Round eight checks it on every OS:** its assertion "no reload when moving" held from every place on macOS, Windows, X11, Weston and both no-display runners.


## 2. Hidden tabs: throttling, pictures and cost

**Verdict: works with limits, and not as the spec has it.** A tab in a window that is never shown, or in no window, **draws no frames on any OS.** With `backgroundThrottling: false` its timers run at full speed and the page says it is visible, but rAF never runs, and nothing that waits for a rendering step happens: `resize` events, rAF-driven apps, and `IntersectionObserver` and `ResizeObserver` callbacks (lazy images, infinite scroll). Round eight counted those: none in a never-shown tab, on every OS. `capturePage` fails there on every OS, with or without `stayHidden` ("Current display surface not available for capture").

What does work everywhere is a **host window that is shown but can't be seen or touched**: 1×1 pixel, frameless, not focusable, click-through and out of the taskbar. A 1280×800 view inside it draws at the display's rate, and `capturePage` gets the whole 1280×800 picture in 7–34 ms. It keeps drawing under another window too. Round eight's control settled that: the same covered host with throttling on went hidden on macOS, Windows and X11, so Chromium saw the cover there, and throttling off is what kept the host drawing.

**Method.** Each configuration is a fresh probe tab in its own partition, measured over 5 s after 2 s to settle. "Throttling" is `webPreferences.backgroundThrottling`. CPU is the whole app's (main, GPU, network and renderer processes), as a percentage of one core. Numbers are from round two unless marked. Rounds three and eight re-ran everything, and what draws and what doesn't came out the same; CPU varied with the runner.

* **What waits for a rendering step** (round eight): an element that moves and changes size twice a second gave `IntersectionObserver` and `ResizeObserver` callbacks twice a second in every tab that drew, and none in a never-shown window or in no window, on every OS.
* **The setting is per tab.** Two tabs in one never-shown window, one with throttling off: 100 Hz and 1 Hz on every OS.
* **Sound exempts a page from throttling,** whatever the setting, as in Chrome. Its media plays at 0.84–0.95× in every hidden place (frames decoded at 25–28 fps).
* **Wayland's 40 Hz is the output's rate** under headless Weston; the shown view runs at 40 too.
* **The macOS-only 60 Hz after `setBackgroundThrottling(false)`** comes from Electron telling the widget it was shown; macOS gives each view its own compositor, so it draws. Aura (Windows, Linux) draws only for windows that are shown. A design can't rest on it.
* **The off-screen window on X11 stops being drawn** within seconds (rAF 0, `capturePage` fails), so on Linux only the 1×1 window works.

**Covered by another window** (round eight, and round nine agreed; rAF in Hz): an opaque window over the host, as the user's own windows would be, and the same host with throttling on as the control.

* **The control settles it on macOS, Windows and X11.** With throttling on, the covered host went hidden (timers at 1 Hz, rAF 0), so Chromium saw the cover. With throttling off it kept drawing at the display's rate, so throttling off is what keeps a covered host drawing. On X11 Chromium takes the X server's `VisibilityNotify` as occlusion, and Xvfb sends it even with no window manager.
* **Weston and the no-display platform have no occlusion,** so there the control drew too, and their rows only show that the cover breaks nothing. Real compositors and window managers are a live gate.
* **Earlier covers showed less.** Round three's cover on Windows was click-through, which makes it a layered window that occlusion tracking ignores, so round five used a plain one. Round three's cover on macOS covered only part of the full-size host (the screen clamped it to 1024×677 at 0,31). Round eight's covered the whole host on every OS (on macOS, 1280×831 over the host at 0,31).

**The host's size and transparency.** Windows makes a frameless window at least 32×31, or 4×31 as a tool window (round eight's host), which would show a corner of the page, so the host runs at opacity 0 there. Round ten made it 32×32, since the 4×31 one lost its content area at a scale factor of 2 (below). In round five that host drew at 64 Hz and cost what a shown tab does: an animated page took 40.6% against 45.6% shown, on a slower runner than round two's. On macOS the final run (on `5bae76e66`) ran the same transparent 1×1 host: 60 Hz, 59 Hz under the cover and 60 Hz always on top, with `capturePage` taking 34 ms (26 ms under the cover). It costs more there than the opaque 1×1 did: an animated page took 39.6% against 30.0% shown, where round two's opaque 1×1 took 29.7%, and round eight agreed (37.1% against 30.9%). macOS seems to composite a transparent window in full, so on macOS an opaque 1×1 host (a single pixel of the page) is the cheaper choice for M1 to weigh.

* **`capturePage` returns the full 1280×800 view from a 1×1 window,** with a picture 11–24 ms old: the view draws in full whatever the window's size. A CDP screenshot takes 4–10 times as long, since it encodes the picture and sends it as base64 text.
* **An offscreen-rendering window draws at its set rate on every OS,** and round twelve showed one in the browser view through a viewport without a reload: Winter's model, §7. Its tab can't become a real view without reloading, which is why rounds one to eleven set it aside. An offscreen `WebContentsView` (no window) never painted at all.
* A frame subscription in a never-shown window gives one picture, but a subscription left running did not make the page draw (rAF stayed 0 on every OS).

**At a device scale factor of 2** (rounds eight to ten: the same checks with `--force-device-scale-factor=2` on macOS, Windows and X11; real HiDPI and 120 Hz displays are live gates):

* **`capturePage` returns the display's pixels:** 2560×1600 for the 1280×800 view, in 22–58 ms across rounds eight to ten (macOS 22–29, X11 38–58, Windows' 32×32 host 41–49). The CDP override at a scale factor of 1 (edit 2) doesn't change that, since it sets only what the page sees. So a bot's picture is scaled to 1280×800 after the capture: scaling a 2560×1600 picture and encoding it as JPEG took 12–24 ms (round nine). A CDP screenshot under the override comes out at 1280×800 directly, but takes longer: 64–85 ms.
* **On Windows the smallest host broke at 2×.** A 1×1 request becomes a 4×31 tool window there, and at a scale factor of 2 its content area was 0 wide (round nine). Without the override a tab in it laid out at 0×0 and drew nothing (round eight). Held at 1280×800 it still drew no frames, though `capturePage` forced out 3 pictures in 4 (round nine). Round ten made the Windows host 32×32 at opacity 0. At 2× every tab in it then drew at 60–64 Hz, and every `capturePage` worked (41–49 ms), with or without the override. The forced scale on that runner reported a 256×192 screen, so a real 200 % display is a live gate too.
* **At 2× a working tab costs about twice the memory on macOS and X11:** a quiet tab in the host took 60–67 MiB there, against 28–35 MiB at 1×, since its surfaces have four times the pixels. On Windows its private bytes stayed at 27–29 MiB a tab. A 120 Hz display could double a drawing tab's CPU, against the 60–64 Hz measured here.

## 3. Wayland

**Verdict: works with limits.** Under headless Weston the 1×1 host window works as on the other systems. What Wayland changes:

* **A never-shown window gives nothing at all.** On macOS, Windows and X11 a CDP screenshot or one frame of a frame subscription still gets a picture from a never-shown window; on Wayland both time out, and so does tab capture (`getUserMedia` of the tab): after about 10 s, with "AbortError: Timeout starting video source" (round nine). Rounds two and three had lost that text (the probe recorded it as `{}`). Round eight lost it behind its fallback, `getDisplayMedia` answered with the tab by the main process, which timed out the same way. Any design that leaves working tabs in a never-shown window fails on Wayland first.
* **An app can neither place a window nor make it transparent.** `setOpacity` exists only on macOS and Windows, and the compositor picks every window's position. `skipTaskbar` and always-on-top do nothing either. So the 1×1 host is a real window that the compositor places, a one-pixel dot that can show in its window list and overview. That makes **one shared host for every working tab required on Wayland**, not just cheaper: a host per tab would put a row per tab in the user's window list. Round eight ran four drawing tabs in one host under Weston: each drew at 40 Hz, and every `capturePage` worked (21–23 ms).
* **Its one pixel can take a click.** Electron's click-through gives a window a 1×1 input region at its top-left corner on X11 and Wayland (`electron_desktop_window_tree_host_linux.cc` in Electron 45), since an empty region means the whole window to Chromium. For a 1×1 host that pixel is the whole window. On X11 rounds eight to ten proved it: a real click at the host's pixel landed on the host every time. On X11 an empty window shape takes the pixel away (below), but Chromium has no window shapes on Wayland, so there the dot can take a click wherever the compositor puts it, when nothing covers it. Headless Weston has no input to try it with, so it is a live gate. If it matters, the fix is an Electron patch that sets an empty input region on Wayland.
* **Focus under Weston proves little:** no window had focus there (round eight), so whether mapping the host takes focus, or raises GNOME's "is ready" notice, is a live gate too.
* **The 1×1 window draws at the output's rate:** rAF 40 Hz, as the shown view does under headless Weston, and `capturePage` takes 22 ms (11 ms old). The screencast runs at 40 fps and WebCodecs at 30 fps (§6). Moving tabs works as on X11 (§1).
* **What headless Weston can't show** is how GNOME (Mutter) and KDE (KWin) treat the dot. Both stop sending frame callbacks to a window that is covered, minimized or on another workspace, and Chromium then stops drawing it. Rounds three and eight put an opaque full-screen window over the dot under Weston, and it kept drawing at 40 Hz, with throttling on as well, since Weston holds no frame callbacks back and Chromium sees no occlusion there. So this is a live gate (below).
* **The fallback is XWayland.** Started with `--ozone-platform=x11` on a Wayland desktop, the app is an X11 client, which times its own frames and gets the X11 numbers above (rAF 60, `capturePage` 13 ms).
  * **On X11 the host leaves the window manager.** Electron 45's own typings say that on Linux `focusable: false` "makes the window stop interacting with wm, so the window will always stay on top in all workspaces": Chromium makes such a window override-redirect (`x11_window.cc`), and round nine's `xwininfo` shows it on the host: "Override Redirect State: yes". So under XWayland, and on a real X11 desktop, the host stays above every window on every workspace (it can't be covered), stays out of Alt-Tab and the overview, and likely sits above the top panel too. Plain, that's a visible 1-pixel dot of the page that takes a click.
  * **An empty window shape removes both** (`setShape([])`, rounds nine and ten). The X server then keeps no pixel of the host (`xwininfo`: "Window shape extents: 0x0+0+0") and gives it no input, so a real click at its point reached the window below (round ten; round nine's click had landed on that window's corner, which is a resize handle on Linux). Yet it drew at 60 Hz, and `capturePage` worked every time (13–14 ms). Its throttling-on control went hidden, so Chromium takes a window with no shape as covered, and throttling off keeps it drawing, as under a cover. Xvfb has no window manager, so where the host stacks on a real desktop is still a live gate.
  * XWayland loses fractional scaling (blurry text on scaled screens) and Wayland-native input methods. So it should be a setting, used only if the Wayland live gate fails.
* Electron 45 uses Wayland natively on a Wayland session (the default since Electron 38). Its sandbox needs the AppArmor profile on Ubuntu, as on X11 (§5).


## 4. Chrome for Testing where no app runs

**Verdict: works, with the headless shell, sandboxed on every OS.** On Linux the sandbox needs the AppArmor profile, as Electron does (§5). Until round eight, Linux ran sandboxed only for its start; round eight loaded the profile before the first launch and ran every step sandboxed, and the table is from that round. **Method.** `src/cft/` is a daemon-side installer and driver, in Bun, launching nothing outside CI:

* **Install** (`install.ts`, `unzip.ts`). It downloads the pinned build from Google's `chrome-for-testing-public` bucket and checks the size, the SHA-256 against `pins.json`, and the server's MD5. All eight archives (two kinds × macOS arm64, Windows x64, Linux x64 and arm64) were pinned from round two's downloads and matched in round three.

On macOS and Linux the pipes are two `pipe(2)` pairs made over `bun:ffi` and handed to `Bun.spawn` as fds 3 and 4 (`fdpipe.ts`, Winter's road). On Windows, Chromium wants handle values, so the pipes are inheritable anonymous pipes named with `--remote-debugging-io-pipes` (`winpipe.ts`). A loopback port is kept only as a fallback.
* **The same tab operations as the app's checks:** background timers and rAF, a resize without a reload, JPEG and PNG screenshots, a screencast, one browser per bot with its own `--user-data-dir`, and the cost of a browser, a tab, a browser context and a second bot's browser.

Notes:

* **Use the headless shell.** In full Chrome's headless mode, a tab behind another in the same window is hidden and throttled (1.0–1.2 Hz, rAF 0, its media stopped). On macOS, one tab in a window of its own was hidden too. Full Chrome also costs several times as much (259–478 MiB a browser and 52–59 MiB a tab in round eight). The headless shell has no windows to stack: every tab is visible and draws, and its layout is the agent's exact 1280×800 (full Chrome's window frame took it to 1264×649 and 1280×657).
* **A bot's browser is its own process tree with its own profile folder**, which isolates cookies and storage and keeps them across restarts. A browser context (`Target.createBrowserContext`) costs no more than a tab but keeps nothing on disk, so it suits throwaway work. Each further bot's browser costs another base (45–115 MiB).
* **The pipe is the right transport.** It starts at least as fast as the port (round eight: 54–125 ms warm, against 58–384 ms for the port), and no other process can connect to it. A Windows reader that looped while bytes were waiting starved every timer during a screencast (round two's 17-minute hang); reading once per tick fixed it. That reader still polls with `PeekNamedPipe` every 4 ms, 250 wake-ups a second while a browser runs, against the daemon's budget of 50 a second. M2 should read with overlapped I/O or a blocking read on a worker thread, as the POSIX worker reader does.
* **The Linux stall: on Linux the daemon spawns only through `Bun.spawn` until lane C isolates the cause.** In rounds three to six, 16 of the 20 Linux browser runs lost the connection to the browser at an arbitrary moment while it kept running. Either it could no longer write to us ("Could not write into pipe"), or it read end-of-file from us ("Connection terminated while reading from pipe"). Our own writes had all gone out, and a reader on a worker thread failed the same way (round six), so something closed our descriptors while they were in use.
  * **What came before every stall.** Without the AppArmor profile, the sandboxed native start fails at once on Linux ("No usable sandbox!"). The start plan then fell through two starts through `node:child_process`, and both crashed at once too:
    * `pipe`, with extra stdio slots (`["ignore","ignore","pipe","pipe","pipe"]`);
    * `port`, with plain stdio (`["ignore","ignore","pipe"]`) and no extra slots.

    The native pipe then started unsandboxed, and the port comparison, a third `node:child_process` start that ran and was closed normally, came right after it. Round two had already seen the `pipe` start hand the browser an end-of-file.
  * **What round seven changed.** It tried the native pipe unsandboxed before any other transport, so neither crashing `node:child_process` start ran, and it moved the port comparison to the end. Every Linux run since has passed every step: round seven's eight, the final run's eight and round eight's sandboxed ones. Round seven kept one crashing start, the sandboxed native one through `Bun.spawn`, which had come before every stall too, so that one alone isn't the cause.
  * **What that can't tell apart:** extra pipe slots, a child that dies at once, or any `node:child_process` spawn under Bun on Linux. The likely cause is a late close of a recycled descriptor in Bun's `node:child_process`, but the spike didn't isolate it.
  * **The rule, until lane C isolates it.** On Linux the daemon starts every child through `Bun.spawn`, with whatever stdio the child needs (extra descriptors passed as plain numbers, as `fdpipe.ts` does), and never through `node:child_process`. It binds:
    * lane C: Bash and the fence's helpers, such as bubblewrap;
    * lane K: ACP agents, which talk over stdio;
    * lane A: the runtime's own children, such as SigV4's process;
    * every other lane that spawns from the daemon.

    Windows is outside the rule: there the browser starts through `node:child_process` (`winpipe.ts`), and no Windows run stalled.
  * **Lane C's reproduction recipe** follows these notes.
* **On a bare Ubuntu 24.04 server** the headless shell lacks 21 libraries (X11, NSS, ATK, GBM, ALSA, D-Bus, GLib…). Installing 20 packages (143 with their dependencies; the list is in `scripts/ci/cft-deps.sh`) makes it start. The `clover-core` server package should depend on them.
* **Cookies on disk are not encrypted** with `--password-store=basic` and `--use-mock-keychain`, which a server with no keyring needs. The profiles live under the daemon's home, with its permissions. They hold each bot's sign-ins, so they belong in the fenced set (below).
* Chrome for Testing has no auto-update. The daemon must move the pin itself: with each Electron upgrade, to keep the engines equal, or ahead of Electron for a security fix. When Google hasn't published Electron's exact Chromium build, the pin takes the nearest build of the same milestone. Chrome for Testing's `known-good-versions-with-downloads.json` lists the builds it publishes, and not every Chromium build that Electron uses is among them.

**What M2's port needs (trust boundaries).** The prototype is a spike. Before `src/cft/` becomes `packages/core/src/browser/`:

* **Windows: the browser's pipes can leak into other children.** `winpipe.ts` makes the child's ends inheritable and closes them in the daemon only after the spawn (`closeChildEnds`). The browser is spawned with handle inheritance on, so a process the daemon spawns at the same moment (another bot's browser, a Bash from a worker) can inherit a DevTools pipe too. M2 should name the two handles in an explicit handle list (`STARTUPINFOEX` with `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`), so only the browser gets them.
* **"No other process can reach it" holds only under the fence.** A same-user process outside the sandbox can open `/proc/<browser>/fd/3` on Linux, or duplicate the pipe's handle out of the browser process on Windows. Lane C's fence needs a PID namespace in bubblewrap, and on Windows a fence that denies the fenced process access to other processes.
* **Per-bot profiles hold sign-ins.** On servers the cookies are plaintext; on desktops they live in the app's Electron partitions. Both belong in lane C's fenced set, so one bot's Bash can't read another bot's sign-ins.
* **The installer must fail closed.** Until round eight the installer installed on trust when a pin was missing, and never checked a reused install again. Round eight's fails closed:
  * with no pin it installs nothing (unless `S7_CFT_TOFU=1`, which exists only to refresh the pins);
  * a reused install is used only if its version, its archive's hash and its binary's SHA-256, recorded at unpack, all match.

  M2 should go further and record a hash for every unpacked file, since the binary isn't the only file a swap could change.
* **CDP over the pipe is a browser-level connection.** It reaches the `Target`, `Browser` and `Storage` domains for every tab and context, where Electron's `webContents.debugger` reaches one tab. On servers, too, the bot never gets the raw pipe, and the CDP allow list sits in the daemon's API, as on desktops.

## 5. The app and daemon pair

**Verdict: works on all three OSes,** with one Windows fix. Task Scheduler does not restart a crashed task, so the daemon runs under a small supervisor.

**Method.** The prototype has three parts:

* **A minimal daemon** (`src/pair/daemon.ts`, compiled with `bun build --compile`). It holds an OS lock on its home and listens on `<home>/run/core.sock` (on Windows, a named pipe). It starts the app through the OS when none is connected within 2 s. It restarts an app that went away without saying so, after 1, 2, then 4 s, and the start after the third crash in two minutes is in safe mode. On the app's Quit it exits 0.
* **A minimal app** (`src/pair/app-main.ts`). It has no window and a tray menu with Quit, and keeps one instance per user. It starts the daemon through the OS when none answers. When the daemon goes away without saying so, it reconnects every 500 ms and starts the daemon itself after 3 s.
* **The login items** (`src/pair/units.ts`):
  * macOS: a launchd user agent with `RunAtLoad`, `KeepAlive {SuccessfulExit: false}` and `ThrottleInterval` 1.
  * Linux: `systemd --user` units, the daemon's with `Restart=on-failure` and `RestartSec=1`. The app has a unit of its own, which the daemon starts with `systemctl --user start`, so it lives in its own cgroup.
  * Windows: a Task Scheduler task for the daemon with a logon trigger, an interactive token, least privilege, no time limit, not stopped on battery, and normal priority. There is an on-demand task for the app, or the daemon spawns it as a detached child (both were measured).

The runner (`src/pair/run.ts`) installs these, starts the daemon as a login would, and then walks through: a second daemon on the same home, an app crash, a crash loop, two daemon crashes (one with the app's help switched off), the tray's Quit, a user starting the app, and the daemon side's Quit. From round eight it also checks each step against a bound and fails the job when one is missed (M1 item 5 lists them); all nine held on every OS. Round thirteen added a tenth, a lock held by another process with no daemon answering (below).

**What lanes E, C and M need to know**

Lane E builds the app's side of the pair and lane C the daemon's.

* **Who owns what, where the plan overlaps.** Plan C-M1 owns "login start on all three OSes", and M-M1 owns "the app installing the daemon and its login item". The split S7 suggests:
  * **lane C** writes the login items' contents (the launchd plist, the `systemd --user` units, the Task Scheduler XML), since they encode the daemon's restart rules. `clover-core supervise` is part of the daemon's binary, so it is lane C's too;
  * **lane M** installs and registers them from the packages and the app's installer, and owns the packages' side: the AppArmor profile in the deb and rpm, the server package's dependencies (§4), and updates that end the Windows task;
  * **for both:** the Task Scheduler XML defaults (below), the plist's `ThrottleInterval`, and registering through `SMAppService` on macOS, which needs the signed bundle that lane M builds.
* **The lock is the kernel's,** so a crashed daemon never leaves a stale one. On macOS and Linux it is `flock(LOCK_EX|LOCK_NB)` on `<home>/run/core.lock`. On Windows it is the lock file opened by `CreateFileW` with no sharing, over Bun's FFI (`src/pair/lock.ts`). A second daemon exits **0**, so its login item does not loop.
  * **Only "another process holds it" means busy:** `EWOULDBLOCK` from `flock` (35 on macOS, 11 on Linux), or a sharing violation (error 32) from `CreateFileW`.
  * The spike's first lock took any failure as busy. A full disk, a permissions error or any other failure would then have looked like a second daemon, and the pair would have stayed down without a word; on Windows the supervisor would have ended too. Since round eight any other failure throws, so the daemon exits non-zero and the OS restarts it.
  * **The fix is pinned on every OS** (round eleven). The classification is a pure function (`classifyLockFailure` in `lock.ts`), unit-tested for all three OSes, and the lock test runs on macOS, Windows and Linux in CI; it passed on all three. On Windows it also pins the old bug directly: a missing directory gives `CreateFileW` error 3, which the first lock read as busy and which now throws.
  * **"Busy" is confirmed on the socket** (round eleven). A process that opens the lock file without sharing, such as a virus scanner at login, gives error 32 on Windows too, and an error code can be misread. So a daemon that finds the lock held dials the socket. If a daemon answers, it exits 0: in round eleven every OS's second daemon was refused that way, in 30–106 ms. If none does, it tries the lock again for a few seconds, and if the lock is still held and still no daemon answers, it **exits 1**, so the OS or the supervisor starts it again. Round thirteen checked that on macOS, Linux and in Windows' three modes: the runner held the lock itself, as a virus scanner would, with no daemon running. The daemon said the lock stayed held and exited 1 in 3.0–3.2 s, and once the runner let go, the next start was up in 106–110 ms.
  * **For lane C's real lock:** bun:ffi has no call that keeps errno or Windows' last error, so the spike reads them with a second FFI call straight after the failing one. A misread could go either way, and the socket check makes both harmless, but lane C should read them inside one native call.
* **SIGTERM exits 0** (`daemon.ts`), and the daemon tells the app it is quitting. So a stray `kill` keeps the pair down until the next login, or until the user starts the app. SIGTERM is also what logout, shutdown and `systemctl --user stop` send, where staying down is right. Lane C should decide this on purpose; a bot's Bash signalling the daemon is a case for the fence.
* **macOS.**
  * Set `ThrottleInterval` to 1. Without it, launchd waits up to 10 s before restarting a crashed job.
  * `KeepAlive {SuccessfulExit: false}` gives exactly "restart after a crash, not after a Quit".
  * The app starts the daemon with `launchctl kickstart gui/<uid>/<label>`. The daemon starts the app with `open -n -g -a` (`-g`: in the background), so launchd is the app's parent.
  * A signed app should register through `SMAppService.agent`, which Electron 45 exposes as `app.setLoginItemSettings({ type: 'agentService', serviceName })`. CI cannot test it, since it needs the signed bundle with the plist inside, so it goes to the live gates.
  * Use `LSUIElement` to keep the app out of the Dock. The spike called `app.dock.hide()` after start.
* **Windows.**
  * **Task Scheduler's "restart on failure" did not restart a killed task**, as a plain task or with the app started as a detached child. Its restart interval can't be shorter than a minute (the spike set `PT1M`, and waited 150 s), so it could never give a 1 s restart even when it fires.
  * The task should run `clover-core supervise`, a mode of the same binary that runs the daemon as its child. The supervisor restarts the child after a crash, after 0.5, 1, 2, 4 s and so on, and ends when it exits 0 (`src/pair/daemon.ts`). Measured: back in 0.6 s, then 1.2 s, and Quit ends the supervisor, so nothing restarts until the next login.
  * **Updates must end the task.** The supervisor runs from the daemon's binary and holds it open, so an update (lane M) ends the task (`schtasks /End`), replaces the binary and starts the task again.
  * The app's own restart after 3 s (`schtasks /Run`) is the second net.
  * Task XML defaults to override:
    * `ExecutionTimeLimit` defaults to 72 hours, after which the task is stopped. Set `PT0S`.
    * `DisallowStartIfOnBatteries` and `StopIfGoingOnBatteries` default to true, so a laptop on battery would not start the daemon at logon, or would stop it. Set both false.
    * `Priority` defaults to 7, below normal. Set 5.
    * Set `MultipleInstancesPolicy` to `IgnoreNew`.
  * `InteractiveToken` worked on the runner, whose user is logged on. Whether a **standard (non-admin) user** can register a logon-trigger task for themselves is a live gate, since the runner is an administrator.
  * The app lived through the daemon's crash both when it was started by its own on-demand task and as the daemon's detached child. The task is cleaner: the app is then never in the daemon's job object.
  * The named pipe (`\\.\pipe\clover-…`) works with Bun's `node:net`, both serving and dialling.
* **Linux.**
  * The app needs its own unit. Started as the daemon's child, it would sit in the daemon's cgroup, and `KillMode=control-group` would take it down with any daemon restart.
  * The app unit needs the session's `DISPLAY` or `WAYLAND_DISPLAY`. A desktop session imports these into the user manager. The spike did it with `systemctl --user set-environment`.
  * On the runner a user manager existed only after `loginctl enable-linger`. That is right for servers (§3.1) and not needed on desktops.
  * The XDG autostart entry is generated (`xdgAutostart` in `units.ts`), but only a real desktop session can run it, so it is a live gate.
* **Electron's sandbox on Ubuntu 24.04 needs the AppArmor profile** the deb and rpm install (spec §4). Without it Electron aborts at once with exit 133: "The SUID sandbox helper binary was found, but is not configured correctly". With a profile that grants `userns` to the binary (`scripts/ci/apparmor.sh`), it runs sandboxed. The AppImage cannot install one, so on Ubuntu 23.10 and later the spec's fallback package starts sandboxed only after the user installs the profile; otherwise it needs `--no-sandbox`.

## 6. The streamed view on other devices

**Verdict: works, with encoded video rather than pictures.** For a tab that moves, WebCodecs video over the link gives 30 fps at 29–68 ms on loopback for about 2.3 Mbit/s. JPEG pictures, as Winter's phone mirror sends them, give 60 fps for 35–66 Mbit/s, far more than a phone's link should spend. With acks and only the newest picture kept, they would fall to what the link carries, a few frames a second.

**Method.** A tab in a host window, and a viewer page in the same app, joined by a loopback WebSocket that stands for the link. Four roads:

* **CDP screencast:** `Page.startScreencast`, JPEG at quality 70, each frame acked, newest only (Winter's road).
* **`capturePage` polled at 30 fps**, sent as JPEG.
* **WebRTC:** tab capture (`getMediaSourceId`, then `getUserMedia` with `chromeMediaSource: 'tab'`) into an `RTCPeerConnection`, with VP8 or H.264.
* **WebCodecs:** the same tab capture through `MediaStreamTrackProcessor` into a `VideoEncoder` (H.264 or VP8, 2.5 Mbit/s target, a keyframe every 2 s). The encoded chunks go over the link to a `VideoDecoder` in the viewer.

Two contents: the whole page animating (worst case), and a page where only the frame marker changes, twice a second. Latency runs from the marker's draw time to the decoded frame at the viewer, on one clock. Each road ran for 10 s after a warm-up (6 s for WebRTC, 2 s for the rest).

**The whole page animating** (frames per second, latency p50, kbit/s):

| Road and source | macOS | Windows | Linux X11 | Linux Wayland |
| :- | :- | :- | :- | :- |
| Screencast, shown tab | 60 fps, 40 ms, 48 900 | 64 fps, 29 ms, 50 900 | 60 fps, 36 ms, 55 000 | 38 fps, 71 ms, 34 900 |
| Screencast, 1×1 host window | 59 fps, 48 ms, 57 000 | 64 fps, 33 ms, 60 600 | 60 fps, 42 ms, 66 100 | 40 fps, 73 ms, 43 800 |
| Screencast or polled `capturePage`, never-shown window | no frames | no frames | no frames | no frames |
| **WebCodecs H.264, 1×1 host window** | **30 fps, 51 ms, 2240** | **30 fps, 31 ms, 2160** | **30 fps, 34 ms, 2400** | **30 fps, 68 ms, 2380** |
| WebCodecs H.264, never-shown window | 30 fps, 43 ms, 2240 | 30 fps, 29 ms, 2170 | 30 fps, 32 ms, 2400 | fails (no capture) |
| WebCodecs VP8, never-shown window | 30 fps, 62 ms, 2290 | 30 fps, 30 ms, 2180 | 30 fps, 34 ms, 2420 | fails |
| WebRTC VP8, never-shown window | 4 fps, 180 ms, 680 | 26 fps, 38 ms, 2490 | 21 fps, 42 ms, 2520 | fails |

**Only the marker changing:** every encoded road sends what changes and nothing else: 1–2 fps, 8–113 kbit/s, 15–57 ms. WebCodecs H.264 sent 8–34 kbit/s.

**CPU** (% of one core, with no hardware encoder on the Windows and Linux runners): capture and encode 75–113% for WebCodecs, 58–110% for WebRTC and 70–159% for the screencast. The viewer used 10–43%.

Notes:

* **Tab capture makes a never-shown tab draw while it is captured** (the source's rAF went to 60–64 Hz on macOS, Windows and X11), the only thing besides being shown that does. On Wayland it fails.
* **WebRTC is the wrong road here.** Its congestion control starts low and climbs, and in a 6 s warm-up it reached only 4–26 fps. It also wants ICE and STUN, which the link (S1) already does. WebCodecs hands the frames to us, and the link carries them on a stream of its own.
* **The bitrate is ours to set:** WebCodecs takes a target bitrate and keyframes on demand. When the link falls behind, the sender can drop frames up to the next keyframe and lower the target, which keeps "newest only" for video. That is a design: no round measured it on a real link.
* **What a viewer can decode wasn't tested here.** Every viewer was Chromium. The iOS companion decodes with VideoToolbox, which takes H.264 and not VP8, and the web companion runs in Safari and Firefox too. Where no hardware encoder exists, H.264 means a software encoder built into Electron, which raises a patent-licensing question for an app we distribute; VP8 measured the same. The codec contract goes to lane I (edit 3).
* A screenshot for a bot stays a still picture (JPEG or PNG through CDP, or `capturePage`), as today.


## 7. Winter's model: offscreen tabs shown through a viewport

**Verdict: works, with gaps, on all three OSes and under Wayland.** A bot's tab drawn offscreen puts no window on screen on any OS, and it draws at the rate the app sets, whatever the desktop does. Shown through a viewport in the browser view, it keeps its document, timers, socket and form across every show and hide (Winter's oracle), and nearly everything a person does in a page works through it. It costs about a frame of latency at most, and several times a native view's CPU while a page animates. It gives a screen reader nothing (edit 1's decision 1a). Three more things have an answer on a stock Electron, and need a patch only to work as they would in a real view: a same-site window the page opens (a real window while the person watches), dropdowns with GPU frames (CPU bitmaps draw them), and JavaScript dialogs (answered at once, as in the host window too).

**What Winter did** (`docs/claude/headless.md`, "Showing a headless tab"). Its headless tabs were windowless CEF: offscreen rendering, accelerated, with frames as shared GPU surfaces. A live tab was shown in the Mac app's panel without reloading. The panel was a viewport that drew the tab's frames and sent the person's input back (mouse, wheel, keys, IME, paste, dialogs, file choosers, popups, drag), and the page reflowed to the panel's size while shown. There was no window at all. Its stated gaps were the page's accessibility tree and a file dropped onto the view from outside.

**Method** (round twelve, `src/electron/viewport.ts`; run 42002018170, and run 41998630149 for macOS's GPU frames; round thirteen ran it again with its conclusions asserted, run 42003365006; round fourteen added a cross-site window, run 42014274318; round fifteen added selecting and copying text, run 42017971488).

* **A bot's tab** is a `BrowserWindow` with `webPreferences.offscreen` that is never shown. Electron lays the page out at that window's size; an offscreen `WebContentsView` with no window never painted (§2). Its frames come as `paint` events: GPU shared textures with `offscreen.useSharedTexture`, or else CPU bitmaps of the changed rectangle.
* **The viewport** is a page in a shown window, which in Clover would be the browser view. It imports shared textures with Electron 45's `sharedTexture` module and draws them on a canvas as `VideoFrame`s; bitmaps come over IPC. It sends input back: mouse, wheel and keys with `webContents.sendInputEvent`, IME composition over CDP (`Input.imeSetComposition`, `Input.insertText`), paste as the tab's own paste, and select-all and copy as Electron's edit commands. The page's cursor comes back from `cursor-changed`, and the tab is laid out at the viewport's size while shown.
* **The checks** fed input to the viewport page as the OS would (`sendInputEvent` on it, and CDP for the IME) and read the result in the tab's page. The same page in a native view gave the comparison. The OS listed the app's windows on screen: `CGWindowListCopyWindowInfo` on macOS, `EnumWindows` on Windows, xdotool on X11. Wayland has no way to list them.

### 7.1 A bot's tab offscreen

Ranges in §7.1–7.3 are over rounds twelve and thirteen, and on macOS round twelve's first run too.

* **No window.** Four offscreen tabs left the OS's list of on-screen windows empty on macOS, Windows and X11, where the same four tabs in the host window put one there. A window that is never shown isn't mapped on X11, isn't ordered in on macOS and isn't visible on Windows. On Wayland a surface that is never shown gets no window role, so it shouldn't appear either, though Wayland can't list windows to check. So nothing shows in a window list, the Dock, the taskbar or an overview, and nothing can be clicked or take focus. Even the tab's own `webContents.focus()` left the OS's focus where it was, on every OS.
* **Its own rate, whatever the desktop does.** An offscreen tab draws at the frame rate the app sets (`setFrameRate`), not the display's, and the OS never draws its window, so covers, Spaces and occlusion tracking have nothing to act on. App Nap on macOS still could, so the power blocker stays, and real desktops (lock screen, sleep) are a live gate. Windows and Linux kept the rate exactly. On macOS the probe page, which plays a video, got frames above 10 fps at a half to two-thirds of the rate asked, for textures and bitmaps alike, while the same page in the host window drew at 58–60 Hz on the same runner. So the shortfall is the offscreen path's, not the runner's. The viewport's lighter page got its full 60 (§7.3). Whether an offscreen tab keeps the rate asked on a real Mac is a design-B live gate. With painting stopped (`stopPainting`), the page still draws and `capturePage` still works, so a bot that only takes screenshots needs no frames delivered.
* **Shared textures need GPU compositing.** The Windows and Linux runners render in software. There Electron drops every frame the capturer hands it in CPU memory, so a tab that asks for textures gets no paint at all: with `useSharedTexture`, `OnFrameCaptured` returns unless the frame is a GPU buffer of the platform's kind, a DXGI handle, an IOSurface or a native pixmap ([`osr_video_consumer.cc`](https://github.com/electron/electron/blob/v45.2.2/shell/browser/osr/osr_video_consumer.cc#L129-L138)). On Linux the first such tab hung Electron's main process for good (round twelve's first run: no log line after it, and no timer fired until the step's 20-minute timeout). So the app asks for textures only where `app.getGPUFeatureStatus().gpu_compositing` is enabled, and uses bitmaps otherwise. With Direct3D in software (WARP, `--use-angle=d3d11-warp`), Chromium on Windows composited on the "GPU" and textures came as NT handles, so the Windows road works where there is a GPU. Real GPUs on Windows (DXGI) and Linux (dmabuf) are a live gate.
* **Screenshots.** `capturePage` of an offscreen tab took about one frame at the rate set: 95–97 ms at 10 fps on Windows and Linux, with painting on or stopped, where rounds one to eleven's offscreen window at 30 fps took 28–32 ms there (§2). So it waits for the tab's next frame (an inference from the two rates), and costs a bot up to 100 ms at 10 fps, against 14–23 ms in the host. macOS's runner varied more (14–127 ms). With painting on, the newest frame is already in the main process, and as a JPEG it takes 5–7 ms. So a bot's picture comes from the newest frame (bitmaps), or from `capturePage` (textures, or painting stopped).
* **Size and scale.** The page takes its window's size, 1280×800, except on Windows, which fits a new window to the screen's work area (1024×720 on the runner) until `setContentSize` puts it back. The output's scale is fixed when the tab is made (`offscreen.deviceScaleFactor`, 1 by default), whatever the display, so a bot's pictures are 1280×800 at a scale of 1 with no override and no scaling. A tab made at 2 gives 2560×1600 frames and pictures at a layout of 1280×800, as the host does at 2× (§2). A CDP override at 2 doesn't change the frames (§7.2).
* **Cost.** A quiet tab painting at 10 fps cost 30–56 MiB, against 26–36 in the host: up to 25 MiB more (its capture buffers). With painting stopped it costs about what the host's tab does: 15–38 MiB. An animated page at the bots' 10 fps costs a sixth to a little over half of what it costs in the host at the display's rate.

* **No reload, as in Winter's proof.** The tab never moves: showing it only sends its frames to the viewport and lays it out at the viewport's size, so nothing about the page changes but its size. The oracle held on every show and hide, on all four desktops. (In round twelve the first read on X11 and Weston came too soon after the show for the page's 100 ms timer to tick, or (on Weston) its socket's next message, also every 100 ms, to arrive; the same document, socket and form were there. Round thirteen reads 600 ms after the show, and every row held.)
* **macOS's slow first show.** In round twelve's first run the first show took 289 ms to the first frame and 299 ms to the viewport's size. In the four macOS runs since (textures and bitmaps, rounds twelve and thirteen), the first show took 26–63 ms and 63–109 ms, and every second show 16–63 ms and 46–72 ms. It happened once in five runs, and the data doesn't say why; the first texture that run's viewport imported is a guess. macOS's first oracle read held in round twelve, where X11's and Weston's came too soon, because a show there takes longer to reach the viewport's size, long enough for the page's timer to tick.
* **Electron cancels a drag in an offscreen tab** as soon as it starts (`OffScreenWebContentsView::StartDragging` ends it), so a plain drag starts and ends with no drop. CDP's drag interception (`Input.setInterceptDrags`) hands the drag to the viewport instead. The viewport turns the person's moves into drag events (`Input.dispatchDragEvent`), and the drop landed with its data on every OS.
* **A same-site window the page opens can't be made offscreen; a cross-site one can.** With `offscreen: true` in the open handler's options, Electron reports a same-site window as offscreen, but it paints nothing, not even after a repaint or a restarted capturer, its page reads its size as 0×0, and its input goes nowhere, on all four desktops. Its page loads, and its opener is kept. This is Electron #55565, filed two days before this report against 44 and 45: a same-site child keeps the widget Chromium made before Electron gave its view a window, at 0×0 and with no paint callback, and the issue proposes a few-line fix. A cross-site window works (round fourteen, a page on 127.0.0.1 opening one on localhost): it moves to a renderer of its own, is laid out at its size, paints, takes clicks directly and through the viewport, and keeps its opener, on every OS, with no new window on screen. Sign-in windows are usually cross-site (a site opening its identity provider), so the common case works on a stock Electron. Winter adopted such windows windowless, which CEF can do. On a stock Electron a same-site window is shown as a real one while the person watches, and refused or reopened without its opener while a bot is alone. The host design should be spared this gap, since Electron's `createWindow` can put the window in a view in the host with its opener kept, but S7 didn't test it.
* **Dropdowns.** With bitmaps, Electron draws a `<select>`'s dropdown into the frame. With textures it sends the dropdown as a texture of its own (`widgetType: "popup"`) with no position, so the viewport can't place it. CEF gives the position. The keys still chose an option.
* **Quick resizes didn't stall.** Winter limited CEF to one change every 300 ms, since two quick ones stalled its painting. Electron's offscreen view followed three changes 40 ms apart on every OS.
* **The IME** composed and committed in the page on every OS, through CDP. The OS draws its candidate window beside the viewport's input element, which the app moves to the page's caret. An offscreen view reports no caret (it has no `TextInputClient`), so the app asks the page, and real IMEs are a live gate.

* **Latency.** A click goes from the viewport page to the main process, then to the tab's page and its compositor, through the capture, and back to the viewport and its compositor. Measured from the input to two rAFs after the frame was drawn, on the same clock as the native view, the viewport added 2–21 ms at p50: about a frame on macOS (14–21 ms), and under half a frame elsewhere (2–10 ms; on X11 a click in round twelve was no slower).

With bitmaps macOS cost about what it did with textures (60–79% against 63–82%), and drew its dropdowns. A still page costs nothing, since no frames come.

### 7.5 How Chrome's own headless browser draws, and what applies inside Electron

The owner's second question. Chrome has two headless browsers, and neither draws into a window anyone sees.

* **Chrome's headless mode** (`chrome --headless`) has been the real browser since Chrome 112, and the only headless mode in the `chrome` binary since 132. It "creates, but doesn't display, any platform windows" ([docs](https://developer.chrome.com/docs/automation-and-testing/headless)). One switch puts the whole process on a headless screen, with a headless window for each OS:
  * **Linux:** Ozone's headless platform ([`ui/ozone/platform/headless/`](https://chromium.googlesource.com/chromium/src/+/refs/tags/156.0.8078.80/ui/ozone/platform/headless/)), whose windows keep their bounds and visibility in memory, with no X or Wayland at all. Chrome adds `--ozone-platform=headless` itself ([`headless_mode_init.cc`](https://chromium.googlesource.com/chromium/src/+/refs/tags/156.0.8078.80/chrome/browser/headless/headless_mode_init.cc)).
  * **Windows:** [`HWNDMessageHandlerHeadless`](https://chromium.googlesource.com/chromium/src/+/refs/tags/156.0.8078.80/ui/views/win/hwnd_message_handler_headless.cc), a real window that the window manager cloaks (`DWMWA_CLOAK`), with its visible and active state faked.
  * **macOS:** [`NativeWidgetMacNSWindowHeadless`](https://chromium.googlesource.com/chromium/src/+/refs/tags/156.0.8078.80/components/remote_cocoa/app_shim/native_widget_mac_nswindow_headless.mm): "the platform window is never made visible, instead the expected window visibility state is faked". The compositor keeps producing frames.

  Pages are composited as usual, by viz on the GPU or in software, into surfaces nothing shows. A screenshot copies the compositor's surface ([`page_handler.cc`](https://chromium.googlesource.com/chromium/src/+/refs/tags/156.0.8078.80/content/browser/devtools/protocol/page_handler.cc)), not a window. Since each window counts as visible and focused, nothing throttles it as hidden or covered.
* **The headless shell** (`chrome-headless-shell`) is the old headless mode, Chromium's [`//headless`](https://chromium.googlesource.com/chromium/src/+/refs/tags/156.0.8078.80/headless/README.md). It is a small browser on Chromium's content layer, with no X11, Wayland or D-Bus ([Chrome's post](https://developer.chrome.com/docs/automation-and-testing/headless-chrome-shell)). On Linux and Windows each tab gets a [`HeadlessWindowTreeHost`](https://chromium.googlesource.com/chromium/src/+/refs/tags/156.0.8078.80/headless/lib/browser/headless_window_tree_host.cc) with no native window behind it, and on macOS a bare NSView. It renders in software unless given `--enable-gpu`, and `--deterministic-mode` lets the caller step each frame (`HeadlessExperimental.beginFrame`). It is what §4 runs where no app runs.

**What applies inside Electron:**

* **The switch doesn't.** The per-OS window and screen code lives in `//ui` and `//components`, so it is compiled into Electron. But the code that turns headless mode on is in `//chrome`, which Electron doesn't use, and Electron doesn't support `--headless`. Its maintainers said so in [electron#48982](https://github.com/electron/electron/issues/48982), where on Windows the switch hid every window, the tray's menus too; the one attempt, [PR #38126](https://github.com/electron/electron/pull/38126), was closed unmerged. Either way it works on a whole process, so every window goes headless, the app's own too.
* **Ozone's headless platform does, for a whole process.** On Linux `--ozone-platform=headless` works in Electron: S7's no-display runners use it (§2, §4). Again every window of the process is headless, so it suits a separate bot browser, which is what §4's Chrome for Testing is, not the app.
* **Per tab, the way is offscreen rendering.** Electron's docs say it "uses a similar approach to that of the Chromium Embedded Framework" ([docs](https://www.electronjs.org/docs/latest/tutorial/offscreen-rendering)), and CEF's windowless rendering is what Winter used. That is §7.1–7.4.
* **One piece Electron already uses.** On macOS a window made with `show: false` gets Chromium's headless NSWindow by itself: Electron sets `params.headless_mode` from `paintWhenInitiallyHidden`, which is on by default ([`native_window_mac.mm`](https://github.com/electron/electron/blob/45-x-y/shell/browser/native_window_mac.mm)). That likely explains §2's macOS-only quirk, where a never-shown window drew at 60 Hz once throttling was turned off after it was made (an inference). Windows and Linux have no such window.

### 7.6 JavaScript dialogs, in either design

Edit 2 had a page's dialogs "answered over CDP". Round twelve tried that in an offscreen tab and in a tab in the host window, on every OS:

* **CDP sees `alert` and `confirm`** (`Page.javascriptDialogOpening`, with `hasBrowserHandler: true`), and `Page.handleJavaScriptDialog` answers the page: the alert returned, and the confirm got true.
* **But Electron shows its own box, and the box stays.** Electron has no hook for a page's dialogs. Its dialog manager puts up a native message box, and CDP's answer doesn't close it. On macOS a 260×96 alert came up, and for an offscreen tab the tab's never-shown window came on screen too (1024×677). On Windows it was a 366×125 box titled "Electron" (`#32770`), and on X11 a 120×81 GTK window per dialog. Each was still up after the page had its answer, in both designs.
* **`prompt()` throws in Electron** ("not supported"): the page gets an exception, not a dialog.
* **`disableDialogs: true` answers every dialog at once** (alert returns, confirm gets false) with no box at all. CDP still sees each one, but can't answer it any more ("No dialog is showing").

So bot tabs run with `disableDialogs`, and CDP tells the bot what the page asked. In design B that is required, not a choice: without it, a dialog in an offscreen tab brought the tab's never-shown window on screen on macOS (above). Winter offered a dialog to the person with the page's origin, through CEF's dialog handler. Restoring that is a small Electron patch that routes a page's dialog to an event the app answers, kept across upgrades, and whether to carry it is part of the project's patched-Electron decision (edit 1). A shim in the page would also work, but pages can detect it. File choosers were fine: with CDP's interception no dialog came up on any OS (§7.2).

In design B no window appears, but a resting tab with painting stopped still runs its page at the frame rate set, so M1 sets the resting rate low and checks the budget with resting tabs open (M1 item 1). Nothing else in the spec conflicts with these results.


## Risks

The owner chose design B with decision 1a's hybrid, so the design A risks below now apply only to the hybrid's host, while a screen reader is on.

1. **Design B: Electron's offscreen rendering is a less-trodden road.** Round twelve hit four of its edges. Asking for shared textures without GPU compositing hung the main process on Linux; a same-site window the page opens can't be made offscreen (Electron #55565); a dropdown's texture comes with no position; and a drag is cancelled as it starts (§7). Each Electron upgrade can move these, so the viewport's checks stay in the browser suite with the gaps pinned (M1 item 5). B ships with an answer to each on a stock Electron: CPU bitmaps by default, which also draw dropdowns; a real window while the person watches; and CDP's drag interception. A hang like the Linux one stops the whole app, so M1 restarts a main process that stops answering into safe mode, with bitmaps only (M1 item 1). Whether Clover carries Electron patches to restore the rest is a project-wide decision (edit 1).
2. **Design B: a screen reader in a watched bot's tab.** The viewport gives the OS nothing of the page (§7.4). Each answer in decision 1a has a cost: the hybrid builds both designs and brings design A's host back for those users, the exception reloads the page, and mirroring the tree is a large job that is always a step behind.
3. **Design A (the hybrid's host): the host window on real desktops.** On CI the 1×1 host kept drawing under an opaque window on macOS, Windows, X11 and Weston. On the first three Chromium saw the cover (the throttling-on control went hidden), so throttling off held up against real occlusion tracking there. Real sessions add more: Spaces and full-screen apps, Stage Manager, the lock screen, a sleeping display and App Nap on macOS; virtual desktops, Win+D and the lock screen on Windows; and on Wayland, compositors that stop frame callbacks to a covered window. If one of these stops the host, its tabs behave like never-shown tabs: their timers run, they don't draw, and a picture is either refused or old. M1's freshness probe (below) must tell the bot so, rather than hand it an old picture. Each case is in the live gates below. Design B's tabs don't depend on the desktop this way, though App Nap and a sleeping Mac still apply to them.
4. **Drawing costs CPU.** In design A a tab that draws costs what a shown tab does (19–30% of a core for an animated page without a GPU), so the rest rule in edit 2 matters on laptops, and a bot that watches a busy page keeps one core partly busy. In design B a bot's tab draws at the app's 10 fps, for a sixth to a little over half of that, but while the person watches a page that animates, the viewport costs 2–7 times a native view (§7.3).
5. **Two Chromiums to keep equal.** Chrome for Testing has no auto-update, so the daemon's pin must move with every Electron upgrade, and sooner for security fixes. That is a release-pipeline task (lane M).
6. **Design A (the hybrid's host): Wayland's dot.** The 1×1 host can show in the window list and overview of a Wayland desktop, and its one pixel can take a click (§3). If GNOME or KDE make that ugly or stop drawing it, the XWayland fallback costs fractional scaling, and the click needs an Electron patch.
7. **A stray close in Bun's `node:child_process` on Linux** (§4, "The Linux stall"). Taking every `node:child_process` start out of the browser's start ended its stalls, but the daemon spawns much else: Bash, plugins and agents. If the cause is in Bun, any of the daemon's descriptors can be hit, its sockets included. Until lane C isolates it with the recipe in §4, the daemon spawns only through `Bun.spawn` on Linux (lanes C, K and A first), and C files it with Bun if it holds.
8. **Design A (the hybrid's host): the host shows unless it is made not to.**
   * **Windows** makes a frameless window at least 32×31, or 4×31 as a tool window, so the host must stay at opacity 0 there, at 32×32 (the 4×31 one lost its content area at 2×, §2). Rounds five, eight and ten ran it at opacity 0, and it drew at 64 Hz.
   * **X11**, and XWayland, have no window opacity in Electron. With `focusable: false` the host leaves the window manager and stays above every window, perhaps the top panel too, and Electron's click-through leaves its one pixel taking a click. An empty window shape takes the dot and the click away (§3), so on X11 only the stacking is left for the live gate.
9. **High-DPI displays.** In design A, at a scale factor of 2, `capturePage` returns 2560×1600 and a working tab costs about twice the memory (§2). On Windows the 4×31 host lost its content area at 2× and its tabs drew nothing; the 32×32 host works (round ten). In design B a tab's output scale is fixed when it is made: made at 1 it looks soft while watched on a 2× display, and made at the display's scale its pictures need scaling, as in A (§7.1). A real 200 % Windows display, and a 120 Hz one, are live gates.
10. **The numbers come from CI runners** with 3–4 vCPUs and no GPU on Windows and Linux. So design B ran its bitmap road there, and its GPU road only on the macOS runner's paravirtual GPU and on Windows' software Direct3D (WARP). Absolute CPU figures will move on real machines. The verdicts rest on what works and what draws, which won't.

1. **A bot's tabs: design B, and the hybrid's host behind the screen-reader switch.**
   * **Design B (decided): offscreen tabs and the viewport,** from `src/electron/viewport.ts`, `src/pages/vp-preload.ts` and `vp-viewer.html`:
     * **a bot's tab** is an offscreen `BrowserWindow` that is never shown (`offscreen: { deviceScaleFactor: 1 }`), with `setContentSize(1280, 800)` after it is made, since Windows fits a new window to the screen;
     * **CPU bitmaps by default, on every OS:** on macOS so a watched tab's dropdowns draw (a tab's frame type is fixed when it is made), on Linux until real dmabufs pass the live gate, and on Windows until a real GPU's frames are checked. GPU textures come later, as an option, and only where `app.getGPUFeatureStatus().gpu_compositing` is enabled: asking for them without it hung the main process on Linux (§7.1);
     * **a heartbeat, and safe mode:** the daemon checks that the app's main process answers (a hang like Linux's stops the whole app, its windows too), and restarts one that stops answering into safe mode, with bitmaps only and no texture request, through the pair's existing restart and safe-mode path (§5);
     * **the frame rates:** 10 fps while a bot works and nobody watches, 60 while the person watches, and painting stopped while a bot only reads or the tab rests. A tab with painting stopped still runs its rAF at the rate set (§7.1), so M1 measures how low a resting tab can go (1 fps, say) and checks §14.2 item 33's idle budget with resting tabs open;
     * **the viewport,** a canvas in the browser view: bitmaps cropped to the changed rectangle, at most three in flight, with a full frame asked for when it falls behind (and, once textures come, textures imported with Electron's `sharedTexture` module and drawn as `VideoFrame`s, one in flight). While shown, the tab is laid out at the view's size;

A window the page opens: a cross-site one is adopted as an offscreen tab like any other (round fourteen); a same-site one is a real window while the person watches, and while a bot is alone M1 chooses between refusing it and opening its address as a new offscreen tab, which loses `window.opener`;
     * **M1's first checks through the viewport,** each an assertion in the browser suite:
       * **copying from a viewport tab,** which the owner asked about: the copy key (⌘C on macOS, Ctrl+C on Windows and Linux) is forwarded as Electron's `copy()` on the tab, and the right-click menu's Copy: the tab's `context-menu` event brings the selection and whether it can be copied, the app draws its own menu at the viewport's point, and its Copy calls `copy()`. Round fifteen tested both through the viewport on every OS, with bitmaps and with GPU frames: the copy key put the page's selection on the clipboard, and the right-click brought `context-menu` with the selection and `canCopy`, after which `copy()` did the same.
       * **drag-selecting text** with the mouse, kept as an assertion: in round fifteen a drag across a line of the page selected all of it, on every OS
       * the cases not yet tested (§7.4): right-click menus beyond Copy, tooltips, date, time and colour pickers, autofill, files dragged in from outside, pinch and touch;
     * **the screen-reader switch** (decision 1a's hybrid). It is on while a screen reader runs, and it decides where a *new* bot tab starts: offscreen while it is off, as a real view in the hybrid's host while it is on. It never moves a tab that exists: a tab made before it turned on stays offscreen and is shown through the viewport (its page isn't read); a tab made while it was on stays in the host until it closes, and the host closes with its last tab. No tab reloads either way. How it is detected, for M1 to confirm on each OS:
       * **everywhere:** Electron's `app.isAccessibilitySupportEnabled()` and its `accessibility-support-changed` event (which Electron documents for macOS and Windows). Chromium turns its accessibility on when any assistive client asks for the app's tree, a screen reader or not (on macOS, window managers and other accessibility clients do too), so on its own it would put more people on the host than need it; it is the fallback where the OS's own signal can't be read;

       * **Windows:** the system's screen-reader flag, `SystemParametersInfo(SPI_GETSCREENREADER)`, which Narrator, NVDA and JAWS set, re-read on `WM_SETTINGCHANGE`;
       * **Linux:** AT-SPI's status on the session's accessibility bus, `org.a11y.Status`'s `ScreenReaderEnabled` property (Orca sets it), watched with `PropertiesChanged`; GNOME also keeps `org.gnome.desktop.a11y.applications screen-reader-enabled`;
     * **decision 2 is open, so no Electron patch.** If the owner decides to carry a patched Electron (edit 1), the patches that would restore what B gives up are a page's dialogs handed to the app (§7.6), same-site `window.open` made offscreen (Electron #55565's proposed fix), and the dropdown's rectangle with GPU frames (§7.4).
   * **The hybrid's host: design A's host window, built only for the screen-reader switch,** from `src/electron/tabs.ts`. It holds only bot tabs made while a screen reader is on, so with the switch off it doesn't exist:

     * **the host's invariants,** as edit 2 lists them, each set where the host is made: 1×1, frameless, `focusable: false`, `skipTaskbar`, click-through (`setIgnoreMouseEvents`) and shown with `showInactive`; on Windows a 32×32 tool window (`type: 'toolbar'`) at opacity 0; on macOS out of Mission Control (`setHiddenInMissionControl`), with opacity 0 weighed against an opaque single pixel, about 10 points of a core cheaper for a page that animates (§2); on X11 and XWayland an empty window shape (`setShape([])`); a neutral title and content protection. Make it always on top, and on every Space on macOS, only if the live gates find that a covered host stops drawing;
     * **the host shaped on X11 from the start,** so every X11 row of the suite (throttling, cost, the shared host, the wake) tests the proposed host. The wake check needs it most: Chromium takes a shaped host as covered, and the wake turns throttling off after the tab is created;
     * **the host closed when none of its tabs is working,** and made again before the next command, so §3.1's exception stays as small as it can and §14.2 item 33's idle budget ("an app with no window under 1% CPU") holds;
