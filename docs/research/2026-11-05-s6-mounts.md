## How it was measured

* **Two processes and a fake link.** The **file service** (`spikes/s6-mounts/server/serve.ts`, Bun) stands for the daemon on the computer that holds the files. The **mount helper** (`native/mounts`, Go) stands for the other computer. Between them is the **fake link** (`spikes/s6-mounts/link/proxy.ts`, Bun): a TCP relay that adds a fixed round trip (half each way), and can go silent (*blackhole*: no FIN, no RST, bytes held, like Wi-Fi dropping or a laptop lid closing) or reset every connection. It can also cap the bandwidth each way, add jitter that keeps the bytes' order, and hold at most a set number of bytes in flight, pausing the sender past that as a TCP window would; the slow-link check uses that mode (§4), and the speed rows don't. The relay also plays the local daemon's hop.
* **The wire protocol** is new and small: [PROTOCOL.md](../../native/mounts/PROTOCOL.md). It is multiplexed, so the kernel's parallel requests (git's preload threads, readahead) go out together. Listings carry attributes (readdirplus). The holder pushes change events. Paths are relative to the exported home.
* **Liveness:** any bytes from the holder prove the link alive. Both ends ping every 250 ms, and 1.5 s with nothing from the holder means the computer dropped. A request's clock starts once it is on the wire, and runs only while no answer bytes arrive: it fails after 10 s of that, or after 60 s at most while answers keep arriving. Change events are handled on their own goroutine, never on the link's reader (§4 says why; the review's slow-link findings changed the rest).
* **Three caching policies:**
  * `nocache`: every lookup crosses the link.
  * `plain`: 1 s of kernel and helper caching, like stock FUSE file systems (libfuse's defaults, sshfs).
  * `cached`: keep everything until the holder says it changed. The holder watches the folder and sends events. The first lookup or listing that misses in a folder fetches the folder's subtree in bulk, breadth first, up to 20,000 entries, once per folder and never for the home folder itself.
* **The machines** are GitHub runners. Linux is Ubuntu 26.04.1 (kernel 7.0.0-1014 to -1019, as the runner images varied; fuse3), the spec's own target. Windows is Server 2025 (10.0.26100, the same kernel as Windows 11 24H2) with WinFsp 2.1.25156. macOS is 26.6.2 (25G83) and 27.0.1 (26A434) with Xcode 26.6 and 27.1. The client, the server and the fake link run on the same machine, so `+0 ms` is about 0.05 ms of loopback, not a real LAN.
* **The workloads** run in "the other computer's home", a clone of this repo at the branch head with its `node_modules` installed. That is about 3,800 tracked files in some 370 directories, and about 12,000 files in all:
  * `git status --porcelain`, with fsmonitor and the untracked cache off
  * `tsc --noEmit -p packages/protocol` (340 files) and `-p packages/core` (1,937 files): this repo's own typecheck, its build step
  * reading and writing 256 MiB
  * copying `packages/protocol` (119 files) out of the mount and into it

  **Cold** means a fresh mount, so the client's caches are empty; the holder's disk cache is warm. On Linux, local cold runs drop the page cache first. **Warm** means the same command again straight away. The added latency is a **round trip**: +20 ms is 10 ms each way.

## 1. Mounting another computer's folder

**The shape.** Each other computer's `home/<Computer>` is served over that computer's link. On Linux one FUSE mount holds the whole tree, and `home/<this computer>` inside it is a link to the real home folder, so programs there run at native speed. On macOS the tree is a real folder: this computer's entry is a symlink, and each other computer's home is its own NFS mount on its folder. On Windows one network volume holds the whole tree, and this computer's entry is served through it as well, because a link inside a WinFsp volume can't leave it (below). A computer that is off still appears, as a folder whose contents answer "offline" at once, so `ls home/` never hangs.

### Linux: FUSE — works

* **Setup:** Ubuntu 26.04.1 with kernel 7.0, fuse3 and go-fuse v2.12.1. go-fuse speaks the kernel's FUSE protocol itself, in place of libfuse3, and mounts through fuse3's setuid `fusermount3`, so the mount is unprivileged.
* **What passed in CI:** every workload across the mount (§3), every fail-fast scenario (§4) and the coherence check.
* **What a dead helper leaves:** the kernel answers `ENOTCONN` for the dead mount until `fusermount3 -u -z`, which the daemon runs before remounting (§4).
* **The `cached` policy** uses the kernel's notify calls (`notify_inval_entry`, `notify_inval_inode`) when the holder reports a change. `plain` relies on 1 s timeouts.

### Windows: WinFsp — works, as a network volume

* **Setup:** Windows Server 2025 (10.0.26100) with WinFsp 2.1.25156, installed silently from its MSI (`msiexec /i … /qn`, which needs admin once). cgofuse v1.6 runs without cgo.
* **What passed in CI:** reads, writes, copies, `git status` and Git Bash inside the mount, every fail-fast scenario, and the coherence check. WinFsp's own cache stays correct when a file shrinks or grows behind it. `tsc` passed only once the tree was a network volume (item 4 below).
* **What a dead helper leaves:** WinFsp tears the volume down with the process, so nothing is left to clean.
* **Four things had to change** for Git for Windows and for Node (`ci/windows-git.ps1` and `ci/windows-tsc.ps1` try the layouts and ask Windows for each folder's final path, as git's `getcwd()` and Node's `realpath` do):
  1. **Names must keep their case.** In WinFsp's case-insensitive mode its FUSE layer hands out upper-cased names (`T:\HOME\DESKTOP1\CLOVER`), and git then stats a path that doesn't exist. Off, names keep the holder's case, and the holder decides how case is matched (NTFS and APFS ignore it, Linux doesn't).
  2. **Folders need an x bit.** Windows has no POSIX modes, and libuv reports `0666` for a folder on a Windows holder. WinFsp turns the missing x into a missing `FILE_TRAVERSE`, so `chdir()` into the repo failed with "Permission denied". The file service now reports folders on Windows with their x bits.
  3. **This computer's entry can't be a link inside a WinFsp volume.** WinFsp's FUSE layer makes every link relative to its volume, and refuses absolute targets and targets outside it. `T:\home\Runner` never resolved.
  4. **Each volume must be one Windows can name.** Bun installs `node_modules` with its isolated linker, so `node_modules/@types/bun` is a link into `node_modules/.bun/…`, and `bun-types` sits beside the link's target. It is found only from the link's real path. On a WinFsp volume on a plain drive letter (`DefineDosDevice`) or a folder, `GetFinalPathNameByHandle` fails with `ERROR_UNRECOGNIZED_VOLUME`, so Node's `fs.realpathSync.native` fails, and TypeScript falls back to the link's own path. It then finds neither `bun-types` nor `@types/node`, and `tsc` fails with "Cannot find module 'bun:test'" (187 files in its program instead of 340). Mounted as a network volume (`--volume-prefix \clover\tree`, as sshfs-win does), `realpath` answers `\\clover\tree\…` and `tsc` passes (`results/windows-tsc.txt`). A drive letter the Mount Manager knows (`\\.\T:`, which needs admin) also has a final path (`results/windows-git.txt`). Every Node tool in a workspace that links its `node_modules`, as Bun and pnpm do, needs one of the two.

  With 1 and 2 fixed, `git status`, `git -C` and Git Bash work in every layout tried: a drive letter from `DefineDosDevice` (WinFsp's default, no admin), one the Mount Manager knows (`\\.\T:`, admin), a network volume (`\\clover\tree`, as sshfs-win does), and a real folder. That holds with `core.symlinks` on (Git for Windows' default) or off. The plain drive letter is the least compatible for other software, since `GetFinalPathNameByHandle` fails there with `ERROR_UNRECOGNIZED_VOLUME`, but git copes.
* **What that leaves for the layout** (`ci/windows-tsc.ps1` tried five):
  * One network volume on a drive letter for the whole tree passes everything, `tsc` included, but this computer's entry can't be a link inside it (item 3).
  * A plain volume mounted on a folder, so that this computer's entry can be a junction beside it, breaks Node (item 4).
  * A network volume can't be mounted on a folder: WinFsp refused it (`c00000ca`, network access denied).
  * A network volume on a drive letter WinFsp picks, reached from the tree's folder by a directory symlink to its UNC path (`home\Desktop1` → `\\clover\Desktop1`), passes everything. Creating such a symlink needs the symlink privilege (admin, or Developer Mode).
* **So the tree on Windows is one WinFsp network volume** (`\\clover\tree`, on a drive letter), and this computer's entry is served into it by the helper through the computer's own tree service over the loopback address, as any other computer is, rather than as a link. That layout is an inference, not something CI built (review S7): the prototype's helper knows this computer's entry only as a link, which `windows-coherence.json` shows as ENOENT. The closest measurement is the network volume at +0 ms (§3), which has the fake link's hop as well. The other choice, a real folder with a junction for this computer and a symlink per other computer, keeps this computer's entry native but needs the symlink privilege whenever a computer is added. That is spec edit 2, and live gate 3 builds the layout.

### macOS: FSKit — doesn't, for now; NFS loopback — works with limits

**Clover's own FSKit module** (`native/mounts/macos/`, Swift) is the volume of spec §9.1: an `FSUnaryFileSystem` taking `clovertree://host:port/Computer` URLs (`FSGenericURLResource`), with the same link and fail-fast rules as the Go helper.

* **What CI shows:** it builds unsigned against the macOS 26 SDK (Xcode 26.6) and the macOS 27 SDK (Xcode 27.1), and registers with `pluginkit`. `mount -F -t clovertree …` then answers "Module com.waifucave.clover.tree.dev.fs is disabled!".
* **A disposable runner can't get further.** Adding the module to FSKit's enabled list by hand (`enabledModules.plist`, what the System Settings switch writes) gets past that check, but `amfid` then refuses to launch it: "The file is adhoc signed but contains restricted entitlements" (`-424`). `com.apple.developer.fskit.fsmodule` needs a provisioning profile from a team with the FSKit Module capability.
* **So the module can't be tested at all without signing with the owner's team, and the switch.** That is live gate 2, and `native/mounts/macos/gate.sh` is the script for it (§ "Left for the live gates").

**FSKit itself, through macFUSE.** macFUSE's FSKit backend is FSKit with a signed module. On a disposable runner it can be turned on by hand, so CI uses it to see what FSKit does to a network file system.

* **It mounts as the user** on any folder (here `$RUNNER_TEMP/s6/tree`), and every read workload ran. Creating files and folders answered `ENOSYS`, although the helper implements `create`, `mknod` and `mkdir`. The cause, in macFUSE's backend or in FSKit, wasn't isolated, so FSKit's write speed is left for live gate 2 with Clover's own module.
* **It fails fast** like the other OSes (§4).
* **It shows nothing the holder changes.** New sizes, new contents and new names never appeared within 10 s.
* **It corrupts short reads** (§2).

That rules FSKit out for the folder tree on macOS 26 and 27 today, whoever writes the module.

**NFS loopback.** The helper serves each other computer's home as an NFSv3 export on `127.0.0.1` (`cmd/clover-nfs`, go-nfs with patches to five files), and the kernel's NFS client mounts it. No extension and no System Settings switch are involved.

* **It mounts as the user, with no approval of any kind.** `mount_nfs` uses a reserved source port by default, which needs root, and it failed as the user with "Input/output error". With `noresvport` it mounts as the user on a folder the user owns, on macOS 26.6.2 and 27.0.1. go-nfs doesn't ask for a reserved port. The first CI runs, without the option, fell back to `sudo`; the rig no longer does.
* **Only the daemon can mount it.** The export is a service on the loopback address, which any local process can reach, and NFS has no authentication of its own (review B2). The helper listens on a port the kernel picks and prints it, with a one-time random export path, to the process that started it. It accepts one MOUNT with that path and refuses every other, so a process that connects first gets nothing, and no process gets a second MOUNT. The folder that holds the mounts is the user's alone (0700). Edit 1 lists these conditions, and the two that are left for M2 and lane C.
* **Stock go-nfs turned "offline" into wrong answers.** A read in flight saw "Permission denied". A lookup saw "No such file". The macOS client then cached the missing name until the folder changed, so the mount never recovered after the link came back (30 s and counting). Three small patches fix that (`third_party/README.md`): an unreachable computer answers `NFS3ERR_IO`, only a missing name answers `NFS3ERR_NOENT`, and a read that comes back short inside the file answers `NFS3ERR_IO` instead of a short read. With them the NFS mount fails fast like the others (§4), on macOS 26.6.2 and 27.0.1 alike. A silent drop fails calls in flight after 1.47–1.66 s, and a reset or a killed file service after 4–21 ms. Every later call answers EIO in under 1 ms, and the mount works again 95–296 ms after the link returns.
* **Stock go-nfs answers one call at a time.** The kernel's client sends all of a mount's calls over one connection, so a read waiting on the far computer held up every lookup behind it. Big reads then failed with `ETIMEDOUT` at +20 ms, and `git status` with 1 s caching took 206 s at +20 ms (§3). A fourth patch handles calls concurrently. Writes stay in line, in the connection's read loop: with them concurrent too, a 1 GiB writer saw the far computer's drop only after 18–29 s (`results/macos2?-nfs-failfast-concurrent-writes.json`). The review (S5) suggested a queue of their own, so the loop keeps taking lookups while a write waits. CI tried it: the writer then ran on for 18–25 s (link silent) and 29 s (file service killed) after the drop on macOS 26.6.2 and 27.0.1, the same failure: the loop takes every write the client sends, so the client never feels the far computer slow down. Writing 256 MiB also took 240 s instead of under a second. So writes stay in line, and a lookup can wait behind one write, one round trip to the holder. In line, a writer meets the drop after 1.58 s (§4), and 256 MiB writes in 1.2 s at +0 ms and 14 s at +20 ms (§3).
* **Stock go-nfs walked every live file handle on every call** (review B1). Its handle cache keeps each handle's folders recent by scanning all live handles, which every NFS procedure pays: 2.3 µs with 100 handles, 112 µs with 4,000, 358 µs with 12,000, 5.1 ms with 100,000. A `git status` makes thousands of handles live (one per name it looks up or lists), so every call paid a scan of all of them, and warm runs, which start with more handles, were slower than cold ones. A fifth patch looks the folders up directly: 0.24 µs with 100 handles and 0.33 µs with 100,000 (`TestFromHandleCostIsFlat`). §3 has what that did to `git status`.
* **A dead helper can leave a caller stuck in the kernel.** A read in flight when the helper died survived SIGKILL for 20 minutes, until the CI job was cancelled. The mount now carries `deadtimeout=5`, so macOS marks a mount whose server stopped answering as dead. With only that, the read in flight failed after 7–13 s, mostly with `ENXIO` once macOS took the dead mount down itself (the runs before this round). The daemon is the helper's parent and learns of its death at once, so it now force-unmounts right then, and the read in flight fails with it: after 1.0 s on both releases (§4). `deadtimeout` stays as the backstop.
* **Coherence is good with the kernel's attribute cache off, or with files' attributes uncached.** With `actimeo=1` and the helper's 1 s cache (`plain`), changes showed after 1.0–2.0 s (once on 27.0.1 a new name didn't show within 10 s). With `noac`, every stat reaches the helper on the loopback address, and the helper's own cache is the one the holder's events keep fresh (`cached`). Then a new size showed after 30 ms, new content after 59–61 ms, a new name after 30–56 ms and a deletion after 29–57 ms, on macOS 26.6.2 and 27.0.1. With `acregmax=0,acdirmax=1` over the same cache: 33 ms, 62–66 ms, 32–35 ms and 59–69 ms. With `actimeo=1` over it: about 1 s for each (`results/macos2?-nfs-*-coherence.json`). That needed one fix: an event must also drop the parent folder's attributes. The client keeps a name it remembers as missing for as long as the folder's attributes don't change, so before the fix a new file never appeared.
* **One narrow window of padding remains.** The client pads a read with zeros up to the size it held when the read began. It does so even when the server answers right. The helper's log (`results/macos27-nfs-short-read-log.txt`) shows the sequence, with `noac` or without:
  1. The client stats `so.txt` and is told 200 bytes. The holder then rewrites the file to 46.
  2. The client asks for 200 bytes and gets 46. The patched go-nfs answers EIO.
  3. The client re-stats, is told 46, asks for 46 and gets them.
  4. The program's `read()` still returns 200 bytes: the 46, then 154 zeros.

  So a program on the Mac that reads a file within one coherence window (about 30 ms here) of the holder truncating and rewriting it in place can get zeros at the end. They are always zeros, never other memory, and never once the window has passed. A file replaced by rename, as editors and most tools save, isn't safe either (review S3): the helper reads by path, so a program reading across the rename can get the start of one version and the end of the other. M2 pins a read-only open to the file it opened (edit 4).

## 2. The FSKit data-corruption bug

**What the bug is.** FSKit keeps the file size it was last given (by `lookupItem` or `getAttributes`), and a read that comes back short doesn't correct it. Linux's FUSE treats a short read as the new end of file; FSKit doesn't. The reader gets the old length, and every byte past what the module sent is padding the module never wrote:

* A file that **shrinks** behind the mount reads back at its old length. In [macfuse#1222](https://github.com/macfuse/macfuse/issues/1222), on macOS 26.5.2, a file cut from 6,000 to 1,500 bytes read as 6,000: the 1,500 new bytes, then 4,500 bytes of padding.
* The padding isn't the module's buffer. In #1222, filling the buffer's unused tail with a marker never made the marker appear. In [#1231](https://github.com/macfuse/macfuse/issues/1231), on macOS 27.2 (26B123) with macFUSE 5.5.0, it was zeros in one run and pointer-like values in another: memory that isn't the file's, handed to the reader.
* A file that **grows** reads back cut off at the old size, and stays cut off until unmount (#1222 waited 240 s).
* A **zero-byte answer** to a read FSKit believes is inside the file is the same case at its extreme. It crashed macFUSE's own extension until 5.4.0 ([#1188](https://github.com/macfuse/macfuse/issues/1188), reproduced on macOS 26.6 25G72), and FSKit then pads it.

This is the data corruption that [macFUSE 5.5.0](https://macfuse.github.io/2026/10/17/macfuse-5.5.0.html) (October 17, 2026) "mitigates … in FSKit on macOS 26 and 27". It rejects empty `FUSE_READ` replies with EIO and clears unused buffer tails after short reads, and it warns that "this workaround can cause read errors when a file's size changes remotely". For the folder tree a remote size change is the normal case, not an edge case: every file another computer's program writes.

**Whether current macOS fixes it: no.** CI reproduced it on both current releases (below), and:

* It is reported on macOS 26.5.2 and 26.6 (#1222, #1188), and on macOS 27.2 with 5.5.0's mitigation in place (#1231, opened November 2, 2026, still open).
* Apple has published no fix and no Feedback number for it.
* Apple DTS says plainly on the FSKit forum ([thread 842736](https://developer.apple.com/forums/thread/842736)): "FSKit isn't currently at a place where it can properly support a network file system."
* The newest macOS 26 is 26.6.x: 26.6.1 (25G76) on this Mac, 26.6.2 (25G83) on the CI image. macOS 27.0.1 (26A434) is on the CI image too.

**Reproduced in CI, on both current macOS releases.** A module of our own can't run in CI (§1), so the `macfuse-fskit` job drives FSKit through macFUSE's FSKit backend. macFUSE's module carries a real signature, and the disposable runner adds it to FSKit's enabled list by hand. The helper mounts with `-o backend=fskit`, and `bench/coherence.ts` takes the one path that reaches the module with a stale size: the mount learns a 200-byte file's size from a `stat` alone, the holder rewrites the file to 46 bytes, and a program reads it.

| macOS | macFUSE | what the reader got (two mounts each) |
| :- | :- | :- |
| 26.6.2 (25G83) | 5.4.0 | 200 bytes each time: the 46 real ones, then 154 the file doesn't have. One mount gave mostly zeros with 4 stray bytes; the other gave text from someone else's memory (`…ionHidde`). |
| 27.0.1 (26A434) | 5.4.0 | 200 bytes: the 46, then zeros in one mount and UTF-16 text in the other |
| 27.0.1 (26A434) | 5.5.0 | 200 bytes: the 46, then mostly zeros with 2 stray bytes in one mount, and pointer-like bytes (`a7 2b 00 1c 06 00 00 00`) in the other |
| 26.6.2 (25G83) | 5.5.0 | 200 bytes in both mounts: the 46, then 154 zeros |

So the bug is live on macOS 26.6.2 and 27.0.1. macFUSE 5.5.0's tail-clearing doesn't stop it: the bytes come from below the module, as #1231 says. Linux FUSE and WinFsp, on the same check, return the 46 bytes and nothing else.

The same job shows a second FSKit gap that matters as much for a network file system. **Nothing the holder changes ever shows.** A new size, a grown file's new bytes, and a new name were all still invisible after 10 s, under both caching policies, on both macOS releases. A read after a change returned the old bytes from FSKit's cache. macFUSE's notes say why: "The FUSE notification API is not supported, yet", and the kernel-side timeouts (`attr_timeout`, `entry_timeout`) aren't implemented for FSKit. FSKit on macOS 26 offers a module no way to make the kernel forget a size or a name. macOS 27's `setCacheState(…, action: .revoke)` is the first.

**The same padding lives in macOS's NFS client** (§1). The kernel trusts a size it was told, and fills a read up to it with zeros. Over NFS the size refreshes, so the exposure is bounded by the coherence window (about 30 ms with `noac`) and the padding is zeros. Through FSKit sizes never refreshed in CI, and the padding held other memory. On macOS the fix is the same in both: keep the kernel's idea of a file's size from going stale, rather than trust what a read returns.

**Related FSKit limits a network module meets** (DTS confirmed each as a bug or a missing VFS feature in thread 842736):

* **Misses stick to the vnode.** Once a name answers ENOENT, a file created there later stays invisible for the life of the vnode (FB24419825, fixed in 27.2).
* **Cache invalidation is unreliable.** A data-cache grant can land after an invalidation and undo it (FB24419858). Invalidating the volume root fails (r.186984837, FB25077250). A replaced directory at the root keeps answering ESTALE until unmount (FB25243414).
* **fsync never reaches the module.** On a URL-backed volume, `fsync`, `F_FULLFSYNC` and `sync` all return success without one call to the module (FB24419870).
* **A failed `activate` wedges the resource.** After one error from `activate`, every later mount of the same URL answers "Resource busy" until fskitd and the extension are killed (FB24419932).
* **No locks, no ACLs, no per-entry xattr flag** (FB24419974, FB24419979, FB24419964).
* **A call left unanswered can hang its caller.** Processes reading from it can become unkillable ([thread 831396](https://developer.apple.com/forums/thread/831396)).

macOS 27 adds the tools a network file system needs, but only for data. `FSVolume.DataCacheHandler` negotiates per-open cache modes, and `setCacheState(for:cacheMode:coherencyType:action:)` can push, invalidate or revoke ("invalidate all caches, revoke all access to the item, and trigger vnode reclamation"). Apple calls it "a generalized form of leasing" ([thread 831417](https://developer.apple.com/forums/thread/831417)). It also has known holes: with `isDataCacheInhibited` it answers ENOTSUP (FB24996000), and the grant race above.

**What a module must do until Apple fixes it.** The `clovertree` module ([Volume.swift](../../native/mounts/macos/CloverTreeFS/Volume.swift)) does the first five, and the live gate can switch the guard off with `?mitigate=0` to see the bug itself:

1. **Clear the unused tail** of FSKit's buffer after every short read. This is macFUSE's mitigation; it doesn't cover padding that comes from the kernel.
2. **Never answer a read FSKit believes is inside the file with fewer bytes than it asked for.** Remember the size last given to FSKit for each item. If the holder's file is now shorter, answer EIO (never zero bytes, never a short read) and refresh the item's attributes. A reader then sees an error, never bytes the holder didn't send. On macOS 26 nothing makes FSKit take the new size (CI, above), so such a file keeps answering EIO on that Mac until FSKit drops the item. On 27, item 6 revokes it. Live gate 2 has to show that FSKit passes the EIO on: macOS's NFS client, given the same EIO, retried and padded anyway (§1).
3. **Answer every call within the link's bound** (1.5 s after a silent drop; on a live link, 10 s with no answer arriving, 60 s at most), so no caller is left in an unkillable wait.
4. **Never fail `activate`.** Answer with the root item even while the computer is offline, so one bad moment doesn't wedge the URL until fskitd restarts (FB24419932). Report offline per call instead.
5. **Keep attributes short-lived** (1 s here) and answer `statfs` from a cache, never from the network.
6. **On macOS 27, adopt `DataCacheHandler`** in negotiated mode, and revoke an item through its parent when the holder reports a change. That is the only way to make FSKit forget a size. Live with the grant race and the root-invalidation bug until they're fixed.

* **Cold runs barely depend on the setting.** 70–80 requests cross the link one after another, so at +20 and +80 ms the round trips dominate: 2.2–3.0 s and 5.2–6.4 s for `git status` whatever the setting.
* **Warm runs do.** `actimeo=1` is fastest when the warm run starts within a second of the cold one (30–62 ms at +0 ms); at +20 ms the cold run took longer than that, its attributes had expired, and it made as many calls as the middle setting. * git then finds every entry's owner changed and re-reads every tracked file: 3,980 reads, one after another. That took 1.7 s at +0 ms, **83 s at +20 ms and 321 s at +80 ms**.
* With `core.checkStat=minimal` (whole-second mtimes and sizes only), it took 256 ms, 856 ms and 2.7 s.

**Reading the numbers:**

* **On Linux, a project already touched runs at local speed.** With `cached`, a warm `tsc` sends no request at all: the attributes, names and pages stay until the holder reports a change. A warm `git status` sends 5. WinFsp re-reads file contents at each open (above), which M2 has to fix for Windows to match.
* **A cold run costs its round trips.**
  * `git status` needs 32 requests, because the first lookup that misses in a folder fetches the folder's tree in bulk.
  * `tsc` reads 2,107 files one at a time, so a cold build is mostly round trips: +45 s at +20 ms, and +168 s at +80 ms.
  * Fetching small files' contents with the tree, up to a budget, would remove most of that. M2 can try it.
* **`plain` caching, like stock FUSE file systems, is not enough.** Its 1 s timeouts expire between runs, so warm costs as much as cold: 26 s for `git status` at +20 ms, against 0.96 s with `cached`.
* **Large files are bound by round trips too** on Linux. Reads go out 128 KiB at a time with about two in flight: 12 MiB/s at +20 ms, 3 MiB/s at +80 ms. Writes go 1 MiB at a time: 39 and 12 MiB/s. The helper should read ahead on sequential access (M2).
* **Small files into a mount cost about five round trips each** (create, write, set times, close; mkdir per folder). Moving a project between computers file by file through the mounts is slow, which is spec edit 8.
* **This is why Bash runs where the files are** (the **[D]** in §9.1). Across a +20 ms mount, `git status` is 13 times slower cold and `tsc` 3 times. Run on the holder, both are local.

## 4. Failing fast when the computer drops

**Method.** `bench/failfast.ts` mounts fresh for each scenario and starts a real program. That is a 1 GiB read or write, a cold `git status` or a cold `tsc` on the mount, all at +20 ms with the `plain` policy (over NFS, `actimeo=1`). Then it injects a fault. It measures:

* how long the program takes to fail, and what it sees
* how fast a new operation fails while the computer is away
* processes left in uninterruptible sleep or as zombies (`ps` state D/Z on Linux, U/Z on macOS)
* how soon the mount works again once the fault is removed
* whether the mount comes off cleanly afterwards

`remote_test.go` checks the same rules at the protocol level on all three OSes.

A new operation while the computer was away failed in under 1 ms on every mount but FSKit's (1–42 ms), with `EHOSTDOWN` on Linux, `EHOSTUNREACH` on Windows and through macFUSE, and `EIO` over NFS. No scenario left a process stuck or a zombie behind, and every mount came off cleanly. macOS 26.6.2 gave the same picture. Over NFS: silent drops failed calls in flight after 1.47–1.66 s, a reset after 8 ms, a killed file service after 4 ms (a read) and 21 ms (a write), a dead helper's read after 1.03 s, and the mount was back in 103–296 ms. Through macFUSE's FSKit backend on 26.6.2 (the earlier run), a reset failed reads in 29 ms and a killed file service in 39 ms, the next call took up to 42 ms, a read in flight when the helper died waited 3.5 s, and the remount took 466 ms.

**The bound.**

* **A computer that drops silently** fails every operation in flight within **1.4–1.7 s**: the 1.5 s silence limit plus up to one 125 ms watchdog tick. FSKit and NFS add a few tens of milliseconds of their own. Every later operation fails at once.
* **A link that resets, or a daemon that dies with its computer still up,** fails in-flight operations in 4–39 ms.
* **A frozen daemon** (SIGSTOP), whose TCP keeps answering, is caught by the same bound. TCP keepalive wouldn't catch it, which is why liveness is the protocol's, not TCP's.
* **The first operation after a silent drop** waits out the rest of the bound (1.37–1.49 s measured). After that, "computer offline" really is at once.
* **When the link returns,** the mount works again within 15–179 ms. That is the redial backoff (100 ms doubling to 1 s) plus a round trip. When the daemon itself restarts, it takes 165–427 ms.
* **What programs report.** A read in flight sees the link's error when its own request failed. It sees `EIO` (Linux) or `ECANCELED` (Windows, helper killed) when the kernel's readahead failed instead, which is the kernel's choice. `git` prints "index file open failed: Host is down". `tsc` dies with a Node stack.
* **A dead helper:**
  * On Linux the kernel answers `ENOTCONN` for anything not cached. Cached entries still answer, and the mount stays until the daemon detaches it with `fusermount3 -u -z`.
  * On Windows the volume disappears with the process, so its folder is simply gone (`ENOENT`).
  * Over NFS the kernel would keep waiting for the server: with only `deadtimeout=5`, the read failed after 7–13 s, and without it one read survived SIGKILL for 20 minutes. The daemon now force-unmounts the moment its child dies, and the read fails then (1.0 s on both releases).
  * Through macFUSE's FSKit backend, a read in flight waited 157 ms (27.0.1) to 3.5 s (26.6.2).
  * The daemon's remount took 116–466 ms on every OS.

**Two bugs the checks found, both fixed in the prototype, both rules for M2:**

* **A kernel cache call on the link's reader stalls the link.** With `cached`, writes into the mount failed with "Host is down" after exactly 1.5 s of silence, at +0 and +20 ms. The reader goroutine was delivering the holder's change events itself. Linux's `inval_inode` for a file being written waits on that write's page locks, and the write's reply could only arrive through the blocked reader. Events now run on their own goroutine (`TestBlockedEventHandlerDoesNotStallTheLink` reproduces the stall against the old code). After the fix, the same runs had no false "offline" at all.
* **Dropping a live directory's entry breaks `getcwd()`.** After a reconnect, the helper invalidated every entry, and git then failed with "unable to get current working directory" in its own repo. Directories now keep their entries unless the holder says they are gone or replaced. The kernel's negative entries live 1 s, and the helper answers repeated misses from its own cache.

**A live link that is slow** (review S1). The first version could call a slow link dead in four ways, and the fake link, with no bandwidth limit, exercised none of them:

* the holder never pinged, so during an upload the helper's own pings queued behind its data and nothing proved the link alive;
* each frame write had a fixed 1.5 s deadline, which a 1 MiB frame misses below about 6 Mbit/s;
* a request's 10 s clock started when it was queued, so NFS's 16 × 1 MiB of read-ahead timed out behind each other's answers;
* once those were fixed, the Windows run showed a fourth: one 32 KiB write sat past the bound while the fake link drained its buffer, with the holder's pings still arriving.

The same run caught the fake link itself: capped, it sent each chunk it read in one piece after the chunk's whole transmission time, so where the socket hands over big chunks (Windows, macOS) a 1 MiB reply arrived after 2 s of silence. The helper was right to call that dead, and no real link behaves so; the fake link now trickles capped bytes in 8 KiB pieces (longest silence 53 ms, against 2.1 s before).

Now any bytes count as life and both ends ping. Writes carry no short deadline: a write that stalls waits while the holder is heard, and the watchdog's close ends it once the holder goes silent too. (A first fix retried a write that hit its deadline; on Windows that garbled the stream, because a cancelled send can still put its bytes on the wire.) A request's clock starts once it is on the wire and runs only while no answer bytes arrive, with a 60 s cap. `TestSlowLinkStaysUp`, `TestQueuedAnswersAreNotTimedOut` and `TestStalledUplinkIsNotOffline` each fail on the code before its fix. The fake link can now cap the bandwidth, with jitter and a bounded buffer, and `failfast.ts` runs a `slow-link` case: 8 MiB written, then another 8 MiB read, at 2 Mbit/s with 0–20 ms of jitter. On Linux and Windows it now passes at the link's own speed (34–35 s each way), with no false "offline" and no request timeout. Over NFS the helper's link stayed up too, with no drop and no timeout, but macOS's client gave up on the export: with 1 MiB calls in line, a write waited behind the ones ahead of it for longer than the client's timer, the kernel logged "nfs server …: dead" (`results/macos2?-nfs-kernel-log.txt`), and the mount went away under the writer, which saw `ENXIO` at its `fsync` after 30 s. With 128 KiB calls and 4 read ahead, the same link wrote 8 MiB in 40 s and read 8 MiB in 35 s with no error (`results/macos2?-nfs-slowlink-128k-failfast.json`). On 26.6.2 the 1 MiB calls got through (35 s and 34 s, no error), so 27.0.1's client is the stricter one, and the next release may be stricter still. So M2 sizes NFS calls to the link, so that no call takes more than a second or so to cross it, and evaluates `NFS3ERR_JUKEBOX` with `mutejukebox` for the calls that still would.

**Tuning.** The 1.5 s bound is a setting (`--dead`). It must stay well above the worst round trip plus a busy holder's scheduling delay. A tighter bound means more false "offline" verdicts on a congested Wi-Fi, and 1–2 s is the right range. With the daemon telling the helper the moment the link layer knows (§5), the common cases (a closed QUIC connection, a sleeping laptop's lost path) are faster than the ping bound.

## 5. Language, packaging and the daemon's side

**The helper is Go, one binary per OS (on macOS, for now, an NFS server); an FSKit module would be Swift.** Go fits for these reasons:

* **Linux:** go-fuse v2.12 is pure Go and mature (gocryptfs, rclone). It speaks to `/dev/fuse` itself and mounts through the setuid `fusermount3`, so no root is needed, and it exposes the kernel's notify calls the `cached` policy needs.
* **Windows:** cgofuse v1.6 is written by WinFsp's author. It loads WinFsp's DLL without cgo, so the Windows helper cross-compiles from any OS (`GOOS=windows CGO_ENABLED=0`).
* **macOS NFS:** go-nfs serves NFSv3 from the same code (§1).
* **The fail-fast rules** (deadlines, a ping watchdog, failing every pending call) are small and clear with goroutines; see [client.go](../../native/mounts/remote/client.go).
* **The binaries** are 10–11 MB, static, with nothing to install on Linux beyond the `fuse3` package.
* **The team already ships Go:** the ts-connect helper and the tsnet fork.

Rust (`fuser`, `winfsp-rs`) would do the job as well. It only becomes the better choice if lane H's link ends up a Rust sidecar that the helper should share a process with (spec §8.3).

**Neither the daemon nor the app should host the file system.** A FUSE server must never run in a process that may itself touch the mount, or a lookup can deadlock. One stuck callback must not freeze the daemon. And libfuse's or WinFsp's threads calling into Bun through FFI would be fragile.

**The daemon's side** has two halves:

* **On the computer that holds the files**, the tree service (`packages/core/src/tree/`, in Bun) answers the wire protocol on the device link. The spike's `serve.ts` is that service, without the link:
  * one QUIC stream pair per peer, or one per request, as lane H prefers
  * file operations with Bun's `fs`
  * paths confined to the exported home: anything that writes checks the parent's real path
  * the computer's own fence applied to every request, whoever sent it: the fenced set is neither readable nor writable and doesn't show in listings
  * absolute link targets inside the home rewritten as relative ones
  * a watch on the home (`fs.watch` recursive: FSEvents, ReadDirectoryChangesW, inotify) that pushes change events to the peers that asked
  * descriptors for stateless reads, and write handles per connection, closed when the connection drops
* **On the computer that mounts:**
  * The daemon starts one helper per tree at login, once the device registry is up, and restarts it after a crash, cleaning up the dead mount first.
  * It hands the helper the computers and a local socket per computer: a Unix socket in `$XDG_RUNTIME_DIR`, a named pipe on Windows, or for an FSKit module a Unix socket in the app group container, with the peer checked by its audit token, since the sandboxed extension can reach nothing else.
  * It forwards frames between that socket and the device link, and tells the helper the moment its own link layer knows a peer is gone. That can beat the 1.5 s ping bound.
  * On Windows it also has the helper mount this computer's own home into the tree, from the local tree service.
  * On macOS it reads the helper's port and one-time export path from its pipe, runs `mount_nfs` and `umount` for each export itself, as the user, and is the only MOUNT the helper accepts (edit 1). If that MOUNT fails, it starts a new helper rather than retry.
  * It owns the timeouts' policy, and shows a computer as offline in the app.

## What the spec should say

None of these is written into the spec; the controller proposes them. Items marked **[P]** change a proposal. Items marked **touches [D]** change or qualify a decision, and need the owner.

1. **macOS mounts other computers over NFS loopback, not FSKit, for now.** This changes §9.1 "How it works" ("FSKit on macOS") and its **[P]** "On macOS the user turns the file-system extension on once in System Settings". Proposed text: "On macOS each other computer's home is an NFSv3 mount that Clover's own helper serves on the loopback address, mounted as the user. No extension and no System Settings step are needed. A Clover FSKit module replaces it once FSKit can serve a network file system (§14.1 item 6)." It removes the step the welcome guide and live gate 2 are built around, so the owner should see it. It is a **[P]** only with all of what follows; without it, it shouldn't be folded.

   **The export is a local network service, so the edit carries these conditions** (review B2). Each says where it stands:
   * **The helper binds an ephemeral loopback port and tells the daemon over its pipe.** There is no fixed port for another process to take first. *Built:* `clover-nfs` listens on `127.0.0.1:0` and prints `{"port":…,"export":…}` on stdout, which the rig reads.
   * **The export path is a one-time random token** (128 bits), passed the same way. *Built* (`nfsloop/gate.go`).
   * **The helper accepts one MOUNT, with that path, then refuses every other.** A process that connects first and names any other path is refused without using up the one MOUNT, so "whoever connects first wins" no longer holds. Without a MOUNT a process has no root handle, and the handles are random (UUIDv4). *Built and tested* (`nfsloop/gate_test.go`, over the wire too), and every CI mount since went through it.
   * **The daemon refuses to mount if its own MOUNT failed**, since someone else may have used it. It starts a new helper with a new token instead of retrying. *Built in the rig* (`bench/lib.ts`).
   * **The tree's root is the user's own folder, mode 0700**, so other local users can't reach the mounts in it. The files inside carry the user's uid and the holder's permission bits. *Built in the rig* (each result file records the mode).
   * **Lane C's Bash fence denies connections to the export's port.** Otherwise a bot's Bash on the Mac could speak NFS to it, reach other computers without the mount path, and skip §9.1's "judged by the stricter of the two". With the token and the single MOUNT it would find nothing to open, so this is a second line. *For lane C.*
   * **The export joins the Wave 3 security review** of trust boundaries (plan §9). *For the controller.*

   Root on the Mac can still read everything, as with any mount. The token shows in `mount`'s output once mounted, by which time the one MOUNT is spent.

   **The owner's choice: speed or freshness.** The kernel's attribute cache sits in front of the helper's event-fed cache, and its setting decides both. Measured after the handle-table fix, `git status` in this repo on macOS 26.6.2 and 27.0.1 (§3):

   | kernel setting | a change on the holder shows after | warm `git status` at +0 / +20 / +80 ms | cold at +20 ms |
   | :- | :- | :- | :- |
   | `noac` | 29–61 ms | 0.8–1.2 s / 1.2–1.5 s / 2.0–2.2 s | 2.5–3.0 s |
   | `acregmax=0,acdirmax=1`: files fresh, folders cached up to 1 s | 32–69 ms measured; up to 1 s for a new name in a folder that hadn't changed lately | 120–265 ms / 0.6–0.8 s / 1.4–1.7 s | 2.2–2.6 s |
   | `actimeo=1` | 0.8–1.0 s | 30–62 ms / 0.6–0.8 s / 1.6 s | 2.2–2.4 s |

   Locally `git status` takes 73–107 ms (22–38 ms warm). Before the fix `noac` took 7–11 s at any latency, which is what the first version of this edit put to the owner. The middle options are the middle setting and a cheaper export. The middle setting gives files the freshness of `noac` at close to `actimeo=1`'s speed; its one cost is that a new name can take up to a second to appear in a folder that hasn't changed lately, because macOS scales a folder's cache time with its age. A cheaper export no longer moves much: the helper now spends about 20 µs on a call that doesn't cross the link, and the rest of a warm `noac` run is the kernel's own cost for its 29,000 calls. Cold runs cost the same under every setting, since the link's round trips dominate them. This report proposes `acregmax=0,acdirmax=1`; the owner decides.

   **Also in the edit, for macOS:**
   * **Where the tree's root lives.** §9.1 still says "the FSKit volume on macOS". A user can't create folders in `/` or `/Volumes`, `/Users/Shared` can be claimed first by another user, and `$TMPDIR` is cleaned. Proposed: `/Users/Shared/clover-<uid>`, created by the daemon, owned by the user and 0700. If another user created that name first, the daemon refuses it and uses a random name, which it remembers.
   * **What macOS writes into other computers' folders.** NFSv3 has no extended attributes, so macOS keeps a file's attributes in an AppleDouble `._name` file beside it, on the holder's disk. CI saw `._a.txt`, `._b-cp.txt` and `._b-ditto.txt` appear there after an `xattr -w`, a `cp -p` and a `ditto` of a file that carried an attribute, as every download does (`com.apple.quarantine`). The `nouserxattr` and `noappledouble` mount options were accepted and changed nothing (`results/macos2?-nfs-volume.json`). Finder also writes `.DS_Store` into folders it shows on network volumes, unless the user has set `DSDontWriteNetworkStores` (a fresh Mac hasn't). Both kinds would land in other computers' repos as untracked files. Proposed: the export keeps `._*` and `.DS_Store` off the holder's disk, in a store of the helper's on the Mac, so attributes still work there and the other computer never sees them (M2).
   * **Spotlight and Time Machine.** They leave the mounts alone: `mdutil -s` answers "Indexing and searching disabled" for an NFS mount, and `tmutil isexcluded` "[Excluded]". The tree's root folder itself holds only a symlink and empty mount points.
   * **FSKit is a build option, not an appex in every build.** Shipping the appex puts an entry in every user's System Settings, for a module nobody may turn on. Builds that include it (the live gate's, and later ones once Apple fixes FSKit) are where it lives until then.
2. **On Windows, this computer's entry isn't a junction, and isn't native.** This touches two §9.1 **[P]** bullets. The tree's root ("a drive letter on Windows", "a junction on Windows") changes, and "Same-computer paths are native" no longer holds on Windows. WinFsp's FUSE layer can't hold a link that leaves its volume, and Node needs the volume to be a network volume (§1). Proposed text for the root: "On Windows the tree is one network volume on a drive letter (`\\clover\tree`). This computer's entry is served through it like any other computer's, from the computer's own tree service." Proposed addition to "Same-computer paths are native": "…except on Windows, where `home/<this computer>` goes through the tree's volume; programs there should use the real home path." **This layout is inferred, not built.** The prototype's Windows helper knows this computer's entry only as a link, which doesn't resolve on WinFsp (`windows-coherence.json`: ENOENT). The closest measurement is the network volume's +0 ms rows (§3), with one more loopback hop than the layout would have. There most cold runs took two to four times as long as on a plain drive letter, and only there did `tsc` find its types. The alternative, a real folder with a junction for this computer and a directory symlink per other computer to its own network volume, keeps this computer's entry native, but needs the symlink privilege each time a computer is added. **[P]**, and live gate 3 builds the layout.
3. **The offline bound, said precisely.** §9.1 "Offline computers fail fast … answers 'computer offline' at once and never hangs." Proposed text: "A computer known to be offline answers 'computer offline' at once. A link that drops silently is known within 1.5 s: any bytes from the computer prove it alive, and both ends ping every 250 ms. Calls in flight then fail with 'computer offline', within about 1.7 s of the drop. A closed link fails them at once. On a live link, a call fails once the link has carried no answer for 10 s. A slow link that keeps delivering answers isn't offline, and a call can then wait up to 60 s. On macOS, when the mount helper itself dies, the daemon takes its mounts down at once." Measured (§4): calls in flight failed 1.50–1.71 s after a silent drop on every mount, a new call while away in under 1 ms (FSKit: up to 42 ms), and a read in flight on a dead NFS helper after about 1 s, where it had waited 7–13 s before. The first text's "nothing waits longer than 10 s" didn't hold for a dead NFS helper, and its "within 1.5 s" was 1.51–1.71 s for calls in flight (review S8). **[P]**
4. **Caching and coherence.** A new **[P]** bullet in §9.1: "Each mount caches names, attributes and contents until the computer that holds the files reports a change. That computer watches its home and pushes change events over the link, and the mount drops what changed within one round trip. The first look into a folder fetches its tree in bulk (up to 20,000 entries; never a whole home). Within that window a reader can see stale data. A file that grew can read as its new content cut at the old length, which is neither version. A file replaced by rename while a program reads it can give that program the start of one version and the end of the other." M2 removes the last case: a read-only open pins the file it opened on the holder, so one open reads one version. On macOS one more caveat stays: a read that races an in-place rewrite can end in zeros (§1).
5. **The holder enforces its own rules.** §9.1, the **[P]** fence. Add: "The computer that holds the files applies its own fence to every request that comes over a mount, and to every file tool and Bash call routed to it. It resolves each path on its own disk, links included, and refuses whatever lands outside the home or in the fenced set, checking the real path of what it opened. A folder swapped for a link therefore can't lead into the fenced set. The fenced set can't be read or written and doesn't show in listings, whoever asks." The approval levels still apply on the computer where the program runs (the **[P]** "judged by the stricter of the two"). The prototype resolves a request's folders (and, where the call follows links, its last component) to their real paths, refuses what lands outside the export or in the fence, opens the real path with `O_NOFOLLOW`, and checks it again after opening. `TestFenceHoldsThroughLinks` swaps a folder the mount had seen for a link to `.clover`; it passes now and fails on the earlier file service (review S2). Links can't simply be refused: a first version that refused any link before a path's last component broke `tsc` on the Windows tree, because WinFsp hands the service whole paths through Bun's `node_modules` links (`TestPathsThroughLinksInsideTheExport`). The resolution and the open can still race a swap on the holder; M1 closes that with `openat2(RESOLVE_BENEATH)` on Linux, and on macOS and Windows a walk that opens each folder in turn without following links and resolves a link's target itself.
6. **Links inside a home.** A new **[P]** detail: "An absolute link that points inside the home is served as a relative link, so it resolves on every computer. A link that points outside the home, absolute or relative, answers 'permission denied' when read from another computer. Served as-is, it would resolve against that computer's own disk, to a file the holder never meant." The prototype does both (the same test, and `READLINK_outside` in the service's counts).
7. **Work where the files are.** This qualifies the **[D]** that the system prompt "says that moving large files between computers is slower". On the fake link, which has no bandwidth limit, a build's cost was its round trips: a cold `tsc` of `packages/core` took 70 s across a +20 ms mount (193 s at +80 ms), against 25 s locally, for 2,107 round trips. On a real link size costs too: 256 MiB is about 18 minutes at 2 Mbit/s, whatever the round trip. The builds measured also only read. A step that writes many files, like `bun install`, costs about five round trips per file (create, write, set times, close, and a `mkdir` per folder). Proposed addition to that **[D]**: "…and that a command that reads or writes many files of another computer (a build, an install, git, a search) should run on that computer, by `cd`-ing into its folder first, so Bash runs there." **touches [D]**
8. **Moving folders between computers.** The **[D]** "`mv home/Desktop1/project1 home/Studio/` moves the folder" works through the mounts as a copy and a delete, one file at a time (`mv` gets `EXDEV`). Copying `packages/protocol` (119 files) into a mount took 10 s at +20 ms and 40 s at +80 ms, against 68 ms locally, at about five round trips per file. Proposed: keep `mv` working, and let the core stream a tree from one holder to the other when Bash's command is a plain `mv` or `cp -r` between two computers' folders, or give the bot a Move tool for it. **touches [D]**
9. **git across computers with different users.** A new **[P]** note: git's index records each file's owner and inode. Through a mount, files belong to the user who mounted, so git on a Linux box re-reads every tracked file of a Mac's repo the first time after the Mac's own git ran (Mac 501, Linux 1000; Git for Windows always records 0). Measured: at +20 ms the first `git status` after the holder's own took 83 s for about 3,800 files (321 s at +80 ms), against under 1 s when the owners match. With `core.checkStat=minimal` it took 0.86 s (2.7 s). Bash already runs git where the repo is (the **[D]** above), so this only hits a person's own tools. The docs should say so, and suggest `core.checkStat=minimal` for repos shared across OSes, with what it gives up: git then compares only sizes and whole-second mtimes, so a change that keeps a file's size within the same second goes unseen until something else changes the file.
10. **Computer names are unique ignoring case, and never a name Windows reserves.** §9.1 **[P]** "Computer names are unique and use only letters, digits and hyphens". Windows paths ignore case, so `home/desktop1` and `home/Desktop1` must be the same computer. Windows also can't hold a folder named `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9` or `LPT1`–`LPT9`, so those can't be computer names either. **[P]**
11. **Windows packaging.** §4 / §13: "The Windows installer runs WinFsp's unmodified MSI (one UAC prompt). The About box and the docs carry WinFsp's notice, as its FLOSS exception requires." **[P]**
12. **The welcome guide on macOS 27** can open the File System Extensions pane itself (`FSClient.openFileSystemExtensionsSettings()`), if FSKit comes back (item 1). **[P]**
13. **For the controller, the plan.** Live gate 2 says "the folder tree (FSKit turned on once)". With item 1 it becomes "the folder tree over NFS loopback, with a capped link and the Mac's sleep and wake, and the FSKit module once, from a build that includes it". `gate.sh` does all of it. §14.1 item 6 can point to this report. The mounts are M2 in the plan, and stay there (What M1 and M2 should start with).

## Risks

* **FSKit isn't ready, so macOS rests on the kernel's NFS client.** The kernel's NFSv3 client has shipped with every macOS release. The known risks are a hung server (the daemon's force-unmount and `deadtimeout` bound it, §4) and Apple deprecating it (no sign of that). Its behaviour shaped every result here, and small changes moved it a lot: handling calls one at a time made big reads time out, handling writes concurrently or on a queue delayed a writer's error by 18–29 s, and 27.0.1's client dropped a mount on a slow link that 26.6.2's kept. M2 should keep this spike's NFS checks as tests and run them on each new macOS release.
* **go-nfs is a small project, and Clover's copy patches five of its files.** The export is the one piece macOS depends on, and two of the patches (one call at a time, a scan of every handle per call) were the difference between usable and not. M2 either keeps the patched copy (and offers the patches upstream) or writes its own NFSv3 export, with handles of its own; the protocol subset a loopback mount uses is small.
* **The NFS export is a service any local process can reach.** NFS on TCP has no real authentication (AUTH_UNIX is self-declared), so any process on the Mac can talk NFS to the helper's port, including one inside Bash's sandbox if the sandbox allows loopback connections. The prototype now keeps such a process out with an ephemeral port, a one-time export path and a single MOUNT, and the handles were already random. Edit 1 carries the full list, including the two parts the prototype can't build (lane C's fence on the port, the Wave 3 review). Root on the Mac can still read everything, as with any mount.
* **An NFS mount that stops answering can make macOS show its "Server connections interrupted" dialog.** `mount_nfs`'s own page names the dialog for unresponsive file systems, and the kernel raises it when it marks the server "not responding". That happens whenever a call outlives the mount's `timeo`, which a dead helper causes, but so can a live call on a slow link (review S1). CI shows the second: at 2 Mbit/s with 1 MiB calls, the kernel declared the export dead and took the mount away (§4), with the helper's link up all along. With calls sized to the link it didn't happen, and a dead helper never got that far, because the daemon unmounts first. Live gate 2 asks the owner what he saw, after a dead helper, a 2 Mbit/s link, and sleep and wake. Nothing on a runner shows a dialog.
* **The 1.5 s bound against real Wi-Fi.** A false "offline" fails writes in flight with `EHOSTDOWN`, and a program that doesn't handle it may lose a save. The first CI false alarms were the reader bug above (fixed, with a test). The review's slow link found three more ways a live link looked dead, all fixed with tests (§4, "Tuning"). Real networks can stall for 1–2 s during roaming, though. M1 should measure false-offline rates on lane H's link before fixing the number.
* **The holder's watch can fail.** A recursive watch of a whole home costs one inotify watch per folder on Linux, and a home with `node_modules` has hundreds of thousands of folders, past many systems' `max_user_watches`. A failed watch means caches that never hear of a change. The prototype's file service now arms its watch again with backoff after an error and sends every peer a resync (review S3). M2 has to budget watches, and serve the part of a home it can't watch with 1 s caching instead of the event-fed cache.
* **Kernel cache calls can deadlock a FUSE server.** Linux's `inval_inode` waits on the page locks of a write in flight, and that write's reply needs the link's reader. CI hit it at once: writes into the mount failed with "Host is down" after 1.5 s of silence. The rule for M2 is that cache invalidation never runs on the link's reader or inside a request handler.
* **Dropping a live directory's entry breaks `getcwd()`** for every process working in it ("unable to get current working directory"). Invalidations must keep directories that still exist.
* **Other users on a Windows computer.** The volume is mounted for the user's uid with no umask (`cgofs/tree.go`), so other local users may be able to read it. Live gate 3 checks that, and a umask of 077 is the likely fix.
* **The Windows fence and the tree.** Lane C's fence for Windows Bash (AppContainer or a restricted token, §4) must let Bash reach the WinFsp volumes. WinFsp's FUSE layer builds each file's ACL from POSIX modes for the user's SID. An AppContainer token also needs `ALL APPLICATION PACKAGES` or its own capability SID in those ACLs; a restricted token doesn't. This needs a joint check with lane C.
* **Windows software inside the tree.** Git for Windows needs names that keep their case and folders that report an x bit, and Node needs a volume Windows can name (§1). The network volume gives that without admin; live gate 3 should try Explorer, VS Code and Defender on it. This computer's entry, served through the volume, runs at the +0 ms speeds of §3 rather than natively, so this computer's own tools should keep using the real home path.
* **Bubblewrap on Linux** must bind the tree's FUSE mount into Bash's sandbox. The kernel lets a process in a child user namespace with the same uid use a FUSE mount. That needs checking with lane C's profile.
* **Case and names.** A Linux holder can have `README` and `readme` in one folder; Windows shows one of them. Characters Windows forbids (`:*?"<>|`) are mapped by WinFsp into the Unicode private-use range, so they show, oddly. This wasn't measured here.
* **Memory.** The prototype's caches are unbounded maps. M2 needs an LRU on attributes and pages.
* **WinFsp's licence.** It is GPLv3 with a FLOSS exception. Shipping its unmodified MSI from an Apache-2.0 app is allowed with the notice. Linking it into our own binary is not; cgofuse loads its DLL at run time, which is the documented way.
* **The fake link** is a TCP relay on one machine. The speed rows ran it with unlimited bandwidth; real links add jitter, loss and a bandwidth limit, so the +20 and +80 rows are lower bounds for anything that moves bytes. Only the slow-link check (§4) caps it.

## What M1 and M2 should start with

The plan (§4, lane J) puts the tree on each computer in M1 and the mounts in M2. This report keeps that split. M1 needs no mount, but it already carries the rules this spike found for links, fences and liveness, because file tools and Bash routed to another computer meet the same holder.

**M1, the tree, on the fake link with several daemons:**

1. **The computer registry,** with holds, the user-working mark and `computers.control`, kept for opensky.
2. **The tree on each computer:** the root per OS and this computer's entry (edits 1, 2 and 10: on macOS a folder of the user's own, 0700, outside every home; on Windows the network volume's drive letter; names unique ignoring case and never a name Windows reserves). Every other computer appears as an entry that answers "offline" at once until M2 mounts it.
3. **File tools and Bash run where the files are** (with lane A). A call on `home/<Other>/…` goes to that computer's daemon. Its tree service applies the holder's rules from this spike:
   * the fence on every request, with paths resolved the way the holder's kernel would and the fence checked where they really land (edit 5, review S2);
   * links that leave the home answer "permission denied" (edit 6, review S9);
   * writes confined by the parent's real path.
4. **An answer at once when a computer is offline,** with the link rules from §4: any bytes count as life, both ends ping, a write that stalls fails only when the holder is silent too, and a request's clock runs only while no answer arrives (review S1). The bound is said as edit 3 says it (review S8).

**M2, across computers: other computers' folders mounted.**

1. **The tree service's mount side** in `packages/core/src/tree/`, ported from `serve.ts`:
   * the watch with coalesced events, not echoing a computer's own writes back to it, armed again after an error, with a budget of watches and 1 s caching beyond it (review S3);
   * per-connection write handles, and a read-only open pinned to the file it opened (edit 4);
   * `fsync` passed through to the holder's disk (below);
   * one stream per peer on lane H's link.
2. **The helper** from `native/mounts/`, with the rules from this spike:
   * events handled off the link's reader;
   * directories' entries kept unless the holder says they are gone;
   * a change drops the parent folder's attributes too;
   * the `cached` policy subscribes to events whenever a link comes up, the first included, and a fill whose request went out before an event never caches over it (review S3; `TestOfflineAtStartSubscribes`, `TestFillAfterEventIsNotCached`);
   * an LRU on the caches, and read-ahead on sequential reads;
   * on Windows, file contents kept between opens (Defender is ruled out, §3).

   Keep the `cached` policy as the default.
3. **macOS: the NFS export,** with:
   * edit 1's conditions: an ephemeral port and a one-time export path over the daemon's pipe, one MOUNT, no retry after a failed MOUNT, a 0700 tree root (review B2);
   * file handles in a table of its own, O(1) per call (review B1; patch 5 is the stopgap);
   * writes in line, so the client feels a slow or gone holder at once (a queue of their own let a writer run on for 18–29 s after a drop, and slowed writes 300-fold, review S5). A lookup then waits behind at most one write; if that matters, answer WRITE as UNSTABLE from a small bounded buffer and make COMMIT wait for the holder, and measure the drop again;
   * COMMIT, and a WRITE that asks for it, reaching the holder's disk: today WRITE always answers `FILE_SYNC` and COMMIT never reaches the holder, so an `fsync` on the Mac doesn't sync the holder's disk, the same gap FSKit has (review S5);
   * a WRITE's post-op attributes taken from the write's own answer, not from a second round trip;
   * `dumbtimer`, with a `timeo` above the helper's own bound for a call with no answer arriving; the daemon force-unmounts the moment its helper dies (review S1);
   * for calls on a live link that will outlive the client's timer, an evaluation of answering `NFS3ERR_JUKEBOX` and mounting with `mutejukebox`, and of choosing `rsize` and read-ahead from the link's speed (review S1, §4);
   * the kernel attribute-cache setting the owner picks (edit 1);
   * the AppleDouble files kept off the holder's disk (edit 1, review S6);
   * FSKit as a build option, kept building, for when Apple fixes FSKit.
4. **The daemon's side:** start and supervise one helper per tree, clean a dead mount and remount, give the helper a local socket per computer, and tell it at once when the link layer knows a peer is gone.
5. **The CI checks** of this spike (coherence, fail-fast with the slow link, speed with the NFS call counts, the macOS volume checks) as M2's tests on the fake link with several daemons. That is lane J's "done when" for M2.
