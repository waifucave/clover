Beyond choosing iroh, these results change the spec, and one touches decisions:

* **How clover-core holds iroh** [P]: in a sidecar process of Clover's own, `clover-link`, over framed stdio, not through n0's binding; `LinkTransport` keeps an in-process addon possible (Q2, "The addon or the sidecar").
* **Relay-free iroh needs two things from the handshake** [P]: each device learns its public address with STUN on the port iroh then binds, because iroh has no STUN and, without a relay, learns an address only from a router that grants it a port mapping (UPnP, NAT-PMP or PCP); and both devices dial each other at the same moment, and again 100 ms later (Q3).
* **Priorities aren't enough** [P]: the data already in flight decides how fast control messages stay during a transfer, so stream windows are sized per path; and the congestion controller decides how much a lossy path delivers (Q4).
* **Re-dial on every network change and wake** [P]: no existing connection came back quickly from a long outage, and relay-free iroh took 1.1 s to follow a new address, or 6 s on a network without a default route (reported to n0); behind NATs a re-dial needs the handshake service, and requests in flight need a retry rule (network changes).
* **What "no relay for coordination" means with n0's relays on** touched four [D]s, and the owner decided it (edit 6): a configured relay always sees which devices are online, whatever Clover dials, and that is accepted; QAD stays on; set-up goes direct first for pairs whose two STUN answers match, and races the relay otherwise; devices paired without an account swap addresses through the waifucave handshake with a pair credential, with n0's address lookup as the fallback. Edit 6 lists four problems in that last decision for M1's design to answer.

## The bench

One protocol, written twice: in TypeScript for the napi binding ([`iroh-napi.ts`](../../spikes/s1-transport/bun/src/iroh-napi.ts)) and in Rust for native quinn and iroh ([`bench.rs`](../../native/link-sidecar/src/bench.rs)). The first byte of each bidirectional stream picks the server's handler: `E` echoes 64-byte frames, `R` answers one RPC per stream, `S` sinks a bulk transfer and acks its size. The client measures 64-byte round trips on one stream (`rpc`), one stream per RPC (`rpcPerStream`), one large transfer (`bulk`, MB/s, 10^6 bytes), 1 MB transfers one stream each (`screenshot1MB`), and round trips every 5 ms while a bulk transfer runs on the same connection, with the RPC stream at priority 10 or at the bulk's priority 0 (`rpcUnderLoad`; from run 8 the netem jobs' native bench repeats the transfer until there are at least 200 round trips). Every check prints one `S1RESULT` JSON line; the per-run files are in each CI run's artifacts.

What this shows:

1. **It loads and compiles everywhere.** napi-rs's loader names each platform package literally, so `bun build --compile` embeds the right `.node` by itself. A compiled binary writes that file to a new temporary file on every start: 10–16 ms on Linux, 21–241 ms on macOS and 44–233 ms on Windows runners, 290–450 ms on the owner's Mac. The same file kept beside the binary and loaded from disk (`NAPI_RS_NATIVE_LIBRARY_PATH`) loads in 4 ms once the OS has seen it. On the owner's Mac, every successful compile also left a byte-identical 63 MB copy of the Bun executable (`.<hash>.bun-build`) in the working directory, one per binary, so build scripts should compile from a scratch directory or delete them. That is a known Bun bug when the `bun` executable is read-only, as Homebrew installs it ([oven-sh/bun#14020](https://github.com/oven-sh/bun/issues/14020), with a fix open in [#46624](https://github.com/oven-sh/bun/pull/46624)); M1 item 15 tracks it.
2. **Its byte API is the bottleneck.** Every `read` and `write` takes or returns `Vec<u8>`, which napi-rs turns into a JS `Array<number>`, one element at a time. The probe ([`napi-probe/`](../../spikes/s1-transport/napi-probe/), 64 KB per call, runs 2–9) puts the cost at 0.5–2.3 ms of JS-thread time per call under Bun (28–135 MB/s) and 2–10 ms under Node. Typed buffers cost microseconds: a `Uint8Array` in 1–5 µs, a `Buffer` out 8–58 µs, and either one as an async call 21–99 µs (0.66–3.1 GB/s); Windows' async `Buffer` out was the slowest, 58–99 µs. Until run 8 the probe's typed sinks didn't copy the bytes, so their figures were the cost of a call; from run 8 the sinks copy them into Rust, and measured the same (in 2–3 µs, async 29–86 µs). So the binding, not iroh or Bun, makes transfers 4–16 times slower than native and holds the daemon's thread while they run.
3. **Bun 1.3 stops firing timers while napi completions keep arriving.** With a transfer running, a 10 ms interval that should have fired 159–353 times fired 1–42 times, on every OS; under Node it fired on time. The probe reproduces it without iroh: two independent loops of async napi calls whose results each take about a millisecond to convert left a 10 ms timer firing 0–7 times in 44–90 periods, while lock-step pairs (64–94 % of periods), typed buffers (93–100 %) and Node (58–97 %) kept it going. Bun 1.3 appears to run every queued completion before its timers, and two loops keep that queue from emptying. It needs no addon: on the owner's Mac, two loops that each await `fs.stat` or `crypto.subtle.digest` and then do 1 ms of work kept a 10 ms interval from firing even once in a second under Bun 1.3.14. Bun 1.4.4, the current release, mostly fixes it: the same script fired 62–70 times of about 100 (the longest gap 18–19 ms; Node 26.7: 99, and 10–12 ms), and the probe's two loops 26 times of 34 (Bun 1.3.14: 1 of 37). So it was not reported to Bun (M1 item 15), and M1 moves to Bun 1.4. For a daemon whose keep-alives, lease renewals and clock sync are timers (spec §6.4), this matters more than speed. Yielding once per write (`setImmediate`) fixes it at no cost to throughput; a buffer-typed binding avoids it, since each completion is cheap; a sidecar keeps every completion out of the daemon.
4. **node-datachannel loads under Bun on all four targets, and compiles with a 10-line plugin.** Its loader computes the package name, so the bundler can't follow it; [`compile.ts`](../../spikes/s1-transport/bun/scripts/compile.ts) swaps the loader for a literal `require` of this platform's `.node`. Bun to Bun in one process: open 3–78 ms, RTT p50 0.08–0.30 ms, 18–124 MB/s.
5. **quinn has no maintained napi binding.** Under Bun it is reachable only through our own addon or a sidecar. The sidecar prototype (`clover-link-sidecar ipc`, framed echo over stdio) measured, from Bun and from compiled binaries in runs 2–9: spawn and first round trip 3–34 ms; 64-byte round trip p50 0.02–0.08 ms (p99 0.3–3.5 ms); 0.4–1.7 GB/s each way; timers unaffected. That confirms the spec's "adds microseconds" for the fallback.
6. **Compiled sizes**: 63–76 MB on macOS, 99–115 MB on Windows, 94–131 MB on Linux, for a binary carrying Bun plus one of these addons (iroh's `.node` alone is 12 MB).

**The addon or the sidecar.** n0's binding is out (points 2 and 3), so clover-core holds iroh through code of Clover's own, either a napi addon passing buffers or a sidecar process. On the criteria that matter:

* **Shipping: a tie.** Either is one more file beside clover-core, built per target in CI: a `.node` loaded from disk, or an executable.
* **Speed: a tie at network rates.** An async buffer-typed napi call cost 21–99 µs per 64 KB and the sidecar's round trip 0.02–0.08 ms; the addon moves 0.66–3.1 GB/s and the sidecar 0.4–1.7 GB/s each way. Both are far above the 12.5 MB/s of a 100 Mbit/s path and the 2–150 ms of a round trip between devices.
* **Isolation: the sidecar.** iroh runs its own threads, can panic or abort, and in an addon every native completion lands on the daemon's event loop, the path by which n0's binding stopped Bun 1.3's timers. In a sidecar none of that reaches the daemon, so risk 2 can't happen through the link: a crash costs a restart and a re-dial, and the daemon sees pipe reads.
* **What the sidecar costs:** a framing protocol over stdio that carries streams, priorities and per-stream credit, and path and network-change events; handing the device's secret key to a child process, over its stdin at start and never in arguments, the environment or a file; and supervising it (restart, re-dial, a version check against the daemon).

**Decision for M1: the sidecar,** `clover-link`, from one crate in `native/link/` with a library target that holds the link and a binary target that speaks the stdio protocol. `LinkTransport` in clover-core sits on an interface the sidecar's client implements; a napi addon over the same library can implement it too, so M1 can switch if measurements ever show the hop.

**Verdict: works, with limits.** The limits are n0's binding's: it moves bytes slowly and starves Bun 1.3's timers. Clover's own code removes both, and M1 starts with the sidecar.

## Question 3: punching with no relay, and with one

**Method.** [`nat/matrix.sh`](../../spikes/s1-transport/nat/matrix.sh) builds a small internet from Linux network namespaces on a CI runner: one bridge for the public internet (203.0.113.0/24), two STUN responders on it at different addresses (RFC 5389, standing in for Cloudflare's and Google's), and two peers, each behind a router namespace whose iptables rules make one NAT type (RFC 4787 terms):

| Type | Mapping | Filtering | How |
| :- | :- | :- | :- |
| public | none | none | the peer sits on the bridge |
| full | endpoint-independent | endpoint-independent | SNAT keeping the port, and DNAT of the peers' ports (full cone) |
| restricted | endpoint-independent | address-dependent | SNAT, plus DNAT only from addresses the inside host has sent to (`xt_recent`) |
| port-restricted | endpoint-independent | address-and-port-dependent | Linux's ordinary SNAT and conntrack, as most home routers behave |
| symmetric | address-and-port-dependent | address-and-port-dependent | SNAT `--random`: a new port for every destination |
| lan | | | both peers on one LAN behind one port-restricted router (the same-Wi-Fi case) |

The routers drop unsolicited UDP silently, every pair starts from fresh namespaces, and in the matrix and timing phases nothing relays. The two peers ([`punch.rs`](../../native/link-sidecar/src/punch.rs)) exchange `{identity, candidates, mapping}` through a shared folder, the waifucave handshake's job (spec §8.3), where the candidates are the LAN address and the address STUN reported, and `mapping` says whether the two STUN servers saw the same address (from run 8). Then:

* **iroh** (Minimal preset, relays off, no address lookup, port mapper off from run 8; the lab's routers grant no mappings, so earlier runs were the same): the peer binds UDP port P, asks STUN from P, closes the socket, and binds iroh on P, because iroh has no STUN of its own (below). This relies on the mapping the query made outliving the socket, as it does on a NAT that keeps mappings per inside address and port. The lab can't show that: every endpoint-independent NAT here keeps the inside port, so a new mapping would have looked the same (lab limits, risk 13).
* **quinn** asks STUN from the socket it then gives quinn, and sends 1-byte punch packets from it every 100 ms to the peer's candidates.
* **Strategy "both"**: each peer dials the other at once and also accepts; the first connection wins. **Strategy "one"**: only peer `a` dials.

Peer `a` then runs 20 RPCs on the connection to prove data flows. The time is from the moment a peer had the other's record to its first connection; the lab's rendezvous polls every 20 ms, which is most of the 22 ms values.

| full | | 22 ms | 1 ms | 23 ms | 23 ms |
| restricted | | | 23 ms | 1 ms | 981 ms |

What this shows:

1. **Relay-free iroh punches everything that can be punched without a relay**, 13 of 15 pairs, the textbook result: only a symmetric NAT against a port-restricted or symmetric one fails, since the symmetric side's port for the peer is one nobody has seen (Linux picks it at random, so no prediction helps).
2. **With relays off, iroh learns a public address only from a port mapping.** In iroh 1.4.1 an endpoint finds its public address through QUIC address discovery against its relays (`net_report` builds its probes from the relay map), or from its port mapper, which asks the router for a mapping over UPnP, NAT-PMP or PCP and, with no relays, adds the mapped address to the endpoint's own at once (`socket.rs`, `update_direct_addresses`). There is no STUN. The mapper is on by default, and iroh's own docs warn that its gateway probing can raise firewall prompts, notably on macOS; the lab's routers speak none of these protocols, and the lab's endpoints now turn the mapper off. So where the router grants no mapping, the handshake's STUN has to run from the port iroh will use, before iroh binds it, and Clover should hand the result to iroh with `add_external_addr` so iroh's later NAT-traversal rounds advertise it; where it does, the mapped address is one more candidate for the handshake. On NATs whose mapping depends on the destination (symmetric), a STUN answer is an address no peer can use.
3. **Both peers must dial at the same moment.** Before a connection exists, iroh sends its Initial to every address it was given, which opens the dialler's own NAT toward the peer; the peer's NAT lets it in only once the peer has sent something back the other way. So the handshake has to tell both devices to dial each other at once. Restricted × symmetric shows what "at once" has to cover: only the symmetric side's dial can get in, and only after the restricted side has sent something toward it. When the symmetric side started first, its first Initial was dropped, and QUIC sent it again at its first timeout, 999 ms with the default initial RTT of 333 ms, so the connection came 980 ms after the later peer started. That happened in 21 of 36 tries: 12 of the 16 full matrix runs across both stacks (iroh in runs 2–5, 8 and 9, quinn in runs 2, 3, 5, 6, 7 and 9) and 9 of the 20 tries in the timing phase of runs 8 and 9. In the others the restricted side started first and the pair connected in 22 ms. Which peer read the other's record first decided it; any lost Initial costs the same, as in a netem connect of 1,163 ms at 1 % loss (Q4).
4. **Sending again sooner fixes the 1 s case.** A second dial 100 ms after the first connected the pair within 82 ms in all 20 tries; an initial RTT of 100 ms for direct dials, which iroh takes per dial (`connect_with_opts`), within 0.28–0.30 s, its first timeout being three times the initial RTT. Both fit inside a 0.5 s head start (edit 6); the second dial is the faster, and costs only a duplicate Initial when the first one got through.
5. **The two stacks reach the same pairs.** Punching is a property of the NATs, not of the QUIC library, once both sides have their address and dial together. quinn's punch packets changed nothing: they leave the dial's socket at the moment it sends its Initial, so they open nothing the Initial doesn't.
6. **With a relay configured, set-up stays off it only when the dial leaves it out.** A dial given only direct candidates sent nothing through the relay in any pair. A dial given the relay too connected through it first in every pair, including those that went direct a moment later, and the relay kept a path on those connections; the lab's relay sits next to the peers, so on real paths, where n0's relays are tens of milliseconds away, a working direct path may connect first, but the relay still carries the dial's first packets. The head start kept every pair that can go direct off the relay, but where the 1 s case fell after it (restricted × symmetric at 0.5 s, in run 8), the relay forwarded 29 datagrams around a connection that came up directly at 501 ms, once the second dial's fresh Initial got through. Pairs that needed the relay waited about the head start (482–504 ms, 983–1,003 ms).
7. **iroh remembers the relay.** Once a pair had used the relay, a later dial given only direct addresses went through the relay at once wherever direct couldn't work: iroh keeps a peer's relay address and the path that worked. Where the earlier connection had moved to a direct path, the later dial went direct, and in 2 of 10 cases iroh also opened a relay path on it, as its source does for a client connection whose first path is direct, for every relay address it knows for that peer (`remote_state.rs`). So after one fallback, later direct connections to that peer can carry a relay path as well. iroh forgets the peer about 60 s after its last connection to it closes (`remote_state.rs`, `remote_map.rs`); the lab's second dial came 200 ms after the first connection closed, so it never reached that.
8. **The relay is part of coordination as soon as it is configured.** Both peers connected to it as their home relay (it accepted two clients in every pair, under every policy), so it knew both were online, and each learned its own public address from it through QAD, even under the direct policy where it forwarded nothing: behind the port-keeping NATs the same address STUN reported, behind the symmetric NAT a third port, the mapping toward the relay. A relay configured without its QAD port runs no address discovery (iroh skips QAD for such an entry), leaving it to STUN.
9. **Option (c) connected every pair at the speed of a race,** 1–22 ms, and kept the pair whose mappings were both endpoint-independent entirely off the relay. Every failed pair involved a symmetric NAT, which the two STUN servers mark.

**Verdict: works, with limits.** Every pair that can connect without a relay did, given STUN on iroh's port and a simultaneous dial; a symmetric NAT against a port-restricted or symmetric one needs a relay. With a relay configured, how much of the coordination stays off it depends on how Clover dials, which edit 6 settles: per pair, from the two-STUN check. How common each NAT type is on real networks is live gate 1's question.

2. **During a transfer the stream window sets the delay, not the priority.** On the LAN profile every RPC under load waited about 8 ms more than on an idle link, prioritised or not, with Cubic on both stacks, and quinn's BBR did at the 99th percentile. But priorities alone don't keep control messages fast during a transfer: the data already in flight decides, and a stream window sized to the path keeps it short. On lossy paths only quinn's BBR held its throughput. M1 sizes the windows per path and chooses the controller (edit 7).

## Network changes

Spec §8.3 asks for the time to first byte after sleep and after a Wi-Fi-to-mobile switch on real networks. The lab can't sleep a laptop, but it can do the network side of both to one live connection and watch whether it lives through it.

**Method.** [`nat/migrate.sh`](../../spikes/s1-transport/nat/migrate.sh) puts a client and a server namespace on one veth pair with 10 ms of delay each way, and no NAT. The client ([`bench.rs`](../../native/link-sidecar/src/bench.rs), `ping`) sends a 64-byte echo every 50 ms on one stream without waiting for replies. The script then breaks the path at a known time: the client's address changes, or every packet is dropped for a while, or both. In some scenarios it also tells the client the network changed, as clover-core would on the OS's event: quinn then moves to a new socket (`rebind`, its active migration) and iroh re-checks its paths (`network_change()`). In the "re-dial" scenarios (from run 8) the client instead dials a second, fresh connection at the change or the wake and times its first echo, while the old connection carries on. The namespaces have no default route, which turned out to matter to iroh (point 2). From run 10 the job also runs a cut-down reproduction of iroh's address change for the upstream report ([`nat/iroh-address-change.sh`](../../spikes/s1-transport/nat/iroh-address-change.sh) with [`examples/iroh_address_change.rs`](../../native/link-sidecar/examples/iroh_address_change.rs)), from run 11 with and without a default route, and keeps iroh's debug logs (`run10/` and `run11/` in the results).

Its debug logs (runs 10 and 11) show why. iroh opened a path from the new address about 0.3 s after the change, then closed it as redundant, because the path from the vanished address was still its selected one. It dropped that path only once it told QUIC about the change, which it holds back until the host has a default route, for up to 5 s (`PendingNetworkChangeNotify` in `socket.rs`), and these namespaces have none; `network_change()` goes through the same wait. Then, in 4 of 6 runs, the server sent on the path the client had closed for another 6.5 s. With a default route put back at once, as DHCP does on most networks, iroh switched paths within 60 ms of seeing the change, and replies were missing for 1.1 s (three runs). In the Wi-Fi-to-mobile case iroh went about 8 s without replies, and in four of six runs a tenth of the echoes still hadn't arrived 8 s after the test ended. With relays on, iroh would have had the relay path meanwhile; that is live gate 1's to measure. Reported to n0 as [n0-computer/iroh#4657](https://github.com/n0-computer/iroh/issues/4657).
3. **Long outages heal slowly, and the wake call doesn't speed them up.** After 20 s, iroh resumed 4.5–4.7 s after the link returned and quinn 8.4 s, with or without the call. Both had backed off their retransmission timers, and after a loss that long congestion control holds them back too, so quinn's rebind ping waits as well.
4. **Past 30 s the connection is gone.** Both close it after 30 s with nothing received (quinn as configured here, iroh by default), so a sleep longer than that always needs a new connection.
5. **A re-dial, without NATs, has its first reply back in 48–70 ms on a 20 ms path:** one or two round trips to connect (the second, in this lab, comes with the first packet to an address the other side hasn't seen yet; every first connection shows it too) and one for the echo, after a 40 s blackout as after an address change. The exception was iroh at the wake after 20 s, while the old connection to the same device was still open with its timers backed off: 0.41–0.66 s to connect in both runs. That new connection also woke the old one, which resumed 0.4–0.7 s after the link returned instead of 4.5 s.
6. **Behind NATs a re-dial costs more, and the lab didn't measure it.** A device whose network changed needs a fresh public address (a STUN query), the handshake to carry it to the peer, and both devices dialling at once (Q3). iroh holds its port, so a fresh STUN answer needs a fresh port, and rebinding iroh drops every link that endpoint holds (risk 4). So the handshake service has to be up at every wake and network change, for devices paired without an account too, which reach it with a pair credential (edit 6); that matters to lane I. While it is down, only the relay gets two devices behind NATs back together.
7. **What was in flight on the old connection stalls.** In the Wi-Fi-to-mobile case, 20 of iroh's 201 echoes on the old connection were still missing 8 s after the test ended, in four of six runs; a re-dial doesn't bring them back. Requests sent before a change have to be retried on the new connection, and only those that are safe to repeat; a tool call whose start was sent but whose result never came is recorded "interrupted, may have run on <computer>", as spec §6.4 does for a takeover, and not re-run on its own.

The first two runs of this test (CI runs 2 and 3) got every row with an address change wrong, and those rows are not used: deleting the client's old address also deleted the new one, because Linux drops secondary addresses with the primary unless `promote_secondaries` is on. Their blackout rows were unaffected.

**Verdict.** Neither stack makes a sleep or a network switch invisible, and relay-free iroh handles a new address worse than plain QUIC. clover-core should dial a new connection at once on every wake and network-change event, keep whichever connection answers first, and let the old one go, as spec §8.3's "re-dial at once" already says (edit 8). Without NATs that took 48–70 ms to the first reply on a 20 ms path, on either stack, except iroh while a stale connection to the same device was still open (0.55–0.85 s); behind NATs it also needs a fresh STUN answer and the handshake, which live gate 1 times.

## Risks

1. **Our own sidecar is code to keep up with iroh.** iroh went from 1.0 to 1.4.1 in five months, and the sidecar has to follow. Keep it thin (endpoint, streams, paths, network change), pin iroh exactly, check it against the phone's iroh in CI, and put `LinkTransport` in front of it so nothing else sees iroh. It also brings a stdio protocol to keep right (priorities and per-stream credit across the pipe) and a child process to supervise.
2. **Bun's event loop can starve timers.** On Bun 1.3, any native addon that delivers a steady stream of costly completions (n0's binding, a plugin's), and even plain async I/O in two busy loops, can stop keep-alives, lease renewals and clock sync, on every OS; Bun 1.4.4 mostly fixes it, though a 10 ms timer still waited up to 18–19 ms in the same pattern (Q2, point 3), so M1 moves to Bun 1.4. The sidecar keeps the link's completions out of the daemon, and native plugins already get their own process (spec §3.1); buffer-typed APIs and a yield in hot loops avoid it elsewhere, and a timer-lag watchdog in clover-core would catch the next case.
3. **Mobile and carrier NATs are often symmetric**, and every pair with a symmetric NAT against a port-restricted or symmetric one needs a relay. The relay share could be much higher on phones and hotel Wi-Fi than at home; live gate 1 measures it.
4. **STUN before bind only works once per port.** After a network change the public address changes, but iroh now holds the port, so Clover can't ask STUN from it again without rebinding, and rebinding drops every link the endpoint holds. Ways to re-learn it without dropping links, for M1: iroh's observed-address reports from any connected peer (`send_observed_address_reports` / `receive_observed_address_reports` in iroh's transport config), which give the address as that peer sees it; QAD, which edit 6 keeps on; or a port mapping, where the router grants one. Rebinding on a fresh port after a fresh STUN is for a major change, when the old links are dead anyway.
5. **Priorities don't protect small messages under load** on their own (Q4): the bulk data already in flight does, and only a stream window or controller that keeps it near the path's bandwidth-delay product bounds it.
6. **Relay-free iroh follows a new local address slowly.** In the lab it took 1.1 s with a default route, and about 6 s without one (8 s with a 2 s outage in front), since iroh then closes the path from the new address as redundant and waits up to 5 s for a default route before acting on the change; in four of six runs a tenth of the data was still missing 8 s after the end. Reported to n0 ([n0-computer/iroh#4657](https://github.com/n0-computer/iroh/issues/4657)). So clover-core must catch the OS's network-change and wake events on all three OSes and re-dial at once, rather than rely on `network_change()`, which goes through the same wait; with no event, the old connection limps.
7. **Lossy links collapse loss-based congestion control** (Q4): with loss spread over single datagrams, Cubic moved 0.2–0.3 MB/s at 1 % and at 0.5 % loss on both stacks, noq's BBRv3 mostly under 1.3 MB/s, and only quinn's BBR held 3.4–4.9 MB/s.
8. **Requests in flight at a network change stall** with the old connection (network changes, point 7). Clover has to retry on the new connection only what is safe to repeat, and record a tool call that may have started as interrupted (§6.4).
9. **The default stream window is a fixed 1.25 MB.** It adds about 8 ms to every control message during a transfer on a fast LAN, and caps one stream at about 8 MB/s on a 150 ms path (1.25 MB per round trip). M1 sizes it per path (Q4).
10. **Browsers:** SCTP has no priorities, and the page's direct path rests on the browser reaching one of the daemon's addresses, which the lab showed only on one machine (Q5).
11. **Firewall and privacy prompts.** Windows Firewall may ask the user the first time clover-core's sidecar receives unsolicited UDP. On macOS, iroh's port mapper probes the gateway over UPnP, NAT-PMP and PCP, which iroh's own docs say can raise firewall dialogs, and reaching LAN addresses can raise the Local Network prompt. CI runners never prompt, so only live gates 1 and 3 can show them; the lab's endpoints run with the mapper off, and n0's binding, which can't turn it off, runs only in CI.
12. **Size:** a compiled binary with Bun and one of the spike's addons is 63–76 MB on macOS, 99–115 MB on Windows and 94–131 MB on Linux, and the spike's sidecar binary, with quinn, iroh and a relay server in it, is 21 MB on macOS.
13. **The lab's limits:** shared runners vary by up to 2× between runs, so the comparisons here are within one run. With GSO on (every netem run until run 8, and the main table still), netem dropped whole batches of up to 10 datagrams, so its "random" loss came in bursts and single transfers varied by more than 10× between runs; spread over single datagrams (GSO off, runs 8 and 9), the same rates cut Cubic further and narrowed most cells. Whether real Wi-Fi and mobile loss comes in bursts or singly is live gate 1's to see. Every endpoint-independent NAT in the lab keeps the inside port, so STUN before bind, and a mapping outliving the socket that asked it, were never exercised: routers that change ports are a live-gate case. And a loopback or netem pair shares one machine's CPU.

## What M1 starts with

1. **The sidecar, `clover-link`,** in `native/link/` (approved by the controller): one crate over iroh 1.4.1 with a library target that holds the link and a binary target that speaks a framed stdio protocol, built in CI for the four targets and shipped beside clover-core. Its surface: bind on a chosen port after a STUN query from it, connect and accept by device key, streams with priorities and per-stream credit, path and network-change events, `network_change()`, close. The device key goes in over stdin at start, never in arguments, the environment or a file. clover-core supervises it: restart and re-dial on exit, and a version check.
2. **`LinkTransport` on top**, against the spine's contract, taking either the sidecar's client or an in-process addon over the same library: one link per device pair, priority classes (control, token streams, screenshots, files), liveness from any inbound frame with a keep-alive on quiet links (Winter's phone link learned this), re-dial on loss, and the OS network-change and wake hooks on all three OSes.
3. **The handshake's part of punching:** candidates (the LAN address, STUN's answer from the link's port, and the port mapping where the router grants one), whether the device's mapping depends on the destination (two STUN servers, asked again after every network change), and a "dial now" message that makes both devices dial at once, then again about 100 ms later, so a first Initial that loses the race costs 0.1 s rather than QUIC's 1 s first timeout; for devices paired without an account, the same messages through their pair credential (item 14), besides LAN discovery and the last known address.
4. **Stream windows per path:** each bulk stream's receive window sized to about 1.25 times the path's bandwidth-delay product, from the measured round trip and rate, instead of the fixed 1.25 MB, which adds 8 ms to control messages on a fast LAN and caps one stream at about 8 MB/s on a 150 ms path (Q4).
5. **Congestion control** for bulk streams, chosen from Q4's numbers with loss spread over single datagrams, and checked on real Wi-Fi and mobile in live gate 1.
6. **Re-dials:** the rule for requests in flight (retry only what is safe to repeat; a tool call that may have started is recorded "interrupted, may have run", §6.4); how the link re-learns its public address without dropping links (observed-address reports, QAD where a relay is on, a port mapping; rebinding only after a major change; risk 4); and, for iroh, whether to close a stale connection to the device before re-dialling, since the re-dial took 414–664 ms with it open and 41 ms with it gone (network changes, point 5), and re-dialling rather than relying on `network_change()`, which on a network without a default route waits up to 5 s ([n0-computer/iroh#4657](https://github.com/n0-computer/iroh/issues/4657)).
7. **The port mapper's policy:** when to run iroh's mapper given the prompts it can raise on macOS (risk 11), and its mapped address as one more candidate. The lab runs it off.
8. **The relay policy as decided** (edit 6): n0's relays on by default, with presence accepted; the dial policy chosen per pair from the two-STUN check (a head start of about 0.5 s when both devices' answers match, a race otherwise); QAD on, and re-learning the device's address through it after a network change (risk 4); and n0's address lookup as the fallback for devices paired without an account.
9. **A timer-lag watchdog** in clover-core, and yields in every hot native loop.
10. **CI:** the interop check between the phone's iroh-ffi 1.1.0 and the link's iroh on every iroh bump, and the spike's workflow, whose `lane/h-*` trigger already covers `lane/h-m1`.
11. **Lanes C and M cover the sidecar.** It is a second executable that holds the device key, so it needs lane C's fence and secret hiding (spike S8) and lane M's signing and notarisation.
12. **The relay lab with `--redial-ms 100`,** so the head start and the second dial run together, which edit 6's dial policy so far infers from the timing phase.
13. **Two stale comments** in [`webrtc-browser.ts`](../../spikes/s1-transport/bun/src/webrtc-browser.ts) (lines 239 and 258) still say libdatachannel can't resolve the browsers' mDNS names; the lab showed the browsers connect with hiding on (Q5), and Safari's name was resolved on macOS.
14. **The account-less handshake** (edit 6, decision 4), designed in M1 with lane I, which builds the service side: what the pair credential is (recommended: each device's own key, with the service keeping both public keys from first pairing, rather than one key both devices hold, so either device can revoke the other; problem 1); how the service scopes and rate-limits pairs without an account (per pair and per IP address, a pair accepted only when both devices sign it, small and short-lived records; problem 2); what it learns (the pair's two device keys, when each device is online and from which IP address, and its network changes, but never the candidates in the clear; problem 3); how a pair revokes it (either device, with its own key, including after losing the other); and the fallback to n0's address lookup, which dials through n0's relay (problem 4).

Until it is fixed, the re-dial on network changes covers it (item 6; network changes, point 2).
