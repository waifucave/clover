# Spike S5: ACP support

Date: November 5, 2026. Lane K, milestone M0. It answers [spec](../clover-spec.md) §14.1 item 5 for §9.3 (revision 17), [plan](../clover-plan.md) §4 lane K.
Prototype and evidence: [`spikes/s5-acp/`](../../spikes/s5-acp/README.md). Every claim below cites either a run in [`results/2026-11-05/`](../../spikes/s5-acp/results/2026-11-05/) or the shipped code of the agent named. In the evidence, every session, conversation, tool-call and MCP-session id is a stable placeholder (`cursor-session-3` is the same session in every file).

The question the spike exists for, whether Cursor accepts our MCP servers and passes their tools to the model, is **yes**. Both the stdio and the HTTP stub were started from the `session/new` entry, got the `env` and `headers` we passed, and their tool results reached the model. The model's reply carried both nonces, and so did the file it wrote. Antigravity CLI gives the same yes.

Model calls (the limit was five per CLI):

* Cursor: **4**. One was refused by the plan in 0.7 s, with no model output; three were real.
* Antigravity CLI: **3**.
* Every other CLI: none; they ran only `--help` and `--version`. `claude` was never run.

The ledger is in [`model-calls.ndjson`](../../spikes/s5-acp/results/2026-11-05/model-calls.ndjson), generated from the probe's own ledger (see the README).

## Method

* **The client** is the official SDK, `@agentclientprotocol/sdk` 2.4.0. It speaks protocol v1 through the `/unstable` entrypoint, with typed handlers, plus a wire tap that logs every JSON-RPC message.
  * It advertises `fs.readTextFile`, `fs.writeTextFile` and `terminal`, and serves them confined to the session folder.
  * It answers permission requests from a policy: allow once, and refuse the scripted step. It never picks an "always" option.
* **Two MCP stubs** log every request.
  * One runs over stdio; the agent starts it from the `session/new` entry. It records the environment names it got and the hash of the token passed in `env`.
  * One runs over Streamable HTTP. It checks the `Authorization` header passed in `headers`.
  * Each stub's tool result carries a nonce, and its server instructions carry an instruction word. A nonce in the model's reply means the tool result reached the model; an instruction word means the instructions did.
  * Both stubs are legacy-era MCP servers (`initialize`). They answer MCP 2026-07-28's `server/discover` with the legacy fallback, which is what a dual-era client expects.
* **Five checks**, each a separate command:
  * `initialize`
  * `session/new` with both stubs, then watching the stubs before any prompt
  * a prompt that has the agent call both MCP tools, write a file, run one command and have a second one refused, and name the instruction words
  * `session/cancel` while a `sleep` runs
  * `session/load` (and `resume`) in a fresh process, plus one question answered from memory
* **A fake ACP agent** runs every check without a model. It makes up the self-test (`bun test`, 5 tests passing, the last asserting that no token reaches any file). The self-test ran on macOS only: the probe uses POSIX process groups and `/bin/ps`.
* **Which code each run used.** The probe changed twice during the runs; neither change altered a decision.
  * **The permission policy's safety net** refuses requests that look like browser, web or screen use. It was added to the working tree just before the first Cursor prompt (00:21:04), so every prompt ran with it, and it was committed later. No permission request in any of the 13 wire logs matched its patterns.
  * **The follow-up prompt** asked for the instruction words only from 00:28 on. Cursor's follow-up (00:24:52) used the earlier text, so its summary has no `instructionsReachedModel`; Cursor's instructions verdict rests on the main prompt's "none" and on its code.
* **Both agents ran with their own sandboxes off.** Cursor's user config has `sandbox.mode: disabled`, and `agy acp` was started without `--sandbox`.
* **Safety on the owner's Mac:**
  * Each agent got a minimal environment and its own process group, and was stopped as a group.
  * PATH started with logging stand-ins for `open`, `xdg-open`, `osascript`, `afplay`, `say` and `terminal-notifier`; none was ever called.
  * Every call had a timeout and every check a deadline.
  * The work folder was a fresh temp folder.
  * The probe edited no config and ran no login, logout or update. `AGY_CLI_DISABLE_AUTO_UPDATE=1` was set for every `agy` run, and Cursor's `acp` command loads no update code.
  * **But Cursor wrote its own config.** When the probe called `session/set_config_option` for the model, Cursor saved the selection into `~/.cursor/acp-config.json` and `~/.cursor/cli-config.json`. The selection ended at `default[]`, where it started (§1, "Model and effort").
* **Versions:** Cursor CLI 2026.10.22-27dcf5f (bundling ACP SDK 0.14.1), Antigravity CLI 1.4.12, macOS 26 on arm64.

## 1. Cursor's CLI over ACP

`acp` is a hidden command: `cursor-agent acp --help` works, `cursor-agent --help` doesn't list it. The spec's `agent acp` is unsafe as a name. Here Homebrew linked only `cursor-agent`, and `agent` on PATH is Grok's CLI (`~/.grok/bin/agent`).

**Verdict: works, with limits.** For Clover, the limits are:

* edits inside the root, and commands on the user's own Cursor allowlist, never reach a card (deletes likely not either);
* a delegation's model choice becomes the user's own;
* server instructions aren't in the prompt;
* refusals look like successes on the wire;
* plan errors arrive as text;
* `session/list` can't be relied on.

## 2. Antigravity CLI

`/opt/homebrew/bin/agy` is the CLI, not a launcher. Checks made before running it:

* It is a 197 MB Go binary signed by Google (identifier `cli`).
* Its strings hold a full agent: an ACP server, a plugin manager and a policy engine.
* Its docs say plain `agy` opens a terminal TUI.
* `--help` and `agy acp --help` printed and exited.

`acp` is missing from the top-level help but [documented](https://antigravity.google/docs/ide/extensions/acp), with the editor config `{"command": "agy", "args": ["acp"]}`.

**Verdict: works, natively, with limits.** It has other modes too:

* print mode: `agy -p --output-format json|stream-json`, plus `--input-format stream-json`;
* `--settings` for one session;
* `--sandbox`, which is off by default;
* `--dangerously-skip-permissions`.

None is needed, since ACP works. **The adapter costs nothing.** What a backend plugin must handle:

* start it with `--disable-telemetry` and `--sandbox`;
* treat everything it is given as stored in plain text (edit 4);
* drop the replay on resume;
* filter `session/list` itself, or better, never rely on it;
* treat a refusal as the end of the turn.

## 4. Proposed spec changes

Each edit is marked **[P]**, for the controller to apply, or **touches [D]**, for the owner to decide. There are 13: 12 [P] and 1 touching a [D] (edit 6).

1. **[P] §9.3, "Agents with ACP today".** Replace the three bullets:
   > * Native: Gemini CLI (`gemini --acp`), Grok CLI (`grok agent stdio`), Cursor's CLI (`cursor-agent acp`), Antigravity CLI (`agy acp`), Devin (`devin acp`) and DeepSeek Harness (`dsh --profile acp`, one workspace; MCP servers need `dsh-acp` 0.1.2 or later, a prerelease today). Since June 18, 2026, Gemini CLI needs a Gemini API key or Vertex AI, and Google's free and subscription accounts use Antigravity CLI.
   > * Through adapters: Claude Code (`@agentclientprotocol/claude-agent-acp`) and Codex (`@agentclientprotocol/codex-acp`, which drives `codex app-server`).
   > * Checked in spike S5 (November 5): Cursor's CLI and Antigravity CLI accept the stdio and HTTP MCP servers passed at `session/new`, pass on their `env` and `headers`, and give their tools to the model.
   > * Clover never trusts a command name on PATH: `agent` is both Cursor's and Grok's. It resolves each backend's binary to its real path and checks that it is that vendor's (its version output, and the signer where the OS has one) before starting it.
2. **[P] §9.3, "Cloud placement".** Add: "Devin's cloud is the exception: `devin acp --cloud` relays ACP to cloud Devin sessions, so its backend is an ACP backend with cloud placement. Whether the stdio bridge reaches a cloud session, and what the root folder means there, is settled before it ships." This rests on `devin acp --help` alone.
3. **[P] §9.3 "How that maps onto ACP", and §6.1's "ACP agents" bullet.** Add: "Cursor and Antigravity file MCP server instructions as documents the model may open, not in its prompt. So the bridge's essentials (who sent the work, `SendMessage` to report, `Glossary` for skills) go into the agent's system prompt where the backend lets a client add to it: Antigravity's `_meta.antigravity.systemPrompt.append`, the unstable ACP `systemPrompt`, or the Claude adapter's `_meta.systemPrompt`. Text added there survives the agent's own compaction; otherwise they go into the first prompt. The plugins' instructions, which the bridge still sends as its server instructions, also stay reachable through `Glossary`, and every bridge tool's description stands on its own."
4. **[P] §9.3, "The bridge's link" and "Local placement", and mirrored in §7 of this report.** This replaces the earlier edit, whose single-session token was still stealable while the session ran:
   > * Clover treats everything handed to an agent as stored in plain text, readable by the user's other processes and passed to every server the agent starts: its environment, argv, `mcpServers` entries, `_meta` and prompts.
   > * The bridge token is the only secret handed over, and it goes only in the bridge entry's `env`.
   > * The daemon accepts the token only from a process descended from that session's agent process (the caller check of §3.1), with one live connection per token.
   > * The token is revoked at `TaskStop`, at session end and on a daemon restart, and minted anew on `load` or `resume`.
   > * The agent's environment comes from an allow-list. It carries the agent's own login only where that backend needs it there.
   > * Settings marks the backends that store what they are given in plain text (Antigravity) or pass their environment on to the servers they start (Antigravity).

   Why: Antigravity writes every `mcpServers` declaration, `env` and headers included, into its conversation database on `session/new`, `load` and `resume`, and hands each stdio server its whole environment. While the session runs, any process running as the user, a bot's Bash included, can read that database: the fence denies reading only the run folder and the secrets file. A stolen token would give the bridge's tools at that delegation's level, which can be a raised routine level, plus `SendMessage` as the agent, breaking the [D] "Bots cannot raise their own access".
5. **[P] §9.3, permissions** (a new bullet beside the [D]):
   > * Clover answers with `allow_once` or `reject_once` and never picks an agent's "always" option, which Cursor would write into its own allowlist, out of reach of Clover's levels. A card's "always" answer is saved as Clover's own rule, and the agent still gets `allow_once`.
   > * An agent that offers no `allow_once` gets a refusal (`reject_once`, or the cancelled outcome when it offers none).
   > * Clover keeps its own record of each answer, since agents report a refused call as `completed` (Cursor) or `failed` (Antigravity). When a cancel leaves tool calls open, Clover closes them itself.
6. **Touches [D] §9.3, "Permissions work as in Devin Desktop and Zed … It is started in a mode where it asks before risky actions".** On Cursor, three things never reach Clover's levels:
   * **edits inside the root**: Cursor has no mode that asks before them;
   * **commands on the user's own Cursor allowlist**: they never send a request, at every level;
   * **deletes inside the root**: by Cursor's code they don't ask either, though the default level asks before deleting files (§9.1). This is untested.

   Antigravity's own settings may pre-approve actions as well (`access_grants`; `--include-default-customizations`, on by default). Its unasked read-only MCP calls are no gap for the bridge's tools, since the bridge applies Clover's approval itself.

   The options for the owner:
   * **(a) Accept**, add "On Cursor, edits, allowlisted commands and likely deletes inside the agent's root never reach a card; the root folder and the agent's own deny rules are the boundary", and have Settings mark the backend.
   * **(b) Map Clover's read-only level to Cursor's `ask` or `plan` mode**, which ACP offers; this closes the gap at that level only.
   * **(c) Start Cursor with a Clover-owned `CURSOR_CONFIG_DIR`** holding an empty allowlist and the fence's deny rules, if Cursor's login survives it. That is untested, and testing it touches the owner's login (a live gate).
   * **(d) Drop Cursor.**

   **Rec:** (a) and (b) now, and (c) once the live gate shows the login survives.
7. **[P] §9.3, the bridge's own tools.** Cursor asks before every MCP call, the bridge's own tools included, and the bridge already applies Clover's approval rule when a call arrives. Add: "A permission request is answered `allow_once` at once only when it exactly matches the session's bridge server name and a tool from the bridge's own list. Clover reads both from the structured input of the matching tool call (Cursor's `rawInput.providerIdentifier` and `toolName`), never from the title, since Cursor titles MCP requests `<server>-<tool>: <tool>` and either part can hold a hyphen. Anything else, or anything ambiguous, goes to the level and the card." This answers automatically, as the [D] already allows.
8. **[P] §9.3 "The transcript".** Add: "Updates that arrive between a `session/load` or `session/resume` request and its response are a replay, and are neither recorded nor shown again. Clover reattaches with an honest `resume` where the backend has one, otherwise with `load`, dropping the replay. Antigravity's `resume` replays too, so it counts as a `load`." Loads replayed 20 updates on Cursor and 6 on Antigravity, and Antigravity's `resume` replayed 8; recording them would duplicate history at every reattach.
9. **[P] §9.3 "How that maps onto ACP", "Delivery".** Add: "A refused card ends the agent's turn on Antigravity, with no reply. The task notification says the agent stopped at a refusal, and the bot can message it to go on. A plan or quota refusal can arrive as ordinary agent text with `end_turn` (Cursor), so the notification carries the final text unchanged."
10. **[P] §9.3, "Local placement"** (beside edit 4's bullets):
    > * "One agent process serves one delegation, contained as a group: a process group on macOS and Linux, a job object on Windows. `TaskStop` sends `session/cancel` (both agents answered `cancelled` within 15 ms and killed the running command), then ends the group."
    > * "Clover keeps its own record of agent sessions and never relies on `session/list`: Cursor listed only the calling process's own session, and Antigravity ignores the folder filter and lists every session on the computer."

## 5. Risks

1. **Undocumented doors.** Cursor's `acp` is hidden, and agy's is missing from its top-level help. Either can change without notice. The agent suite pins versions, and Settings shows each backend's version.
2. **Moving parts.**
   * SDK 2.x removed the legacy connection API.
   * The adapters release weekly (`claude-agent-acp` is at 0.100.0), and `codex-acp` was rewritten in TypeScript.
   * DeepSeek's ACP is a prerelease, and npm's `latest` tag lacks MCP support.
   * The ACP v2 draft already ships in both adapters, while Cursor and Antigravity are v1.
   * M1 targets v1.
3. **Agents bend the protocol.** `resume` replays history, `list` ignores the folder or lists only the caller's session, refused calls show as completed, and there are non-standard fields (`name`, `args`, snake_case duplicates). The client must parse tolerantly and keep a per-backend quirks table. SDK 2.4's typed handlers accepted every message from both agents (no error response either way, and every `session/update` on the wire was recorded), but the stable/unstable split drops legacy fields such as `models`, so the transcript comes from the raw wire.
4. **No card before some actions on Cursor:** edits and allowlisted commands inside the root, and likely deletes (edit 6). On Antigravity, read-only MCP calls ran without asking, which is no gap for the bridge's tools: the bridge applies Clover's approval itself.
5. **A delegation changes the user's own Cursor selection** (edit 11).
6. **Instructions out of the prompt**: the bridge's guidance must travel in the system prompt or the first prompt (edit 3).
7. **Secrets on an agent's disk and in its children's environment**: Antigravity stores `mcpServers` in plain text, readable while the session runs, and passes its environment on (edit 4).
8. **MCP sign-in.** Antigravity probes OAuth discovery on every HTTP server, and Cursor keeps MCP OAuth in `mcp-auth.json`. A 401 from the bridge could start a sign-in that opens a browser. The bridge never answers 401 and stays on stdio.
9. **Shared on-disk catalogs.** Antigravity's MCP catalog folder is keyed by server name alone (`mcp/<server>/`). Two concurrent sessions whose bridge serves different tools under the same name may collide. M2 tests this before choosing per-session server names, which would change the tool names the model sees.
10. **Gating and cost.**
    * Cursor's cheapest models need a higher plan.
    * Antigravity offers third-party models only to named clients; Clover won't impersonate one.
    * Antigravity's five-step test turn reported 43k input tokens, mostly its system prompt and tools.
11. **Only macOS was tested.** Windows (job objects in place of process groups) and Linux are untested, and the probe itself is POSIX-only.

## 7. What M1 should start with

Start from the spine's contracts and their fakes (§8). Then move the probe's fake agent, stubs and five checks into a conformance suite that runs against fakes in CI, and build the client to pass it.

**Where the code goes:**

* **clover-sdk's ACP package:** the protocol layer.
  * the client connection: the pinned SDK, the wire tap, the replay window and tolerant parsing;
  * the quirks table's types;
  * the fake agent, with one mode per quirks-table row;
  * the conformance suite;
  * later (K-M3), the agent side of Winter's coding agent.
* **`packages/core/src/agents/`:** the daemon side.
  * launch, with the environment allow-list and containment;
  * the `ApprovalBroker` and `SessionHost` wiring;
  * transcripts and task notifications;
  * the bridge server and its token checks;
  * the stall watchdog.
* **`plugins/clover/agent-*`:** one backend each, holding its `agentBackends` entry and its quirks data.

**The quirks table** has one row per fact §8 lists under `AgentBackend`, with each backend's value from this spike. For example: Cursor keeps a delegation's model choice as the user's own and Antigravity doesn't; Antigravity's `resume` replays and Cursor has none; Cursor's `session/list` shows only the caller's session and Antigravity's ignores `cwd`; a refusal ends the turn on Antigravity and is reported `completed` on Cursor.

**The client's shape:**

* **Launch:**
  * Reads the argv from the backend's `agentBackends` entry, after checking the binary's identity (edit 1).
  * The working folder is the translated root, and the environment comes from the allow-list (edit 4).
  * Each agent is contained as a group: a process group on POSIX, a job object on Windows. Its stderr goes to the transcript folder.
  * Stop: `session/cancel`, wait up to 5 s for `cancelled`, end the group, then kill it. Both agents exited on `SIGTERM` here without needing `SIGKILL`.
* **Connection:**
  * `@agentclientprotocol/sdk` pinned exactly, protocol v1, the `/unstable` entrypoint, since `usage` and newer session fields live there.
  * A raw wire tap writes the transcript to `bots/<bot>/agents/<id>/acp.ndjson`, redacted, minus replays: updates between a `load` or `resume` request and its response are dropped (edit 8).
* **Handlers:**
  * `session/update` feeds the live tab's event stream.
  * `session/request_permission` goes to the `ApprovalBroker` (level, then card), mapping options by kind and never choosing an "always". Requests for a bridge tool are answered `allow_once` only on the exact match of edit 7.
  * `fs/*` goes through the folder tree under the fence; only Gemini CLI uses it today.
  * `terminal/*` goes to Bash under the fence.
  * `elicitation/create` goes to a card, or is declined.
  * **Auth required** (by Cursor's code and Antigravity's docs, both answer `session/new` with an auth-required error when signed out; not run here) stops the session with a notification telling the user to sign in to that agent themselves. Clover never calls `authenticate` with a browser-based method.
* **`AgentSession`**:
  * a state machine: starting, ready, prompting, cancelling, idle, stopped;
  * its own record of each tool call (decisions, closing open calls on cancel), and of its sessions;
  * **the 10-minute stall watchdog.** Progress is any message from the agent. A running command sends nothing on the wire in either agent, so while a tool call of kind `execute` is in progress, a live child in the agent's process group counts as progress instead, up to the command's own limit. Ten minutes with neither stops the agent.
  * a task notification carrying the final text unchanged, the stop reason ("stopped at a refusal" and "sign-in needed" included), usage when given and the transcript path.
* **The bridge** (edit 4, mirrored):
  * a stdio MCP server that answers both MCP eras (`server/discover` and `initialize`), as Antigravity probes the new one first;
  * its token is the only secret handed over, and it goes only in the bridge entry's `env`;
  * the daemon accepts the token only from a process descended from that session's agent process, with one live connection per token;
  * the token is revoked at `TaskStop`, at session end and on a daemon restart, and minted anew on `load` or `resume`;
  * everything else handed to the agent counts as public: its environment (from an allow-list), argv, `mcpServers` entries, `_meta` and prompts;
  * self-contained tool descriptions, and the bridge's essentials in the system prompt where the backend allows, otherwise in the first prompt (edit 3).

## 8. For the spine: what `AgentBackend`, `ApprovalBroker` and `SessionHost` must express

Plan §3 has lane B pin these three in `packages/core/src/contracts/`, each with an in-memory fake, with lane K's sign-off. From this spike, each must be able to express the following. Each fake should be able to play every row.

**`AgentBackend`** (one per `agentBackends` entry):

* **Launch:** the command and args per OS; how to check the binary's identity; the environment builder (an allow-list, plus what the backend needs, such as `AGY_CLI_DISABLE_AUTO_UPDATE`, `CODEX_PATH`, `NO_BROWSER` or `NO_OPEN_BROWSER`); the root as `cwd`; containment (process group or job object); the tested version range.
* **Capabilities** as negotiated, read tolerantly: snake_case duplicates (`load_session`, `session_capabilities`), and HTTP MCP that works though `mcpCapabilities` is missing.
* **MCP:** the transports accepted (stdio always); whether it stores what it is given in plain text; whether it passes its environment on; whether instructions reach the prompt; its system-prompt channel (`_meta.antigravity.systemPrompt.append`, ACP `systemPrompt`, the Claude adapter's `_meta.systemPrompt`); whether it tells MCP servers its conversation id (Antigravity's `_meta`).
* **Sessions:** `load` versus `resume`, and whether each replays; whether `session/list` filters honestly (Cursor lists only the caller's session; Antigravity ignores `cwd`); `close`.
* **Turns:** how a refusal ends (the turn ends with no reply on Antigravity; the call is reported `completed` on Cursor); cancel, and the tool calls it leaves open (both); whether usage is reported (Antigravity yes, Cursor no); plan and quota errors that arrive as text.
* **Permissions:** the option kinds offered (`allow_once`, `allow_always`, `reject_once`; Antigravity has no "always"); what the agent never asks about (Cursor: edits inside the workspace and allowlisted commands; Antigravity: read-only MCP calls); how an MCP request names its server and tool (Cursor's `rawInput.providerIdentifier` and `toolName`).
* **Config:** the model and effort config ids and categories, and whether a choice persists into the user's own settings (Cursor yes, Antigravity no).
* **Auth:** the auth methods offered, which of them are headless, and the auth-required error (`-32000` in Antigravity's docs; in Cursor's code, an error telling the user to run its login command).
* **Progress:** what the stall watchdog may count (§7).
* **Placement:** local or cloud (Devin's `--cloud`).

**`ApprovalBroker`:**

* **A request from an agent** carries the session, the backend, the origin (a bot's delegation, a routine, the user's own coding session) and so the level, the tool call id, the kind (`edit`, `execute`, `other` …), the title, the structured input (for MCP, the server and tool), the paths it touches (for the fenced-path rule) and the options by kind.
* **The answers** are `allow_once`, `reject_once` or cancelled. It never returns an agent's "always"; a card's "always" becomes Clover's own rule.
* **Automatic answers** come by level, with the bridge's exact-match rule (edit 7). A request touching a fenced path is always a card.
* **Lifecycle:** pending requests are answered cancelled when the session is cancelled or stopped, as ACP requires of a client; a card from a turn the user didn't start is denied after 10 minutes (§9.1).

**`SessionHost`:**

* A background agent is a session like any other, for `ListAgents`, `SendMessage` and `TaskStop`.
* **States:** starting, ready, prompting, cancelling, idle, stopped, plus failed for sign-in needed, crashed or stalled.
* **The transcript:** the raw wire minus replays, and Clover's own tool-call record.
* **Messages to the agent:** `SendMessage` becomes the next prompt, queued while a turn runs, since ACP has no standard mid-turn input (the adapters' `_session/steering` is an extension).
* **The task notification:** the final text unchanged, the stop reason, usage when given and the transcript path.
* **Reattach after a daemon restart:** an honest `resume`, otherwise `load` with the replay dropped, and always a new bridge token.
* **Its own record of agent sessions**, never `session/list`, and the stall watchdog's notion of progress.

## 9. What the evidence can't settle

These were left open rather than run again, since no new model calls were allowed for the review's fixes.

* **Antigravity's MCP approval for write-type tools.** Our stub tools were annotated read-only, so whether `agy` asks before a write-type MCP tool is untested.
* **Antigravity's prompt.** Its prompt text refers to an `<mcp_servers>` system-prompt block, but whether that block holds the servers' instructions is unconfirmed; the model said "none". Its system-prompt append was advertised but not exercised.
* **Cursor's instruction files.** Cursor's `INSTRUCTIONS.md` behaviour comes from its code; the project folder was empty after each session, so the files themselves were never seen.
* **Cursor and deletes.** Whether Cursor asks before deleting a file inside the workspace comes from its code, not a run.
* **Cursor's `session/list`.** Whether it ever lists more than the calling process's own session is unknown.
* **Cursor's login under `CURSOR_CONFIG_DIR`.** Untested, since testing it touches the owner's login.
* **Top-level flags under the ACP subcommands** (Cursor's and Grok's `--sandbox`, Devin's `--permission-mode` and `--sandbox`): untested, for S8.
* **Devin's cloud.** Whether the stdio bridge reaches a cloud session, and what the root folder means there, rests on `--help` alone.
* **Antigravity's `--process-per-session`.** Its docs say HTTP servers need it, but HTTP worked without it in one session. Maybe it matters with several sessions per process, which Clover won't use.
* **The six backends not run.** For Claude Code, Codex, Grok, Gemini CLI, DeepSeek Harness and Devin, MCP at `session/new` comes from their code and docs, not from runs.
