# S9: Clover layers — November 5, 2026

**Verdicts, at Electron 45.2.3 (Chromium 156) on macOS, Windows and Ubuntu:**

1. **Process split: works.** Six frames, five origins, five renderer processes on every OS; a second independent window reuses every plugin renderer.
2. **Memory: works with limits.** Each added layer costs about 18.2 MiB of private memory on macOS, 18.9 MiB on Ubuntu and 23.7 MiB on Windows, plus about 1 MiB in the main process. Full-app totals are not measured.
3. **Crossing layers: works with limits.** Typing, Tab order, composition and drags cross layers with no help. Menus, focus return and app shortcuts need the host, and the host's part was shown to work, except focus return, which needs the layer too. Real hardware input, IME windows and OS file drags are live gates.
4. **Declared hosts: doesn't, in stock Electron 45, for WebRTC; works for everything else.** CSP plus the `initiatorOrigin` filter stop every request-based way out, and `Connection-Allowlist` closes DNS prefetch and ICE servers per document. But a remote ICE candidate makes Chromium send connectivity checks to any address from a directly mounted plugin document, with the full stack on, on all three OSes. Closing it needs the browser to give plugin frames no P2P sockets. Stock Electron 45 does that only for frames that stay in a restricted parent document's process, and there it kills the plugin's renderer. **This needs an owner decision** (section 4.5 and the proposed changes).

**Decided:** the owner chose reading (a) of "renders once": one origin and process per shared plugin, one frame per place it appears, state held by the core, each frame in its own tab's theme.

## 1. Process split — works

Register `clover-plugin`, `clover-core` and `clover-sealed` before app readiness as `standard`, `secure`, `supportFetchAPI` and `corsEnabled`; never grant `bypassCSP` or service workers. Turn on `--site-per-process`. The trusted root is `clover-core://shell/`; plugins are `p1`, `p2` and `p3`, with `p1--child` nested in `p1` and a second `p2` frame mounted inside `p1`. Sealed cards get their own scheme, so no plugin id can share an origin with the core or a card. Every frame has Node off, the sandbox on and context isolation on. The only preload samples memory and exposes no callable bridge; `nodeIntegrationInSubFrames` is measurement scaffolding, not a proposed setting.

Electron's `mainFrame.framesInSubtree` gives each frame's process and OS PID, and `app.getAppMetrics()` lists the processes independently. On every OS there are **six frames, five origins and five renderer OS PIDs**. Both `p2` frames share a PID and the child has its own. `typeof require` is `undefined` in all six documents.

| Runner | core PID | p1 PID | p2 PID (both frames) | p3 PID | p1 child PID | New PIDs, independent window | New PIDs, related window |
| --- | ---: | ---: | ---: | ---: | ---: | --- | --- |
| macOS 15 arm64 | 1484 | 1487 | 1488 | 1489 | 1490 | root only | none |
| Ubuntu 24.04 x64 (xvfb) | 2944 | 2958 | 2967 | 2977 | 2994 | root only | none |
| Windows Server 2025 x64 | 3264 | 1152 | 8792 | 6064 | 6516 | root only | none |

**Two windows.** A second, independent `BrowserWindow` on the same session got a new process for its root only; every plugin frame in it joined the existing plugin renderer. A related window opened with `window.open` shared everything, the root included. Chromium reuses a same-site process for subframes across browsing contexts, but not for main frames. So a second window costs one root renderer plus each plugin frame's document inside processes that already exist, not a new process per plugin. That reuse is a Chromium policy, not a guarantee, and it has a cost: a plugin's renderer crash takes that plugin's frames down in every window (section 4.5).

This shows process placement, not resistance to a compromised renderer. Same-origin frames share a process but have separate documents and globals, so shared state lives in the core, as decided in (a).

## 3. Crossing layers — works with limits

**Method.** Two sibling plugin frames under the trusted root. Input goes through CDP on `webContents.debugger`, which routes keys, text and composition to the focused frame's widget (`Input.dispatchKeyEvent`, `insertText`, `imeSetComposition`). Drags use `Input.setInterceptDrags`: a drag starts in the source frame, the host receives it as `Input.dragIntercepted`, then drops it into the target. OS-level keys come from xdotool (XTEST) on Ubuntu and SendKeys on Windows; macOS CI has no way to send them without accessibility rights. Screenshots show a wide plugin menu and a host overlay.

| Runner | Typed text in plugin | Tab order | Shift-Tab back | Composition | App shortcut, OS input, plugin focused | Host returns focus after its overlay | Drag source → target | IntersectionObserver v2 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| macOS 15 arm64 | "ab" | p1#first → p1#second → p2#first → p2#second → out | p2#second | 日本 | no CI input tool | frame yes, element no | dropped, `text/plain` intact | visible |
| Ubuntu 24.04 x64 (xvfb) | "ab"; XTEST "xvfb" + Tab | same | p2#second | 日本 | host saw Ctrl+K first and consumed it; plugin got no keydown | frame yes, element no | dropped, intact | visible |
| Windows Server 2025 x64 | "ab" | same | p2#second | 日本 | host saw Ctrl+K first and consumed it; plugin got no keydown | frame yes, element no | dropped, intact | visible |

* **Works as is:** typed text, Tab and Shift-Tab across sibling layers, and composition (start, updates, end, committed text) reach the focused out-of-process frame through Chromium's own routing.
* **App shortcuts: the host can own them.** With OS-level input and a plugin field focused, the host's `before-input-event` saw Ctrl+K before the plugin did, and `preventDefault()` kept it from the plugin (Ubuntu XTEST, Windows SendKeys). CDP-injected keys never reach `before-input-event`, because DevTools marks them to skip the browser, so CDP can't test shortcuts. macOS, and its menu key equivalents, joins the live batch.
* **Focus return needs the host and the layer.** While a plugin has focus, the root's active element is that plugin's `IFRAME`. After the host's own overlay closes, refocusing that iframe gives focus back to the plugin's frame but not to the element inside it: no element is active and a typed key is lost, on all three OSes. So the layer's runtime (the plugin SDK in each layer) must restore its last focused element when its window regains focus, or on a "focus returned" message from the core.
* **Menus need the host.** In all three screenshots the plugin's 250 px menu, starting 80 px into a 180 px frame, is clipped at the frame's edge, and a host overlay crosses it. A z-index can't paint outside a frame.
* **Drag and drop works, with the host in the middle.** A drag started in the source frame reached the host with its data (`text/plain: clover-fixture`) and was dropped into the target frame. That handoff is where a host broker checks MIME types and the source's and target's rights. OS file drags and drops from outside the app are live gates.
* **IntersectionObserver v2** reports `isVisible: true` for a same-process srcdoc frame. A cross-origin nested frame, the case sealed cards need, is not tested yet (E-M1).

**Design for M1.** The host owns application shortcuts through `before-input-event` on the window's webContents, before any layer sees them. Menus go through a host broker with validated item and action IDs, sender-bound coordinates, clamping and dismissal; the trusted root draws data menus, or main shows native ones. If a plugin must paint its own popup, that code stays at its plugin origin on a separate surface, never in the core's origin. Ordinary focus and Tab order stay with Chromium. The host owns modal focus fences and returns focus to the frame, and the layer's SDK restores the element. A drag broker validates declared MIME types and both ends' rights, and hands out files through scoped grants, never raw paths. Sealed-card buttons stay outside plugin menu and drag authority; the hardware event, full visibility, OS overlap, minimum size, fallback and ancestor-style checks remain separate gates (E-M3).

## 4. Declared hosts — doesn't, in stock Electron 45, for WebRTC

### 4.1 The original reading, corrected in review

The original report misread its own evidence. **DNS prefetch leaked resolver intent for the undeclared host; link prefetch stayed inside the boundary.** The command-line WebRTC switch was never read by Electron, and the original STUN packets went to the *declared* `127.0.0.1`, so they proved nothing about undeclared hosts. The claim that stock Electron was insufficient was unsupported at the time, because `Connection-Allowlist` hadn't been tried. That run's JSON and its decoded speculative-resolver events stay in `evidence/run-41942765712/`.

### 4.2 Method

Seven variants run in one Electron process, each in its own session:

1. **control:** no checks.
2. **CSP:** the core serves plugin documents and workers with a CSP listing only the plugin's hosts.
3. **filter:** the session cancels requests whose `initiatorOrigin` isn't granted that exact origin and port.
4. **combined:** CSP and the filter.
5. **allowlist:** combined, plus `Connection-Allowlist: ("<declared-origin>/*" response-origin)` on every plugin document and worker script.
6. **IP policy:** combined, plus `webContents.setWebRTCIPHandlingPolicy('disable_non_proxied_udp')`.
7. **non-plugin:** an ordinary page in the same app, to show the closures don't leak into other webContents, such as the Clover Browser's.

Every vector, and every context's copy of it, has its own name and loopback port, so each listener hit is attributed exactly. Host-resolver rules send only `*.s9.test` to loopback; DNS, STUN, TURN and remote-candidate fixtures use unique `*.localhost` names. UDP listeners record the STUN magic cookie (`0x2112a442`) and source ports; TCP listeners record connections and bytes. Two plugins with different grants share one session. The probes run in the directly mounted plugin document, then in a nested plugin document, a srcdoc, a sandboxed (opaque) srcdoc, about:blank and a dedicated worker. The harness decodes each variant's netlog itself, and `netlog-extract.mjs` turns the raw netlogs into socket and resolver counts by fixture (committed as `netlog-extract.json`). Positive controls are required: a closure only counts where the same vector reached its listener without that check.

* **Prerender and speculation rules** fired in no variant, so there's no positive control for them.
* **`<object>` and iframe navigation to an undeclared URL** were stopped by the host's `will-frame-navigate` guard where CSP was off, and by CSP where it was on.

Prerender, speculation rules, `top.location` and downloads reached nothing even in the control variant, so they have no positive control. The host's guards were the check for popups, forms and navigation in every variant, including control. Service-worker registration fails on the custom scheme, which is deliberately not granted service workers.

**Embedding.** Plugin documents load only for single-use mount tokens issued by the core. A spent token, a never-issued token and a bare URL all get 403, and a fresh token gets 200, in every plugin variant on every OS. A plugin that tries to embed another plugin, the core shell (with or without its root token) or a sealed card is blocked every time. Where plugin CSP is on, `frame-src` blocks all five. Where it is off (control, filter), the mount check refuses the plugin embeds (403 with `frame-ancestors 'none'`), and the permissive policy's `*` still doesn't match the core and sealed schemes.

Two results bound the design:
* **WebTransport passes the filter.** `webRequest` doesn't see it, so in the tested design CSP is its only check.
* **A browser download the filter can't see.** On Ubuntu, the first plugin session to focus a text field made Electron fetch its Hunspell dictionary from Google's CDN (`redirector.gvt1.com/.../en-us-10-2.bdic`, about 87 QUIC datagrams). The browser process made the request on the session's behalf and `webRequest` never saw it. No plugin code controls that URL, so it is not a plugin escape, but it is non-loopback traffic from a plugin session. macOS and Windows use the OS spellchecker and fetched nothing.

### 4.5 What Connection-Allowlist does in Chromium 156, and the escape

`Connection-Allowlist` takes effect on `clover-plugin:` documents, served through `protocol.handle`, on all three OSes. It works in two places, and the gap is between them.

* **In the renderer (Blink).** When a document's policy blocks WebRTC, Blink drops every ICE server from the configuration before it reaches the native layer, skips `addIceCandidate`, and reports the connection as failed. That's why STUN and TURN went silent and gathering finished at once with only a host candidate. But a remote description's `a=candidate` lines are not stripped. The native layer then sends ICE connectivity checks (STUN binding requests) to whatever address the page wrote, from the P2P sockets, carrying a username fragment the page wrote into that description. That is a one-way channel to any address, measured at the undeclared listener with the magic cookie.
* **In the browser.** When a frame's policy blocks WebRTC, the browser leaves `P2PSocketManager` and `MdnsResponder` out of that frame's interfaces. In Chromium 156 that ban applied to the nested document, srcdoc and about:blank, which stay in their restricted parent's process. There the renderer's first request for `MdnsResponder` is a bad message, and the browser kills the whole plugin renderer (`No binder found for interface network.mojom.MdnsResponder`, three times per OS). The ban did not apply to the directly mounted document or the sandboxed srcdoc: the browser bound P2P sockets for them (12 in the netlog) and sent their checks. From the evidence, the ban follows how a frame's host was set up, not the document it shows. Frames that stay in their restricted parent's process got it. Two frames did not: the directly mounted document, created under the core's unrestricted shell, and the sandboxed srcdoc, moved to a process of its own.
* **Crash detection.** Electron 45 raised no `render-process-gone` for these subframe kills. The harness listens on the app-level event, which Electron raises for every webContents. It saw the kills only because the renderer's OS PID left `app.getAppMetrics()`.
* **DNS.** Speculative lookups stop because the network service refuses to resolve unlisted hosts for the document. The evidence is an absence, with the same vector's positive control in the same run, since the refusal logs nothing.

Chromium fixed the kill upstream in `46fcf3faed` (October 8, "Enforce WebRTC blocking in binders via no-op impls"), which isn't in 156.0.8078.80. Whether upstream also applies the ban to directly mounted documents is not known from this spike.

**The IP-handling policy is not a closure on its own.** `disable_non_proxied_udp` stopped STUN and the remote-candidate checks, since it disables UDP ports, but TURN over TCP still connected, 10 times, and DNS prefetch still leaked. Chromium's allocator leaves TCP ports on under that policy, so remote *TCP* candidates are the next probe for the obvious stock interim, the allowlist plus the UDP policy. That combination is untested.

**The non-plugin control** in the same app still reached STUN, TURN and remote candidates and made its lookup. Every closure here is per document or per webContents, so the Clover Browser keeps WebRTC.

**Limits.** The allowlist variant also has CSP and the filter on, so the allowlist's own effect on request-based ways out isn't isolated. Worker-side WebRTC isn't exposed, so that branch is unexercised rather than closed. All of this is the pinned Electron; every upgrade reruns S9.

## E-M1 decision on the Chromium 156 renderer kill

The kill is fail-closed: no traffic leaves, and only the offending plugin's renderer dies, though that takes the plugin's frames down in every window. The escape is the reverse: no crash, but traffic leaves. One Electron patch handles both. Options, cheapest first:

1. **Stub `RTCPeerConnection` in plugin pages.** A courtesy against surprise crashes from third-party libraries, never a boundary. Plugin code can get a fresh constructor from a sandboxed srcdoc child, which isn't banned and leaks.
2. **Wait for an Electron release whose Chromium has `46fcf3faed`.** That turns kills into silent failures, but on the evidence it doesn't close directly mounted documents.
3. **Patch Electron in lane M (recommended, needs the owner's agreement).** Give every frame whose document is on the plugin scheme no-op `P2PSocketManager` and `MdnsResponder` implementations, keyed on the committed document, not the frame's creation context. This backports `46fcf3faed`'s no-op approach, closes the remote-candidate escape in directly mounted and sandboxed documents, and ends the kill.

Until a patched build exists, M1 should:
* treat the kill as an accepted fail-closed outcome;
* detect it by PID census and show the layer as crashed, with a reload;
* keep S9's remote-candidate vector as a gate that must read zero before the declared-host promise is called met.

If the owner declines a patched Electron, the spec has to say that WebRTC is not closed for plugin UI code in stock Electron, or the [D] must change (see below).

## Owner decision: what "renders once" means — decided (a)

The owner chose **(a)**:
* one origin and process for each shared plugin;
* one frame for each place it appears;
* shared state held by the core;
* each frame using its own tab's theme.

It fits Chromium's document model and what S9 measured. A second independent window reuses the plugin's renderer (section 1), so a part shown in two windows costs one more document in an existing process, not a new process. M1 still opens the island and the pill as related windows with explicit opener lifetimes, which share the root process too. Reading (b), one live page shown in several places at once, is set aside: a document can't be in two visible places at the same time.

## Proposed changes from building C2 — controller applies

Section 5 is frozen (§14.2 item 73). These go through the controller as changes "from building C2". Marked **[P]**, or as touching a **[D]** the owner decides.

1. **§5.3 declared hosts, mechanism — touches the [D].** The [D] (revision 14) keeps its promise; the mechanism sentence changes to:
   * CSP and the `initiatorOrigin` filter stop requests;
   * `Connection-Allowlist` on plugin documents and worker scripts drops ICE servers and closes DNS prefetch;
   * the browser gives plugin frames no P2P sockets, which needs a patched Electron (lane M) because stock Electron 45 lets a remote ICE candidate reach any address.

   The owner decides between the patched Electron and stating WebRTC as an open gap for plugin UI code. Preconnect only raises a session event in Electron, and link prefetch passes through the CSP and the filter, so neither needs its own switch. Closures stay per document or per webContents, so the Clover Browser keeps WebRTC.
2. **[P] §5.5 mounts.** Plugin documents load only through single-use, unguessable mount tokens issued by the core, with `frame-ancestors` naming the authorized ancestors and `frame-src` limiting each plugin to its own contributions. The core and sealed cards use their own schemes, never a name in the plugin-id namespace. A host component controls how frames nested in it look; process isolation doesn't stop it clipping or covering them, so sealed visibility and hardware checks stay mandatory.
3. **[P] §5.5 input and state.**
   * The host owns app shortcuts, ahead of every layer, through the window's `before-input-event`.
   * Menus go through a host broker that binds sender, coordinates and action IDs.
   * The host returns focus to a layer's frame, and the layer's SDK restores the element.
   * Shared state lives in the core, per decision (a).
   * Plugin popup HTML never runs in the core's origin.

**Plan edits, for E-M1 and §10, not the spec:**
* Make S9 a pass/fail gate on `main` and on every Electron upgrade once a closing build exists; today its jobs pass on negative verdicts by design.
* Keep the positive controls, including the remote-candidate vector.
* Detect layer crashes by PID census.
* Turn off or redirect browser-made fetches that `webRequest` can't see: point the spellchecker's dictionary download at the core, or turn spellcheck off in plugin layers. Then assert zero non-loopback traffic from plugin sessions.
* Have one request-policy dispatcher that resolves exact, immutable initiator origins, rechecks redirects and fails closed on unknown or opaque initiators.

## Risks

* **WebRTC exfiltration from plugin UI in stock Electron 45**, through remote ICE candidates, as above. Plugins are trusted code (§1.1), but the declared-host promise does not hold for WebRTC until a closing build exists.
* **A patched Electron is a lane-M cost:** building Electron from source with a patch queue, on every upgrade. The patch is small, but the build is not.
* **Crash blast radius:** a killed plugin renderer takes that plugin's frames down in every window, and Electron 45 doesn't report it.
* **Process reuse across windows** is Chromium policy and could change; the memory estimate for extra windows depends on it.
* **Requests the filter can't see:** WebTransport (CSP only) and browser-made fetches such as the dictionary download.
* **`Connection-Allowlist` is new:** Chrome Status lists an origin trial in M148–151 with shipping planned for M152, and Chromium's own comments call the design a prototype that may change. Every Electron upgrade reruns S9.
* **Memory:** baseline only. Windows varies about 6% between runs, and GPU and utility memory are unmeasured.

## What's left for the live gates (plan §10)

Proposed additions to §10's existing machine batches:
* **macOS (item 5):** real typing and app shortcuts with a layer focused, menu key equivalents, IME candidate windows, OS file drags into a layer, and focus return after a core overlay. Item 5 already holds sealed cards answered with real clicks.
* **Windows 11 (item 3):** the same input checks, the island strip's overlapping surfaces, and sealed-card OS overlap and fallback.
* **Ubuntu 26.04 and Fedora (item 4):** the same on Wayland, which CI's xvfb doesn't cover.
* **The real base and Alpha themes**, once they exist (E-M2 with G-M1), before E-M3 accepts sealed cards.

Synthetic keyboard, composition, text drags and host shortcuts are CI work, already done here, not owner gates.

## What E-M1 should start with

1. **The WebRTC closure.** Take the owner's decision on the lane-M patch. Probe remote TCP candidates under the allowlist plus the UDP policy, which tells the owner whether a stock interim exists. Then prove the closing build with S9: zero STUN, TURN and remote-candidate traffic in every plugin context, no kill, and the non-plugin control still connecting.
2. **Layer crash handling:** PID-census detection, a crashed-layer placeholder with reload, and what the other windows show.
3. **Core-issued mounts and embedding**, with S9's hostile-embed and token-reuse probes as the regression gate.
4. **Focus and shortcuts:** the host's shortcut table in `before-input-event`, modal focus fences, and the layer SDK's element restore, checked by the same CI input probes.
5. **Two windows:** the island and pill as related windows with explicit opener lifetimes and failure handling.
6. **IntersectionObserver v2 from a cross-origin nested frame**, to de-risk E-M3's sealed cards.
7. **An empty `Connection-Allowlist: ()`** as the fail-closed default for third-party layers until declared hosts are wired, and plugin sessions with spellcheck downloads off.
