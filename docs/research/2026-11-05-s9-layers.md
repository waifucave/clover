# S9: Clover layers — November 5, 2026

**Review correction:** per-plugin OOP renderers work, and the memory numbers stand. ## 1. Process split — works, within the tested topology

Register `clover-plugin` before app readiness with `standard`, `secure`, `supportFetchAPI`, `corsEnabled` and worker support; never grant `bypassCSP`. Enable `--site-per-process`. Serve trusted root at `clover-plugin://core/` and plugins at `p1`, `p2`, `p3`, with `p1--child` nested inside `p1`. Mount a second `p2` inside `p1` as well. All frames have Node disabled, sandbox and context isolation enabled. Revised probes serve trusted root and sealed documents from `clover-core:` and `clover-sealed:`; the original listing below predates that correction. The only preload samples memory; it exposes no callable host bridge. `nodeIntegrationInSubFrames` is measurement instrumentation, not a proposed application setting.

Electron's `mainFrame.framesInSubtree` supplies Chromium process IDs, OS PIDs and routing IDs. `app.getAppMetrics()` independently lists the processes. In each OS there are **six frames, five origins and five renderer OS PIDs**. Both `p2` frames share their PID; the child has its own. `typeof require` is `undefined` in all six document worlds. The memory runs also retain listings for 1, 5, 10 and 20 plugin origins plus the trusted root.

## 2. Private memory — works with limits

Each count starts a fresh Electron process with a fresh temporary home and in-memory session. After load/settling, collect three samples spaced 600 ms apart. A sandboxed preload calls Electron's `process.getProcessMemoryInfo()` every 500 ms; main joins it to the frame tree using `senderFrame.osProcessId`. Linux renderer `process.pid` is in a PID namespace and is not the OS PID; joining on it produced missing measurements in an earlier run and was corrected. Missing data must remain unavailable, never zero.

The fixture contains inputs, a CSS menu and drag/drop text. It has no production React tree, transcript, avatar, audio or sleeping-layer implementation. Numbers are baseline allocation estimates, with instrumentation overhead; not an app budget or a stress test. Electron defines `private` in KiB as memory not shared with other processes ([ProcessMemoryInfo](https://www.electronjs.org/docs/latest/api/structures/process-memory-info)). macOS compression makes direct resident-memory comparisons misleading ([process](https://www.electronjs.org/docs/latest/api/process)).

Multiple fresh repetitions, representative content and an OS-level whole-process-tree private-memory measurement are needed before a budget is set.

## 3. Crossing layers — does not meet the full acceptance gate

Method: two sibling plugin frames; synthetic Electron input; Electron screenshots of a wide plugin menu and an overlay drawn in the trusted root; CDP drag enter/over/drop at the second frame. No native file, clipboard or OS automation was involved.

| Runner | Test character inserted | Useful Tab traversal | Host shortcut events | Target drops with expected text |
| --- | ---: | --- | ---: | ---: |
| macOS 15 arm64 | 0 | Not demonstrated | 2 | 1 |
| Ubuntu 24.04 x64 (xvfb) | 0 | Not demonstrated | 2 | 1 |
| Windows Server 2025 x64 | 0 | Not demonstrated | 2 | 1 |

* **Menus need the host.** In all three screenshots the plugin's 250 px menu starts 80 px into a 180 px frame and is clipped at its edge. A trusted-root overlay crosses that edge. A CSS z-index cannot paint outside the frame. The prototype demonstrates this rectangular overlay, not a finished native menu or plugin-code portal.
* **Focus is partly observed.** Programmatic focus sets the input's active element, and `document.hasFocus()` identifies the focused frame. This is not proof of a usable keyboard path.
* **Keyboard remains unresolved.** The top-level `webContents.sendInputEvent` path did not insert the test character or produce a useful Tab traversal on any runner, even with explicit CI window activation. The host saw two shortcut events (down/up). Treat this as a failed synthetic-input method; it does not prove hardware typing into OOP frames is broken. Do not design around forwarding synthetic DOM key events on this evidence. IME was not checked.
* **Drop delivery works with limits.** All three runners recorded one `drop` in the target with text `clover-fixture`. CDP injected a drag at the destination; it did not initiate a drag in the source. Native drag initiation, source-to-target negotiation, files and dragging outside the app are unproven.

Design to take into M1, subject to these gates: give menus a host broker with validated item/action IDs, sender-bound coordinates, clamping, dismissal and focus restoration; never accept arbitrary privileged HTML. The trusted root can own data menus, or main can present native menus. If custom plugin code must paint a popup, keep that code at its plugin origin and test the additional surface/process rather than execute it in core. Let Chromium handle ordinary focus and Tab first; the host owns application shortcuts, modal focus fences and restoration. A drag broker should validate declared MIME/data and source/destination capabilities and expose file handles through scoped grants, never raw privileged paths. Those broker details and real input behavior remain to be implemented/validated; this spike does not claim they already work.

Sealed-card buttons must remain outside plugin menu/drag authority. The spec's hardware event, complete visibility, OS overlap, minimum size, fallback and ancestor-style checks are separate gates. No real base-theme or Alpha-theme assets were exercised here.

## 4. Declared hosts — original verdict corrected; attributed rerun

The original report misread its own evidence. **DNS prefetch leaked resolver intent to the undeclared host; link prefetch stayed inside the declared-host boundary.** The original flags did not implement the claimed closures. Original STUN packets targeted **declared `127.0.0.1`**, and Electron did not read `--force-webrtc-ip-handling-policy`. Those packets cannot establish an undeclared-host escape or failure of the actual per-webContents API. The prior claim that stock Electron was insufficient was unsupported: `Connection-Allowlist` had not been tested.

Original evidence is unchanged in `evidence/<os>/network.json`. The now-committed `original-resolver-extract.json` files decode the original netlogs: every variant on every OS has speculative `HOST_RESOLVER_MANAGER_REQUEST` intent for undeclared localhost. With an external name that path can perform DNS. `--dns-prefetch-disable` is not read by Electron/Chromium; the header `X-DNS-Prefetch-Control` did not close the path. The extracts preserve this finding beyond artifact expiry.

Link prefetch's declared request was seen by webRequest. The undeclared request was independently refused by CSP `default-src` and the filter. Active declared prefetch is **not** an escape. If disabling even declared link prefetch is retained as a separate requirement, cancel requests whose `Sec-Purpose` is `prefetch` in `onBeforeSendHeaders` rather than rely on unsupported feature names.

The rerun replaces the old shared-port fixture with one loopback listener, unique hostname and port per vector/context. Host-resolver rules route only `*.s9.test` to loopback; DNS-prefetch uses a unique `*.localhost` name, whose speculative resolver intent remains visible in netlog without outside DNS. UDP records include the STUN magic cookie (`0x2112a442`), source address/port and timestamp; TURN/TCP records actual connections and bytes. UDP WebTransport probes record the first packet. Session `preconnect` events independently test the hint path; Electron emits the event rather than opening a preconnect socket.

The original four variants remain: control, CSP, filter and combined. The **fifth** is combined plus `Connection-Allowlist: ("<declared-origin>/*" response-origin)` on every plugin document and worker-script response. A sixth explicitly calls `webContents.setWebRTCIPHandlingPolicy('disable_non_proxied_udp')`; an unrestricted non-plugin webContents is the compatibility control. No process-wide network closures remain. The constructor existing is not a failure: sockets reaching listeners and gathered candidates decide WebRTC results.

Every vector has an independent endpoint: fetch, XHR, images, CSS/import/background, fonts, scripts, WebSocket, WebTransport, EventSource, beacon, keepalive, downloads, anchor ping, fetchLater, redirects, workers, navigation, top.location, window.open, forms and each hint. Two plugin origins with disjoint exact origin/port grants share one session. Own-host success and other-plugin/wrong-port refusal are recorded. Unsupported APIs and timeouts are explicit, never successful blocks. Worker peer connections are checked for API availability; no candidate API means that branch is not exercised, not a measured cutoff.

The header is checked in a directly mounted plugin, a nested document, srcdoc, opaque sandboxed srcdoc, about:blank and a worker script. Each context gets distinct STUN, TURN, DNS and fetch endpoints. Netlogs are decoded **inside the harness**, with source IDs and phase/error records retained. Positive controls must reach undeclared STUN/TURN without the header; the header must produce zero STUN UDP, zero TURN TCP, no candidates and refused speculative DNS, while the non-plugin control still connects.

**Attributed rerun results are pending CI at this intermediate commit.** No conclusion about header support or a fallback is made before those results. If the header is ineffective on `clover-plugin:` documents, the fallbacks are an Electron patch (per-frame P2P binder and DNS-hint refusal), or plugin documents served through an intercepted https origin. An IP-handling policy alone leaves TURN-over-TCP/TLS possible and cannot replace the per-document boundary.

Mechanism references: [Chrome's Connection-Allowlist guidance](https://developer.chrome.com/docs/modern-web-guidance/guides/security/restrict-outbound-connections), [Chromium design](https://chromium.googlesource.com/chromium/src/+/main/docs/connection_allowlist_design.md), and [Electron's per-webContents API](https://www.electronjs.org/docs/latest/api/web-contents#contentssetwebrtciphandlingpolicypolicy). Shipping behavior is tested at the pinned Electron/Chromium versions rather than inferred from current documentation.

## Proposed changes from building C2 — controller applies

Section 5 is frozen (§14.2 item 73). These **[P]** proposals go through the controller as changes “from building C2”; they are not direct spec edits and do not weaken the [D] declared-host promise.

1. **[P], §5.3:** use a tested per-document `Connection-Allowlist` on plugin documents and worker scripts alongside CSP and origin-bound request filtering. The admission condition is no connection or speculative DNS lookup to an undeclared host, no WebRTC socket traffic and no gathered ICE candidates; the constructor may remain present. Verify this on the actual document scheme. Closures are per document or per webContents so the Clover Browser remains unrestricted. The final result below determines whether this mechanism is usable or needs the named fallback.
2. **[P], §5.5 mounts:** plugin documents load only for mounts issued by core, using an unguessable per-mount token and `frame-ancestors` for the authorized ancestor chain. Each plugin's `frame-src` permits only authorized contributions/its inherited local contexts. Core and sealed cards use their own schemes, never a name in the plugin-id namespace. Process isolation does not stop a host component from clipping, covering or making a nested guest visually misleading: the host controls its nested frames' appearance. Sealed visibility and hardware gates remain mandatory.
3. **[P], §5.5 menus/state:** host menu brokers bind sender identity, coordinates and action IDs and restore focus; shared state lives in core, with the owner interpretation below. Never run plugin popup HTML in a trusted root origin.

Request-policy dispatcher details, positive controls, unavailable-memory handling and regression gates are proposed **plan** edits to E-M1/§10, not additions to the direction spec. One authoritative dispatcher resolves exact immutable initiator origins, rechecks redirects and fails closed for unknown/opaque initiators. It must not authorize from a frame's mutable current URL. Keep S9 permanent on main and the next milestone, and rerun it on every Electron pin upgrade.

## Owner decision: what “renders once” means [D]

The controller should present both readings, with the reviewer's recommendation **(a)**:

* **(a)** One plugin origin/process within a related browsing-context group, **one frame per place** it appears, core-held shared state, and each frame taking its own tab's theme. This fits Chromium's document model and the measured repeated-origin frame behavior. Independent windows may still duplicate the plugin renderer.
* **(b)** One live page shown in every place at once. A live document cannot simultaneously occupy the main window and an island/pill or a second visible tab/window. With only one visible place, core could move the same frame with `moveBefore()`, but core would need to place and own every frame, conflicting with guests mounted inside bot-tab components. It does not implement simultaneous appearances.

One independent window can add another roughly **19–24 MiB per visible plugin layer** (baseline only), plus a root renderer and further main/GPU/utility memory. Twenty layers in each of three independent windows can therefore approach three times the plugin-renderer baseline, before actual UI content. Do not promise one renderer per plugin **per app** from a single-window test. M1 can create island and pill using trusted core `window.open` and validate the resulting related browsing contexts and opener lifetimes, rather than construct independent BrowserWindows for each. The added process probe records independent and related-window frame/PID listings; no owner decision is assumed from those listings.

## Risks, live gates and M1 order

The original process and memory evidence stands. Per-added-layer slopes between 1 and 20 layers are approximately **18.5 MiB macOS / 18.9 MiB Ubuntu / 23.3 MiB Windows**. Main private memory also rises about **1 MiB per added layer**. Windows repeated-run renderer memory varies approximately **3–8%**; these are small-fixture baselines, not precision budgets. Full-app GPU/utility private totals remain an explicit measurement limit.

Base-theme and Alpha-theme assets do not yet exist. **E-M2 with G-M1** owns testing their sealed-frame ancestor filtering/opacity/transform rules, before E-M3 card acceptance. This is an identified integration milestone, not a claim that S9 exercised nonexistent themes.

Adopt the reviewer's E-M1 order:

1. Complete the `Connection-Allowlist` rerun first; its result determines whether lane M needs patched Electron or an intercepted https origin.
2. Establish CI input via CDP and xdotool under xvfb: keyboard, Tab/Shift-Tab, core-overlay focus restoration, synthetic composition and source-to-target text dragging. This PR adds those probes; only real hardware, native IME candidate windows and OS file drags belong in the live batch.
3. Core-issued mounts, token/ancestor validation and restricted embedding, using the hostile embedding probes added here as the regression gate.
4. Two windows and process placement; choose related contexts with explicit opener lifetime and failure handling if the owner accepts (a).
5. IntersectionObserver v2 from a nested frame to de-risk E-M3's sealed cards; the CI input check now probes the API, while full coverage/overlap and hardware authorization remain separate gates.
6. An empty `Connection-Allowlist: ()` is the fail-closed default for third-party layers until the manifest's declared hosts are wired.

Live gates retain real-hardware clicks/typing, actual OS IME candidate windows, native file drags and outside-app drops, release Windows/macOS/Wayland focus and overlapping surfaces, sealed-card OS overlap and fallback, and the real base/Alpha themes once integrated. Synthetic keyboard/composition/text-drag gaps are CI engineering work in this PR, not deferred to the owner. Multi-policy sessions, worker lifecycle updates, mount revocation/reload, crash/rebuild and header behavior on each Electron upgrade remain permanent regression concerns.
