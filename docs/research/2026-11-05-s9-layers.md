# S9: Clover layers — November 5, 2026

**Decision for the controller: do not admit this configuration as the declared-host boundary.** Per-plugin OOP renderers work in the tested window. The declared-host configuration does not: WebRTC still sends STUN packets, and ordinary link prefetch remains enabled. This is a negative spike, not a production implementation. No spec, shared contract, Winter source, live install or account setting was changed. Work on an alternative network design stops here under plan §9.

## Reproduction and evidence

The self-contained package is [../../spikes/s9-layers/prototype](../../spikes/s9-layers/prototype); see its [README](../../spikes/s9-layers/README.md) for one command per check. It sits below the `spikes/*` workspace glob and has its own npm lockfile. Nothing makes it a root workspace member. All Electron execution was in GitHub Actions: macOS 15 arm64, Windows Server 2025 x64 and Ubuntu 24.04 x64 under xvfb. These are runner OSes, not proof on the release OS versions or Wayland.

Electron **45.2.3** was npm's `latest` and the [current stable release](https://releases.electronjs.org/release?channel=stable) when checked November 5. Its embedded Chromium is **156.0.8078.80**, Node **24.22.2**. An exact pin makes the result reproducible and includes the `initiatorOrigin` API used here ([Electron webRequest](https://www.electronjs.org/docs/latest/api/web-request)). CI explicitly runs Electron's `install.js`; local install used `--ignore-scripts`, and no local command required Electron. Local verification: TypeScript checking and three Node policy tests, all pass. No browser, Electron, daemon, Keychain integration or native UI test ran locally.

Evidence: [three-OS run 41942765712](https://github.com/waifucave/clover/actions/runs/41942765712), all three jobs successful, tested code commit `12ca3e48fc2ee614d699d45092f1c87d3e83291b`. Each OS completed seven Electron invocations, including the four memory counts and 40 network vectors in each of four variants. Raw process, memory, crossing and network JSON are retained under `spikes/s9-layers/evidence/`; CI artifacts additionally contain screenshots and Chromium netlogs. JSON verdicts describe empirical outcomes. A green CI job means the experiment completed and uploaded evidence; it does **not** mean all four design requirements passed.

## 1. Process split — works, within the tested topology

Register `clover-plugin` before app readiness with `standard`, `secure`, `supportFetchAPI`, `corsEnabled` and worker support; never grant `bypassCSP`. Enable `--site-per-process`. Serve trusted root at `clover-plugin://core/` and plugins at `p1`, `p2`, `p3`, with `p1--child` nested inside `p1`. Mount a second `p2` inside `p1` as well. All frames have Node disabled, sandbox and context isolation enabled. The only preload samples memory; it exposes no callable host bridge. `nodeIntegrationInSubFrames` is measurement instrumentation, not a proposed application setting.

Electron's `mainFrame.framesInSubtree` supplies Chromium process IDs, OS PIDs and routing IDs. `app.getAppMetrics()` independently lists the processes. In each OS there are **six frames, five origins and five renderer OS PIDs**. Both `p2` frames share their PID; the child has its own. `typeof require` is `undefined` in all six document worlds. The memory runs also retain listings for 1, 5, 10 and 20 plugin origins plus the trusted root.

| Runner | core PID | p1 PID | p2 PID (both frames) | p3 PID | p1 child PID |
| --- | ---: | ---: | ---: | ---: | ---: |
| macOS 15 arm64 | 1287 | 1317 | 1318 | 1319 | 1323 |
| Ubuntu 24.04 x64 (xvfb) | 2265 | 2290 | 2294 | 2310 | 2326 |
| Windows Server 2025 x64 | 2368 | 8756 | 5020 | 8436 | 8908 |

This demonstrates process placement, not resistance to a compromised Chromium renderer. It does not establish globally one process per plugin across multiple independent BrowserWindows, crash recovery, sealed-card IPC authentication, or safe shared state between multiple documents. Same-origin frames share a process here; they still have separate document/JavaScript globals. Shared contribution state should live in the core/broker rather than assume a single React instance can appear twice.

## 2. Private memory — works with limits

Each count starts a fresh Electron process with a fresh temporary home and in-memory session. After load/settling, collect three samples spaced 600 ms apart. A sandboxed preload calls Electron's `process.getProcessMemoryInfo()` every 500 ms; main joins it to the frame tree using `senderFrame.osProcessId`. Linux renderer `process.pid` is in a PID namespace and is not the OS PID; joining on it produced missing measurements in an earlier run and was corrected. Missing data must remain unavailable, never zero.

The fixture contains inputs, a CSS menu and drag/drop text. It has no production React tree, transcript, avatar, audio or sleeping-layer implementation. Numbers are baseline allocation estimates, with instrumentation overhead; not an app budget or a stress test. Electron defines `private` in KiB as memory not shared with other processes ([ProcessMemoryInfo](https://www.electronjs.org/docs/latest/api/structures/process-memory-info)). macOS compression makes direct resident-memory comparisons misleading ([process](https://www.electronjs.org/docs/latest/api/process)).

Multiple fresh repetitions, representative content and an OS-level whole-process-tree private-memory measurement are needed before a budget is set.

## 3. Crossing layers — does not meet the full acceptance gate

Method: two sibling plugin frames; synthetic Electron input; Electron screenshots of a wide plugin menu and an overlay drawn in the trusted root; CDP drag enter/over/drop at the second frame. No native file, clipboard or OS automation was involved.

| Runner | Test character inserted | Useful Tab traversal | Host shortcut events | Target drops with expected text |
| --- | ---: | --- | ---: | ---: |
| macOS 15 arm64 | 0 | Not demonstrated | 2 | 1 |
| Ubuntu 24.04 x64 (xvfb) | 0 | Not demonstrated | 2 | 1 |
| Windows Server 2025 x64 | 0 | Not demonstrated | 2 | 1 |

* **Menus need the host.** In all three screenshots the plugin's 250 px menu starts 80 px into a 180 px frame and is clipped at its edge. A trusted-root overlay crosses that edge. A CSS z-index cannot paint outside the frame. The prototype demonstrates this rectangular overlay, not a finished native menu or plugin-code portal.
* **Focus is partly observed.** Programmatic focus sets the input's active element, and `document.hasFocus()` identifies the focused frame. This is not proof of a usable keyboard path.
* **Keyboard remains unresolved.** The top-level `webContents.sendInputEvent` path did not insert the test character or produce a useful Tab traversal on any runner, even with explicit CI window activation. The host saw two shortcut events (down/up). Treat this as a failed synthetic-input method; it does not prove hardware typing into OOP frames is broken. Do not design around forwarding synthetic DOM key events on this evidence. IME was not checked.
* **Drop delivery works with limits.** All three runners recorded one `drop` in the target with text `clover-fixture`. CDP injected a drag at the destination; it did not initiate a drag in the source. Native drag initiation, source-to-target negotiation, files and dragging outside the app are unproven.

Design to take into M1, subject to these gates: give menus a host broker with validated item/action IDs, sender-bound coordinates, clamping, dismissal and focus restoration; never accept arbitrary privileged HTML. The trusted root can own data menus, or main can present native menus. If custom plugin code must paint a popup, keep that code at its plugin origin and test the additional surface/process rather than execute it in core. Let Chromium handle ordinary focus and Tab first; the host owns application shortcuts, modal focus fences and restoration. A drag broker should validate declared MIME/data and source/destination capabilities and expose file handles through scoped grants, never raw privileged paths. Those broker details and real input behavior remain to be implemented/validated; this spike does not claim they already work.

Sealed-card buttons must remain outside plugin menu/drag authority. The spec's hardware event, complete visibility, OS overlap, minimum size, fallback and ancestor-style checks are separate gates. No real base-theme or Alpha-theme assets were exercised here.

## 4. Declared hosts — does not

Method: a loopback HTTP/WebSocket fixture declares only `127.0.0.1` and uses `localhost` as the undeclared host, on the same ephemeral port. A loopback UDP listener observes actual STUN packets. Run four isolated variants: control (CSP/filter off), CSP only, filter only, both. Candidate WebRTC/hint switches, a DNS-prefetch header, permission denial, and host popup/navigation guards stay present in every variant. This isolates CSP/filter effectiveness; it is **not** a switches-off positive control for hints or WebRTC.

The request filter examines `initiatorOrigin` before a request and rechecks each redirect destination. Missing/opaque/foreign initiators fail closed. This is a one-plugin fixture allowlist, not the manifest registry or production authorization code. Workers' JavaScript responses get CSP too; blob workers inherit document policy. The handler logs the initiator, resource type, destination and decision; server hits independently establish actual HTTP/WS reach. Request errors and font/image decode failures are never counted as policy proof.

| Runner | Control undeclared HTTP/WS hits | CSP / filter / combined undeclared hits | Combined STUN packets | Combined peer connection disabled |
| --- | ---: | --- | ---: | --- |
| macOS 15 arm64 | 20 | 0 / 0 / 0 | 3 | No |
| Ubuntu 24.04 x64 (xvfb) | 20 | 0 / 0 / 0 | 3 | No |
| Windows Server 2025 x64 | 20 | 0 / 0 / 0 | 3 | No |

The control produced **29 HTTP/WS fixture requests, 20 to the undeclared host**, on every OS. Each of CSP-only, filter-only and combined produced **9 requests, zero to the undeclared host**. The declared fetch, XHR, CSS and WebSocket controls succeed; font/image data intentionally do not decode, but their network arrivals are recorded. Service-worker registration succeeds, so worker coverage is exercised rather than assumed unsupported. `sendBeacon()` returning true is queuing, not delivery.

| Attempt | Observation / check responsible |
| --- | --- |

The configuration actually tested uses `--dns-prefetch-disable`, `X-DNS-Prefetch-Control: off`, `--disable-background-networking`, `--force-webrtc-ip-handling-policy=disable_non_proxied_udp`, and candidate disabled features `PreconnectToSearch,Prerender2,SpeculationRulesPrefetch,SpeculationRulesPrerender,WebRtcHideLocalIpsWithMdns`. Their names are recorded to reproduce a **failed candidate**, not recommended as supported security switches. Removing mDNS hiding is not a WebRTC cutoff. A list of flags and no HTTP hits would not prove DNS/TCP/UDP isolation.

The tests do not prove impossibility of the spec's desired boundary. They prove this stock Electron configuration is insufficient. No alternate boundary, Electron patch, network broker, dedicated-session redesign or weaker [D] policy was implemented after this result.

## Concrete proposed spec edits (controller applies)

1. **[P], §5.3 after declared hosts:** “Admission of plugin UI code waits for a three-OS conformance test of the full boundary. CSP and `initiatorOrigin` filtering alone do not cover WebRTC or speculative DNS/TCP. A candidate configuration that still creates peer connections, sends STUN/TURN traffic, or issues link prefetch is not admitted. Camera/microphone denial and WebRTC IP-handling policy are not a WebRTC disable mechanism.” Keep the existing [D] host restriction; do not weaken it to accommodate this spike.
2. **[P], §5.3 implementation checks:** “Install one authoritative request-policy dispatcher per session. Resolve immutable initiator origins against the plugin registry; deny unknown/opaque initiators unless a separately authenticated core request explicitly authorizes them. Recheck every redirect and serve worker scripts with policy. Gate navigations and popup creation separately. Never authorize by a frame's current URL after an asynchronous navigation.” The prototype's single allowlist is not that dispatcher.
3. **[P], §5.5 layers:** “A layer's cross-frame overlays use a core broker that binds sender identity, bounds, action IDs and focus restoration. Shared contribution state is broker/core state; repeated same-origin frames do not share one document instance. Per-window and per-plugin lifetime/process assertions are tested explicitly.” If “renders once” is intended to require literally one live DOM instance simultaneously in several tabs/windows, resolving that stronger interpretation **touches [D]** and needs the owner; this prototype does not resolve it.
4. **[P], §14.1 item 9:** “Report private renderer totals separately from main, GPU and utility memory, preserve unavailable values, and include representative content before setting the layer budget. Test native keyboard/Tab/IME and source-to-target native drag initiation; synthetic destination-drop delivery is insufficient. Include positive controls and DNS/TCP/UDP telemetry for each speculative path.”

No [D] decision is changed or assumed to be wrong. The declared-host [D] remains blocked on an effective implementation. A fallback that removes plugin-direct networking, changes the rendering model, or relaxes the promise must return to the controller and the owner if it changes [D].

## Risks, live gates and M1

The immediate risk is claiming a network boundary while a data channel still sends UDP. Also unresolved: DNS/TCP hint attribution, secure HTTPS/WSS endpoints and redirect chains, fresh renderer/worker lifecycle races, multiple plugin policies in one session, same-origin policy confusion, process placement across multiple windows and crash/rebuild cycles. The fixture is not a security review of sandbox escape resistance or sealed cards. Baseline memory omits production content and full-process-tree private totals. Synthetic keyboard failure prevents an input-acceptance claim.

The owner batch in plan §10 must cover real hardware typing, Tab/Shift-Tab, shortcuts, IME composition, accessibility navigation and focus restoration on release macOS/Windows/Linux (including Wayland); native text/file dragging across layers and outside windows; menu dismissal and overlapping surfaces; sealed cards with real hardware clicks, OS overlap, filtering/transforms, fallback and actual base/Alpha themes; and production-like layer memory/sleep/rebuild on the release targets. Full declared-host enforcement is a **pre-M1 engineering gate**, not something to postpone to a real-account live test. Its future regression test should remain CI-local with instrumented DNS/TCP/UDP and positive controls, without contacting outside services.

M1 should start with the already-proven origin/OOP layout behind the manifest and protocol fakes, a sender-bound core broker and explicit lifecycle/state ownership. Do not enable third-party UI networking or mark S9 accepted until the controller chooses and verifies an effective WebRTC/hint cutoff, native keyboard behavior is understood, and full-app memory is measured. Pair/tray/daemon work can use fakes without asserting those gates passed. Lane reviewer owns the required review after this PR; the controller merges. This implementer does not self-review, merge, or proceed to M1.
