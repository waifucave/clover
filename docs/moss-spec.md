## 1. What MOSS is

MOSS is the next major version of Winter, with a new name, a new home and a new shape. It is a **desktop agent platform** for macOS, Windows and Linux, made of **two apps on one shared engine** [D] (revision 19, item 95):

* **[D] MOSS is the app for bots.** Its window is fixed, closed and minimal: a list of bots, one conversation per bot, and a side panel with the bot's own screen and its routines (§6.10). It takes tools, models and voices from plugins, and no plugin changes its interface. **[P]** It has its own built-in Settings (the account, the keys and sign-ins for models and voices, the approval level and devices), since it runs alone (§6.10). It is meant to feel like Grok Bot.
* **[D] MOSS Code is the app for chat and code with coding agents.** A session in it is a session with a coding agent the user picks, and its window is made of plugin parts, with the full plugin system, the browser, Office and customization (§9.4). It is meant to feel like Claude's desktop app.
* **[D] The engine, `moss-core`, is shared.** It holds the home (`~/.moss`: bots, sessions, plugins, keys, settings), runs every session, bot, model, voice, coding agent, skill and tool, hosts every plugin, and routes everything that needs the user (§3). Each app carries a copy of it and runs alone; with both installed they use one shared engine **[D]**, and **[P]** one home (§3.1).

What the product is, in the engine's terms:

* **[D] Bots are the centre of MOSS.** A bot is an engine feature, shown only by MOSS (§6), not a plugin. **Alpha** is an ordinary bot that MOSS offers as a default (§6.2); users make the rest.
* **[D] All bots are equal.** Every bot has the same tools and sees every plugin, MCP server and skill scoped to bots (§5.1). A bot changes only its own `<bot-instructions>` block; the harness owns the rest of the system prompt.
* **[D] Each bot lives one continuous life.** There is one conversation per bot, compacted over time, with persistent memory (a `MEMORY.md` index linking to memory files) and routines that wake it on schedules, webhooks and integrations.
* **[D] The user's messages interrupt a bot immediately,** to be as fast as possible. Messages from other bots and routines fold into the running turn instead.
* **[D] Bots reach the user's computers.** They run bash, tools and, once opensky arrives, computer use on every computer the user connects, including cloud computers, through one folder tree with a folder per computer (§9.1). By default a bot asks before risky actions.
* **[D] Bots work together.** They message each other (`SendMessage`) and delegate work to coding agents over ACP (`Agent`).
* **[D] A bot is live on every device that is on.** It thinks on the user's **main computer**, and the device in use takes over while the main is offline. Transcripts and memories stay in sync without a cloud server.
* **[D] Bots can talk and listen** through voice provider plugins (§6.6).
* **[D] Everything outside a fixed core is a plugin.** In MOSS Code that includes the window itself, and users restyle anything there (MOSS's own window is built in, §6.10). Plugins include models, UI, themes, floating surfaces (island, Dispatch pill), voice, computer use, relays, companion apps and the avatar. Bots are not plugins: they are engine data (§6.1). The agent runtime and core app functions are **not** replaceable. **[D]** Every plugin belongs to the engine, and a part shows wherever its place exists (§3.4): tools, models and voices need only the engine; parts that draw on the screen need the engine's background host; parts inside a window need MOSS Code's window.
* **[D] A plugin is just a folder with files.** Making one never needs a tool: the user or a bot writes the folder, and the engine finds it. A plugin can hold other plugins (§5.1).
* **[D] The look.** MOSS draws its bots with the living-bots kit: each bot is a flat shape in one colour with two eyes, made from its name (§6.9). MOSS Code uses the Shards kit's icon and mark; **[P]** how the base theme's colours sit against the Shards look is open (item 121), and the pink the base theme used to carry is replaced by the kit's mark (G8). **[P]** The avatar is an ordinary bundled plugin that applies to every session and is not a part of any bot, drawn in a window, inside sessions or on the screen, as the plugin chooses (§10). **[D]** MOSS Code's default shell is laid out and measured like Claude's desktop app, with its own marks, icons and wording (items 83 and 86, §5.5).

MOSS is much closer to Grok Bot (bots with memory, routines and their own computer) than to a chat window; MOSS Code, the app for chat and code with coding agents, is the one that is like Claude's desktop app.

### 1.1 Non-goals

* **[D] Replacing the agent runtime is not allowed.** DeepSeek Harness lets a plugin replace the agent loop, storage or the model plumbing; MOSS does not.
* **[D] No relation to Discord Waifus.** Discord Waifus is an ordinary plugin (§11), and nothing in the product's design comes from it.
* **[D] No group rooms for now.** Conversations are one user to one bot; bots coordinate with `SendMessage`. **[D]** Teams of bots in one conversation (two faces in one row of MOSS's list) come later, after single bots (item 106); rooms could come later as a plugin.
* **[D] No paid cloud backup.**
* **[D] No spending limits or loop guards.** Bots spend freely, and the user watches their provider dashboards.
* **[P] No promise of a full sandbox for plugins.** Plugins are trusted code, as with DeepSeek Harness and Claude Code mods. The core keeps them away only from other plugins' UI and the sealed cards, keeps their UI code to the hosts they declare (WebRTC aside, a known gap, §5.3), and on macOS keeps host code from MOSS's Keychain items and the daemon's socket (§5.2, §5.5, §5.6).

### 1.2 The two apps

| | MOSS | MOSS Code |
| :- | :- | :- |
| For | Bots: a conversation, a face, routines and a screen for each | Sessions with a coding agent the user picks (§9.4) |
| Window | Built in and fixed (§6.10); no plugin part is mounted in it | Made of plugin parts: the default shell, replaceable, with the panels (§5.5) |
| What plugins give it | Tools, models and voices, and, through the background host, on-screen parts such as a desktop avatar or a replaced island; its Plugins page adds them behind the normal OK card | Everything: any part, in the window or on the screen; the browser, Office, themes and customization |
| Look | The living-bots kit | The Shards kit's icon and mark, and the base theme (item 121) |
| Alone | Runs every bot, tool, model, voice, ACP agent, skill and plugin that needs no window of MOSS Code | Runs sessions with any coding agent, with every plugin part |

* **[D]** Each app works on its own when the other is absent. Plugins that change an app's interface need MOSS Code. **[P]** MOSS has its own built-in window and Settings (§6.10), so it needs nothing from MOSS Code.
* **[D]** Bots are only in MOSS. MOSS Code shows sessions with coding agents and no bots; with both installed, a bot's coding task carries an "open in MOSS Code" link (§9.4).
* **[P]** MOSS is a second build of the same app code, not a new codebase. Each app says which it is when it connects, and the engine tells it what to mount (§3.1).
* **[D]** A third app, an installer and hub called 550W, stays parked: the owner does not know whether it should exist (item 108). Each app updates itself, and the engine, its tree, the host and both apps run one release (§3.1).

## 3. Architecture

### 3.1 Processes on one device

The engine is the daemon: one `moss-core` process per home, shared by both apps. The apps are places to show things; the background host is the engine's own helper for everything that is drawn outside a window.

```text
┌───────────────────────────── one device ─────────────────────────────┐
│                                                                      │
│  MOSS (bots)       MOSS Code (coding agents)        other clients    │
│  fixed window      window made of plugin parts      CLI · iOS · web  │
│       │                    │                              │          │
│       │         background host (no window)               │          │
│       │         island · pill · on-screen parts           │          │
│       │         voice player · carried in each app        │          │
│       │                    │                              │          │
│       └──────── local socket (JSON-RPC) ──────────────────┘          │
│                                                                      │
│  moss-core (Bun daemon, one per home, always on)                     │
│  ├─ fixed core: agent runtime (the SDK), event log, permissions +    │
│  │   approvals, the router (§3.5), routine engine, plugin registry,  │
│  │   settings, identity, pairing, sync, links                        │
│  ├─ bots, sessions, models, voices, coding agents, skills, tools     │
│  ├─ plugin hosts (two Bun processes, the bundled tree's and third    │
│  │     parties', a worker per plugin; Node/native plugins get        │
│  │     their own process)                                            │
│  └─ starts and supervises the background host (§3.1)                 │
│                                                                      │
└──── one persistent encrypted link to each other device ──────────────┘
```

* **[P] Keep a real engine, the daemon.** Bots must answer other devices, run routines and stay reachable while every window is closed, and survive an app crashing. DeepSeek Harness's model, where the app owns a child process, cannot do that. `moss-core` starts at login:
  * macOS: a launchd user agent
  * Windows: a per-user scheduled task
  * Linux: a `systemd --user` unit

  It also runs headless on servers and cloud VMs.
* **[D] The daemon stays on Bun.** It ships as a `bun build --compile` binary for `darwin-arm64`, `windows-x64`, `linux-x64` and `linux-arm64`; macOS 27 runs only on Apple silicon, so there is no `darwin-x64` (§4). `Bun.secrets` (experimental since Bun 1.2.21) already maps to macOS Keychain, Windows Credential Manager and the Linux Secret Service, which needs a running secret-service daemon such as GNOME Keyring or KWallet. **[P]** The daemon and CI run Bun 1.4.x: Bun 1.3 stopped firing timers while a native addon delivered a steady stream of completions (S1, fixed in 1.4.4), and crashed under Worker churn in 1.3.14.
* **[D] The apps are Electron and TypeScript.** Each is a client of the engine, as the Swift app is today, and so is the background host, which each app carries. The daemon remains the single source of truth, and every client is a view of its event stream. Today's JSON-RPC 2.0 over NDJSON protocol carries over; the transport is a Unix socket on macOS and Linux and a named pipe on Windows. **[P]** As in Winter, every client says hello with its role and proves it with a token, and each role has its own list of allowed methods (`packages/core/src/ipc/server.ts`, `auth/app-token-acl.ts`). **[P] Client kinds** (the controller's ruling G1, revision 19): the hello's `app` role carries one more field, `surface: "moss" | "code" | "host"`: `moss` (MOSS's window), `code` (MOSS Code's window) or `host` (the background host). It chooses what the engine mounts, by a mount list for each surface (§3.4), and grants no method: all three are the `app` role for the caller check and for registering an answer key (§5.5). **[P]** The program an answer key belongs to is the client's signed identity, which tells the host's fixed helper id from the two apps, never the hello's `surface`; on Windows and Linux, where there is no running-image signature, the `surface` field plus the caller check stand in for it (§5.5). The engine refuses a second live `host` and tells an older second client of a surface to stop. A change to the press rules (§5.5) raises the engine's minimum protocol version; it adds no field. The daemon also checks a caller's process tree, so a command started by a bot, an agent or a plugin never counts as the user or the app (§5.5). **[P]** A caller counts as the user or the app only if it also runs outside every sandbox and escape floor: not sandboxed on macOS, in the host's namespaces on Linux, and neither restricted (`IsTokenRestricted`) nor in an AppContainer on Windows. A command that leaves Bash's sandbox still runs under the escape floor (§4), so a bot's command never counts as the user, even after a double fork, which a process-tree check alone misses. **[P]** Besides the process tree and token flags, the check asks which principal a process runs as and how it was started, so a process launched through a service, or one whose token was changed, never passes as the user; on Windows, Bash's sandbox principal (§9.1) never counts as the user (S2). **[D]** It also tells the two plugin-host processes apart, since only `moss`'s may use the waifucave token and `keys.open` (item 84, §5.2). **[D] The apps' peer image.** On macOS an `app` hello counts only from a process signed as one of the profile's three programs: MOSS Code (`com.waifucave.moss.code`), MOSS (`com.waifucave.moss`) or the background host (`com.waifucave.moss.host`) for dist, or the dev profile's copy of each (the copy of Electron that `bun run dev:app` signs with the dev identity), on Apple's chain and the company's team. The dist app's leaf must be a Developer ID Application certificate, unless the daemon itself isn't Developer ID signed (the owner's `--sign-dev` alpha, or a checkout), which would otherwise refuse its own app. The process must also run under the hardened runtime, never with `get-task-allow` or as a debugged process, and with none of the entitlements that open it (`get-task-allow`, `allow-dyld-environment-variables`, `disable-library-validation`). The signature is read through the connection's audit token, so a pid reused since never passes, and an unsigned or ad hoc binary, another identifier or team, or an unhardened one, is refused (`platform/peer-signature.ts`). **[P]** The host is a nested helper app with an identifier of its own, the same in both apps (below), so the check names three programs, and a host started from either app's copy passes the same way. The identifiers are item 120's. The check holds only while a signed program can't be made to run other code: the packaged app's Electron fuses turn off `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS` and the inspector (its flags and `SIGUSR1`), and load only its integrity-checked `app.asar` (`electron-builder.yml`'s `electronFuses`), and each program must refuse to start with Chromium's remote-debugging switches, which would let another process drive its windows (lane E, in the app's main process). The dev app loads its code from the checkout, so on the dev profile the check names the binary, not the code. Linux and Windows have no equivalent, and none is faked: Linux keeps no code signature for a running process, and any process of the user's can start the app under `LD_PRELOAD` or trace it; on Windows Authenticode signs files, a running image's file can be renamed and a signed one put in its place, and any process of the user's can write code into the signed app. There the floor and the lineage stand alone. Bash's fence keeps Winter's closed doors on macOS (`open`, `launchctl`, `osascript`) and closes `systemd-run --user` on Linux and the Task Scheduler on Windows. A bot may run the CLI with its own session's rights. Plugin code on Windows and Linux runs as the user and is trusted as such (§5.2).
* **[D] Each app carries a copy of the engine and of the background host, and runs alone; with both installed, they use one shared engine** (the owner, 2026-11-16, item 95). **[P]** For one home (the controller's reading). The engine installs itself under the home (the self-update `bin/` design) and owns its login item, and starts and supervises the host from the newest app that carries it. Removing one app leaves the other working. Removing both leaves the engine in the home; what an uninstall cleans up is open (item 109). Each app updates itself with electron-updater on all three OSes, replacing Sparkle, from its own feed in the same repo's releases (item 120).
* **[P] One release for everything** (ruling D; it changes item 22's one release back). The engine, its bundled tree, the background host and both apps run the same release; the bundled tree is the engine's. The newest installed copy wins for the engine, the tree and the host. An app older than the running engine updates itself before it connects. A newer app brings its engine: it waits until nothing is mid-work (the engine between turns and no agent running), stops the host, then swaps the engine, the tree and the host; while it waits it says it is waiting for work to finish and offers "switch now". The older app that is already open shows that it is updating and updates itself. An app that cannot update (offline) does not connect until it can. The protocol range stays one version wide (the hello carries a protocol version, and the engine's minimum and current versions are equal), so item 117 is closed. A client outside the range is refused and told which release it needs. **[P]** In the first build this is enforced by the engine refusing an app that is not on its release, which then updates itself at launch; staging both apps' updates together, coordinated by the engine, comes later, and is the job a hub such as 550W would do (item 108).
* **[P] Where the copies are found.** Each app records its bundle path and version under the home at every start, and the engine drops a path that no longer exists. The install into the home's `bin/` runs under the engine's lock, comparing build versions; the loser just connects. Opening a newer second app while an older engine runs is an update that carries a newer engine (above). The home's `bin/` and the login item stay inside the bots' write fence, as today (§9.1); no new mechanism.
* **[D] The engine and the background host are the always-on part, and the apps' windows come and go** (the owner, 2026-11-16, item 98; this replaces revision 12's always-on pair of app and daemon). The engine runs from login and starts and keeps alive the background host, a small windowless process that runs every plugin part that is not inside a window: the island, the pill, parts drawn on the screen and the voice player. Closing or quitting either app stops nothing: bots, routines, cards and the island keep working while every window is closed. There is one owner of the screen layer, so there is exactly one island, always above anything a plugin draws. **[P]** On Linux the engine starts the host once the graphical session is up. A server or cloud computer with no display runs the engine alone. **[P]** While a screen reader is on, the browser's host window, which the user isn't meant to see or use, is the one window open before the user opens one (§12.1, item 93). **[P]** The background host owns the one menu-bar icon, with open MOSS, open MOSS Code and a third entry, "quit everything", which stops the engine, the host and both apps, is worded so that it cannot be read as quitting the bots app, and warns when something is mid-work; `app.tray` lines go in its menu, and quitting an app never stops work; and revision 13's "Hand over and quit", which released the main computer's lease at once (§6.4), is retired (item 112).
* **[P] The engine and the host, precisely:**
  * One engine per home, holding an OS file lock for its life, one background host per home (not per user), with a lock of its own, and one of each app per user. Winter's pid-file lock lets a second daemon take over one that is still starting (`packages/core/src/lock.ts`); this one doesn't.
  * The engine starts the host through the OS: Launch Services and `launchctl kickstart` on macOS, the scheduled task on Windows, `systemctl --user start` on Linux. Opening an app starts the engine when it isn't running, from the newest copy.
  * On Windows the logon task runs `moss-core supervise`, which runs the daemon as its child and restarts it after a crash: in S7, Task Scheduler's restart on failure never fired for a killed task, and its interval can't be under a minute anyway.
  * A side that exits on purpose tells the other first. The engine restarts a crashed host with growing delays, and after three crashes in two minutes the host starts in safe mode, which covers the host's UI parts only: the engine's third-party tools keep running (§5.8). **[P]** At login the engine and the host start and no app window opens by itself; an app that crashed is reopened by the person (item 116).
  * A daemon restart stops agents, the plugin host and background commands, and records running calls as interrupted.
  * An update that carries a newer engine (above) waits until the engine is between turns and no agent runs, then stops the host and the engine, installs the newer engine, tree and host, and starts them again.
  * **[P] The host is a nested helper app with one fixed identifier,** `com.waifucave.moss.host`, the same in both apps, with its own single-instance lock and its own user data, so its microphone grant, its protected storage and its preferences do not change when it runs from the other app's copy. An app update that replaces the bundle the host runs from stops the host first.
  * **[P] After an engine restart** the windows send their presence again, and until a report arrives cards go to the island (§3.5). A restarted engine adopts the running host, found by the host's lock, and does not start a second. With no app left on disk the engine runs headless and does not restart a missing host for ever; what an uninstall cleans up stays open (item 109).
  * On Linux the app copies the daemon out of the AppImage and starts with the desktop session (XDG autostart). A server turns lingering on and updates its daemon itself, checking the same signature.

### 3.2 The fixed core

These are **not** pluggable [D]. Plugins can extend them only through the declared extension points in §5.

| Core part | Owns |
| :- | :- |
| Agent runtime | The turn loop, tool dispatch, interrupts, compaction and context assembly, from `clover-sdk` |
| Event log and storage | Event-sourced transcripts and bot state; the source for sync (§8.5) |
| Permissions and approvals | Approval policy, rules, the fence that keeps bots out of settings, levels and credentials (§9.1), and **sealed approval cards** whose text plugins can show but never read, and which only sealed buttons and paired devices can answer (§5.5) |
| Routine engine | Watches the routine files on each computer and fires each routine on the computer that holds its file (§7) |
| Plugin registry | Watches the plugins folder, asks before loading a new plugin, reads manifests without running anything, starts each contribution once its extension point exists, stops dependents first, hot reloads, checks capabilities (§5) |
| Plugin host | Runs every plugin's host half in its own worker, under its own identity, in `moss`'s plugin-host process or the third parties' (§5.2) |
| Folder tree | One folder per connected computer, served by the computer that holds it; runs file tools and bash on that computer (§9.1) |
| MOSS Browser | A browser on each computer: on desktops its pages run offscreen in the background host, so they keep running with every window closed, and a panel shows a tab as a picture; headless on servers; with an API for plugins (§12.1, item 111) |
| Bots | Each bot's data, conversation, memory, routines and face, its last line of activity and unread state, kept in the bot's folder under the home's `bots/`; shown only by MOSS (§6) |
| The router | Decides where a card, a question or "a bot needs you" is drawn, from the presence each program reports (§3.5) |
| MOSS's window | **[P]** The fixed window of MOSS and its own Settings (the account, the keys and sign-ins for models and voices, the approval level, devices), built in with no plugin part, drawing the sealed cards the router places there (§6.10) |
| Background host | A windowless process, one per home, that the engine starts and keeps alive, which runs every plugin part that is not in a window, and the browser's pages (§3.1, §3.4) |
| Live data for every place | The activity feed, a tool's live picture and data scoped by kind (§3.6) |
| Settings | Layered settings with the live-reload rules Winter already has |
| Identity, pairing, links, sync | Device keys, accounts, the main computer and its lease, encrypted links, replication |
| Protocol | Every RPC method and event. Plugins add none and cannot change them: clients run a plugin's `commands` by full name, `<namespace>.<name>`, through the core method `command.run` (§5.4) |

### 3.3 The agent SDK and model plugins

* **[D] `winter-runtime-sdk` is archived.** Today every session is a runtime child driven through the router. In MOSS the daemon embeds `clover-sdk` directly. Chat and Dispatch already run the SDK inside `winter-core` (one Bun Worker per session). Code sessions stop going through the router too: in C1 they run embedded, and in C6 they become Winter's coding agent, an ACP agent started like any other (§9.3); MOSS's own coding agent is one of the agents a MOSS Code session can start (§9.4).
* **[D] Model plugins are ordinary plugins.** They use the same folder format and the same install flow as any other plugin. Adding a model is installing a plugin.
* **[D] Every model adapter is a plugin, including the ones Winter has today.** This replaces Winter's rule that providers live in the SDK:
  * `clover-sdk` keeps the agent loop, a stable **provider adapter interface** and the **catalog row schema**. It ships no providers.
  * Every provider the SDK has today moves out into a **bundled model plugin**, one per provider, carrying its adapter, its catalog and its sign-in. **[P]** They are children of the bundled `moss` plugin (§5.1).
  * A third-party model plugin works the same way. It can also be declarative only: catalog rows plus an OpenAI- or Anthropic-compatible endpoint, with no code.
  * **[P] Where adapters run:** in the plugin host, like every host half (§5.2). Each streamed chunk crosses local IPC, which adds microseconds. If the plugin host restarts mid-turn, the model call is retried.
  * **[P] Logins stay in the core.** As in Winter (`packages/core/src/runtime-sdk/host-credentials.ts`), refresh tokens never leave the core. It refreshes `oauth-pkce` sign-ins itself, and only on the refresher (§8.5); a `custom` sign-in handler refreshes only when the core calls it there. Adapters get access tokens by reference, with a generation number, and ask for a newer one after a 401. Other computers get the new token over the link.
* **[D] Model access on first launch:** a **welcome setup guide** walks the user through entering an API key or signing in to one of the supported subscriptions. Claude subscription sign-in is not supported, as in Winter today. **[P]** Anthropic Console sign-in (API billing, through the official login) carries over from Winter.
* **[D] Subscriptions may be used for anything,** routines and bot-to-bot turns included; staying within a plan's terms is the user's responsibility.
* **[D] Codex `originator` becomes `"moss"`.** Codex's `originator`, now set in the bundled Codex model plugin, identifies MOSS as `"moss"`, replacing `"winter"`. The CLAUDE.md hard rule is updated with the rename in C0.

### 3.4 Where a plugin's parts show

* **[D] Every plugin belongs to the engine, and the engine decides where each part shows** (the owner, 2026-11-16, item 96). The apps are places to show things, not owners of plugins. A plugin's host half, tools, models, voices, hooks, skills, triggers and everything else that is not drawn run in the engine's plugin hosts (§5.2) whichever app is open, so closing MOSS Code never stops the island.
* **[D] A part shows wherever its place exists:**

  | The part | Needs | For example |
  | :- | :- | :- |
  | Tools, models, voices, skills and anything not drawn | The engine alone | Computer use, the browser's tools, web search, a model provider, a voice |
  | The browser's pages | The background host, which runs them offscreen, so they keep running with every window closed; a panel shows a tab as a picture | MOSS Code's browser panel (it forwards the person's input under the press rules of §5.5), MOSS's side panel (watch only) |
  | A part drawn on the screen: a surface (`app.surface`), a part kept running with no window (`app.background`), a menu-bar line (`app.tray`) | The background host | The island, the pill, a desktop avatar following the user's bots, a replaced island, the voice player |
  | A part inside a window: the spots of the shell that fills `app.root` (§5.5) | MOSS Code's window | The sidebar, the conversation view, the composer, panels |

  So an on-screen plugin works with MOSS alone, and a plugin that changes the interface needs MOSS Code. **[P]** A contribution whose place does not exist waits, as one whose point is missing does (§5.4), and Settings says what it waits for ("waiting for MOSS Code's window").
* **[P] Mount lists** (G1, §3.1). The hello's `surface` field picks the list and grants no method. `code` gets the window's points and spots; `host` gets the screen's points (the island, the pill, parts on the screen) and the background parts; `moss` gets nothing from plugins, since MOSS's window is built in. A part may have pieces in both MOSS Code's window and the host; each piece has its own connection to the engine and they reach each other only through it (item 121).
* **[P] Two programs show parts.** Where older text of this spec says "the app's main process", "the app's plugin runtime", "the layers" or "the sealed frames", it means the program that shows the part: MOSS Code's window process, or the background host, each with its own main process, layers and sealed frames. MOSS carries no plugin runtime in its window, but it draws the sealed approval cards the router places there (§3.5): the sealed frames are core, not a plugin part, and the press rules of §5.5 hold in its window as in any surface, and its main process keeps its own press record, trusted pointer-down report, fresh visibility reading and stacking rule for the cards it draws (§5.5). The plugin runtime is one library, used by MOSS Code's window process and by the host process (item 121).
* **[D] There is no MOSS API and no MOSS Code API: there is one API, the engine's** (the owner, 2026-11-16, item 105). Bots, their state, conversations and cards are engine data, and a part on the background host can follow bots as well as sessions, with the matching capability named on its OK card (§3.6, §5.4). MOSS's window stays closed; its data does not. **[P]** The Dispatch pill targets what the engine has, bots and sessions, whichever apps are installed (§5.3).
* **[D] With only MOSS installed,** a person can still add a plugin's tools, models or voices, and an on-screen plugin, through MOSS's Plugins page (§6.10), behind the normal OK card. Parts that need a window wait for MOSS Code.

### 3.5 The router and presence

* **[D] The engine routes everything that needs the user** (the owner, 2026-11-16, item 97): approvals, questions, "a bot needs you" and the like, through one router, whichever app the request came from. A card is answered in one place and cleared everywhere, and when the user is looking at something else, the island shows it.
* **[P] Presence** (G2, ruling A). The main process of each program reads, from the OS and from the program's own state, whether one of the product's windows is focused and which session or bot it shows; a plugin part never reports it (E1). A report expires when the program's connection drops or after a short silence, and a change places the pending cards again.
* **[P] Where a card is drawn** (ruling A). Whichever of the product's windows is focused draws every pending card: in the conversation when that window is showing the card's session or bot, otherwise in that window's own strip, drawn by the core. A card with no session (a plugin's OK from a Plugins page, an update card, an answer-key card) is drawn in the focused window that asked for it. With no window of the product focused, the island on the background host draws it. With no surface on the computer, the card goes to the phone or the CLI. A card is never left with no place a person can see (item 119).
* **[P] The island and the press gate** (ruling A). The island steps aside only for a focused window of the product (the presence the windows report), and never while the router has placed a card on it; a window that is visible but not focused (on a second screen, or while the person types in another app) does not move it. Its press gate follows the router's placement, not window focus: it takes a press only for a card the router placed there.
* **[P] Presence decides only where a card is drawn, never who may answer.** An answer still needs a real press on a sealed button, under the press rules of §5.5, in whichever surface drew it, and the overlap check there reads the OS's window list (§5.5, ruling B). A surface that draws cards on the host (`window.cards`, §10) draws the ones the router places there.
* **[P] One live place is per computer** (ruling A). §5.5's rule that every device shows a pending card and the first answer wins (item 91) stays as written. Item 119 is closed: the engine keeps the background host running, so a desktop always has the island, and a computer with no screen keeps the card pending for a device or the CLI, as today.
* **[P]** After an engine restart the windows send their presence again, and until a report arrives the cards go to the island (§3.1).

### 3.6 What the engine gives every place

* **[P] The activity feed** (G4). One general feed per session and per bot: idle, listening, thinking, working, asking, stuck, done, asleep. MOSS's faces read it for their moods (§6.9); a plugin reads it by capability (§5.4). **[P]** It carries states and names, never message text, tool arguments or card text; for bots its OK line says "all your bots".
* **[P] A tool's live picture** (G5). A general capability: a tool plugin may publish a live picture of its work for its session, over the engine's byte stream (§5.4 "Streams"). MOSS's side panel shows it, watch only (§6.10); a plugin may show it by capability, with its own OK-card line. It is not a path of the browser or of computer use: any tool plugin may publish one for its session, declaring it in its manifest, and its OK card says it "shows a live picture of what it is doing" (item 115). **[P]** The engine keys a picture to the session of the tool call, never to an id the publisher names. It is inert pixels, shown with the publisher's plugin id, never markup. A picture of the user's own screen keeps today's rule that the product's own windows are blacked out. The `picture.read` OK line says that it can include the user's own screen and the pages the user is signed in to, with a warning (§5.4).
* **[D] Reading is scoped by kind of data, never by app** (the owner, 2026-11-16, item 105). The plugin's author chooses what it attaches to and reads, and the engine enforces the choice. A plugin that asks only for code sessions never sees bots and is unaffected by whether MOSS is installed; one that wants both asks for both. **[P]** (G6) Code sessions, bots' conversations and pictures of their screens are separate capabilities, each with its own line on the OK card ("reads your code sessions", "reads your bots' conversations"), so the card says how far the plugin reaches.
* **[P] What the engine gives MOSS as plain data,** all of it built-in UI with no plugin part in the window: each bot's last line of activity and unread state, the activity feed for the faces' moods, each bot's routines and a tool's live picture. The same data is open to plugins by capability.

## 5. Plugins

### 5.1 A plugin is a folder

* **[D] A plugin is just a folder with files.** Nothing else makes something a plugin. Installing one means putting its folder in the plugins directory (`~/.moss/plugins/` [P]), and **making one never needs a tool**: the user writes the folder there, and a bot writes it in its scratch and installs it with its `PluginInstall` tool (§5.6, the workshop rule), since bots' tools don't write the plugins folder (§9.1). The registry watches the directory and loads, reloads or unloads plugins live, with no restart. Installing from an index or npm only downloads a folder into that directory.
* **[D] A plugin contributes to any extension points** (November 3; this replaces "a plugin does one job, of one kind"). Its manifest, `moss.json` (§5.9), lists what it adds and where: models, tools, skills, themes, parts of the UI and so on (§5.3). **Plugins have no kinds.** What a plugin is ("Model provider", "Tools", "Theme", "UI", "Cloud computer", "Collection") and whether it is data, web or code are worked out from what it contributes, never declared.
* **[D] Plugins can hold plugins** (November 3; this replaces plugin packages). A plugin may keep **child plugins** in its `plugins/` folder, one level deep:
  * A child is a full plugin, with its own manifest, contributions, on/off switch, secrets and worker. Its id is `<parent>/<folder>`.
  * **[P]** Wherever a plugin's id names a file, a folder or an origin, its `/` is written `--` (`plugin-data/tarot--tarot-panel/`), which no id can contain.
  * The top-level folder is installed, synced, updated, approved and removed as one unit, so a whole suite is still one folder to share.
  * **[P]** Each child is switched on and off by itself (default: on), and switching the parent off switches its children off. The parent's `version` covers the whole tree, which updates in one step.
  * **[P]** A child does not plug into its parent automatically; it contributes like any plugin. A parent that declares an extension point can ship its default guests as children (§5.4).
  * **[P]** No dependencies by plugin name in 1.111.1. Plugins depend on each other through extension points: a contribution whose point is missing waits, and Settings shows what it is waiting for. Running another plugin's commands (`call:<plugin-id>`, §5.4) is not a dependency either: a call to a missing plugin fails with "not installed".
* **[P] The folder shape,** with a plugin that brings a skill, a theme and a panel as the example:

  ```text
  tarot/                         # the folder name is the plugin's id
  ├── moss.json              # the manifest (§5.9)
  ├── skills/spread/SKILL.md     # a skill (data)
  ├── theme/theme.json  theme.css   # a theme, as data (§5.5)
  ├── client/index.tsx           # optional: React components (code)
  ├── host/index.ts              # optional: runs in the plugin host (code)
  ├── assets/cards.webp  fonts/ …
  └── plugins/                   # optional: child plugins
      └── tarot-panel/
          ├── moss.json      # id tarot/tarot-panel: a panel in MOSS Code's window
          └── client/index.tsx
  ```

* **[P] Ids:** lowercase letters, digits and single hyphens (`^[a-z][a-z0-9]*(-[a-z0-9]+)*$`), 2–40 characters, so there is never a `_` or `.` and tool names always split cleanly (§6.7). The folder name must equal the id; a mismatch is not loaded, and the app offers a one-click rename.
* **[P] What ships:** one read-only plugin in the apps' resources, `moss`, which holds everything we ship, as children. Alpha is not a plugin: she is a bot MOSS offers as a default (§6.2).
  * MOSS Code's window: the shell, sidebar, conversation view, composer, panel host and its panels (terminal, diff, files and the browser view), settings screen, plugin index browser and the archive of old Winter sessions
  * the island and the Dispatch pill, with the island's Needs you, Devices and Usage tabs (they run on the background host, §3.4)
  * the web and browser tools (`mcp__moss__…`)
  * one model plugin per current provider
  * Fish Audio, the avatar plugin with its VRM and Live2D renderers (item 87, §10) and the base theme, which MOSS Code's window uses until the user picks a theme (§5.5)
  * the schedule and webhook triggers, the waifucave forwarder, two relays (n0's public relays, on by default, and the cloud computer relay, off until a cloud computer exists), and the Google Cloud and Hetzner providers
  * the iOS and web companions, waifucave push and desktop notifications
  * the agent backends: Claude Code, Codex, Grok, Gemini CLI, DeepSeek, Cursor, Antigravity CLI, Devin and Winter's coding agent (§9.3)
* **[D] The engine asks when it finds a new plugin,** and the card is drawn where the router places it (§3.5). A folder that appears in the plugins directory loads only after the user's OK, whoever wrote it; installs made through the app or the CLI were already confirmed there. **[P]** The OK says what the plugin is, and for a plugin with code it says plainly that it runs code on the user's computers (§5.6); on Windows and Linux it adds that this code could read MOSS's logins and approve its own cards (§5.2), **[P]** and, since any desktop answers another computer's cards (item 91), approve actions on the user's other computers. One card covers a plugin and its children, with a checkbox per child. The OK is bound to the tree's hash, so other devices don't ask again. A code change asks again, whoever made it (§5.6). An install counts as confirmed only when the user makes it in an app or in their own terminal; bots, agents and plugins can't act on the daemon's socket as the user (§3.1), so what they install is a found folder, and asks. **[P]** A bot installs with its `PluginInstall` tool, from its scratch or its conversation's outputs, and its OK names it as the builder (§5.6).
* **[D] The plugin is the only unit.** MCP servers, skills and agent definitions exist only inside plugins, and are **wrapped automatically**, so no one ever has to build a plugin by hand:
  * **Adding a bare item creates a plugin around it.** That covers a pasted MCP config, an MCP URL, `moss mcp add`, a bot adding a server, a dropped skill folder with a `SKILL.md`, or a Claude Code plugin folder (revision 14). MOSS generates a small plugin around it in the plugins folder, and from then on it installs, syncs, gets approved and is enabled like any plugin. The user can open and edit the generated plugin. **[P]** Wrappers are named `mcp-<server>` (one per server, with the server's name lowercased, each run of characters other than `a-z` and `0-9` turned into one `-`, cut so the id fits 40 characters, hyphens at either end then dropped (the same for `skill-`, `agent-` and `claude-` names), and a number added on a clash or for `moss` (`server` if nothing is left), and that name used for its tools: `mcp-blender` gives `mcp__blender__Render`), `skill-<name>`, `agent-<name>` and `claude-<name>` (a Claude Code plugin, whose name is also its namespace), and record how they were made.
  * **[P] Accepted as-is and wrapped:** `.mcp.json` entries, the Claude Code `mcpServers` JSON shape, agent-skill folders (`SKILL.md`), and Claude-style agent files (`agents/*.md`). **[D]** Claude Code plugin folders (`.claude-plugin/plugin.json`) are wrapped too, since every plugin is MOSS-shaped (revision 14). **[P]** The wrapper turns the plugin's skills and commands into `skills`, its agents into `agents`, its MCP servers into `mcpServers`, its hooks into Claude-style `hooks` (§5.3) and its `userConfig` into settings, and rewrites `${CLAUDE_PLUGIN_ROOT}` as `${plugin}` and `${CLAUDE_PLUGIN_DATA}` as `${data}`. Parts with no MOSS point yet (output styles, LSP servers, mods) stay in the folder unused, and the OK names them. **[P]** A folder is a Claude Code plugin if it has `.claude-plugin/plugin.json`, or no `moss.json` but `skills/`, `commands/`, `agents/` or `hooks/hooks.json`, where Claude Code looks for them; a folder with only `.mcp.json` is wrapped per server. Its name gets a server name's clean-up, and each command file becomes a generated skill folder. `${user_config.KEY}` becomes `${setting:KEY}`, or `${secret:KEY}` when the option is `sensitive`, and `directory` and `file` options become strings. As in Claude Code, its hook processes get `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA` and `CLAUDE_PLUGIN_OPTION_<KEY>`, its `stdio` processes the two paths, and both paths are filled in within its skill and agent text. A hook keeps its own timeout (600 seconds when unset). Unmatched hook events and types, `multiple` options, `bin/`, monitors, workflows, themes and `dependencies` stay unused too, and the OK names them.
  * **[D] A repo's own items are not wrapped.** MCP servers and skills a repo defines (its `.mcp.json` or skills folder) load only while a bot works inside that trusted repo. They are never installed, synced or shown to bots working elsewhere. **[P]** A bot works inside a repo while the turn's Bash folder, or a file tool's path, is in it; the repo's items then stay for the rest of that turn.
  * **[D] Every bot on every device sees every server.** Local servers (a `stdio` command such as Blender's, or plugin code bound to its computer, such as computer use) run on each computer they are installed on, and the user can mirror one to the other computers. Remote servers work from anywhere (§9.1). (Grok Bot also makes servers account-wide, but it has a single computer where they all run.)
  * **[P] Secrets stay out of the folder.** API keys and sign-in tokens go into the synced credential store, so a plugin folder can be shared or synced without leaking them. When the core wraps a pasted config, it moves every `env` and `headers` value into the credential store and writes `${secret:<name>}` in its place; the user can mark one as plain.
  * **[P] Settings:** a plugin's manifest declares its settings; the default shell shows them, and secret fields go straight to the credential store.
* **[P] Sign-ins:** any plugin may list `auth` for its own service. The core runs those sign-ins as it does a model's, the refresher refreshes them (§8.5), and the tokens reach the plugin's code only through the core's fetch, which adds them and reaches only the plugin's `network:` hosts; that is what the capability gates, for keys and tokens alike. Only a process of the plugin's own sees a value: a `stdio` server through `env`, or an adapter that must sign with it (§5.2) through `secrets.get` (§5.4). `${secret:<name>}` in `env` or `headers` names only the plugin's own secrets.
* **[P] Updates:** (the owner's ruling, 2026-11-13, replacing the automatic updates of answer E) plugins from an index or npm are offered updates, only forward, and nothing updates on its own, whatever the source: the Plugins page lists them and the user's click applies one (`plugin.update` with its id; from the page it asks on a sealed update card first). The OK for an index or npm plugin also covers a later version that adds none of the triggers in §5.6; one that adds a trigger waits for a new OK, so nothing new runs silently. The previous version is kept beside it (across restarts) until the new one starts, and comes back if it is refused or fails. Local plugins change only when their folder does; the bundled tree is the engine's and updates with the engine's release, the one release of everything (§3.1). Newer means above the version recorded at install, which must match the manifest's. A pin is this computer's alone, never synced: a pinned plugin isn't offered updates, holds against an asked-for update too, and the pin goes when the plugin is removed. Besides §5.6's triggers, an update that changes where its keys and calls go, its read-only tools, or its name or author asks again.
* **[P] Indexes and npm:** an index is a plain JSON file (`index: 1`) listing ids and versions, each with its tree hash and download URL. **[P]** (the owner's ruling, 2026-11-13, replacing the official signed index, its key in the app, the revocation list and "run anyway") there is no official index and nothing is signed: the user adds an index by its https URL, with no card (adding one runs nothing), and every plugin from it asks for its OK as any install does. A failed fetch keeps the last good copy. An npm install unpacks the package as it is: no install scripts run and no dependencies are fetched, so code ships bundled. It updates like an index plugin. The tree hash is SHA-256 over a sorted list with one line per file: its path in the plugin folder (with `/`), its executable bit and the SHA-256 of its bytes. It leaves out only `.DS_Store`, `Thumbs.db` and `.git/`, and a symlink out of the folder makes the plugin invalid. A version downloads as a `.tar.gz` whose tree hash must match the one its index lists.
* **[P] Live changes:**
  * On reload, the plugin's worker is replaced. Tool calls in flight get a grace period, then are recorded as interrupted; model calls retry; the client half remounts and loses its state.
  * A removal syncs as a delete, and the user's data stays under the plugin's id.
  * Bundled plugins, and children of index plugins, can only be switched off.
  * A refused plugin stays off until its folder changes.
  * Assets are served by hash, SVG with scripts off and never through a symlink, and Markdown renders without raw HTML.
* **[P] Formats:** the app reads every `manifest`, `theme`, `layout`, `locale` and `index` format it has shipped, and refuses a newer one with "needs a newer MOSS"; `moss plugin validate --upgrade` rewrites old ones. A plugin whose `engines.moss` range leaves out the app's plugin API is invalid, with the version it needs, and is checked again when the app updates. In `contributes`, an unknown key without a dot refuses that contribution, and a dotted one is a plugin point and waits for it (§5.4). A child that fails validation is invalid alone, and the rest of its tree loads.
* **[P] Entry ids:** every id that other plugins or files refer to (a model provider, voice provider, agent backend, trigger type or computer provider) is unique among enabled plugins. On a clash only that entry is refused, and the plugin enabled first, by the synced list's order, keeps the id. Theme and `ui` ids are unique within their plugin; elsewhere a theme is named `<plugin-id>#<theme-id>`. A reference to another plugin's entry is resolved when it is used, and a missing one turns off only that feature, with the reason.
* **[P] States:** Settings shows each plugin as found (waiting for its OK), refused, invalid, off, waiting (for a point or a setting), running or stopped (after crashes), with the reason. The registry reads a folder once it has been unchanged for 2 seconds and its manifest parses.
* **[P] Crashes and logs:** a crashed worker restarts after 1 second, the delay doubling up to 1 minute. After 3 crashes in 10 minutes the plugin stops on that computer, its tools answer "plugin stopped: <reason>", and Settings shows its last log lines until the user restarts it. A worker that misses the plugin host's heartbeat for 30 seconds counts as crashed. A folder holding a native module runs in a process of its own (§5.2). Each plugin logs to `logs/plugins/<id>.log`, which Settings and `moss plugin logs` show.
* **[D] Each plugin declares its scope: `bots`, `agents` or `both`.**
  * Scope covers a plugin's MCP servers, skills, agent definitions and hooks, and defaults to `both`.
  * **[P] One rule everywhere** (hooks, a bot's Glossary, MCP servers, an agent's bridge and the parts placed in an agent's own folders): `bots` reaches a bot's own sessions (its conversation, side threads) and the agents a bot delegates to, since they do that bot's work; `agents` reaches every agent, a bot's and the user's own coding sessions (§9.3), and no bot's own session; `both` reaches all of them.
  * **[D] No plugin ships a bot** (revision 19, item 101), so a plugin's scope is `bots`, `agents` or `both` and the `own-bot` scope is retired.
  * A plugin may also limit itself to certain agent backends (`onlyBackends`), for example only Claude Code. **[P]** An agent session on a backend the list leaves out gets none of the plugin's MCP servers, skills, agent definitions or hooks; a session the engine's own runtime drives (a bot's delegation on MOSS's own coding agent, the user's coding session) is on the backend `moss-code` (§9.4). Bots aren't agent backends: the list never narrows what a bot gets.
  * The user can override the scope in settings.
  * An agent definition can narrow which in-scope plugins its agent receives.
  * Bots stay equal: everything scoped to bots is visible to every bot.
* **[P] A plugin's UI half is React,** loaded into its own layer, in the program that shows its part (§3.4). What it can fill and restyle, and how layers work, are in §5.5.

### 5.2 Where plugin code runs

**[D] Named programs and folders outside the sandbox** (the owner, 2026-11-15: "Yes, named on the card"). A top-level plugin with a host process of its own may name, in `host.outside`, programs of the user's that its host half runs OUTSIDE the plugin sandbox with the user's own access (their sign-ins, their Keychain, their files, their network), through `outside.run`, which the daemon starts, and folders of the user's that its host process reads, read only (never the whole home or a folder that holds it, never the MOSS home, never one of the disk's top folders or anything under `/System`; the Keychain's files, the tools' credential files and the coding agents' sign-ins stay denied inside them, one list with the bots' secret places). Any plugin may ask, bundled or third-party. The OK card lists every program and folder by name, each with a warning, one line a program that says the plugin chooses its arguments and it runs with the user's own access; a change to either list is a change card. Only the named programs run outside; everything else the plugin does stays fenced. "Of yours" holds: a program inside the MOSS home, the plugin's own folder or a folder it can write is refused, by its path or found on the PATH (a PATH folder in one of those is skipped), and none runs in the MOSS home. A plugin that names a program has no tool that skips the card (`readOnly`, `contained`, `webSearch`, `webFetch`, the build's copy included): a tool is its code, which could run the program with what a bot hands it, so its card says its tools still ask. It is the door for any plugin that works with a tool installed on the computer (the usage readers' `codex` and `claude`, a git or docker integration).

**[D] (delegated, decided here).** Host halves run in a **plugin-host process**, separate from the daemon, with **each plugin in its own worker**. A plugin that needs Node or native modules, opensky for example, gets a process of its own. **[D] There are two plugin-host processes** (the owner, revision 18, item 84). The bundled `moss` tree's host halves run in one of their own, and every third-party host half shares the other. The core decides which from the plugin's install record, never from its manifest. Only `moss`'s process may use the waifucave account token and the per-computer keys (`keys.open`, §5.4), and the daemon's caller check tells the two apart (§3.1). **[P]** A plugin may also bring a **helper**, a native program such as opensky's, which the plugin host starts and supervises. OS permissions such as Accessibility and Screen Recording are granted to that helper. **[P] Not in this version** (the controller's ruling, 2026-11-13): nothing starts a helper yet, so validation refuses `helper`, and refuses `host.runtime: "node"` outside MOSS's own plugins, each saying what to use instead: Bun runs Node-style code (`node:` modules, npm packages), and a program of its own runs from a host half with `host.programs` (in a process of its own) or as a `stdio` server. The OK card never names a helper.

| | Where plugins run | What one broken plugin does |
| :- | :- | :- |
| Claude Code mods | Inside the Claude Code process | Can stall Claude Code itself; per-hook time limits contain it |
| Claude Desktop extensions (MCP servers) | One separate process each; the Blender extension runs as its own Python process | Only that extension dies |
| DeepSeek Harness | All plugins inside one shared Node host process | Can take down every plugin and the agent with it |
| **MOSS** | Two plugin-host processes (`moss`'s and third parties'), a worker per plugin; Node or native plugins in their own process | Only plugins die; the daemon and the bots keep running, and a third-party plugin can't take down the bundled ones |

Why not inside the daemon: a buggy plugin would freeze or crash the always-on daemon, and with it every bot on every device. Keeping plugins out of the daemon also enforces "plugins cannot replace the core" and checks declared capabilities at the boundary. The cost is a few milliseconds per call and roughly 40–60 MB for each shared host.

**[D] On macOS the plugin host is fenced away from secrets.** It runs as a separate signed binary, never as a re-run of the daemon's own (which the Keychain would serve), so it does not pass the Keychain's "this app only" check, and a macOS sandbox blocks it from the Keychain, as Winter's workflow workers are blocked today. A plugin gets only its own secrets, through the plugin API; workers in the shared host are not isolated from each other's memory. **[P]** So, on every OS, adapters never hold a key: a request that needs one goes out through the daemon, which adds the key or token (§5.1). An adapter that must sign with the secret (AWS SigV4 for Bedrock) runs in a process of its own. The SDK's adapter interface therefore hands adapters that fetch where Winter's hands them a credential store (`ProviderContext.credentials`).

**[P] On macOS every process that runs a plugin's code is fenced to its plugin** (B-M2's 2f, and the controller's rulings on #345): a plugin-host process, a supervised host, a hook's command and a stdio MCP server. Each one reads its plugin's tree, MOSS's run files and shared packages, and its Bun. It writes only its own data and temp folders (and `/dev/null`, `/dev/tty`, `/dev/fd`). It can't read the MOSS home or the user's home, the per-user temp and cache folders, the Keychain or credential files, can't reach any Unix socket but the DNS resolver and the ones it's named, and can't ask launchd to start anything. A hook or MCP server also reads the package managers' installs, keeps every cache in its own temp folder, and may run any program, fenced the same. **The session's project folders**, its working directories, are readable to a hook or MCP server of that session, and writable only when its plugin holds `project.write` (§5.4), bundled plugins included. The allow is added for each spawn from that session's own folders, which change only by the user's own act (the app's picker, `moss add-dir`, the phone). It never covers a home, a folder above one, or a folder holding a place where a write runs later or a tool's settings live (`~/Library`, `~/.config`, `~/.local`, `~/bin`, `~/.ssh` and the like). Writes are denied to anything in them that runs without the user running their project: `.git`, `.vscode`, `.idea`, `.claude`, `.moss` and the old `.clover` whole, `.mcp.json`, `.envrc`, `.gitconfig`, `.gitmodules`, shell start files and Git's `core.hooksPath` folder. The folders that hold any of these are write-denied too, so none can be renamed away and back. Credential files are neither read nor written. Last in every fenced process's profile, the places where a write runs later (§9.1's persistence list) and the fence's other places outside the MOSS home are write-denied in both their own and their real spelling, so a dotfiles project can't reach `~/.zshrc` through its real file.

**[P] On macOS every plugin process is its own TCC-responsible process** (the controller's ruling after #345). Each one starts through MOSS's spawn trampoline, which disclaims responsibility (`posix_spawn` with `POSIX_SPAWN_SETEXEC` and the disclaim attribute), keeping its pid, process group and descriptors. So a plugin process never inherits a privacy permission (Screen Recording, Accessibility, the microphone, the camera) granted to the daemon, the app or whatever started them. That covers plugin-host processes, supervised hosts, hooks and stdio MCP servers.

**[P] A privacy grant is held by a program, not a plugin.** Once responsibility is disclaimed, macOS judges each process by its own program: the one shared plugin Bun for hosts, and `sh`, `node` and the like for hooks and MCP servers. A grant the user approves for one plugin's process is therefore held by every plugin that runs the same program.
* **File grants (Documents, Desktop, Downloads, iCloud Drive) may be shared this way.** The fence already holds each process to its own folders and its session's project folders, so a shared grant opens nothing outside any plugin's fence.
* **Privacy services that aren't files are denied in every plugin profile, before TCC is asked.** So no plugin can raise a prompt or share such a grant. This covers:
  * the camera and microphone (`device-camera`, `device-microphone`);
  * Apple Events (`appleevent-send`);
  * screen capture;
  * location;
  * Contacts, Calendar, Reminders and Photos, through their Mach services and their data folders (and any Photos library, wherever it is).

  No plugin capability grants any of these yet; one that does needs its own row in §5.4.

**[D] On Windows and Linux, plugin code runs as the user** (revision 13; this replaces the narrow jail chosen in revision 12). Windows Credential Manager and the Secret Service have no per-app check, and a jail loose enough for plugins to work can't stop a plugin asking another program (a terminal, the Task Scheduler, a desktop service) to act for it; AppContainer, the strict kind, would have shut out computer use. So, as in VS Code, Claude Code and Devin, the sandboxes go on what the models run (bots' Bash, §9.1; coding agents' commands, §9.3), and code the user installs is trusted: a plugin's OK there says its code could read MOSS's logins and approve its own cards (§5.1), **[P]** and approve actions on the user's other computers, since any desktop answers another computer's cards (item 91, §5.5). Computer use is plugin code like any other and needs no exception. **[P]** On macOS the plugin host's sandbox also blocks the daemon's socket; on every OS the host talks to the daemon over the pipe it was started with.

**[P] Where each contribution runs:**

| Contribution | Runs on |
| :- | :- |
| `skills`, `agents`, themes and layouts | data, on every device |
| `models`, `hooks` | every computer running a session (§6.4); started when first needed |
| Local MCP servers: `stdio`, and `host` servers bound to their computer | each computer they are installed on (§9.1) |
| Remote MCP servers: `http`, and every other `host` server | the computer running the session, or the one that holds a call's `saveTo` folder (§9.1) |
| `triggers` | each computer, started at once |
| `computerProviders`, `notifiers`, `companions`, `commands` | the main, or the takeover computer while the main is offline, unless the entry's `runsOn` says otherwise (desktop notifications say `each`) |
| `relays` | every device that uses them; a relay a computer serves (the cloud computer) runs there |
| `agentBackends` | the computer the agent is placed on |
| UI | the place its spot names: the background host, or MOSS Code's window (§3.4) |
| Entries for a point a plugin declares, other than UI spots | wherever the declarer runs (§5.4) |

**[P] `platforms`** (the controller's ruling, 2026-11-13): a plugin whose `platforms` leave a computer out is off there after its OK, which is the ordinary card: its host half never starts there, its components and tools aren't offered there, and its state says "Not for this computer: it supports <list>". Routing a call to a computer it supports needs the synced list between the user's computers (parked with `plugin.setComputers`). A plugin's host half starts on a computer when one of its contributions runs there, or at once where its `host.start` says, for a plugin that runs a service of its own. **[P]** `host.start` and every entry's `runsOn` mean the same thing: `each` is every computer (for a command, the one it is called from), `main` is the main or the takeover computer while the main is offline, and `chosen` is the computers the user ticks, as for local servers (§9.1). An entry with no `runsOn` runs where the table says. **[P]** The computers ticked for `chosen` are an account setting, synced with the installed-plugins list (§8.5); a new plugin starts ticked on the computer it was added on. **[P]** Until that synced list ships (parked with `plugin.setComputers`), `chosen` is the computer the plugin was added on. A `main` host half waits until this computer knows who the main is, and is let go (its calls fail, and it starts again on its next use) when this computer stops being the main. A host half the user or the crash rules stopped stays stopped. **[P]** The OK card says when a plugin runs without being asked: "It runs in the background from the moment MOSS or MOSS Code starts", on every computer it's installed on, on the main computer, or on the computer it is added on; a plugin with `triggers` (which start at once on each computer) also says it adds routine triggers. **[P]** On macOS a helper is a signed `.app` started through Launch Services, so OS permissions attach to it.

### 5.3 Extension points

**[D] Plugins have no kinds.** A plugin contributes to **extension points**, which are named places to plug into. **[P]** The core owns a fixed set, listed below; plugins declare the rest (§5.4). The test for a core point: it exists only where the core itself reads or calls what is contributed. So the core gains a point only when one of its own parts must read or call a contribution that the plugin API can't reach: the turn loop, tool dispatch, the routine engine, the links, the list of remote calls, the protocol's command method, the computer registry, the credential store, or the app's main process, plugin runtime, audio, theme engine and sealed frames. Everything else is a point some plugin declares. **[D]** Every point belongs to a place (§3.4): the window's, the screen's or the engine's. A new core point is a minor version of the plugin API, and no core rule names a point a plugin declares, or any plugin but `moss`.

**[P] Daemon core points** (the daemon reads or calls them):

| Point | Shape | What the core does with it | Data or code | Ships with |
| :- | :- | :- | :- | :- |
| `models` | list, one per provider | Calls the adapter, or the declared endpoint, for every turn; the welcome guide reads the sign-in methods (§3.3) | code, or data for a compatible endpoint | every provider Winter has today [D] |
| `mcpServers` | named servers | Dispatches tool calls, builds the MCP block and shows MCP Apps pages (§5.5, §6.1, §6.7) | code (`host`, `stdio`) or data (`http`) | the **web** tools, `mcp__moss__WebSearch` and `mcp__moss__WebFetch` [D]; `mcp__moss__Browser` [P]; computer use later, as **opensky** [D] (`mcp__opensky__…`, or `mcp__moss__…` if it ships as a child of `moss`) |
| `skills` | list | Indexes them in `Glossary` (§6.8) | data | — |
| `agents` | list | Offers these presets to `Agent`: backend, model, effort, instructions, default computer and root folder, which plugins it gets (§9.3) | data | — |
| `agentBackends` | list, unique id | Starts agents for `Agent`: an ACP agent or a vendor cloud agent (§9.3); in-process subagents are a core backend (§14.2 item 15) | code | Claude Code, Codex, Grok, Gemini CLI, DeepSeek, Cursor, Antigravity CLI, Devin, Winter's coding agent |
| `hooks` | list | Calls them in the turn loop: before and after a tool call, messages in and out, turn start and end, compaction. | `commands` [P] | list, unique name | Runs a plugin's public functions for any client at once, with no model turn (§5.4) | code | — |

| `companions` | list | Serves a remote client within the fixed list of remote calls (§10) | code | **iOS app** [D], `clover.waifucave.com` |

**[D] There is no `bot` point** (revision 19, item 101): bots are engine data (§6.1), and no plugin ships one.

**[P] Hook order:** `tool.before` hooks run first. The reviewer, the fences and the approval check then judge the input as the hooks left it, as in Winter, and nothing changes an input after it is approved. `tool.after` hooks change only results. **[P] What each event may return:** `tool.before` may deny, ask or replace the input, never allow; `tool.after` may replace the result; `message.in` may replace a message's text before the model sees it, the user's or one that folds in, and `message.out` the bot's text before it is stored and shown, so while a `message.out` hook is on, replies show and are spoken only after it runs; `turn.start` may add a labelled note to the turn; `turn.end`, `compact.before` and `compact.after` only observe, and **[P]** `turn.end` is told how the turn ended (`outcome`: `completed`, `failed`, or `interrupted` for a turn the user stopped or that was cancelled). Hooks on one event run one after another, in the order of their plugins' ids, each seeing the last one's output. A hook that throws or runs past its `timeoutMs` (default 10 seconds) is skipped, and Settings shows it. **[P] Handlers.** A `host` server is an MCP server built with the official MCP SDK on an in-process transport the plugin SDK provides. A hook handler gets `{ event, session, bot, computer, tool?, input?, result?, text? }` and returns only what its event allows. A hook's `command` speaks Claude Code's hook protocol (JSON on stdin and stdout, exit code 2 to deny) under Claude Code's event names where one exists (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact`, `PostCompact`), and the core ignores an `allow`. `tools` lists exact names, or patterns with `*`. **[P] What hooks cover:** a bot's own calls, and its delegations' (a hook scoped to `bots` covers the agents a bot starts, and an in-process agent's calls meet the hooks in its own runtime), but not what an external coding agent such as Claude Code or Codex does inside its own session: there `tool.before` sees only the requests the agent asks MOSS about (a deny refuses the request) and never the calls it runs without asking. A hook can refuse starting such an agent, since the bot's `Agent` call names the backend, and the OK says what hooks see and that they don't see inside a coding agent.

**[P] Window and screen core points** (the plugin runtime of the program that shows the part reads or calls them: MOSS Code's window for the window's, the background host for the screen's, §3.4):

| Point | Shape | What the app does with it | Data or code | Ships with |
| :- | :- | :- | :- | :- |
| `themes` | list, unique id in its plugin | Applies the base theme, the user's global theme (the base theme until the user picks one) and the themes that plugins dress parts with (§5.5) | data | **the base theme** [D], in `moss`, which MOSS Code's window uses until the user picks a theme |
| `app.root` (a UI spot) | single | Mounts MOSS Code's main window's root: the shell, which declares every other spot (§5.5) | code | **the default shell** [D] |
| `app.surface` (a UI spot) | list | Opens top-level floating windows on the screen, on the background host | code | **island**, **Dispatch pill** [D] |
| `app.background` (a UI spot) | list | Runs parts that have no place in a window, in a hidden window of their own on the background host | code | nothing bundled; any plugin |
| `app.tray` (a UI spot) | list | **[P]** Adds a line to the menu-bar menu (F4; the host's menu, item 112): `toggles` an own surface, or runs an own `command`; needs `tray` | data | **Dispatch pill**'s Hide / Show |
| `locales` | keyed by language | Supplies the strings for the core's own text, sealed cards (from trusted packs only) and the welcome guide included, and for each plugin's keys, in the user's language (§5.5) | data | English, built in |

**[P] Bundled tool names, for now:** until the agent runtime lets the host add tools to its standing `moss` server (or names that server differently for bot sessions), a bundled plugin's tools are `mcp__<server>__…`, its server's own name (`mcp__web__WebSearch`, `mcp__web__WebFetch`), not the `mcp__moss__…` this section and §6.7 give. The runtime keeps `moss` for itself and won't start a session that configures a server under it; the request is in `docs/research/2026-11-10-agent-sdk-host-tools-in-standing-server.md`.

**[P] Data, web or code** is worked out from the manifest, never declared, and the OK shows it (§5.6):

* **Code:** the plugin has a `host`, `client` or `helper` part, or a field that names something to run: a `stdio` server, a hook's or agent backend's `command`, or a field whose format is `program` or `code` (§5.4). Every handler, adapter, custom sign-in and component is an export of `host` or `client`, so this rule names no point a plugin declares.
* **Web:** no code, but a UI part that shows a web page in an isolated view (§5.5).
* **Data:** everything else: JSON, Markdown, images, audio, VRM and GLB files, fonts, cleaned CSS and layouts.

The network hosts a plugin talks to are listed separately, whatever its class: its `network:` capabilities, plus the host of every field whose format is `url` (an `http` server's `url`, `endpoint.baseUrl`, the `auth` URLs, `web.url`). **[D]** The plugin's components can reach only those hosts (revision 14), except through WebRTC (below): the core serves each plugin origin's documents and workers with a Content-Security-Policy listing only those hosts, as Figma does, and the layer's session refuses other requests that origin starts (`initiatorOrigin`); together they stop every request-based way out (S9). **[P]** Plugin documents and worker scripts also carry `Connection-Allowlist`, which drops ICE servers and closes DNS prefetching, and DNS prefetching and speculative hints (preconnect, prefetch, prerender) stay off, since they can reach a host before `webRequest` or the CSP sees the request. **[P]** As defence in depth, plugin webContents also get Chromium's `disable_non_proxied_udp` WebRTC policy. Together with `Connection-Allowlist` it read zero on every vector that had a positive control in S9's runs. These closures are per document or per webContents, so the MOSS Browser keeps WebRTC. **[D] WebRTC is a documented known gap** (the owner, revision 18, item 94; this replaces "WebRTC is off in plugin origins"). In stock Electron a directly mounted plugin document can still try to send WebRTC connectivity checks (remote ICE candidates), carrying text it chose, to an address it never declared, and no stock configuration is proven to close that: the TCP route had no positive control, and the sandboxed srcdoc was never tested with both measures on. MOSS ships stock Electron, so the gap stays documented until an upstream Electron's Chromium closes it, and S9's check runs again on every Electron upgrade. **[P]** S9's PAC belt and its preload stub are both off: the PAC broke the plugin's declared host on Ubuntu and, on a shared session, would let every plugin reach every plugin's hosts, and the preload never reached the out-of-process plugin frames. Isolated web views stay open, since a site loads from many hosts; the OK says so. **[P] Host code is held to the list too** (B-M2's 2g; this replaces "host code isn't held to the list"): every process that runs a plugin's code (its host process, supervised host, hooks and stdio MCP servers) reaches the network only through its tree's own loopback proxy in the core, named in `HTTPS_PROXY`, `HTTP_PROXY` and `ALL_PROXY`. The proxy passes a CONNECT tunnel, or one plain HTTP request per connection, only to a host and port the tree's `network:` grants name (`<host>` on 443 and 80, `*.<domain>` for subdomains only, `<host>:<port>`, a raw address only when named), reading the grants at each connection, and answers anything else `403`. On macOS the fence denies every other outbound address and socket and the resolver's services, so the proxy resolves names and the process can't; a process with no proxy has no network. The `moss` tree's proxy passes the union of its plugins' lists, since they share a process. **[D] A wrapper the user brought reaches any host** (the owner, 2026-11-10): a plugin the core generates around an MCP server's config or a Claude Code plugin folder (§5.1) declares no hosts, so its stdio servers and hooks reach the whole network, with no proxy, fenced for files as any plugin's process is. The grant is the install record's (`wrapped.network`), never the manifest's: the OK states it in MOSS's words, `plugin.get` shows it and the fence reads it. Once the plugin's tree declares a `network:` host (the user edited the generated plugin, which asks for its OK again as any tree change does), it is held to those hosts like any other plugin. A plugin that isn't a wrapper and declares no hosts reaches nothing. **[P]** A listed name is resolved by the proxy and connected to by the address it checked, and a name that resolves to a loopback or private address is refused unless the name says it's local (`localhost`, `*.local`), whose grant the OK names; the core's keyed fetch sends by the same rules. Each proxy takes only requests carrying its own random token (in the proxy URL its processes get), so a plugin granted `localhost` can't use another plugin's proxy by its port; macOS lets a process read the environment of another non-platform process of the same user (`KERN_PROCARGS2`, which no Seatbelt rule closes without breaking Bun), so the token alone stops a borrowed port, not a plugin that reads another's environment. **[P] The mitigation is the `restrict` code-signing flag** (the controller's ruling on #377): the daemon and the plugin Bun are signed with it, which hides their environment, the proxy token and the core's own included (lane M). **[P] A third-party stdio MCP server's environment stays exposed:** its program (`npx`, `uvx`, `node`, `python`, …) isn't MOSS's to sign, so a secret given to it through `env` is readable by other plugins' processes on that computer. The OK says so for each such server. **[P]** Where a server can read its key from a file, the manifest names `${secretFile:<name>}` in its `env` or `args` instead, and gets no such line: the core writes the secret to `<home>/run/plugin-secrets/<plugin>/<server>/<instance>/<name>`, mode 0600 in folders of 0700 that must be real folders owned by the user (never a link planted there), through a fresh name renamed into place, and passes that path. Each running instance of a server has its own folder, so one stopping never takes another's keys. The plugin's own fenced processes read that folder and none writes it; no other plugin's fence lists it. It isn't in the plugin's data folder, which the plugin writes and could plant a link in. The file goes when its instance stops, on every stop path, when its plugin is removed, and at every daemon start. Trust is per plugin: a plugin's hooks and its other servers read the same folder, so they can read each other's key files, as they could ask the core for the same secrets. The proxy limits connections (256 in all, 64 per tree), a request head's time (10 s), resolving and connecting (30 s) and idle time (5 minutes), and pauses a sender rather than holding more than it bounds. It judges only the CONNECT line's host: inside a granted host's TLS a client can name any server that host serves (domain fronting), and a tunnel already open outlives a revoke until it closes. Names are matched as ASCII; an internationalised one is granted in punycode. Scripts inside skills are not plugin code: a bot runs them with `Bash` under the computer's approval level, and the OK says so.

**[D] No plugin ships a bot** (revision 19, item 101; this replaces November 3's "a bot's plugin may carry code"). A bot is engine data (§6.1), so it has no plugin, no tab and no UI of its own; a plugin with code is code whatever it contributes.

**[D] Computer use is not special.** A computer-use plugin contributes an MCP server, plus a helper when it needs one (opensky's native helper). Several can be installed at once, each with its own tool names, and they drive browsers too, the MOSS Browser included (§12.1). Both apps use it through the engine (item 104).

**[P] What became of the old kinds:** `tool` is the point `mcpServers`, `ui` is the UI spots (§5.5), `surface` the spot `app.surface`, `avatar-renderer` a point of the bundled avatar plugin (§10), and `webhook-ingress` the point `webhook.ingress`, which the webhook trigger declares (§7). A cloud computer folder gets the new point `computer`. Every other kind became the point of the same name.

### 5.4 Plugins that host plugins, and the plugin API

**[D]** A plugin may declare its own extension points, and other plugins may contribute to them. For example:

* The **island** plugin declares `island.tab` (with its requirements: size, idle state, attention rules), and other plugins add tabs such as Usage, Devices or Servers.
* The **Dispatch pill** declares `pill.target`. The pill targets what the engine has, every bot and every session, whichever apps are installed (F9), and plugins can add others.
* The **webhook trigger** declares `webhook.ingress`, and the waifucave forwarder fills it (§7).

**[P] How it works:**

* A point is declared in a `declares` field, on any contribution or on the `host` part, with its shape (`single`, `list` or `keyed`), its fields and props as JSON Schemas, and a short description. It exists while the contribution that declares it is active; a point the host declares exists wherever the host half runs, so such a host sets `host.start` (§5.2). A UI spot exists while the entry that declares it is active, and waiting and Settings go by that; it is mounted only while that entry's component is on screen, so several can be mounted at once, such as two windows that each have a `composer`.
* A point whose declaration has `props` (what it hands each component; `{}` for nothing) is a UI spot: only a `ui` entry with a `component` declares one, and it is filled through `ui`. Any other point a plugin declares is filled with a top-level key in `contributes`, and its name always has a dot. New names start with the declaring top-level plugin's id and a dot (`luna.cards`). The well-known names the plugin SDK publishes (§5.6), such as `composer`, `island.tab` or `webhook.ingress`, are exempt, and a plugin that declares one must use the catalog's schema, or it is refused. A `private` point is open only to the declaring plugin's own tree.
* Hosting and packaging are separate. A child plugin does not plug into its parent automatically, and any plugin can fill another plugin's point. A host may ship its default guests as children, as the island ships its Needs you tab. A plugin that fills another plugin's point is still an ordinary plugin, which MOSS installs, syncs and approves like any other; only add-ons in a format of a plugin's own are outside MOSS (below).
* A contribution whose point is missing waits, and Settings says what it is waiting for ("waiting for `island.tab`"). Contributions start as their points appear, and stop before the plugin they depend on does.
* **Point schemas:** an entry is checked against its point's schema when the point appears; one that fails is invalid, with the reason, and the rest of the plugin runs. When a point appears, or its declarer's update changes the schema, and an entry's values then name a program, code or a host its plugin's OK didn't list, that entry waits for a new OK, as an update adding them would (§5.6). A format in a schema tells the core what a value is: `path` (a file in the plugin, handed over as an asset URL), `url` (its host is a network host, §5.3), `handler` (an export of `host.entry`), `component` (an export of `client.entry`), `program` (a program to run) or `code` (a folder of code). A point other than a UI spot has one active declarer; a second one waits ("declared by …") until the user picks between them. Points change only compatibly: new fields are optional, a breaking change takes a new name (`luna.cards2`), and `deprecated` marks the old one in Settings, `validate` and `Glossary`.

**[P] The plugin API.** Every host half and component gets one object from the plugin SDK (§5.6), and nothing in it names a kind of plugin:

* **Points:** a declarer reads its point's entries (`points.entries`, with paths turned into asset URLs), hears them change (`points.watch`) and calls an entry's handler (`points.call`). The handler runs in the contributor's worker, on the declarer's computer. A plugin's events are points too: listeners contribute handlers, and the declarer calls them.
* **[P] One at a time** (the owner's general capability P4, 2026-11-15): a point, in the platform's catalog or declared by a plugin, may say `oneAtATime: true` (a plugin's with a `title`, on a list or keyed data point; a UI spot draws every filler, so it can't say it yet; a core point's flag and title would be in `CORE_POINTS`, and none is marked as shipped; MOSS Voice's own `moss.voice.modes` is one, titled "Voice", which it fills itself). Its fillers are its entries whose plugins are on and running, in the synced list's order; one of them is active: the user's choice while it runs, else the first bundled filler, else the first installed. The choice is kept with the registry's records (`installed.json`), outlives its plugin being off, stopped or crashed (it is active again when it runs again), and goes with its plugin's removal. When the active one stops being a filler, the next takes over and the user is told once, in words, under the point's declarer. `points.active(point)` answers the active entry as its plugin and entry id (never its value), and `points.onActive(point, listener)` hears it change; the declarer's tree reads it, and so does a plugin of a tree with an entry in it (a filler learns whether it is the one). Only the user changes it: Settings draws one picker per one-at-a-time point with two or more fillers, from the registry, titled by the point's own title (`point.active.list`, `point.active.set`, the user's own); no plugin's call or setting decides it. `points.entries` still lists every filler.
* **[P] What a point gives its fillers, on their OK cards** (`fills`, F1's review, 2026-11-15): a point's declaration may carry the line its fillers' OK cards show, `fills: { ok, warns? }` (a plugin's in its `declares`, a core point's in `CORE_POINTS`). A plugin with an active entry in such a point gets one line per point on its own card, attributed to the declarer so it can't pass as MOSS's words: `Fills <declarer's name>'s (<its id>) "<the point's title>": <ok>.` (the id alone when the name is empty or is the id; a core point's by "MOSS", with no id; `warns`: the line starts with "Careful: " and comes first). The words are the declarer's, made plain (control, line-break, zero-width, direction-mark and direction-override characters to spaces) and at most 300 characters, shown as text; the declarer's own tree and a point with no `fills` get none. The lines are kept with the OK: a card that gains one asks the user again, whether the filler added the entry (an edit or an update) or the declarer changed its words (the registry reads its fillers again, and the very tree it was OK'd for asks again). A declarer's own change of its `fills` words is its own trigger too: an update or a workshop edit that changes them waits for the declarer's OK first.
* **Commands:** a command is a plugin's public function, named `<namespace>.<name>`, with a JSON Schema for its `args` and a JSON result. The user runs one from the app (the command palette, or a button that names it), the CLI (`moss run <namespace>.<name>`) or the iOS app, and **[D]** another plugin runs one only with `call:<plugin-id>`, which its OK lists (revision 14). Callbacks and events go the other way, through points. **[P]** `call:<plugin-id>` names a top-level plugin and covers its children, whose commands share its namespace, and command names are unique within that namespace. A call to a plugin that isn't installed fails at once with "not installed". Its `key` is a default shortcut, bound while MOSS Code's window has focus, and the user can rebind it; a core shortcut or the user's own binding wins over it. **[P]** A key binding may ask for the key's release too (`hold: true`, with `key` and no `args` of its own, never on a text-editing key: the arrows, Home, End, Backspace, Delete, Enter, Tab; 2026-11-16): the main process, which sees each key go down and up, runs the command with `{ key: "down" }` when its chord goes down (a held key's repeats are no new press) and once with `{ key: "up" }` when its key or any of its modifiers comes up (another key's up is not it; the up waits for the down's call); a hold that ends with no release of the user's (the window loses the focus or closes, or the chord's key goes down afresh without its modifiers after an up that never came, which then reaches the page as an ordinary press) runs it with `{ key: "cancel" }`, which gives nothing. A held command runs only from its key: `command.run`'s `held`, which only the connection of the program that saw the key may send, from its main process, and no route of a part's sets; the CLI, the palette, a session or another plugin is refused ("a held command runs only from its key"). The chord, its repeats and its key's up are kept from the page (a modifier's up is not): its key's up by main, its down and repeats by the app's preload in the focused frame, before any page listener (main answers it which key-down is the held binding's), since Chromium drops every key-up that follows a key-down the browser handled. It is active wherever a key binding is: while MOSS Code's window has focus, not while a sealed card or the key dialog's secret field does; there is no narrower scope. **[P]** Plugin key bindings and held commands apply in MOSS Code's window only, and the down and up of a held key come only from the main process of the program that saw the key, never from a plugin part. MOSS has its own built-in microphone button and talk key, which are no plugin's binding (item 113). That release counts as the user's press for the binding's owner (`user.send`, below), and for nothing else.
* **Its own host:** a component calls its plugin's handlers (`host.call(name, args)`) and hears what its host half sends it (`host.on(event)`). A call runs on the component's own computer, where the host half starts with the component (§5.2), unless `platforms` leaves that computer out; then it runs on the main, which starts it if needed. **[P]** A component reaches only its own plugin, on its plugin's own connection (the core takes the plugin from that connection, never from the call): its `host.call` reaches only the functions its host half lists for its components (`export const ui = { … }`), never a tool's, hook's, command's or trigger's handler, and runs as the plugin, never as the user, with no session, so it can't press, approve or act as the user; it hears only its own plugin's `ui.send` messages and store changes; and it reads its synced store (`storage.synced.get`, `keys`, `watch`) but never writes it: its host half writes it, checking what a component hands over first. A store key is a plain name (letters, digits, `.`, `_`, `-`, at most 128, not starting with `.` or `moss.`, no `..`), and each plugin's store is its own. A connection that falls 4 MiB behind is ended, and the app opens it again with its subscriptions; the app hands a plugin's own messages and store changes to its documents latest-wins per topic or key (a part that needs every message in order is a case the avatar plugin raises; the order of speech cues stays open, item 122). A component's calls are capped at 64 KiB each and 20 a second per plugin; `ui.send` at 64 KiB and 50 a second; a store key's change reaches the components at most once every 100 ms, the last always. Nothing sealed or card-related crosses it.
* **Storage:** each plugin has a data folder on each computer (`<home>/plugin-data/<id>/`, `${data}` in `stdio` arguments), never synced, kept when the plugin is removed, and fenced from bots' writes (§9.1), and a synced store of up to 1 MB. Neither sits in the plugin folder, so neither changes its hash.
* **The keyed fetch:** `net.fetch(url, init, { auth })` goes through the core, which adds the named `auth` entry's key or token (the only one, by default), reaches only the plugin's `network:` hosts, refuses a redirect elsewhere, streams both ways with no time limit while data flows, and after a 401 gets a newer token from the refresher and retries once (§3.3). A process of the plugin's own that must sign (§5.2) reads its secret with `secrets.get(name)`; a worker can't. **[P]** Where the key goes is never chosen per call. The core takes it from the `auth` entry's `placement` (§5.9), one of a fixed list: `authorization` with a scheme (`Bearer` when none is named), `x-api-key`, `api-key` or `x-goog-api-key`. It refuses a request that sets that header itself, and strips from every response it hands back, redirects and 401s included, each header whose value holds the key. The SDK's model adapters follow the same rules.
* **The account token and per-computer keys** (only in `moss`'s plugin-host process, item 84): **[P]** a bundled plugin's keyed fetch can add the user's waifucave account token (`auth: "waifucave"`), sent only to the `*.waifucave.com` hosts in its `network:` list, and `keys.publicKey(name)` and `keys.open(name, …)` give it a key pair per computer whose private half never leaves the core (HPKE base mode, never synced). The forwarder opens webhooks with it (§7).
* **Settings:** `settings.get` and `settings.watch` read the plugin's own values, and `settings.set` changes them, from its host half or its components alike; a plugin changes only its own values, and the core's settings change only as §5.5 says. **[P]** A component reaches them on its plugin's own connection (`plugin.layer.call`'s `settings.get` and `settings.set`, the plugin the connection's), every part alike, the bundled tree's too: at every scope, as the host half does (F2: `settings.get(key, { bot })` and `settings.set(key, value, { bot })` for a `bot` field, any bot); a read gives a `secret` field only as whether it is set, and a change, with no card, is never to a `secret` field (only the app's key dialog sets one) or a setting written into what the plugin runs or reaches (`${setting:…}`), which only the user changes, on a sealed card; at most 30 changes a minute. Never another plugin's. The user's own change (the Plugins page, `plugin.settings.set`) is a different path: from a layer that method is a sealed card.
* **[P] About itself:** `plugin` is plain frozen data, not a call: the plugin's id, namespace and version, and `computer`, the name of the computer it runs on. Every plugin reads it, with no capability; no part of §5 gates the computer's name, as reads are open elsewhere (the controller's ruling, for the owner's sign-off).
* **Its components:** `ui.send(event, data)` reaches their `host.on`.
* **[P] Turns** (2026-11-15): a one-at-a-time queue the platform runs, for anything two plugins or two bots could do at once and should not (speaking, moving one figure, driving one tab, holding the microphone). In both halves: `turns.take(name, { limitMs?, note?, signal? }, onEvent?)` resolves when it is the caller's turn with `{ id, until, done(), extend(ms), lost }` (`lost` resolves `"limit"` or `"stopped"` if the platform ended it, never after `done`); `turns.done(id)`, `turns.extend(id, ms)`, `turns.state(name)` (the holder's plugin, note, since and until, and how many wait) and `turns.watch(name, listener)` (each change from now on). First come, first served; one holder per name. The platform ends a turn when its holder says done, when its limit passes (default 60 s; `extend` moves it on, never past 10 minutes from the grant), when the holder's frame is gone (its part removed, its document reloaded or asleep), its host process exits, its plugin stops (turned off, removed, stopped, crashed), or the app quits (for a frame); a take still waiting leaves the queue the same ways, and an aborted `signal` takes it out. Names: `<plugin id>/<name>` is the plugin's own and needs no declaration; another plugin may take, read or watch it only if the owner lists `<name>` in its manifest (`contributes.turns: [{ name, doc }]`), and is refused otherwise. Device-wide turns are in the platform's catalog (the SDK's `DEVICE_TURNS`): `device/speech`, one voice at a time on this device, behind `audio`; `device/microphone`, one recording at a time, behind `microphone`; more are added as features need them, as data. The queues live in the daemon (`packages/core/src/turns/`), so both halves of every plugin see one queue, and every grant, end and loss is one line in the daemon's log (`turns: …`). A take is a watch on the wire, so it ends with whatever ends the frame's or the process's watches; the app ends a frame's watches when the frame goes. A plugin may have at most 64 takes of one name and 256 over all its names held or waiting, and the computer 4,096; a take over a cap is refused with why. A take's note reaches the log and `state` with its control characters (C0, DEL, C1, line and paragraph separators, bidirectional overrides) turned to single spaces.
* **[P] Streams** (2026-11-15): a byte stream between a plugin's two halves, for media and files (speech audio from a provider to the player, microphone audio to a transcriber, a video editor's frames) where `ui.send`'s messages (64 KB, 50 a second) don't fit. No capability: a stream connects only one plugin's own halves, or a caller to a handler it may already call. In both halves: `streams.accept(name, (stream, meta) => …)` registers the half as an acceptor of `name` (it resolves a `ReadableStream<Uint8Array>` per stream, which acknowledges the bytes as they are read) and `streams.open(name, { meta?, signal? }, onEvent?)` resolves a `WritableStream<Uint8Array>` once an acceptor took it (`close()` ends it, `abort()` cancels it). A component opens to its host half and a host half to one of its components; when several halves accept the name, the newest registered one is picked (a reloaded frame replaces the old one), and none is a refusal that names why. Chunks arrive in order with back-pressure: the daemon buffers at most 256 KiB per stream, a `write` resolves only when its bytes fit, and it sends the reader chunks of at most 32 KiB while at most 192 KiB are unacknowledged (the SDK's writable cuts bigger writes; the readable acknowledges what is read). At most 8 streams are open at once per plugin (a points stream counts for its caller and its contributor) and a plugin's halves accept at most 16 names; a stream's `meta` is plain data of at most 4 KiB; a component's stream calls are not counted in its 20 calls a second, the credit is their rate. A stream ends when the writer ends it (the reader hears `end` after the last chunk) or either side cancels, when either side's watch ends (a frame gone, its host process exited, the app quit), when the plugin stops or the host half restarts, and when the daemon closes; the other side is told once, with why, and the daemon's log has one line for each stream opened and one for each ended, with its bytes. The low-level members (`streams.write`, `end`, `cancel`, `ack`) are what `open` and `accept` stand on: only a stream's writer writes or ends it, only its reader acknowledges. `points.stream(point, entry, field, args?, { timeoutMs?, signal? }, onEvent?)` is `points.call` for a handler that answers with a stream: the same entry, field and checks, a `ReadableStream` for the caller, and the contributor's handler may return a `Uint8Array`, an async iterable or a `ReadableStream` of bytes, which its host half pumps into the stream with back-pressure; a handler that fails or returns anything else errors the stream with why, and the caller leaving (cancel, abort, its watch ending) cancels the handler's call. The streams live in the daemon (`packages/core/src/streams/`); every endpoint is a watch on the wire, so a stream ends with whatever ends the frame's or the process's watches.
* **The caller:** every command, tool and point handler is told who called: the user and the client, a bot's or agent's session, or a plugin by id. Clients run commands through the core method `command.run`, with `command.list` for the palette, and a bot that runs one through the CLI runs it as the bot (§3.1). **[P]** A call a plugin makes while it serves a tool call acts as the session that made the tool call. The core binds that session from the tool call's own context, which the plugin host carries, and never trusts a caller the plugin supplies, such as a caller it writes into `_meta` (the controller's ruling R7).
* **Capabilities:** each one gates a fixed set of calls and live events, listed in the plugin SDK's reference and versioned with `engines.moss`. Without the capability, those calls don't exist for that plugin. **[D] No door checks a plugin's id** (the owner, 2026-11-15: "Yes, all with a warning"): any plugin may ask for any capability, the OK card is the gate, and a risky one says so in its line (the catalog's `warns`). A bundled plugin holds its capabilities because the build grants its manifest, with no card, which is the only thing "bundled" means. A plugin's MCP server says in its manifest which of its tools the approvals judge as a read (`readOnly`), a display-only call (`contained`), a web search (`webSearch`) or a page fetch (`webFetch`), each named on the card, and which tool it offers only while it holds a capability (`needs`); the core names no plugin's tools.

### 5.5 The UI and styling

**[D] Users can restyle anything in MOSS Code** (MOSS's window is built in, §6.10). Themes stack, lowest first [P]:

1. core defaults
2. **[D]** the base theme, which `moss` ships (revision 13)
3. the user's global theme
4. plugins that dress a smaller part, inside that part, style-only entries included (below)
5. the user's own overrides

**[D]** Revision 19 retires the bot's own theme and the steps that were scoped to a bot's tab (the owner's "more scoped wins" of November 14 with them): a bot has no tab in a plugin window (items 99 and 100).

**[P]** Settings picks the base theme, `moss`'s by default, as it picks the global theme. **[D]** Until the user picks a global theme, step 3 is the base theme too, so MOSS Code's whole window starts from it (revision 14).

Themes use design tokens first, and arbitrary CSS when tokens are not enough. **[P]** The plugin SDK publishes the token catalog: each token's name, type and default, with `card.*` the set sealed frames take. It is the one source of token names. **[P]** In CSS a token is the custom property `--moss-` and its name with dots as hyphens (`color.text.muted` is `--moss-color-text-muted`). A plugin's own tokens are `plugin.<top-level id>.<name>`, and in CSS the id's hyphens become underscores (`plugin.mcp-blender.glow` is `--moss-plugin-mcp_blender-glow`), so the map from names to properties stays one to one. **[P]** Tokens flow down, so a plugin that dresses a smaller part uses the colours around it unless it sets its own. CSS stops at the edge of a part that a smaller plugin dresses (CSS `@scope … to …`).

**[D] The whole shell is plugins,** as in DeepSeek Harness:

* The sidebar, session views, conversation view, composer and panels ship as **bundled UI plugins**.
* Any of them can be replaced, for example with a visual-novel-style conversation view.
* The panel's contents (the session view, terminal, diff, browser and files, and later an editor) are bundled plugins too, each its own, enabled by default and replaceable (item 83).

**[D] MOSS Code's default shell is laid out like Claude's desktop app** (its Code view; the owner, revision 18, item 83):

* the left sidebar
* the conversation, with runs of tool calls collapsed
* the composer, with model and level pills
* panel toggles at the top right
* a right panel holding the session view, terminal, diff, browser and files, each panel a replaceable plugin
* the settings modal and the language chooser

It uses its own marks, with no Claude logo, mark or wording.

**[D] Its look matches Claude's desktop app almost exactly** (item 86): radii, spacing, colours, borders, states and type, measured from the owner's screenshots, with its own icons (an open-licensed set), system fonts and wording. Controls follow the OS accent colour, and the product's colour appears only in its mark, which is the Shards kit's (**[P]**, revision 19, G8; this replaces item 86's pink). The left sidebar is its own plugin and translucent (the macOS sidebar material, Windows acrylic, solid on Linux), the top bar is semi-translucent, with the transcript scrolling beneath it, and two panels can be stacked.

**[D] Which panels a session gets** (item 90, revised in revision 19): MOSS Code has no bot tab, so the slim column of a bot's tab, its browser panel and the `agent` panel that opened a bot's agent beside it are retired. A code session keeps the full set: the session column, terminal, changes, files (rooted at the session's folder, §9.1) and browser. Bots have no file view (item 88); MOSS's side panel shows the bot's own screen, watch only (§6.10).

**[P] UI spots.** A UI plugin fills named spots. A spot shows one entry (`single`), every entry in order (`list`), or one entry per key (`keyed`). **[P]** In a keyed spot, an entry with no `key` fills every key that has no entry of its own; a `key` ending in `*` (`image/*`) fills the keys it matches, after exact ones. A plugin can replace one part and leave the rest alone: only the composer, say, or only the message bubble. **[D] It can also restyle a part or hide it without replacing it** (revision 14), so plugins style, add and remove parts. **[P]** An entry with only `style` (a theme-format file: tokens and cleaned CSS) restyles whatever fills its spot or key, inside that part, as step 4 of the theme stack. It is data, it does not compete to show, and several apply in the reverse of the order the rules below give, so the one that would win applies last; the core inserts each after the filler's own CSS and gives the part it dresses `contain: layout paint`, as a tab's root has. An entry with `hide: true` in a single spot or a keyed cell competes like any entry and, when it wins, shows nothing there; Settings can bring the part back. A key that its point's declaration lists in `keep` can't be hidden (the catalog lists `approval`, as item 70 says), and the 2-second fallback card still applies (below). The default shell declares the well-known spots, and the plugin SDK's catalog (§5.6) lists each one's shape, fields and props:

* `app.root` holds the shell, which declares `sidebar` (it lists sessions, not bots), `sidebar.app` (app buttons), `main` (keyed by route: a session, settings, plugins and an app page), `panel` (the panel host, keyed by panel: `session`, `terminal`, `diff`, `files` and `browser`; a key no plugin fills shows the host's placeholder; **[D]** an entry whose key is none of those ADDS a panel of the plugin's own, below), `panel.view` and `settings.section`.
* **[D]** A session's view declares `conversation` and `composer`, and the composer declares `composer.action` (keyed by action id, so one button can be dressed on its own). The spots that belonged to a bot's tab, `bot.tab`, `bot.header`, `bot.side` and `bot.stage` with its `avatar` spot and `bot.stage.action`, are retired (revision 19, items 99 and 100: MOSS's window is built in and bots are only in MOSS; **[P]** the list of spots retired is the controller's, G8).
* `conversation` declares `conversation.message`, keyed by `user`, `bot`, `tool`, `approval`, `question`, `routine-result`, `task-notification`, `agent-report` and `note`, and `tool.result`, keyed by tool name.
* The island declares `island.tab`, and the pill declares `pill.target`. **[P]** The island also declares `island.line` (the owner, November 14): a plugin fills it with `{ id, handler }`, and while no window of the product is focused (the owner's November 14 rule, in presence terms, §3.5) the island calls each handler (as that plugin, no arguments) and draws what it returns as one line of plain text (80 characters), an optional icon from a named set (`bolt`, `check`, `clock`, `info`, `sync`, `link`) and an optional progress from 0 to 1, in its own style, with the plugin's id beside it; the first line also shows on the closed strip, below the housing, unless a card waits. The island decides how many show (four, two from one plugin, in install order), how often it asks (every two seconds on the open Needs you tab, about every six for the closed strip's first line, never while a window of the product is focused, nothing when no plugin fills the point, and a sender that answers nothing a few times in a row is left alone until a plugin changes or a bot starts work) and how long a line lasts (as long as its handler returns it; a handler over 1.5 seconds or that throws shows nothing that time, and three failures in a row leave it alone for 30 seconds). A line never opens or raises the island, a plugin that is off or removed has no entry and so no line, and the OK says it puts a line of text on the island. Nothing in it needs `call:` or a capability.
* Parts also declare list spots for add-ons, so a plugin can add to a part without replacing it: `conversation.message.extra` under each message, **[P]** `conversation.message.action` (data entries, a title, an icon and a handler in the plugin's own host, that the conversation part draws as buttons in a reply's icon row, with no frame of the plugin's) and the shell's `status` bar. Wherever a file shows, the part declares `file.preview`, keyed by media type. The bundled avatar plugin declares its own pack point, so an avatar pack is a data plugin (§10).

A replacement for a container should declare the container's own spots (a new composer declares `composer.action`); otherwise what fills them waits, and Settings says why. **[P]** A component shows a spot with the plugin SDK's `<Spot name key props>`, and the core mounts each entry there, inline when it is in the same layer or as a frame from its own layer. An entry gets only the declared props (data, plus callbacks the core routes back) and the tab's resolved tokens, which its own CSS may override. A declaration lists the capabilities its props carry data for (`needs`; the catalog sets the read for the kind of data a part shows: `sessions.read` wherever a code session's messages show in MOSS Code's window, `conversation.read` for a part that shows bots' conversations), and an entry whose plugin lacks one isn't mounted there. A callback that sends a message counts as the user's only when it uses up the frame's transient user activation from a key press or click the app saw come from the hardware, as for sealed buttons (below). One such key press or click covers one send, and any other send is the plugin's (§5.4). **[P]** The `composer` spot hands its entry, whichever plugin's it is, more than a send: the models its session can switch to, a model switch, and interrupt and stop. The core decides each one from the mount it made (which entry sits in the spot, for which session) and, for each that acts, from the key press or click it saw, one for one call. The bot tab's layout is retired with the tab; the layout format stays for MOSS Code's window (item 121). The user can hide and reorder the entries in a list spot. A whole new shell goes in `app.root`, and part replacements keep working inside any shell that declares their spots. A shell that breaks the app is what safe mode is for (§5.8).

**[D] Whoever owns a plug sets the rules for what plugs into it** (the owner, November 14; revision 19 removes the plug a bot had). There is no "bot plugin" type and no "app plugin" type. A plugin is a box of things, and each thing follows the rules of what it plugs into: a tool or a skill goes to bots and coding agents, an island tab or an island item follows the island's rules, a part of MOSS Code's window follows the window's. **[D]** MOSS has no plug: its window is built in (§6.10) and no plugin changes its interface. A bot has none either: no top bar, no right panels, no tab and no stage of a plugin's making (items 99 and 100).

* **[D] A plugin can keep a part running in the background** (the owner, November 15: no infrastructure in the core or the app that only one plugin uses). A `ui` entry at `app.background`, `{ "spot": "app.background", "id": "player", "component": "Player" }`, is a component of the plugin's client with no place in any window. The background host mounts it in a hidden window of its own (one per part, never shown, never focused, never in the task switcher) while the engine runs the plugin, so it outlives every window (closing and reopening one changes nothing), is never put to sleep, and its timers, animation frames and sound are not slowed while nothing is on screen. It goes when the plugin stops, is turned off or removed, and it reloads when the plugin's files change. At most two per plugin. A background part plays sound with no press from the user only when its plugin holds `audio` (a plugin without it gets a window that still wants a press, which never comes); there is one mute over all plugin sound (every test build is muted: its audio is produced and counted but never sounds). The OK card says "It keeps a part running in the background while the engine runs" and the Plugins page labels it Background.
* **[D] A plugin can add its own panel on the right** (the owner, November 14: an Office plugin for sheets, slides and documents). A `panel` entry whose key is not a stock one (`session`, `terminal`, `diff`, `browser`, `files`) adds a panel in MOSS Code's window, with a button of its own beside the stock ones; it needs a `title` (the button's name), `icon` is optional (a stock glyph otherwise) and `when.session` names the sessions that show it, all of them when absent (MOSS Code's sessions are code sessions, §9.4). A stock key keeps replacing that panel as before. The shell draws the own buttons after the stock ones, in `order`; past three the rest go into one menu button, and at most two panels are open at once. A panel's id is `<plugin id>#<key>` in `panels.open` and `panels.available` and in `shell.openPanel`, `closePanel` and `togglePanel` (a frame names its own key; the app adds the plugin). The panel is an ordinary frame of the plugin's layer and needs no capability; a part that draws nothing shows the host's placeholder. The OK card says "It adds a panel, "<title>", …" and the Plugins page labels it Panel.
* **The island and the pill are plugins with their own look,** on the background host. The cards they show are in their styling, not the window's. A plugin that wants to show something on the island sends the island data (an item: a line of text, an icon, an optional progress bar) and the island draws it by its own rules, or adds a tab in the island's tab plug.
* The Plugins page labels a plugin by what it brings (Tools, Skills, Island tab, Theme, App page, Voice, Model).

**[D] A theme is data, and its CSS is cleaned** (these rules came with the bot's tab look, which revision 19 retires with the tab, item 101; they hold for every theme). A theme carries design tokens, fonts, backgrounds, and CSS. The CSS is cleaned first: no `@import`, `url()` only for files inside the folder, and no remote fonts or images. The root of a part that a theme dresses has `contain: layout paint`. The cleaner keeps only the at-rules it knows (`@media`, `@supports`, `@container`, `@scope`, `@starting-style` and the named ones below) and drops the rest, `@property` included; it prefixes the names that `@keyframes`, `@font-face`, `@layer`, `@counter-style` and `@font-palette-values` define, and the plugin's own uses of them, with the plugin's id. A layer's preload answers only frames of its plugin's origin. Every ancestor of a sealed frame stays free of filters, opacity below 1 and transforms other than moves or enlargements, whatever a theme says; S9 checks the base theme. The iOS app and the web page honour a theme's tokens, since a theme is data; components run only in MOSS Code's window and on the background host.

**[D] Each plugin's UI renders in its own layer, and shared parts render once** (revision 12, restated in revision 19: a bot has no tab). A layer is a renderer process of its own, and code in one layer cannot reach another, so a plugin's components reach only their own parts. A part that several places share, such as a composer two sessions use, renders in one layer and is the same in each. **[D]** It takes each place's colours, unless its plugin sets its own (revision 13), so a shared composer matches the window it shows in. **[D] "Renders once" means** one origin and one renderer process for each shared plugin, one frame for each place it appears, its state held by the core, and each frame themed by its own place (the owner, revision 18, item 77). A document can't show in two places at once, and S9 found that a second window reuses each plugin's renderer. **[P] How:**

* Every plugin with UI code gets its own layer and origin, a child included (its origin writes the child's `/` as `--`, §5.1), so a plugin's components never share a process with what its children add elsewhere. Everything we ship under `moss` shares one layer, the default shell's, and keeps it when a third-party shell fills `app.root`. A plugin that is data only needs no layer: the core applies its theme, which cannot run.
* A part from another layer shows as a frame from that plugin's own origin, drawn by its own process (Chromium's out-of-process frames). The core sizes the frame, and a menu that must cross the frame's edge asks the core to draw it on top.
* The core applies data (tokens, CSS, layouts) in every layer it dresses.
* Only parts near the screen are mounted, and a layer hidden for a while sleeps and is rebuilt from the core's state.
* No layer has Node, and the plugin API in every layer has the limits listed under approvals (below).
* **Mounts (S9):** plugin documents load only through single-use, unguessable mount tokens the core issues, with `frame-ancestors` naming the parents allowed and `frame-src` holding each plugin to its own contributions. The core and the sealed cards use schemes of their own, never a name in the plugin-id namespace. A host component still controls how frames nested in it look (process isolation doesn't stop it clipping or covering them), so the sealed cards' visibility and hardware checks stay mandatory (below).
* **Input and state (S9):** the app's main process owns app shortcuts, ahead of every layer (the window's `before-input-event`). Menus go through a broker in the main process that binds the sender, the coordinates and the action ids. The main process returns focus to a layer's frame, and the layer's SDK restores the focused element. Shared state lives in the core. A plugin's popup HTML never runs in the core's origin.
* Spike S9 checked the isolation, the memory each layer costs (about 18–24 MiB of private memory each), and focus, keyboard and drag and drop across layers (§14.1).

**[P] Plugins** fill spots wherever the spot exists (§3.4). `when` limits an entry by surface, OS or setting; tools, skills and hooks can't be limited to some bots, because bots are equal (§1).

**Which entry shows** in a single spot or a keyed cell:

1. **[P]** the user's pick
2. **[D] the smaller part** (revision 12): an entry that dresses a smaller part beats one that dresses a part around it, so a plugin for one composer button takes that button. (The owner's "more scoped wins" of November 14, which put a bot's own look above plugins for all bots, retired with the bot's tab, item 101.)
3. **[P]** a plugin the user installed, over a bundled one
4. **[P]** the most recently enabled

When step 4 decides, Settings shows a conflict badge on that spot with a picker. Authors never set priorities. **[P]** The part an entry dresses is the smallest spot holding all its plugin's entries in that window, a child counting as its own plugin: a send-button plugin dresses the button, a shell the window. Sealed frames take only `card.*` tokens, so card styling is that set plus the components that place sealed frames.

**[P] Web pages:** a UI part can show a web page (a URL, or a page inside the folder) in an isolated view with its own session, no Node, no plugin API and no access to sealed cards. Discord Waifus works this way (§11). Connecting such a page to bots needs a component, which makes the plugin code.

**[D] MCP Apps** (revision 14): when a tool names a `ui://` page (`_meta.ui.resourceUri`, the MCP Apps extension `io.modelcontextprotocol/ui`), the page shows where the tool's result shows, and the core runs it in an isolated view like a web page's, with no plugin API. **[P]** The core bridges the page's JSON-RPC calls to its own server under the same approvals and levels, enforces the page's declared domains and content rules (`_meta.ui.csp`; undeclared domains are refused), and shows the result as text where no view can run, such as on the iOS app and the web page. Since the page runs isolated, it doesn't change its plugin's class. **[P]** The bridge gives the page `tools/call` only for its own server's tools whose `_meta.ui.visibility` includes `app`, plus `resources/read` and `ui/request-display-mode`. `ui/message` and `ui/update-model-context` reach the bot as outside content labelled with the plugin, never as the user's, so a turn they start is the plugin's; `ui/open-link` opens the user's browser; the page gets no camera, microphone, location or clipboard. A tool whose visibility leaves out `model` never reaches a bot, `Glossary` or an agent. A component that shows a tool's result places the page with the plugin SDK's `<AppView call>`; a page no component places within 2 seconds shows as text.

**[D] Translations** (revision 14): the app core point `locales`, keyed by language, holds string tables for the core's own text, sealed cards and the welcome guide included, and for any plugin's keys, which components read through the plugin API (`t(key)`; components only: a host half's API has no `t`, and the core refuses it there). Keys start with their plugin's id and a dot, and the core's and `moss`'s with `moss.`, so one language pack, a data plugin, can translate the core and many plugins. **[D]** The strings on sealed cards and in the OK come only from the built-in tables, `moss`'s packs and packs whose tree hash matches the official index (revision 15), so a pack that a bot edits can't relabel them; other packs translate everything else, and those strings fall back to English. **[P]** The user picks a language in Settings; a missing string falls back from a regional language to its base (`pt-BR` to `pt`), then to English, then to any language its plugin has, and a manifest's `Text` can carry its translations inline (§5.9). Strings use `{name}` placeholders, and a key may hold plural forms (`{ one, other, … }`, by the language's rules). A child's keys start with its top-level plugin's id. For one key, a plugin's own table beats a pack's, and between two packs the user picks in Settings, the first enabled applying until then.

**[D] Approvals are core data that plugins show but cannot read.**

* The core hands each approval to the UI as **sealed fields** (what is asked, the command, the computer, the risk…) and **sealed approve and deny buttons**. A plugin places and styles them however it likes, but never sees their text, so it cannot rewrite or fake it.
* A plugin may leave fields out. For example, a clean UI can show one approve and one deny button and nothing else, and the buttons themselves can be restyled, even without text.
* **[D] A plugin can style the approval card in the parts it fills** (November 3; it was a bot's plugin in its own tab until revision 19), through its theme or its components, like any UI plugin.
* **[P] How:** each sealed field is a small frame from a core-owned origin, isolated from the plugin's page. Style tokens go in; nothing comes out. The core accepts a click only while its button is visible and uncovered (Chromium's IntersectionObserver v2).
* **[P] Only sealed buttons answer:**
  * The core takes an answer only from a sealed frame, over a channel the app's main process opens for that frame alone, or from a paired device's own app, signed with its answer key over the card's id and hash.
  * **[D] Who may answer another computer's card** (the owner, revision 18, item 91): any desktop, as well as phones; browsers never. A desktop signs with an answer key apart from its link key, held by the app where the OS can protect it (the macOS Keychain, Windows Hello or the TPM). **[P]** (ruling C) There is one answer key per (device, program): MOSS, MOSS Code and the background host each hold their own key in their own protected storage and register it; the device registry keeps one per program; an answer's proof names its key; and the engine takes a key only from a client whose signed identity is one of the product's programs (§3.1), the key's program being that identity (the host's fixed helper id tells it from the two apps), never the hello's `surface`; on Windows and Linux, where there is no running-image signature, the `surface` field plus the caller check stand in for it. **[P]** So on Windows and Linux a process of the user's that holds the app token and passes the caller check can register the FIRST key of a program (a program that hasn't registered one yet) under that program's name before the real program does; the real program's own key then counts as a replacement, behind the hand-over card it cannot sign, and the user sees it refused. This is the same reach the owner accepted for plugin code running as the user there (below); on macOS the signed identity closes it. No press is forwarded from one program to another: a card is answered with the key of the program whose sealed frame took the press. Receivers always rebuild the card for the bound call and compare hashes. The owner accepted that a compromised plugin on a Windows or Linux computer, where plugin code runs as the user (§5.2), could approve actions on the user's other computers.
  * Cards and answers travel on the core's own link; a companion plugin never sees either (§10).
  * The layers that run UI plugins have no Node, and their plugin API cannot answer cards, change levels or devices, or read secrets. **[P] The door for parts goes by capability, never by id** (F2, the owner's ruling of 2026-11-15: no door checks a plugin's id). A part changes the core's settings, the bots' settings and the plugins on the app's own connection only through the app's door for parts (`tree-calls.ts`), and each call there is allowed by a capability the calling part's plugin holds (`app.settings`, `bots.edit`, `plugins.read`, `plugins.manage`, `tools.permissions`, `account.read`, `commands.run`, and the existing `conversation.read`, `sessions.read`, `logs.read`, `computers.read`, `bots.read`, `user.send`, `audio`), from the main process's own record of the mount, whichever plugin it is: the bundled Settings, Plugins page, shell and composer hold theirs because their manifests list them and the build grants them, a folder copy of one under another id because the user OK'd them on its card. Every write there is the user's own press in that frame, one call per press: a press in the calling part's own frame: the main process saw the press in the window, and the frame it landed in is the one whose own document received it (for a click, reported by the app's preload from a trusted pointerdown, which a page's script cannot make; for a key, the focused frame at the key down; a press no frame reports, on a drag region or the window's own root, is no frame's; the bundled tree's parts share one document, whose presses are that document's), never one in another plugin's frame, on a sealed card's button or elsewhere in the window, and the same holds for `user.send`, the composer spot, the pickers, the shell API and an open; what is a sealed card today stays one for every holder. A part without the capability gets the `layer` role's door, where its change becomes a sealed card, as before; a call the layer role doesn't have is refused, naming the capability. A plugin's own settings are its own (§5.4); sensitive changes (below) are a sealed card from every layer. The window's shell (what the window shows, where it is, its drag) is the part the core mounted in `app.root`, whichever plugin's, and no other part; opening a place in MOSS Code's window (a Settings section) is `shell.control`'s, on the user's own press in that frame; the user's statement that they are 18 or older, from any part, is a sealed card.
  * Socket clients prove their role with a token, and the daemon checks a caller's process tree (§3.1).
  * A click counts only while no other window overlaps the button and no computer-use action is running on that computer. **[P]** The overlap check reads the OS's own window list, not one program's windows (R12, ruling B): any window over the button, from any of the product's programs or from any other app, refuses the press. While a card is pending, the host keeps plugin overlays below the sealed windows or hides them, and tells the other programs where its surfaces are. **[P]** It counts only when the program's main process saw it come from the hardware: on macOS an event no other process posted (`eventSourceUnixProcessID`), so an accessibility press never counts; on Windows one without `LLMHF_INJECTED`; on X11 one not sent through XTEST. The whole button must show, at 24 by 24 CSS pixels or more, with no browser view over it. On Wayland, plugin overlay windows hide while a card is pending, and only the focused window of the product takes clicks. **[P]** (E7) MOSS's main process holds its own press record, trusted pointer-down report, fresh visibility reading and stacking rule for the sealed cards it draws, as the other programs' main processes do for theirs. A plugin with `computers.control` learns where the product's windows are (§5.4) and must not act on them, as Winter never controls itself today (`WINTER_OWN_BUNDLE_IDS`); ours also blacks them out of its screenshots.
* **[P] A fallback:** if no plugin puts the approve and deny buttons on screen, visible, within 2 seconds, the app shows its own card. A filter, opacity below 1, or a transform other than a move or an enlargement, on a sealed frame or anything around it, counts as hidden (IntersectionObserver v2 reports it so), so card styling may not use them.
* **[P] The limit:** a plugin can still put misleading words next to a button that has no text, or make deny look like approve. So the OK given when the plugin was found (§5.1) says "restyles approval cards" for any plugin that does, and **[D] a later change to that styling waits for its own OK** (revision 12): until the user OKs it, cards keep the styling last OK'd, while the rest of the change applies at once. **[P]** Card styling is every component that places sealed frames, wherever it shows them (the `approval` cell, an island tab, the pill), plus the token values handed to the frames. A component gets sealed frames only if its plugin has the `approvals` capability, so the OK can say so before anything runs, and no other CSS reaches inside an approval card. A development folder (§5.6) is exempt. **[P]** A component with `approvals` hears pending cards' ids and computers, never their text (`approvals.watch`), and places one with the plugin SDK's `<Card id>` and its parts (`<Card.Field name>`, `<Card.Approve>`, `<Card.Deny>`). While a change to a component's card styling waits for its OK, the core keeps the last OK'd version of that component and mounts it wherever it places frames.
* **[P] Sensitive changes are approvals too.** Raising a routine's level, changing a computer's level, adding or revoking a device, choosing the main computer, loading a found plugin, adding a development folder, trusting a repo, and adding a saved allow rule or a connector permission all end in a sealed card unless the user makes them in their own terminal (§5.1), so a plugin can ask for them but never do them silently. On Windows and Linux that holds for UI code; host code runs as the user there (§5.2).
* **[P] Where cards appear:** in any surface (conversation view, island, Dispatch pill), on the user's other desktops (item 91) and in the native iOS app, but not on the web page (§14.2 item 5). Every device shows a pending card, and the first answer wins; on this computer the router names the place that draws it (§3.5, ruling A). A request from a turn the user's own message did not start (a routine, another bot, a task notification, an agent working alone, a plugin) is denied after 10 minutes unanswered; one from a turn the user started waits, in any session (§9.1).

**[D] `AskUserQuestion` is different.** Plugins can read its question and options and show them in any form, charts included. It is a conversation, not a security boundary.

### 5.6 Trust

* **[P] Plugins are trusted code within their reach.** UI code can restyle anything in its own layer, but no other layer (§5.5). Host halves run as the user. On macOS they are kept from MOSS's Keychain items and the daemon's socket; on Windows and Linux nothing keeps them from either (§5.2).
* **[P] The OK shows what a plugin is:** data, web or code (§5.3), what it adds, the network hosts it declares (saying that its components reach only those, except WebRTC connectivity checks, a known gap (§5.3), and that its host code is held to them where the fence holds it, macOS with the sandbox on, and can reach any host elsewhere; **[D]** a wrapper the user brought that declares no hosts is said to reach any host on the network, the owner, 2026-11-10, §5.3), the OS permissions its helper wants, its capabilities, its children (a checkbox each), and who wrote it, from the core's own record: the user through the app, a bot through its tools, the migration, or "found on disk" (`generated.by` in the manifest is only a hint). It flags `stdio` commands that fetch code at run time (`npx`, `uvx`) and plugins that load add-ons of their own (§5.4). **[P]** (the owner's ruling, 2026-11-13) It carries no "reviewed" or "not reviewed" mark: there is no official index. An optional Review control on the card asks an internal job to read the plugin's files and write a short report onto the card as advice; it never answers, pre-selects or delays the card.
* **[P] When the app asks again:**
  * A code change waits for a new OK, whoever made it, since the core cannot always tell who wrote a file.
  * An update asks again if it turns data into code, or adds capabilities, network hosts, helper permissions, hook events, add-ons of its own (`addons`), a `stdio` command that fetches code at run time, code children, adult content, routine triggers, or host code that starts at once (`host.start`) or starts somewhere new. These are **the triggers**. **[P]** Every line the OK card shows from the tree counts: an update whose card would show a line the OK'd one didn't asks again.
  * A local edit asks again on the same triggers, and any edit that changes what runs is a code change wherever it is written: a `stdio` server's `command`, `args` or `env`, a hook's or agent backend's `command` or `args`, the `host`, `client` or `helper` fields, or a field whose format is `program` or `code`; a changed setting `default` waits for the user's OK too, since bots can't change settings (§9.1). Other data edits (themes, layouts, CSS, Markdown) apply at once, except approval-card styling (§5.5). A change to a bot's instructions applies at the bot's next turn, however short its conversation: the prompt is rebuilt and the transcript resumes under it, at the cost of one cache miss per edit; while the bot's background work runs, the change waits for it to end.
  * **[P] The workshop rule** (the owner, November 12: a bot can build a plugin and the card decides). A bot builds a plugin in its scratch, checks it with `PluginValidate { folder }` (what `moss plugin validate` prints, and for its own installed plugin whether the folder would apply without a card) and installs it with `PluginInstall { folder }`, from its scratch or its conversation's outputs. It lands found like any install, and its OK card's source line says "Built by <bot>. <bot> can change its code later without asking, within what this card lists." The install record (`by: "bot"`, with the bot) makes it that bot's workshop plugin: that bot's own sessions (its conversation and side threads, never an agent's or another bot's) write its folder in the plugins folder (§9.1), and the registry judges each change against the user's last OK. Code included, it applies at once while it asks for nothing the last OK didn't list: every trigger and every OK-card line an index update is held to, and also a program it runs that it didn't (a `stdio` server's or hook's command, its helper, a point's code field, a hook's scope), a tool that runs without a card that didn't, a changed default of a setting it runs with, and its window skin. One that does stops the plugin and puts its sealed OK card before the user at once, as an install does (the controller's ruling): a yes runs it with the new grant and moves the snapshot; a no leaves it off, and a later change that takes the request back out applies and runs again with no card, since it is judged against the last OK; a further change while the card waits replaces that card, and one that takes the request out withdraws it. Card styling waits for its own OK as always; in a tree the user OK'd with `approvals`, which places sealed cards in its own components, every code change waits as card styling (§5.5). Each applied change becomes the OK snapshot, so the ceiling only goes down: a grant one edit drops, a later one asks for again. `PluginInstall` with the id of the bot's own workshop plugin replaces its folder from scratch as an update, judged the same way; any other installed id is refused. `PluginStatus { id }` shows one of its own workshop plugins: its state and why (a client build's failure included), what it waits for, its validation findings and its log's last lines. A workshop plugin may ask for whatever any third-party plugin may (what is bundled-only stays so), and the user decides on its card. Removing it stays the user's.
  * **Development folders** are the exception. A folder the user adds in Settings, or with `moss plugin dev <folder>` from their own terminal, reloads on every change without asking. It never syncs, the fence keeps bots out of it (§9.1), and no agent's root may contain it. Adding one is a sealed card, unless the user adds it in their own terminal (§5.1). While one is on, the tray shows it and lists each reload (the tray, when built, gets its own event for the reloads; the protocol keeps no name for it until then), and it turns off after 24 hours unless renewed. **[P]** A development folder's contributions exist only on its own computer: its models, tools and UI serve only that computer. One with an installed plugin's id replaces that plugin there while it is on.
* **[P] The guards:**
  * the OK when a plugin is found (§5.1)
  * the approval level for each computer (§9.1); bots are equal, so there is no per-bot policy
  * **sealed approval cards** (§5.5)
  * on macOS, the plugin host's own identity and its sandbox away from the Keychain and the daemon's socket (§5.2)
  * the layers, which keep each plugin's UI code to its own part of the app (§5.5)
  * the manifest's capability list, which gates the plugin API only. It is **not** a containment boundary: a host plugin can do anything the user can, except, on macOS, reach MOSS's Keychain items and the daemon's socket.
  * **the load guard** (#234): a plugin process MOSS starts (a host half, a hook, a stdio MCP server) runs Bun as `moss-plugin-bun`: a Bun binary of its own, the core's version, signed under its own identifier, so no Keychain item's access list (which names `moss-core` alone) admits it. Never the core's binary, never with `BUN_BE_BUN`, never one the plugin ships. It runs with MOSS's own `bunfig.toml`, no `.env`, and a preloaded guard that refuses to load any file, native addon or worker code from outside the plugin's own folder and MOSS's shared packages. Bun hands an ESM load of a file without an extension to no hook, so two more walls stand in for the guard there: no runner may write a `node_modules` in any folder above one plugin code loads from (`~/node_modules` among them), and the OK refuses a plugin that imports or declares a dependency it doesn't ship in its own `node_modules`, except that a file only its client entries reach may import what every layer's import map serves (React 19, its JSX runtimes, react-dom and the UI API: the SDK's `CLIENT_BARE_IMPORTS`, one list with the map and the client build's externals); the client always gets the layer's React, whatever react the plugin ships. That install scan is an early, friendly error, not the wall: the guard preloaded into every plugin process is. What the scan can't follow (a computed `import()`, `require` of a variable, a Worker's path, `eval`) is not followed; it is refused at run time if it leaves the folder. A host half therefore runs under Bun; only MOSS's own plugins keep a Node host. **Known limit:** a program that isn't Bun (a `stdio` server's command, a helper, a `node` the plugin's code starts) resolves its own imports as it likes. It is code by declaration, the OK says "It runs its own programs, which MOSS doesn't confine", and the static check in `moss plugin validate` is its only early warning. Neither does the guard judge what the approved code chooses itself: `eval`, or a child it starts with a clean environment.
* **[P] `moss plugin validate`** prints a folder's class, contributions, declared points, network hosts, helper permissions, capabilities, tool names, settings and children without running anything, like `claude plugin validate`. It checks every schema and catalog name, prints the OK's text, takes `--json`, and exits non-zero on any error. Model plugins also get Winter's provider conformance suite (`@yanlinglabs/winter-provider-conformance`, renamed) as their test kit.
* **[P] The plugin SDK** (`@waifucave/moss-plugin-sdk`) ships on day one, from one source: JSON Schemas and TypeScript types for the manifest, theme, layout, locale and index formats; the catalogs of spots, points, tokens, hooks and capabilities; the plugin API (§5.4); `moss plugin new <template>`, with templates for a theme, a tool, a UI part, a model, a trigger and a point; and a bundled skill that teaches bots the same. A template is only a starting point that writes an ordinary plugin folder. The docs are generated from the same catalogs.
* **[P]** A full OS sandbox for plugins can come later; until then only macOS keeps host halves from MOSS's Keychain items and the daemon's socket.

### 5.7 Content and age

* **[D] MOSS is rated 13+.**
* **[D] The default app ships with no adult content.** Alpha, the default theme and everything bundled are safe-for-work. Adult content can only come from plugins other users make (avatar packs, mods…).
  * **[P] Stated precisely:** it can also come from bots and avatars the user makes, and from what the model writes, which follows the user's own provider's rules.
  * **[P]** Provider terms differ by age: some providers require users to be 18 or older, others need a parent's permission under 18. The welcome guide shows each provider's terms before sign-in.
  * **[P]** The harness keeps a safety block in the system prompt that no bot or data plugin can remove. A model plugin sees the whole prompt, and its OK says so.
* **[P] Because users can be 13:**
  * a plugin that may contain adult content must say so in its manifest
  * the app keeps such plugins off until the user confirms they are 18 or older
  * voice listens only while the user holds push-to-talk, by default

### 5.9 Manifest reference

**[P]** `moss.json`, format 1. JSON with comments and trailing commas is accepted.

```ts
type Path = string;   // relative to the plugin folder; must resolve inside it (real path, no symlinks out)
type Text = string | { en: string; [lang: string]: string };
type Os = "macos" | "windows" | "linux";
type Platform = "darwin-arm64" | "windows-x64" | "linux-x64" | "linux-arm64";   // no darwin-x64: macOS 27 is Apple silicon only
type Scope = "bots" | "agents" | "both";
type JsonSchema = object;   // JSON Schema 2020-12; its formats (path, url, handler, component, program, code): §5.4

interface Manifest {
  manifest: 1;                      // required
  id?: string;                      // required at top level; must equal the folder name. Children omit it
  name: Text;                       // required
  version?: string;                 // semver; default "0.0.0"; required to publish to an index; children inherit
  description?: Text; icon?: Path;  // icon: svg, png or webp, at most 256 KiB
  author?: { name: string; url?: string }; license?: string; homepage?: string;
  namespace?: string;               // tool prefix (top level only): lowercase letters, digits and
                                    // single hyphens, a letter or digit at each end, at most 40; default = id; children share it; "moss" reserved
  engines?: { moss: string };   // plugin-API semver range; required when the plugin has code
  platforms?: Platform[];           // code runs only on these; default all
  adult?: boolean;                  // whole tree; off until the user confirms they are 18+
  enabledByDefault?: boolean;       // children only; default true
  scope?: Scope;                    // default "both"; covers mcpServers, skills, agents, hooks (§5.1)
  onlyBackends?: string[];          // only these Agent backends receive it, e.g. ["claude-code"]
  host?: { entry: Path; runtime?: "bun" | "node";   // bun = a worker in the plugin host; node = its own process, MOSS's own plugins only (§5.6, the load guard)
           start?: "each" | "main" | "chosen";     // starts at once there (§5.2); otherwise only when needed
           declares?: Record<string, PointDecl> };  // points the host serves (§5.4)
  client?: { entry: Path };         // React module loaded into the program that shows the part (MOSS Code's window or the host, §3.4)
  helper?: { bin: Partial<Record<Platform, Path>>;   // a signed .app on macOS, started through Launch Services
             permissions?: ("accessibility" | "screen-recording" | "input-monitoring" | "microphone" | "camera")[];
             ipc?: "socket" | "stdio" };
  capabilities?: string[];          // conversation.read, sessions.read, activity.read, picture.read, conversation.post, memory.read, bots.read, routines.read,
                                    // computers.read, computers.control, approvals, files, browser, usage.read,
                                    // logs.read, notify, audio, call:<plugin-id>, network:<host> (§5.4).
                                    // They gate the plugin API; they are not containment
  settings?: Record<string, Setting>;
  auth?: Auth[];                    // sign-ins for the plugin's own service (§5.1)
  addons?: { description: Text };  // runs add-ons of its own, in a format it chooses (§5.4)
  contributes?: Contributions;
  generated?: { from: "mcp-config" | "mcp-url" | "skill-folder" | "agent-file" | "claude-plugin" | "winter";
                by: "user" | "bot" | "migration"; at: string };   // a hint; the OK shows the core's own record (§5.6)
}

interface Setting {
  type: "string" | "number" | "boolean" | "enum" | "color" | "secret";  // a secret goes to the credential store only
  title: Text; description?: Text; default?: unknown; options?: (string | { value: string; title: Text })[];
  min?: number; max?: number;
  scope?: "account" | "device" | "bot";   // default account; device values don't sync; bot = one value per bot
  required?: boolean;                     // the plugin waits until the value is set
}

interface Contributions {
  models?: Model[];
  mcpServers?: Record<string, McpServer>;     skills?: Path[];            // folders holding SKILL.md; globs allowed
  agents?: (Path | AgentDef)[];               agentBackends?: AgentBackend[];
  hooks?: Hook[];                             commands?: Command[];
  triggers?: { type: string; title: Text; fields?: JsonSchema; handler: string; declares?: Record<string, PointDecl> }[];
  computerProviders?: { id: string; name: Text; auth: Auth[]; handler: string }[];
  computer?: { provider: string; name: string; size: string; region: string; image?: string;
               makeMain?: "ask" | "no"; onRemove?: "ask" | "keep" };   // deleting a VM always asks
  relays?: Service[];  notifiers?: Service[];  companions?: Service[];
  themes?: { id: string; file: Path }[];      // theme format 1 (below)
  locales?: { lang: string; file: Path }[];   // locale format 1 (below)
  ui?: Ui[];
  // any entry above may also carry declares?: Record<string, PointDecl> (§5.4)
  [pluginPoint: `${string}.${string}`]: unknown;   // a point another plugin declares, e.g. "webhook.ingress"
}
```

## 6. Bots

### 6.1 A bot

**[D] What a bot can change:**

* **The harness owns the system prompt.** It enforces fixed blocks (tools, safety, memory, devices…). A bot supplies only its **`<bot-instructions>`** block: who the bot is, how it talks, what it cares about.
* **Every tool is every bot's.** Every bot sees every installed plugin, MCP server and skill scoped to bots (§5.1). No tool is kept inside one bot: the `own-bot` scope is retired with the plugin-made bot (item 101). Alpha's stage tools and her `/scene`, `/mood` and `/outfit` came with her plugin and the stage; they move to her avatar pack (item 122).
* **[D] MCP server instructions go into the system prompt.** The instructions every enabled MCP server gives (in `initialize`, or from `server/discover` under MCP 2026-07-28) are always included, whether its tools are preloaded or on-demand, in a harness-owned block.
  * **[D] The block is rebuilt only at compaction,** so the prompt cache is not thrown away every time something changes. It lists installed and enabled servers, not only connected ones: a server on a sleeping computer stays listed, and its tools answer "computer offline". Servers added between compactions, and a repo's own servers, arrive as an appended note in the conversation at the next turn and move into the system prompt at the next compaction.
  * **[P] When the cache has already expired,** the next turn rebuilds the MCP block, the devices block and the `computer` lists without compacting, since there is no cache left to save. A conversation under the compaction threshold would otherwise never rebuild.
  * **[P] Labelled and capped:** each server's text is labelled with its plugin and server name and capped in size (about 4 KB), since it is third-party text.
  * **[P] Stable order:** servers are sorted by plugin id, so a rebuilt block differs only where servers or their text changed.
  * **[P] Plugins too:** a plugin's own tools are an MCP server of type `host` (§6.7), so they supply instructions the same way.
  * **[P] ACP agents:** the bridge MCP server sends the instructions of the plugins it serves as its own server instructions. Since Cursor and Antigravity don't put server instructions in the prompt, the bridge's essentials also go into the agent's system prompt where the backend allows it (§9.3, S5).

**[D] A bot is engine data** (the owner, 2026-11-16, items 95 and 101): an engine feature shown only by MOSS, not a plugin. It has its `<bot-instructions>`, a default model and effort, a voice choice, a greeting, its memory and routines, and its face, a built-in living bot made from its name, whose shape and colour the user may pin (**[P]**, G8; §6.9). **[P]** A bot's id is its own; no plugin ships a bot or a pack of bots. If the user has no key for the default model, the bot uses the user's default model. **[P]** (item 124) MOSS never spends a stored key on a provider the person did not pick: a bot's model is the person's choice in MOSS. The consent rule narrows to the default bot: before it first spends the user's stored key on a provider the user did not choose for it (an agent it starts on another provider, or its voice), the engine asks once per bot and provider on a sealed change card, and a no holds until the user's next message; with nowhere to ask, it is refused. A provider the user chose never asks, and neither does one chosen by the product's own bundled plugin (its record staged from the verified bundled bytes, never a manifest's claim).

**[D] Retired in revision 19:** a bot is not a plugin and has no plug in a plugin window (items 99, 100 and 101: no plugin ships a bot, MOSS's window is built in, and bots are only in MOSS). **[P]** (G8) What goes with them: the `bot` point, one bot to a plugin, a pack of bots in child plugins, the plugs a bot had (its top bar, right panels and inside its tab, `bot.tab` and `BOTS_OFFER`), the stage (`bot.stage`, the avatar spot, the stage's chips) and the `own-bot` scope. A bot's code, theme and layout for its own tab are gone with the tab.

**[P] A bot's state lives in the home.** Memories, the transcript and the bot's settings are stored in the user's data under the bot's id, and routines in routine files (§7). Nothing about a bot lives in a plugin folder.

**[P] A bot's data is its folder under the home's `bots/`** (F1; §6.5, §9.1), made engine data in Split 1, with the existing bot plugins moved over once (§13). It holds the bot's memory, its agents' transcripts and its instructions file, which the bot edits with the normal Write and Edit: the `<bot-instructions>` block is read from that file, so a change applies at the bot's next turn (§5.6). **[P]** A bot may edit its own instructions file and those of a bot it made, with no card; changing another bot's instructions needs a card. That closes the first half of item 114; exporting, importing and sharing a bot stay open (item 21). **[P]** "A bot builds a bot" creates a bot, a folder of this kind, and never a bot plugin; a bot that builds a plugin follows the workshop rule (§5.6). **[P]** A bot's other settings (its name, model, effort, voice and face pins) are the user's, changed in MOSS's window (§6.10), and bots cannot write them (§9.1).

### 6.2 Alpha

**[D]** Alpha is an ordinary bot that MOSS offers as a default (the owner, 2026-11-16, item 102): its instructions, memory and tools, and a living-bot face like any bot's. She is not a plugin, and no plugin ships a whole bot with its own look. **It is not special in any way:** she has the same tools and powers as any other bot, and is simply the first one the user meets. **[P]** (G9) Her Live2D figure and her scenes become an avatar pack for the bundled avatar plugin (§10), which shows in MOSS Code's window and on the screen like any pack and is not a part of her. Her waifu-style tab theme goes with the tab. The DeepSeek-chan model stays personal-use only and is never redistributed. Her voice and her model's rights are §14.2 item 26.

### 6.3 One continuous life

* **[D] One conversation per bot,** like texting a person (the owner, 2026-11-16, item 106): MOSS's window shows that one conversation (§6.10). There are no separate chats per bot and no rooms for now; teams of bots in one conversation come later.
* **[D] Compaction:** besides compacting before the context window fills, a bot compacts its conversation **when the cached prompt is about to expire and the context is over about 100k tokens**.

  **[P] Why that moment is cheapest:** compacting just before expiry reads the long context while it is still cached and cheap. The next message then starts from a short summary, instead of paying full price to re-read 100k+ tokens of expired cache. The threshold and the timing come from the model's cache lifetime, and are settings.

  **[P] A user message during compaction:** a cache-timed compaction is dropped and retried at the next idle moment, since the cache is still warm; a compaction forced by a full context window finishes first.
* **[P] Switching model:** the user can change a bot's model or effort at any time, as with Winter's mid-session switch; the next turn uses it. A change to its instructions reaches the next turn the same way (§5.6).

### 6.4 Messages, interrupts and the main computer

* **[D] A bot is live on every device that is on.** The user can talk to it from any device, and every device shows its activity live.
* **[D] Messages are ordered by send order, on one shared clock,** so every device sees the same time.
  * **[D] Sending needs a live connection.** A device can message a bot only while it is connected to the user's other devices, so no message ever arrives late from an offline device.
  * **[P] Precisely:** connected to the computer running the bot. A user with one computer is always connected to it. A phone or browser that cannot reach any computer keeps the draft and says the bot is asleep (§14.2 item 18).
  * **[P] The shared clock:** the main computer keeps its time from public time servers (Cloudflare's and Google's). Every other device continuously measures its offset from the main over the persistent link, the way NTP does, and stamps messages in that shared time. Accuracy is about half the round trip: a few milliseconds on the same Wi-Fi, tens over the internet. Ties go by device id, and while the main is offline the takeover device is the reference.
  * **[P] Late arrivals:** a message whose stamp falls before output the model has already produced is placed after that output, showing its real send time, so the log always matches what the model saw.
* **[D] The user's messages interrupt.** A message from the user stops the bot's current step at once and starts a new step with that message.
  * **[P]** The model's in-flight answer is cancelled.
  * **[P]** A running tool call is cancelled and recorded as interrupted. Background tasks such as a running dev server keep running.
  * **[P]** A pending approval card for that step is withdrawn. If the cancel cannot reach the computer running the tool, the call is recorded as interrupted and that computer stops it when the link returns.
* **[D] Messages from other bots and routines fold in.** They join the running turn after its next tool call, as Winter's mid-turn push does today, so bots cannot keep cutting each other off.
* **[D] Background work never runs in the main conversation:**
  * **Routine runs** each run in a **side thread** of the bot (its own context, the same `<bot-instructions>` and memory) on the computer that holds the routine, and post a short result into the main conversation (§7).
  * **`Agent` delegations run as background agents** with their own context (§9.3); their messages and final reports arrive in the main conversation.

  The user's interrupt stops only the main conversation, never side threads or background agents, so a quick "hi" never cancels a deploy or a long delegation.
* **[P] The computer running a session:** the main (or the takeover computer) for a bot's main conversation; the routine's computer for a side thread; the agent's computer for a background agent. "The computer running the bot" means the one running its main conversation.
* **[D] The main computer:**
  * **Chosen automatically** — the always-on device, meaning a connected cloud computer, otherwise a desktop — and **the user can change it** in settings.
  * **While the main is online:** bots think and write memory there. The other devices show everything live and lend the bot their bash, files and screen.
  * **[D] The main holds a lease.** It renews a short lease with the waifucave handshake (metadata only). Another device takes over only after the lease lapses. If the main is alive but unreachable, the app says "can't reach your main computer" instead of taking over. **[D]** Without an account it works the same way, automatically, through the handshake with the pair credential in place of the account (§8.1; the owner, revision 18, item 85). **[P]** A user's devices without an account share one group record at the handshake service: each device joins it at pairing, and the service holds one lease record for the group, so "the first computer to take it wins" (below) holds with three or more devices too. This links those pairs to each other at the service, only within one user's own devices; per-pair leases could split the main computer, so they are not used.
  * **[P] Fencing the old main:** a main that can't renew its lease stops starting turns, tool calls and memory writes before the lease ends, with a margin for clock error, unless no other computer could take over, or it still has a live link to each such computer that is on. A computer takes the lease only after failing to reach the main over every link, relays included. Events carry their lease epoch. A tool call's start syncs before the call runs, so a takeover computer that finds a started call with no result records "interrupted, may have run on <computer>". It never re-runs that call on its own, and the real outcome is posted once the link returns. When several computers could take over, the one the user is using takes the lease first; if the user is on a phone, on the web page or away, the first computer to take it wins.
  * **While the main is offline:** the device in use takes over and runs the bots locally. **[P]** Only a computer running `moss-core` can take over, never a phone or the browser.
  * **When the main returns:** it catches up from the synced log and takes back over between turns, never in the middle of one: **[P]** each bot at that bot's next idle moment. **[D]** Work already running (side threads, background agents) finishes where it started and posts its result.
  * **[D] A new cloud computer becomes main only after the user confirms** (§9.2).
* **[P] Why one main computer:** credentials, plugins and memory writes stay in one place, there is no race over who answers, and memory sync stays simple (§6.5). The network adds little to a turn (§8.2).
* **[P] Sleep:** a computer running bots stays awake while a turn, an agent or a routine runs, and wakes for its next routine. A laptop main hands its bots over before it sleeps, when another computer is on to take them.

### 6.5 Persistent memory

* **[D] Each bot keeps its own persistent memory,** like Claude Code's: a main `MEMORY.md` index the bot maintains, linking to individual memory files in the bot's memory folder.
* **[D] There is no memory tool.** Bots read and write `MEMORY.md` and their memory files with `Bash` and the ordinary file tools.
* **[D] Memory syncs across the user's devices without a cloud server.**
* **[P] Where it lives:** a bot's memory is `bots/<bot>/memory/` at the top of the folder tree (§9.1). It always resolves to the computer running the bot, and side threads and background agents on other computers use it over the link. Agent transcripts go in `bots/<bot>/agents/` (§9.3), and scratch is `home/<Computer>/.moss/scratch/<bot>/`. The system prompt names all three. Until C5 there is no tree: the prompt names real local paths (`<home>/bots/<bot>/memory/` and so on), and C5 changes the prompt, not the files.
* **[P] The computer running the bot is the only writer,** and every other device receives copies of its memory files.
* **[P] During a takeover,** the takeover computer writes. When the main returns:
  * a file changed on only one side keeps that side's version
  * a file changed on both sides is kept twice, and the bot merges the two copies on its next turn

  No CRDT library is needed.
* **[P] When devices actually sync:** whenever any two of them are on and connected. A connected cloud computer is always on, so it carries changes between devices that are never on at the same time.
* **[P] A later free option:** a plugin that uses the user's own iCloud Drive, Google Drive or Dropbox as an **encrypted mailbox** between devices, at no cost to waifucave. Paid backup is ruled out [D].
* **[P] Scratch is per computer and not synced.** Each computer keeps the bot's scratch folder for working files (`home/<Computer>/.moss/scratch/<bot>/`), as Grok Bot keeps its scratch on its cloud computer.

### 6.6 Voice

* **[D] Voice is a plugin, MOSS Voice (`moss/voice`), built on general capabilities only** (F1, 2026-11-15): a third party could ship it from a folder with no change outside it. Its player is a background part of its own (`app.background`, §5.5, run by the background host) that takes the device's speech turn (`device/speech`, §5.4 "Turns") before it sounds; its host half hears each bot's reply through an observing `message.out` hook (§5.3, it holds no reply up) and the turn's end, and streams the provider's audio to that part (§5.4 "Streams"); the part publishes the speech cues, the mouth's levels, that the avatar plugin reads to lip-sync (§10; the avatar plugin follows speech through these general speech cues by capability, item 122). The avatar, VRM or Live2D, lip-syncs only from those cues, never from a microphone. Text works with no voice plugin installed.
* **[D] Voice providers are entries of MOSS Voice's own point** (`moss.voice.providers`): an entry's `speak` handler answers `{ text, voice, model?, format }` with the audio as it is made (pcm16-24k bytes, through `points.stream`). Fish Audio fills it from its own plugin folder. **[P]** An entry's optional `listen` handler answers `{ audio, format }` (push-to-talk's recording, 16 kHz 16-bit PCM) with `{ text }`; Fish Audio's does.
* **[P] A bot's voice is the voice plugin's own setting for that bot, and "Speak replies" is MOSS Voice's own setting** (item 113): each bot's voice choice (`provider`, `voice` and `model`) is a bot-scoped setting of the voice plugin, never a field of the bot's record (the engine keeps nothing that only one plugin uses), and `speakReplies` (account scope, on by default) is MOSS Voice's. A home whose core held them (a bot's `voice`, `ui.json`'s `voice.speakReplies`) has `speakReplies` moved once into MOSS Voice's settings at boot. MOSS Voice's parts in a window (a section on a bot's Edit page, the speak button in a reply's row of actions, a chip on the bot's stage) have no place now: MOSS's window has no plugin part and MOSS Code has no bots, so MOSS draws a plugin's declared bot-scoped settings itself, from their schema, the same way for every plugin (`bot.pluginSettings`); a bot's voice choice is one of them.
* **[P] A reply is spoken on the device where its turn ran** (the computer running the bot, whose background host plays it, with MOSS Voice's part); anything finer with several devices open is after try 15. **[P] Listening is push-to-talk, MOSS Voice's own button** (F1, 2026-11-15): its entry in the composer's buttons (`composer.action`, under a key of its own, `voice`, which the composer draws among the buttons plugins add, in the spot's order, as it would any plugin's; nothing looks for that key), shown only where a conversation can use it, and only while the voice picked would hear it (in MOSS Code's window; MOSS has its own, below). Held (the mouse, Space or Enter while it has the focus, or Ctrl+Shift+Space anywhere in the window: MOSS Voice's own command `moss.push-to-talk`, a held key binding, §5.4 `hold`), it takes `device/microphone`, opens the microphone itself (`microphone`, §5.4) and streams the recording to its host half (§5.4 "Streams"), which holds MOSS Voice's player meanwhile; at most a minute. Released, the voice picked writes it down (another plugin's `hear`, else the bot's provider's `listen`), and the words go to the bot as the user's message (`useUserSend`, with `user.send`: one send after the press and release main saw), with nothing shown to the user first, which each filler's OK line says; the words go as one plain line, cut at 2,000 characters. A stream that refuses a piece, or a hold past the host half's minute, closes the microphone at once. The app and the core keep no recorder, no listening method and no voice point of their own. **[P]** (item 113) In MOSS, the built-in microphone button and talk key run the active voice plugin's talk command (`moss.push-to-talk`) from MOSS's main process; the recording and the playback run in the voice plugin's background parts on the host, so MOSS needs no plugin part in its window. A test or acceptance build records a generated clip, never the microphone.
* **[P] One voice at a time on the device.** Every plugin that speaks takes `device/speech` before it sounds (behind `audio`), so two never talk at once, whichever plugins they are. MOSS Voice's own queue: a bot's new reply replaces its reply that is playing (in the same turn); anything else waits its turn, first come first served across bots; push-to-talk stops whatever it sounds at once, and nothing starts until the user lets go.
  * **Which voice:** MOSS Voice's own point `moss.voice.modes` takes one filler at a time (§5.4 "One at a time", titled "Voice"): the user's pick in Settings, else MOSS Voice, which fills it itself, and the user is told when their pick stops. When it is another plugin's, that entry is handed each reply (`reply`: `{ bot, session, text, asked }`) and says it its own way, and MOSS Voice says nothing; push-to-talk's recording goes to its `hear` (`{ bot, audio, format }` → `{ text }`), and with no `hear` the button doesn't show.
  * **A bot's default voice:** a default voice for a bot used to be given by the plugin that brought the bot, on MOSS Voice's point `moss.voice.defaults` (`{ provider, voice, model? }`); with no plugin-made bots (item 101), a default voice is the voice plugin's own default, and the default bot's is set the same way, as that plugin's setting for that bot (item 113); the point has no bot-giving filler. The user's own choice in the bot's voice setting always wins. A default speaks only through a provider that says the user set it up (its key or sign-in in its own plugin's settings, which its `ready` handler reports; a provider with no `ready` doesn't count for a default, though the user's own pick may use it); otherwise it stays silent and the bot's Voice section says why. No separate consent card: that plugin's OK card says it (MOSS Voice's caution on `moss.voice.defaults`, its `fills`), and so do a voice mode's and a provider's (what they are given). A provider is found by its plugin and its entry id, so another plugin's entry of the same id never gets the text. The user can also say "no voice" for one bot in its Voice section (MOSS Voice's bot setting `silent`): nothing of it is spoken or heard.

### 6.8 Glossary

**[D]** `Glossary` is the single tool for finding and loading anything a bot or agent might want: agent definitions, plugin and MCP tools, plugins, skills…

* **The call:** `Glossary(query?, load?)`. Both are optional, each takes one value or many, and several searches and loads can happen in a single call.
  * **`query`** — free-form text, such as `"deploy to hetzner"` or `"pdf"`. It returns the matching items with their name, what they are and a short description.
  * **`load`** — names to load:
    * a tool becomes callable (`Glob`, `Grep` or `mcp__<plugin>__<Tool>`)
    * a skill's instructions are returned
    * an agent definition becomes available to `Agent`
* **Search:** keyword and semantic search together. It may read a skill's full text to rank results better.
* **[P] Extension points too:** a search can return points, with their shape, fields, current occupants and whether filling one replaces shipped UI, so a bot writing a plugin knows where it can plug in. It also lists the plugins that take add-ons of their own, with their `addons` description.
* **[P] The index:**
  * **When it updates:** whenever a plugin is installed, changed or removed.
  * **What it holds:** names, descriptions, tool schemas and the full text of every `SKILL.md`.
  * **Where it lives:** in the core, on every computer that runs sessions, built from the synced plugins.
  * **Semantic search** uses a small local embedding model, so it works offline at no cost per query, with keyword-only search as the fallback.

## 7. Routines

**[D]** Bots have routines, like Grok Bot's: a routine runs a bot with saved instructions when a trigger fires.

* **[D] A routine is a file.** The bot creates one with the `Routine` tool, choosing a computer; the file is saved on that computer, and that computer runs it. The bot (or the user) changes the routine by editing the file.
  * **[P] The file:** `home/<Computer>/.moss/routines/<bot>/<name>.md`, Markdown with frontmatter (triggers, approval level, time zone, missed-run rule); the body is the instructions.
  * **[P] Live:** the core watches each computer's routines folder, so a new, changed or deleted file takes effect at once. A file written directly, without the tool, works too; the tool only saves writing the frontmatter by hand and hands back a webhook URL.
  * **[P] Secrets stay out:** a webhook's key is kept in the credential store, never in the file.
  * **[P] Moving:** `mv` the file to another computer in the folder tree (§9.1) and that computer runs it; its forwarder re-registers the routine. A copy with the same id on a second computer is paused, and the user is asked.
  * **[P] The id:** `Routine` writes an `id` into the frontmatter, and a file without one gets one when loaded. The same-id rule and the webhook URL both use it.
  * **[P]** The system prompt suggests putting routines that must always run on an always-on computer, such as a cloud computer.
* **[P]** MOSS's side panel lists each bot's routines: name, schedule, and whether it is paused (§6.10).
* **[D] Each run is a side thread.** A routine run happens in a side thread of its bot, on the routine's computer, and posts a short result into the bot's main conversation (§6.4). If the main conversation cannot be reached, the result waits and posts when it can.
* **[P] The routine engine is core; triggers are plugins.** Winter's scheduler (`packages/core/src/routines`: interval and cron schedules, runner, store, audit) carries over, computing schedules in the routine's time zone where Winter uses the host's local time.
* **[P] A plugin's trigger** (the `triggers` point): its handler is an object the routine engine calls as the core, `arm({ routine, type, fields })` and `disarm({ routine, type })` (the SDK's `TriggerHandler`). A routine file that names the trigger's type arms it on the computer that holds the file, and it is armed again each time the plugin's host half starts (a restart, an update, a crash, a plugin approved after the routine), so `arm` replaces. The plugin fires a routine with `routines.fire(routine, type, payload?)`, a host-only call that needs no capability: the core checks that the plugin adds that trigger type and that the routine uses it, and the run starts with the payload (at most 64 KiB) marked as the trigger's untrusted text. The call answers once the run has started.
* **[P] Trigger sources:**
  * **Schedule** (bundled): Winter's `every 15m` and 5-field cron grammar
  * **Webhook** (bundled, from C4 with the forwarder): a URL plus a key, as Grok Bot gives
  * **Integrations** (plugins): Slack messages, Git events (GitHub, GitLab), Microsoft Teams, Linear issues, Sentry alerts, PagerDuty incidents. These should prefer connecting outward (Slack's Socket Mode, polling an API), which needs no public URL.
* **[D] Webhooks arrive through the waifucave forwarder by default,** and the forwarder is itself a plugin, filling the `webhook.ingress` point that the bundled webhook trigger declares (§5.4). It is installed by default and removable like any other.
  * The service (GitHub, Sentry…) posts to `hooks.waifucave.com/<tag>/<routine>` with the routine's key. **[P]** The tag is the account's alias: a version byte, the account's stable id and a MAC under numbered tag keys that can be rotated, so a made-up tag never reaches a Durable Object (I-M1).
  * A Cloudflare Worker checks the key and forwards the payload to the computer that holds the routine.
  * Waifucave sees payloads in transit, because the sender cannot encrypt for the user's device, and deletes them after delivery.
  * **[P] How the Worker reaches a device:** a Worker cannot dial a device behind a router, so each device's forwarder plugin keeps one outbound connection to the user's Durable Object, used only for webhooks. This is the one content path through waifucave. **[P]** The account's Durable Object seals each payload on arrival (HPKE) to every computer on the account, so a held payload is never stored in plaintext. Each computer opens it with its own key, whose private half stays in its core (§5.4).
  * **[P] Drops are reported:** webhooks dropped by the caps or the hold, sent under a key the routine has since replaced, or that a computer can't open, are counted per routine and reported to its computer until it has listed them.
* **[D] Holding rule:** hold a payload for as long as holding stays flat in cost.
* **[P] Holding a payload longer adds almost nothing to the cost,** as long as the object takes the devices' connections through the WebSocket Hibernation API. Holding a payload in a Durable Object costs nearly the same for a minute or a week:
  * Cloudflare charges for the writes and the delete — a few row writes per payload.
  * Stored data is billed per GB-month, a rounding error for webhook payloads.
  * An idle object waiting for a device is not billed for time with the Hibernation API; a plain `accept()` bills the whole connection. Incoming messages count 20 to a request, and keep-alives use automatic responses, which are free.

  So time is not what limits holding. The proposed policy:
  * **Hold until the routine's computer comes back, for at most 7 days,** capped per user (for example 1,000 payloads or 50 MB, oldest dropped first).
  * The routine's missed-run setting decides whether a late webhook still runs.
* **[P] What the free plan covers:** 100,000 requests and 100,000 rows written per day across all users, roughly 30,000 webhooks a day. Past that, the Workers Paid plan is a $5 monthly minimum covering 1 million requests and 50 million rows written.
* **[P] Other ways in, as plugins filling `webhook.ingress`:**
  * the user's cloud computer receiving webhooks itself (fully private)
  * a tunnel plugin (Cloudflare Tunnel, ngrok, Tailscale Funnel)
* **[D] Each routine has its own approval level,** fully automatic included. A routine gets its computer's level by default. **[P]** The level is a field in the file; when the tool or an edit sets it above the computer's level, the routine waits for the user's OK on an approval card (§5.5) before it runs at that level. Lowering it needs no OK. A raised level is bound to the file's hash and to its computer: any edit to the file, or moving it, drops it back to the computer's level until a new OK. A webhook routine's card says that anyone with the URL can start it. A removed bot's routines pause.
* **[P] Outside text is marked as untrusted.** Text from webhooks and integrations still reaches the bot labelled as untrusted outside content.
* **[P] A routine file holds:** the bot, its triggers, the instructions, its approval level, its time zone, and what to do about runs missed while its computer was off (run once on wake, the default, or skip). Where it runs is simply the computer that holds it.
* **[D] Once per fire:** only the computer holding the file fires the routine, so it never fires twice and no lease is involved. While that computer is off, the missed-run rule applies when it wakes.
* **[P] Time zone:** schedules use the routine's time zone, which defaults to the user's (an account setting), not the computer's clock zone, which matters when the main is a cloud computer running on UTC.

## 8. Devices, accounts and links

### 8.1 Identity and accounts

**[D] Accounts are optional:**

* **With a waifucave account:** sign in with the existing waifucave.com accounts (Supabase: email, Discord and Google are live). Waifucave keeps the device list and makes the handshake that introduces devices to each other. It never stores transcripts or memories.
* **[D] Signing in is enough to add a device.** The account is the root of trust. **[P]** This makes the account the key to every computer, so the welcome guide strongly suggests two-factor sign-in, and any device or the account page can revoke a device at once.
* **Without an account:** pair devices with a code or QR, as Winter pairs the phone today, plus its 4-word check, which Winter already has.

**[P]** Every installation has its own Ed25519 key in the OS secret store. Revoking a device cuts its links at once. Keys and logins already synced to it cannot be taken back, so revoking starts a guided rotation of them. **[D]** An app that may answer cards (desktops and phones) also holds an answer key, apart from the link key, kept by the app where the OS can protect it: the macOS Keychain, Windows Hello or the TPM (item 91, §5.5). **[P]** On a desktop each program that draws cards, MOSS, MOSS Code and the background host, holds its own key in its own protected storage, and the device registry keeps one per program (§5.5, ruling C). On Windows and Linux, where no running image is signed, a process holding the app token can register the first key of a program that has none yet (§5.5).

**[P] Without an account:** devices pair by code and save a pair credential; afterwards they find each other on the LAN, at their last known address, or **[D]** through the waifucave handshake with that credential and no account, with n0's address lookup as the fallback (S1; the owner, revision 18, item 81); phone push is off; webhooks arrive only through a cloud computer or a tunnel (§7); **[D]** the main computer is handed over automatically, through the handshake with the pair credential (§6.4, item 85); the web companion needs a one-time pairing.

### 8.2 One persistent link per device pair

* **[P] One link for everything.** Each pair of devices keeps one long-lived, encrypted link open, and everything travels over it: RPC, live event streams, sync, screenshots and files. This avoids the slow part, which is setting up a connection (finding a direct path can take a second or two).
* **[P] Not a WebSocket:**
  * Two devices behind home routers cannot open a WebSocket to each other, because one side would have to be reachable like a server.
  * Over a single TCP connection, a large screenshot holds up the small messages behind it.

  Between devices the link uses QUIC, whose independent streams run over UDP, through iroh (chosen in spike S1, §8.3). The browser uses WebRTC data channels.
* **[P] Speed, in typical figures:**

  | Path | Delay |
  | :- | :- |
  | Same Wi-Fi | 1–5 ms |
  | Direct over the internet | the plain network delay, usually 10–80 ms |
  | Through a relay | roughly 20–100 ms more |

  A model takes 0.5–3 s just to start answering, so the network is a few percent of a turn. Bandwidth matters more than delay for screenshots and files.

### 8.3 Direct first; relays are plugins

* **[D] Links are direct.** The waifucave handshake only exchanges each device's addresses (signalling); it never carries content.
* **[D] Relays are plugins.** **[D] n0's public relays are on by default** (revision 12; this replaces "none is on at first"), and the welcome setup guide has a page to swap them quickly for the user's own: their cloud computer, a server of their own, or their own Cloudflare account. **[P]** Each choice is a relay plugin. No iroh relay exists for Cloudflare yet, so that one is a relay we write: a Durable Object can carry the relay's WebSockets, and finding direct paths stays with STUN, since Workers can't serve UDP. Traffic through any relay stays end-to-end encrypted, so a relay never sees what devices say. **[D]** It does see presence, which is accepted (S1; the owner, revision 18, item 79): each device keeps a connection to its home relay, so the relay knows which devices are online, from which IP addresses, which of them talk through it, and how much they send. No relay is added per pair at run time. The cloud computer relay, bundled and off until a cloud computer exists, has a public address, so every device can reach it directly. Winter's phone already uses n0's relays.
* **[D] Discovery works like waifucave's pairing service today.** pair.waifucave.com and ts-connect exchange each device's addresses as **signed, encrypted** records, so even the handshake never sees them in the clear. Public STUN servers (Cloudflare, Google) find each device's internet address reliably. MOSS reuses this design for coordination. **[D]** A relay also tells each device its public address (QUIC address discovery, QAD, on; item 79). It carries the traffic of pairs that can't go direct, and the first packets of a connection that starts on it: where direct is unlikely, where the direct dial misses its head start, or where a device paired without an account falls back to n0's address lookup, which gives only the relay. Such a connection moves to a direct path when one opens (the dial policy, under "LAN first"; S1, items 80 and 81).
  * **[P] What the handshake carries (S1):** each device's LAN address, STUN's answer asked from the port the link then binds (iroh has no STUN of its own), and any port mapping its router granted; and a "dial now" that makes both devices dial each other at once, and again about 100 ms later. A device behind a symmetric NAT gets a STUN answer no peer can use: two STUN servers that see different addresses mark it, and its pairs need the relay.
  * **[P] The handshake for devices paired without an account** (item 81; lane I builds the service, lane H the client):
    * **Keys:** each device signs its requests with its own key for the pair: a fresh signing key per device per pair, or the link key with a domain-separation prefix, so a signature to the service can't double as a link signature. Both devices sign the registration at first pairing.
    * **Revoking:** a revoke ends the pair at the service, deleting its record and both keys, and the remaining device re-pairs if it needs to. §8.1's local revoke, which cuts the links at once, always comes first, since a lost device can still reach the other at its last known address, on the LAN or through n0.
    * **Limits:** pair registration is rate-limited hardest, since pairs cost nothing to create. Per-IP limits group IPv6 addresses by /64 and leave headroom for shared IPv4 addresses such as carrier NAT. Addresses, presence and "dial now" messages live briefly; a registration expires only after months of silence from both devices. Signed requests carry replay protection.
    * **What the service keeps:** current state only, with no presence history, and IP addresses only for the rate-limit window. Payloads stay end-to-end encrypted, so it sees keys, IP addresses and timing, never the candidates.
    * **The n0 fallback:** only devices without an account publish to n0's address lookup, and only their relay URL. Links refuse unpaired and revoked keys.
* **[P] What turning every relay off means:**
  * A small share of device pairs cannot connect, typically when both sides are behind strict routers or a mobile carrier's network.
  * The web companion needs either WebRTC, which can connect directly, or a relay (§8.4).
* **[D] The connection must be the absolute fastest.** S1 decides on measured speed: time to first connect, time to reconnect, delay, and throughput on the same Wi-Fi, directly over the internet, and through a relay. **[D]** Where the fastest first byte meets keeping set-up off the relay, the dial policy decides per pair (under "LAN first"; item 80).
* **[P] Transport choice (research R2, November 2, 2026):** **iroh 1.0 (QUIC) between devices, WebRTC data channels for the browser.**

  | | iroh 1.0 (QUIC) | WebRTC data channels | Tailscale-style WireGuard (ts-connect) |
  | :- | :- | :- | :- |
  | First connect | 1 round trip for QUIC + TLS 1.3 once a path is known; addresses are the device keys | Slowest: ICE, then DTLS, then SCTP setup | WireGuard is quick, but TCP and a userspace network stack sit on top |
  | Network change or sleep | The connection survives a switch of path, but with relays off it took 1.1 s to follow a new address in S1's lab, and 6 s on a network without a default route (plain QUIC migration: 0.1 s); MOSS re-dials on network changes either way | Needs an ICE restart: slow and fragile | WireGuard copes, but TCP inside it stalls briefly |
  | Big transfer vs small messages | Independent streams with priorities, so nothing blocks | Shared congestion control; a big transfer slows small messages | One TCP stream, so a screenshot blocks the messages behind it |
  | Throughput | Native QUIC | Weakest (SCTP; about 10 MB/s reported on one machine) | High on a LAN; window-limited on long paths |
  | iOS / browser | Official Swift bindings / browser only through relays | Yes / **yes, direct** (the only option) | Possible / no |
  | Bun | `@number0/iroh` 1.2.0 loads under Bun and compiled on all four targets, but passes bytes as JS arrays (18–64 MB/s, and Bun 1.3 stops firing timers meanwhile); MOSS holds iroh in a sidecar process of its own (below) | `node-datachannel` 0.33.6 loads under Bun and compiled on all four targets; compiling needs a small build plugin | Go helper process |

  * **ts-connect is the slowest** of the three for this traffic, but its pairing, word check and revocation design is still worth porting.
  * **A bonus browser path:** WebTransport (HTTP/3) when a device can be reached directly (same LAN or a public IP), using a pinned self-signed certificate.
* **[D] Settled (S1; the owner, revision 18, items 79–81):** the waifucave handshake and STUN do the coordination (above): they swap each pair's addresses and tell both devices when to dial, for devices paired through an account or, without one, through a pair credential (§8.1). n0's relays, on by default, see presence and tell each device its public address (above), and carry a connection's set-up only where direct is unlikely, where the direct dial misses its head start, or where a device paired without an account falls back to n0's address lookup, which gives only the relay.
* **[P] The transport (S1's lab half, November 5, 2026): iroh.** Plain quinn matched iroh's speed and punched the same NATs, and followed a new address faster (0.1 s against 1.1 s, or 6 s on a network without a default route, which re-dialling covers), but needs its own identity, discovery and relay fallback, has no iOS or Bun binding, and cannot use n0's relays. With relays off, iroh connects directly through every NAT pair that allows it (13 of 15 in the lab) given two things from the handshake: each device asks a public STUN server for its address from the port iroh then binds, since iroh has no STUN and, without a relay, learns an address only from a router that grants it a port mapping (UPnP, NAT-PMP or PCP), and both devices dial each other at once ([lab report](research/2026-11-05-s1-transport.md)).
* **[P] How moss-core holds iroh:** in `moss-link`, a Rust sidecar process of MOSS's own that holds iroh and speaks a framed protocol over stdio. moss-core starts it, hands it the device key over its stdin (never in arguments, the environment or a file), and restarts it and re-dials if it exits. Out of process, iroh's threads, aborts and native completions can't stall the daemon's timers, which n0's binding did under Bun 1.3; the hop measured 0.02–0.08 ms per round trip and 0.4–1.7 GB/s each way in S1, against an async napi call's 21–99 µs, both far above any network. `LinkTransport` hides which it is, so the same crate can ship as an in-process addon instead if M1 finds the hop costly. n0's binding is not used.
* **[P] Spike S1 (about 2 days), on real networks** — home, mobile, hotel or carrier-grade NAT, and one strict-NAT case:
  1. `@number0/iroh` loads under Bun and inside `bun build --compile` on macOS, Windows and Linux.
  2. Relay-free mode with addresses from waifucave's handshake reaches a direct path; record the success rate per network type.
  3. Time to first byte: cold, on a LAN, after sleep, and after a Wi-Fi-to-mobile switch.
  4. Small-message delay (median and 99th percentile) while a 100 MB transfer runs on the same connection.
  5. Throughput for 1 MB screenshots and for bulk files.
  6. WebRTC from Chrome, Firefox and Safari to the daemon: time to open, throughput, and delay under a parallel transfer.
  7. The WireGuard approach against iroh on the same path, to confirm QUIC wins.
  8. With n0's relays on, how often traffic falls back to them, and what the Cloudflare relay we write takes (§8.3).

  S1's lab half (November 5, 2026) answered item 1 and the lab part of items 2–6 ([lab report](research/2026-11-05-s1-transport.md)): items 2 and 5 on emulated networks; item 6 from Chrome, Firefox and Safari on the same machine as the daemon; item 3 as connect times and re-dials without NATs, not after a real sleep or behind real NATs; item 4 over repeated 8–32 MB transfers rather than one of 100 MB, with at least 200 samples behind each percentile. The runs on real networks, item 8 and, if still wanted, item 7 wait for live gate 1.
* **[P] Speed measures whatever the transport:**
  * **LAN first:** local discovery, then the LAN and direct paths, dialled by both devices at once and again about 100 ms later, keeping the fastest. **[D]** Whether the relay joins from the start is chosen per pair (S1; the owner, revision 18, item 80): each device asks two STUN servers when it binds and after every network change; when each device's two answers match, the relay is added only after a head start of about 0.5 s; otherwise, or when a device got no STUN answer, it races from the start, and the connection moves to a direct path when one opens.
  * **Connect early, stay connected:** connect at login and wake, send keep-alives, and re-dial at once on network-change and wake events, keeping whichever connection answers first. In S1's lab an existing connection came back 4.5–8.4 s after a 20 s outage ended, telling the stack about the change didn't shorten that, relay-free iroh took 1.1 s to follow a new local address (6 s on a network without a default route), and a connection is gone after 30 s of silence; a re-dial without NATs had its first reply back within 0.1 s on a 20 ms path, or within 0.85 s for iroh while the stale connection was still open. Behind NATs a re-dial also needs a fresh STUN answer and the handshake, so the handshake service must be up at every wake and network change. Requests in flight on the old connection are retried on the new one only if they are safe to repeat; a tool call whose start went out but whose result never came is recorded "interrupted, may have run" (§6.4).
  * **Fast resumption** (QUIC 0-RTT), only for requests that are safe to repeat.
  * **Priorities:** binary frames on separate streams for bulk data, with token streams and control messages ahead of screenshots and files. Priorities only order what QUIC sends next; during a transfer a control message still waits behind the bulk data already in flight, so bulk streams keep in-flight data near the path's bandwidth-delay product (a tuned stream window, or a controller like BBRv3). In S1's lab the default 1.25 MB stream window added about 8 ms to every control message on a clean LAN path whatever its priority, and a window of 1.25 times the bandwidth-delay product cut that to about 0.3 ms at the median, at 0–4 % of the throughput; the same fixed window would cap one stream at about 8 MB/s on a 150 ms path, so the window is sized per path.
  * **[P] Congestion control is chosen for lossy paths.** In S1's lab, with loss falling on single datagrams, Cubic moved 0.2–0.3 MB/s at 1 % loss and 80 ms, and at 0.5 % and 150 ms, on both stacks; noq's BBRv3 mostly under 1.3 MB/s; quinn's BBR 3.4–4.9 MB/s, though it added up to 26 ms of queueing at 1 % loss. M1 picks and tunes the controller (iroh accepts one from MOSS); live gate 1 checks it on real Wi-Fi and mobile.
  * **Compression:** zstd for text and JSON, none for images.
  * **Screenshots:** hardware-encoded JPEG or WebP at about 100–200 KB, or only the changed regions.

## 9. Computers

### 9.1 Computers and the folder tree

**[P]** A computer is **any device running `moss-core`** that the user has connected. Each one reports:

* its OS
* whether it has a display
* which ACP agents are installed

**[D] One folder tree across every computer** (the owner's design, November 3):

* The bot sees `home/<Computer>/` for each connected computer, for example `home/Studio/`, `home/Desktop1/` and `home/Laptop1/`. Each one is that computer's home folder: `home/Desktop1/` is `~` on Desktop1.
* `Read`, `Write`, `Edit`, `Glob` and `Grep` work on any path in the tree. Each call runs on the computer that holds the files; `Glob` and `Grep` search there and send back only the results.
* `Bash` runs on the computer that holds its working folder: `cd home/Desktop1/project1 && git status` runs git on Desktop1.
* Commands can cross computers: `mv home/Desktop1/project1 home/Studio/` moves the folder to the computer called Studio. **[D]** It goes by the direct path (below; the owner, revision 18, item 89).
* `Agent` takes a computer and a root folder in the tree. The core translates the root to the real path on that computer, and the agent runs there only (§9.3).
* The system prompt lists the computers, their OS and how each is linked (same Wi-Fi, over the internet). It says that moving large files between computers is slower, so the bot should work on a project on the computer where it already is, **[D]** and that a command runs on the computer that holds its working folder and sees only that computer's files, so a build, an install, git or a search of another computer's project runs there, by `cd`-ing into its folder first (item 89).

**[D] No OS mounts** (the owner, revision 18, item 88; this replaces mounting other computers' folders as a network file system, which spike S6 measured). No computer mounts another computer's folders into its file system: there is no NFS, WinFsp or FUSE. MOSS works on each folder through the computer that holds it: the holder's daemon serves the tree over the link, behind the holder's fence.

**[P] How it works:**

* **Live access, not sync.** Files are not copied to every device. Each call goes over the link to the computer that holds the files, when it is needed. Syncing whole home folders would copy terabytes to every device and bring conflicts.
* **The tree is MOSS's, not the file system's.** `home/<Computer>/…` is a path in MOSS's tools. A tool's call on another computer's path goes over the link to that computer's daemon. The daemon serves the tree from its own disk (stat, list, read, write, rename, links, change events) and applies its own fence to every request (below). Nothing is mounted.
* **[D] Tools and Bash run where the files live** (item 89). `Read`, `Write`, `Edit`, `Glob` and `Grep` run on the computer that holds the path. `Bash` runs on the computer that holds its working folder, in the real folder there, so builds, installs, git and searches run at that computer's own speed. A program sees only its own computer's files: a command can't open another computer's path, so the bot copies the file over first, or runs the command where the file is. The system prompt says so.
* **[D] Moves and copies between computers take a direct path** (item 89). When Bash's command is a plain `mv` or `cp -r` between two computers' folders, the core streams the tree from one holder to the other over the link. **[P]** It copies first and deletes the source only once the copy is whole, so a drop mid-move leaves the source as it was. Each move is judged by both computers' levels.
* **Same-computer paths are native.** On each computer, `home/<itself>/…` is its home folder, so any program there resolves it at full speed. **[P]** The tree's root is a folder of the user's own outside every home folder: `$XDG_RUNTIME_DIR/moss` on Linux, `/Users/Shared/moss-<uid>` (0700) on macOS, and a folder outside the user's profile on Windows (M1 picks it). The computer's own entry is a symlink (a junction on Windows), so a search of the home folder never walks into the tree. Other computers' entries aren't on disk, and `home/` is read-only, so a program that names one gets "no such file", and nothing it writes lands on the wrong computer.
* **[P] Computer names** are unique ignoring case and use only letters, digits and hyphens, so a path typed in either case means one computer. A Windows computer's own name is never one Windows reserves (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`). A renamed computer keeps its old name as an alias.
* **[P] `bots/<bot>/`,** at the top of the tree, holds each bot's memory, its agents' transcripts and its instructions file (§6.1, §6.5). It always resolves to the computer running that bot.
* **Offline computers fail fast.** A computer known to be offline answers "computer offline" at once and never hangs. **[P]** A link that drops silently is known within 1.5 s: any bytes from the computer prove it alive, and both ends ping every 250 ms. Calls in flight then fail with "computer offline", within about 1.7 s of the drop, and a closed link fails them at once. On a live link, a call fails once the link has carried no answer for 10 s; a slow link that keeps delivering answers isn't offline, and a call can then wait up to 60 s (S6).
* **Approvals follow the files.** Each action is judged by the level of the computer it touches, and a move between computers needs both computers' levels. **[P]** At ask for risky actions, the computer that holds the files runs its own reviewer on another computer's calls, as it does on its own (R1). Only the calls the reviewer judges risky need a card, never a blanket card for every edit from another computer; the card goes to the user's devices, any desktop or phone (item 91), and the signed answer travels with the call.
* **[D] The Files panel exists only in code sessions** (item 88). It is rooted at the session's folder (for example `~/xcode/moss/`), on whichever computer holds it, and never shows more than that folder. Its listings and its change events come from the holder's tree service. Bots have no file view.
* **Outside the home folder,** a computer's other paths (`/usr`, `C:\Program Files`) are reached by Bash running on that computer.
* Computer-use tools on two or more computers take the computer's name in their `computer` field, since screens are not files (below). The system prompt says which computer-use tools work on which computer.

**[D] MCP tools across computers** (the owner's design, November 3):

* **Local servers run on each computer separately.** A local server runs on one machine: a `stdio` command such as Blender's, or plugin code bound to its computer, such as computer use. The user installs it on one computer, or presses **Mirror** to install it on the others too, and each copy runs on its own computer.
* **A local server on two or more computers gets a `computer` field.** Each of its tools gains a field listing the computers that have it, and the model picks one: `mcp__blender__Render({ computer: "Desktop1", … })`. A server on one computer gets no field, and every call goes there.
* **Remote servers work from anywhere.** An `http` server, or plugin code that only talks to the web (such as `mcp__moss__WebSearch`), is not tied to a computer. The computer running the session makes the call, and files the call returns are saved there.
* **A remote tool's `saveTo` field sends its files elsewhere.** It takes a folder in the tree, and the computer that holds that folder makes the call, so the files land there without a second transfer: `mcp__figma__Export({ saveTo: "home/Laptop1/designs/", … })`.

**[P] The details:**

* **Files** are a call's embedded resources and images. The core writes them to `saveTo` and puts their tree paths in the result. Every remote tool gets an optional `saveTo`.
* **Without `saveTo`,** files go to the bot's scratch folder on the computer running the session (§6.4). An ACP agent's bridged remote calls run on the agent's computer.
* **[D] The `computer` field is always required** wherever it appears, so nothing runs on the wrong machine by accident. **[P]** Each user message says which device it came from, so the bot knows where the user is.
* **The list in the field is refreshed at compaction,** or once the cache has expired anyway, like the MCP block (§6.1), so the prompt cache survives. A copy mirrored in between is announced in an appended note and works at once, because the core checks the field against the live list. A server that gained its second computer in between has no field yet, so its calls go to its first computer until the refresh.
* **A computer that is off** answers "computer offline" at once.
* **A name clash:** if a server already has its own `computer` or `saveTo` field, ours is called `mossComputer` or `mossSaveTo` for that server.
* **[D] Plugin folders still sync to every computer** (§8.5). A local server inside a plugin runs only on the computers ticked for it, and Mirror ticks the rest. To take it off one computer, the user unticks that computer; removing the plugin removes it everywhere.
* **Sign-ins:** a remote server's sign-in is a synced credential. Only the refresher of §8.5 refreshes it; another computer that makes the call uses the current token and asks the refresher when it expires.

**[D] Default access on a newly connected computer is "ask for risky actions".** Reads and safe commands run freely. These ask the user first:

* risky commands
* deleting files
* purchases
* screen control outside windows and tabs the bot opened

This works like Winter's auto mode with the safety reviewer. The user can change the level for each computer. Bots are equal, so the level never depends on which bot is acting.

**[D] What a bot does without asking at "ask for risky actions"** (the owner, after his try of November 10: "bots are supposed to be autonomous most of the time"). A bot acts on its own for whatever the fence and its sandbox already hold in, and a card comes up only when it wants to go beyond that, or to do something not easily undone. The fence's refusals, the fenced places that always ask, paths another computer resolved, and read only come first and are unchanged.

* **Runs without asking:** reading; changing files in the user's own folders (Documents, Downloads, Desktop, a project folder); web search; reading a web page whose address the conversation already saw (in the user's own message or as a web search's hit), up to 5 pages from one site and 20 in all in a turn; messaging the bot's own sessions (its side threads, the agents it started) or a session whose level is no wider than its own; stopping an agent it started; starting an agent MOSS has admitted. Shell commands, which run in a sandbox drawn from the fence: at "ask for risky actions" they write only to the bot's own folders and the temp folder and reach no network (the user's home is writable from "accept edits" up).
* **Asks, or goes to the safety reviewer and then asks when it isn't sure:** changing files in sensitive places (the dotfiles and dot-folders in the home and deeper down, `~/Library` with its keychains, application data and preferences, anything inside an app, anything outside the home); moving files; a plugin's tool, unless it is one of MOSS's own bundled tools it knows (a plugin's word that a tool only reads isn't taken: the OK card will name a plugin's read-only tools, and **[P]** the tools it says only change its own display, which run without a card only where its tree can't reach the network and only reads MOSS's state); a web page at an address the bot made up itself or found on a page it read, since a page can tell it which addresses to open and an address can carry what the bot has read, and any page past the turn's 5 from a site or 20 in all; deleting; purchases; screen control outside the bot's own windows; an agent MOSS hasn't tested.
* **[P] What a plugin's tools that run without asking still leave open** (`readOnly` and `contained`, §5.9; a declared read-only tool runs as a read, at every level, only when the router's binding and lane B's check say yes at the call): a declared read may still write the plugin's own data and its synced store, which copies to the user's other computers running the same tree; and (a) what such a tool is handed may reach the plugin's own UI layer, which reaches no network but for WebRTC's connectivity checks, not yet proven closed (§5.3's known gap), so a hostile plugin with a UI layer could try to send it that way; (b) what it is handed may be kept in the plugin's data folder and its synced store, and the store reaches the user's other computers running the same tree; (c) data kept now could be sent by a later version that gains the network: that update asks for a new OK, and its card says in one line that it could then send what its tools were given earlier.
* **Always a card, with no reviewer and no "always" (at "ask for risky actions" and "accept edits"):** changing anything in a `.git` (its hooks and config run later, outside any sandbox), or in a folder on the user's PATH (a program put there runs the next time the user types its name); a message to another bot's conversation at a wider level than the bot's own, naming where it goes. Changes to the engine's own settings, levels, permissions, plugins and trust are always a sealed card, at every level.
* **A shell command that needs more** asks with the bot's `RequestAccess` tool. For a folder of the user's own, it gets a card ("<bot> wants write access to <folder> for shell commands"; "Always allow" keeps that folder for that bot). A sensitive folder is never given to shell commands. Network access for shell commands isn't granted yet: the runtime's sandbox can't let only some hosts through, and the whole network, unix sockets included, is never given. What is granted joins the conversation's sandbox, and the turn goes on at once under it, so the bot runs the command again. It is never an unsandboxed command, and no unix socket (MOSS's own, an SSH agent's, Docker's) is reachable from one at any level. While a background command or monitor of the conversation runs, a file tool's change inside the folders its shell commands write goes to the reviewer and then a card, even in the bot's own folders.
* "Always allow" on a card is kept for the bot that asked, never for every bot. "Accept edits" adds changes in the sensitive places above; "ask" and "read only" stay as strict as before for a user who wants that. The user can loosen the rule on made-up addresses.
* **[P]** A bot's own conversation may run one command outside the sandbox: with the outside-the-sandbox option the call always raises a sealed card ("<bot> wants to run a command outside the sandbox", the whole command shown as code, "It runs as you, with the network and everything your account can reach."), at every level except read-only (which refuses it like any command), with no reviewer, no "always" and no saved rule. A side thread, a subagent and the coding agent keep commands inside the sandbox, and such a call there is refused with no card.

**[P] The levels and the reviewer:**

* The levels are read only, ask, ask for risky actions (the default: Winter's `auto` with the reviewer), accept edits, and fully automatic (`bypass`). Until C5, one level covers the local computer. **[P]** They form a total order, read only < ask < ask for risky actions < accept edits < fully automatic: accept edits is ask for risky actions plus edits and moves without asking. Read only is absolute; no saved rule beats it.
* Bash may write in the home and temp folders, except the fenced set (below), under Winter's network rules. That is wider than Winter's working-folder fence, so the reviewer's prompt is rewritten. **[P]** On every OS a sandboxed Bash or PowerShell command gets no network, as S2 read Winter's sandbox (it takes no domain lists); C-M2 confirms this against Winter's real behaviour. A command that leaves the sandbox keeps a native floor over the fenced set (reads, writes, links and renaming an ancestor) and still can't reach the cloud metadata address, so the escape floor carries an address rule as well as paths (S2, S8).
* The reviewer chooses its model by Winter's `reviewer.model` rules, and asks the user when no model can run.
* As in Winter (`isHumanTurnOrigin`), a card or question from a turn the user's own message did not start is denied after 10 minutes (§5.5).

**[D] Bots cannot raise their own access.** A core fence keeps bots' tools away from the files that hold settings, approval levels, credentials and bots' settings, on every OS. Bots change those only through core tools, and anything that raises access ends in an approval card (§5.5). Routine files are not fenced: bots write routines as files, and the app asks before running one at a raised level (§7). **[P]** The plugins folder is fenced (the `plugins` kind), with one exception per builder: a bot's own sessions write the folder of a plugin it built and the user OK'd (§5.6, the workshop rule), never its root or another plugin's; a bot brings a new plugin in with `PluginInstall`, whose OK card is the user's gate (§5.1).

**[P] The fence, precisely** (built in C1):

* **The fenced set:** settings, levels, saved rules, connector permissions, trust, the device list, bots' settings, the credential store, development folders (§5.6), the plugins folder (but each bot's own workshop plugins' folders for that bot's sessions, §5.6), plugins' data folders (§5.4), the daemon's run folder, **[P]** transcripts and usage rows, the MOSS Browser's per-bot profiles (§12.1) and the places the OS starts programs from (below). Bash's fence denies writing to them on every OS, and Winter's escape floor holds too: a command that leaves the sandbox still may not write them (§4). It also denies reading the run folder, as Winter's does (`runtime-sdk/mode-options.ts`), and on Windows and Linux the secrets file and any key file (§8.5).
* **The secret store:** on macOS, MOSS's Keychain items trust the daemon's binary alone, as Winter's do (`auth/credential-acl.ts`), so no other binary is ever served them silently. As in Winter, Bash's sandbox denies the Keychain (the runtime's `sandbox/profile.ts` allows four system services, none of them the Keychain), so the CLI, the daemon's own binary, can't read its token under a bot. **[D]** Windows and Linux have no such check, so there MOSS keeps its secrets, tokens and device key in one encrypted file, with the key in the OS store (revision 13, item 59). Bash's fence hides the file and the run folder. **[D]** On Windows, model-run Bash and PowerShell run as a dedicated sandbox principal (the owner, revision 18, item 76), so they don't inherit the user's DPAPI, Credential Manager or ssh-agent access. `gh`, git credential helpers, Docker registry logins and ssh-agent signing reach them only through a MOSS credential broker acting in the user's logon context, as on Linux, where the same tools reach the Secret Service through the broker of §4. The broker never hands over raw keys or stores. **[P]** It admits only the credential operation allowed for that session, destination and identity, and MOSS's own secrets, approval tokens and device keys are never served to model commands. On macOS those tools can't reach their Keychain logins from a bot's Bash, so C1 adds a git credential helper that gets logins from the core, which hands bots only the ones the user allows.
* **[P] Nothing a command writes runs later on its own, or carries over** (S2, with the controller's ruling). Bash's writable home and temp folders exclude the places the OS starts programs from at login or on a schedule; they join the fenced set on every OS, escapes included: on macOS `~/Library/LaunchAgents`, login items and shell startup files; on Linux `~/.config/systemd/user`, `~/.config/autostart` and shell startup files; on Windows the Startup folders, the Run and RunOnce keys, PowerShell profiles and Git Bash's startup files. As with the rest of the fenced set, a bot asks the user to change them. On Windows, where Bash runs as a sandbox principal, nothing the principal writes carries over to another command or session, concurrent ones included: a principal per running session or one session at a time; its profile and registry hive reset for each session, checked on every launch and failing closed; its grants and temp folder per session. Fencing a list of auto-run paths is only an interim measure there.
* **[P] The holder enforces its own rules** (S6). The computer that holds the files applies its own fence to every request that comes over the link: the tree service's, every file tool and Bash call routed to it, and the Files panel's. It resolves each path on its own disk, links included, and refuses whatever lands outside the home or in the fenced set, checking the real path of what it opened. It compares names the way its disk does, with case and Unicode form folded and, on Windows, trailing dots, spaces and short names too, so a folder swapped for a link, or a fenced name in another case, can't lead into the fenced set. Over the link the fenced set can't be read or written and doesn't show in listings, whoever asks. The approval levels still apply on the computer where the program runs.
* **[P] Links inside a home** (S6): an absolute link that points inside the home is served as a relative link, so it resolves on every computer. A link that points outside the home, absolute or relative, answers "permission denied" when read from another computer, since it would resolve against that computer's own disk.
* **Other writers:** `stdio` servers, host halves and computer use run as the user and can write these files (§5.2), and agents have them denied through their own sandboxes and settings (§9.3). A change made outside the core takes effect at once only if it lowers access; one that raises access waits for a sealed card.
* **No core tool changes these items in 1.111.1;** a bot asks the user.

### 9.2 Cloud computers

**[D]** Bots can use cloud computers, and all of the user's bots share them.

* **[P] Simplest form:** the user runs MOSS headless in any VM and pairs it, after which it is just another computer.
* **[D] A cloud computer is a plugin folder.** Making one means writing a folder that names its provider, size and region (for example `computer-hetzner-1/`) into the plugins folder. The user or a bot can write it; no tool is involved.
  * **[D]** The app finds the folder and asks the user before creating the VM. The provider plugin (contributing to `computerProviders`; **Google Cloud** and **Hetzner** first) then creates the VM, installs the image and pairs it in one step.
  * **[D]** The app then asks whether to make it the main computer.
  * **[P]** Removing the folder asks whether to delete the VM too; deleting a VM always asks, whatever the folder says.
  * **[P]** The folder contributes `computer` (§5.3, §5.9). The VM's own state (server id, address, pairing) lives in the computer registry, not in the folder, and editing `size` in the folder asks before resizing.
* **[P] Official image:** Linux that runs the daemon alone, with Chrome for Testing's headless shell as the bots' browser (§12.1), and turns lingering on so the daemon starts at boot. A desktop session for computer use comes with opensky.
* **[P] Safety:** pairing tokens work once; VMs get no cloud service account; the bash fence blocks the cloud metadata address, so a bot cannot lift cloud credentials from inside the VM. A core switch pauses all bots and routines at once.
* **[P] Sharing rules:** sharing between bots needs per-app and per-window holds, like Winter's held apps, so two bots don't fight over one window. The core keeps each computer's holds and the user-working mark. Plugins with the `computers.control` capability take and release them through the plugin API, which also tells the approval cards when an action is running (§5.5); its OK says "controls the screen and input of your computers" (§5.4).
* **[P] More than a computer:** a connected cloud computer naturally becomes the **main computer** (once the user confirms), a **relay** the user can choose over n0's (§8.3) and a webhook receiver (§7).

### 9.3 The Agent tool and its placement

**[D]** A bot can delegate to an ACP agent, choosing **which agent**, **model**, **effort**, **which computer** and the **root folder** in the folder tree (§9.1), or a vendor's cloud.

**[D] How a delegation runs.** It works like Claude Code's background agents:

1. **`Agent` starts a background agent and returns at once.** The agent never runs in the bot's main conversation.
2. **While it works,** the agent can message its bot with `SendMessage`. Those messages fold into the bot's conversation like any bot message (§6.4).
3. **The bot keeps control:** `ListAgents` shows the agent (with every other running session and bot), and `TaskStop` stops it.
4. **When the agent finishes,** the bot receives a **task notification** carrying the agent's final report and the path to its full transcript.

**[D] The user can drive agents directly:**

* Each background agent is a **live session** the user can watch, type to, interrupt and stop. **[D]** With MOSS Code installed, a bot's coding task carries an "open in MOSS Code" link, which opens it there as a session (§9.4); **[P]** the task shows in the bot's conversation as activity, with MOSS alone as with both, and the link opens that session live (item 118).
* The user can also start a coding agent directly from MOSS Code or the CLI (`moss code`), with no bot involved (§9.4).
* **[P]** A **session** is any running conversation: a bot's main conversation, a side thread, a background agent, or a coding session the user started. `SendMessage` and `ListAgents` work on sessions.

**[D] How plugins reach an ACP agent,** for plugins scoped to `agents` or `both`:

| Plugin part | Reaches the agent? | How |
| :- | :- | :- |
| MCP servers and MOSS tools | Yes, on every ACP agent | Through **one MOSS bridge MCP server**, handed to the agent at session start (ACP's `session/new` accepts MCP servers; every agent supports stdio). The bridge serves the plugin's tools and MCP servers wherever they actually run, under the same approval rules, and also provides `SendMessage` and `Glossary` |
| Skills | Yes | Through the bridge's `Glossary` tool on any agent, plus placement in the agent's own skills folder where it reads one natively (Claude Code) |
| Agent definitions | Only on backends with subagents | Placed in the backend's own folder (Claude Code's agents directory) |
| Claude Code plugins | As wrapped plugins, on every agent | **[D]** Wrapped into MOSS plugins when they are added (§5.1, revision 14); MOSS never loads them natively; a Claude Code agent still loads what the user installed in Claude Code itself, as it would outside MOSS. Their parts then reach agents like any plugin's, by the rows above and below |
| Hooks | Only on calls through the bridge and on in-process subagents, plus Claude Code's own calls | An ACP agent's own loop is out of reach; **[P]** a hook with a `command` is also placed in Claude Code's own settings for Claude Code's own tools, as skills are placed in its skills folder, through MOSS's shim, which passes its deny and ask and drops an allow (§5.3) |
| UI, themes, surfaces, voice, avatars | No | They belong to the apps and the background host, not to agents |

**[P] How that maps onto ACP:**

* **Messages from the agent:** the bridge MCP server gives the agent `SendMessage`.
* **[P] The bridge's link:** a token for that one agent session, whose role allows only the bridge's own tools, `SendMessage` and `Glossary`. **[P]** MOSS treats everything handed to an agent as stored in plain text, readable by the user's other processes and passed to every server the agent starts: its environment, argv, `mcpServers` entries, `_meta` and prompts (Antigravity writes every `mcpServers` entry, `env` and headers included, into its conversation database). So:
  * The bridge token is the only secret handed over, and it goes only in the bridge entry's `env`.
  * The daemon accepts the token only from a process descended from that session's agent process (the caller check of §3.1), with one live connection per token: a descendant in the process tree on macOS and Linux, and a member of the agent's job object on Windows, where a process can name any process it can open as its parent. The job is unnamed and allows no breakaway.
  * The token is revoked at `TaskStop`, at session end and on a daemon restart, and minted anew on `load` or `resume`.
  * The agent's environment comes from an allow-list. It carries the agent's own login only where that backend needs it there.
  * Settings marks the backends that store what they are given in plain text, or pass their environment on to the servers they start (Antigravity does both).
* **[P] A plugin tool on the bridge** (lane B, checklist row 1.93). The bridge names each tool `<server>__<tool>` (its server's key, so two plugins' tools never share a name); a name two tools would share, or one too long for MCP clients, is left out. Its list is read when the session starts, as an agent reads its MCP servers' lists once; a call is resolved against the plugins as they are when it is made, so a plugin switched off, stopped, refused or not for this computer since then answers "no tool named …". A call meets the plugins' `tool.before` and `tool.after` hooks (the in-process backend runs them itself), then it is judged exactly as the same call in the session that owns it: the user's coding session by its own level and saved rules, a bot's agent by that bot's level and saved rules (never more than the bot), its card naming the agent's session; a bot's agent's card offers no "always", which would be saved under the bot. It runs where its server runs, as the agent's session. A manifest's `preload` tools are offered from the start, as a bot's are. Skills and agent definitions are placed only for Claude Code, in one local Claude Code plugin per session in MOSS's fenced run folder (`run/agents/<session>/claude-plugin`), handed to it at `session/new`: never in the user's `~/.claude` or a project's `.claude`, so a file of the user's with the same name is never touched (how Claude Code shows the two is a live check). The folder is written afresh at each placing, and placed again for the running sessions when a plugin is turned on, off, removed or updated, so what was turned off or removed leaves it; a session that started with nothing placed was handed no folder, so what a plugin adds reaches its next session. Live checks: Claude Code loads the folder, reads a skill's other files there (the folder is in MOSS's run folder, which an agent's own fence denies), and drops a skill removed mid-session. Command hooks are never placed in an outside agent.
* **[P] The bridge's essentials reach the prompt.** Cursor and Antigravity file MCP server instructions as documents the model may open, not in its prompt. So the bridge's essentials (who sent the work, `SendMessage` to report, `Glossary` for skills) go into the agent's system prompt where the backend lets a client add to it (Antigravity's `_meta.antigravity.systemPrompt.append`, the unstable ACP `systemPrompt`, or the Claude adapter's `_meta.systemPrompt`), where they survive the agent's own compaction; otherwise they go into the first prompt. The plugins' instructions, which the bridge still sends as its server instructions, stay reachable through `Glossary`, and every bridge tool's description stands on its own.
* **Messages to the agent:** a message from the bot reaches the agent as its next prompt.
* **Stopping:** `TaskStop` sends ACP's cancel, then ends the process. **[P]** One agent process serves one delegation, contained as a group: a process group on macOS and Linux, a job object on Windows. `TaskStop` sends `session/cancel` (both agents S5 tried answered `cancelled` within 15 ms and killed the running command), then ends the group. When a cancel leaves tool calls open, MOSS closes them itself.
* **The transcript:** MOSS records the agent's session updates into `bots/<bot>/agents/` (§6.5), so the path in the notification opens with the bot's own file tools. **[P]** Updates that arrive between a `session/load` or `session/resume` request and its response are a replay, and are neither recorded nor shown again. MOSS reattaches with an honest `resume` where the backend has one, otherwise with `load`, dropping the replay; Antigravity's `resume` replays too, so it counts as a `load`. MOSS keeps its own record of agent sessions and never relies on `session/list`, which Cursor limits to the calling process's own session and Antigravity answers with every session on the computer.
* **Delivery:** a task notification folds in after the bot's next tool call if the bot is busy. If the bot is idle, it starts a new turn. **[P]** A refused card ends the agent's turn on Antigravity, with no reply, so the task notification says the agent stopped at a refusal, and the bot can message it to go on. A plan or quota refusal can arrive as ordinary agent text (Cursor), so the notification carries the final text unchanged.
* **Paths:** files the agent's report cites are given as folder-tree paths (`home/Desktop1/…`), so the bot can open them wherever they are.

* **[P] Local placement:** the daemon on the chosen computer starts the agent's ACP process there and streams its events back to the bot.
* **[P] Agents with ACP today** (checked in spike S5, November 5):
  * Native: Gemini CLI (`gemini --acp`), Grok CLI (`grok agent stdio`), Cursor's CLI (`cursor-agent acp`), Antigravity CLI (`agy acp`), Devin (`devin acp`) and DeepSeek Harness (`dsh --profile acp`, one workspace; MCP servers need `dsh-acp` 0.1.2 or later, a prerelease today). Since June 18, 2026, Gemini CLI needs a Gemini API key or Vertex AI, and Google's free and subscription accounts use Antigravity CLI.
  * Through adapters: Claude Code (`@agentclientprotocol/claude-agent-acp`) and Codex (`@agentclientprotocol/codex-acp`, which drives `codex app-server`).
  * Cursor's CLI and Antigravity CLI accept the stdio and HTTP MCP servers passed at `session/new`, pass on their `env` and `headers`, and give their tools to the model.
  * MOSS never trusts a command name on PATH: `agent` is both Cursor's and Grok's. It resolves each backend's binary to its real path and checks that it is that vendor's (its version output, and the signer where the OS has one) before starting it.

  Model and effort are passed where the agent exposes them, **[P]** through `session/set_config_option` (categories `model` and `thought_level`). Cursor folds effort into its model values, and the models offered depend on the account's plan (Cursor) and on the client's name (Antigravity). On Cursor a delegation's model choice becomes the user's own selection, kept across processes and in Cursor's config, so MOSS restores the user's selection after the delegation unless M2 finds a way to choose that doesn't persist. Antigravity doesn't persist its choice.
* **[D] Winter's own coding mode becomes an ACP agent** that bots can delegate to like any other. **1.111.1 waits for it.** The release ships only once this agent speaks ACP, so Winter users keep a first-party coding agent. It is MOSS's own coding agent (§9.4).
* **[P] Cloud placement:** vendor cloud agents (Claude Code on the web, Codex cloud, Cursor background agents) are **not** ACP. Each needs its own plugin, contributing to `agentBackends`, that speaks that vendor's API. Devin's cloud is the exception: `devin acp --cloud` relays ACP to cloud Devin sessions, so its backend is an ACP backend with cloud placement. Whether the stdio bridge reaches a cloud session, and what the root folder means there, is settled before it ships.
* **[D] Permissions work as in Devin Desktop and Zed, plus our levels.** Each agent runs as its own process with its own install, login and sandbox; MOSS does not wrap it in another sandbox (macOS cannot nest them). It is started in a mode where it asks before risky actions, and each request it sends (ACP's `session/request_permission`) goes through the computer's or the routine's approval level: answered automatically where the level allows, otherwise shown as an approval card. A model never answers them.
  * **[P] How MOSS answers:** with `allow_once` or `reject_once`, never an agent's "always" option, which Cursor would write into its own allowlist, out of reach of MOSS's levels. A card's "always" answer is saved as MOSS's own rule, and the agent still gets `allow_once`. An agent that offers no `allow_once` gets a refusal (`reject_once`, or the cancelled outcome when it offers none). MOSS keeps its own record of each answer, since agents report a refused call as `completed` (Cursor) or `failed` (Antigravity).
  * **[P] The bridge's own tools:** a permission request is answered `allow_once` at once only when it exactly matches the session's bridge server name and a tool from the bridge's own list, read from the structured input of the matching tool call (Cursor's `rawInput.providerIdentifier` and `toolName`), never from its title, since Cursor titles MCP requests `<server>-<tool>: <tool>` and either part can hold a hyphen. The bridge applies MOSS's approval when the call arrives. Anything else, or anything ambiguous, goes to the level and the card.
  * **[D] Cursor is accepted with its workspace folder and its deny rules as the boundary** (the owner, revision 18, item 78). On Cursor, edits inside the agent's root, commands on the user's own Cursor allowlist and, by Cursor's code, deletes inside the root never send a request, so they never reach a card. Settings marks the backend as "edits inside its folder without asking". **[P]** At the read-only level MOSS starts Cursor in its `ask` or `plan` mode, which ACP offers. Antigravity's own settings may pre-approve actions as well (`access_grants`, and `--include-default-customizations`, on by default); the bridge's tools still go through MOSS's approval.
* **[D] The fence reaches agents through their own settings** (revision 12), **the way Devin does it** (revision 13). Each agent's commands run in its own sandbox, started with the fenced set (§9.1) denied in its own format (Claude Code's deny rules and sandbox settings, Codex's sandbox settings, Devin's `Read(...)` and `Write(...)` rules), and with the run folder and, on Windows and Linux, the secrets file hidden from its commands and its read tool. An agent with no sandbox on that computer (on native Windows, Claude Code and Devin today) starts only after the user's OK, which says it could read MOSS's logins and approve its own cards; like Devin, MOSS never quietly runs one unsandboxed. `Agent` refuses a root folder that contains the MOSS home, and a permission request that touches a fenced path is always a card, at every level. **[P]** A backend that can't take the deny list relies on the rest (its own sandbox, a root outside the MOSS home, and cards for fenced paths), and Settings marks it; on Windows and Linux it also needs the OK above. **[P]** A backend counts as protected only for an exact version and configuration shown to protect its shell's descendants and its file tools, to refuse a widened policy, and to keep the floor on retries and exclusions (S8); every other combination needs the OK above, and MOSS still adds no outer sandbox.
* **[P] Stalled agents:** Winter's stall watchdog carries over. An agent that makes no progress for 10 minutes is stopped, and its bot gets a task notification saying so.

Claude's own app starts only Claude; MOSS Code starts any agent MOSS supports.

## 10. Surfaces and companions

* **[D] The island and the Dispatch pill become plugins contributing to `app.surface`.** In Electron they become frameless, transparent, always-on-top windows that the background host opens from their `app.surface` entries, with small native add-ons only where needed (notch geometry, gestures). The Swift versions stay in the repo as the reference for rebuilding them (§12).
* **[P] Surfaces by capability, not by name** (F4, the owner's ruling of 2026-11-15: no infrastructure in the core or the app that only one plugin uses). Every behaviour of the island and the pill is a manifest field or a capability any plugin may ask for behind its OK card, and no door checks a plugin's id: floating on top is `overlay` (`window.alwaysOnTop`); stepping aside for the product's windows is `window.front: "steps-aside"` (while a window of the product is focused, and never while the router has placed a card on it); drawing the pending cards is `window.cards` with `approvals` and `approvals.all` (the platform's one-place-at-a-time rule stays, now the router's per computer (§3.5): a surface with `cards` draws the cards the router places on it, which is the island's when no window of the product is focused); the four-finger tap is `window.summon: ["tap"]`; a line in the tray menu is an `app.tray` entry (`toggles` one of the plugin's own surfaces, kept per surface across restarts, or a `command` of its own) with `tray`; the pill's send is `user.send` (the protocol method `pill.send` is now `user.send`). A third-party surface with these can draw any pending card's sealed buttons (it sees the card's id, place and meta, never its words, and the press stays the sealed frame's own) and send as the user on a press. What does not move: a surface's size is at most 800 by 600 without `overlay`; a surface's `given` card tokens are taken only from a plugin with `approvals.all`; the entry ids and titles a spot reserves (the island's Needs you) are the bundled `moss` tree's alone.
* **[D] The island looks the same on all three OSes** (the owner, revision 18, item 82): one top-centre island, themed by tokens, with no fixed Apple blue. It sits at the notch, and on a screen without one it grows from the top edge; on Wayland, which has no always-on-top, it is a normal window (§4).

It applies to every tab and session, not to a bot. **[P]** (G7) It is drawn in a window, inside sessions or on the screen, as the plugin chooses. A user may write a renderer plugin that draws whatever it wants on the screen, maybe several figures; the bundled plugin is what limits itself to one avatar at a time, with its own one-at-a-time rule (§5.4).

A model's outfit parts are the glTF nodes its author marks in `extras` as `"moss": { "outfit": "<name>" }` (with `"on": false` for one that starts hidden, an alternative outfit; several nodes may share a name); the renderer lists them in its catalogue and an outfit cue shows or hides them, nothing more. ### 12.1 The MOSS Browser

**[D] MOSS runs its own browser, headless, on each computer.**

* **A browser plugin shows it.** The browser view (a UI plugin of MOSS Code's window) displays its tabs in its own way, and another plugin could display them differently. **[P]** MOSS Code's browser view shows code sessions' tabs and the person's own, not bots' tabs; a bot's tab is watch only in MOSS's side panel (§6.10), and taking one over, the screen-reader case included, is later.
* **It has an API.** Plugins with the `browser` capability can open tabs, navigate and use the DevTools protocol, so users can build their own browser tools.
* **[P] A tool's live picture.** The Browser tool and the computer-use tools publish a live picture of their work for their session (§3.6), which MOSS's side panel shows, watch only (§6.10).
* **Computer use sees it as one more browser.** To a computer-use plugin, the MOSS Browser is a browser like Chrome or Safari, and it can drive it headless, as it can Chrome. opensky covers both the computer and its browsers.

**[P] How:**

* **[D] On desktops, the browser lives in an Electron program of the product** (revision 12, the owner's design; this replaces the separate browser process first chosen in the same review). **[P]** Revision 19 settles which: the background host (item 111). A tab is either headless, in a hidden window that is never shown, or shown in the browser view, and it moves between the two without reloading. **[P]** The pages run offscreen in the host, so they keep running with every window closed; a panel shows a tab as a picture. MOSS Code's browser panel forwards the person's input under the press rules of §5.5, and MOSS's side panel shows the same picture, watch only (item 111).
* **[D] A bot's tab is drawn offscreen** (design B; the owner, revision 18, item 92). It renders with no window and is shown through the browser view's viewport without reloading, as in Winter's headless helper. The [D] sentence above and §3.1 stay as written: its "hidden window that is never shown" is an offscreen one. A plain tab in a never-shown window would never draw, on any OS (S7).
* **[D] Screen-reader users** (item 93). A screen reader reads nothing in the viewport, so while one is on, new bot tabs start instead as real views in a hidden host window that is shown but that the user isn't meant to see or use (design A, only then), and a screen-reader user takes one over as a real view. No tab ever reloads: the switch decides only where a new tab starts and never moves one, and tabs made before stay offscreen.
* **[P] How:** tabs live in the background host's main process (item 111), each bot's tabs in that bot's own session partition and the user's in another, with sandboxed renderers and no Node or preload. **[P]** A bot or a coding session uses its own partition. Driving the person's own logged-in partition needs an explicit card for each session, and is never the default (R10). A bot's tab is an offscreen `BrowserWindow` that is never shown (Electron's offscreen rendering), and the person's own tabs are `WebContentsView`s. DevTools access goes through each tab's own debugger and reaches only browser tabs, never the app's windows or the sealed cards; there is no debugging port. The API passes an allow list of CDP domains (no `Target`, `Browser` or `Storage`; no paths outside the bot's scratch), and the app's own schemes never serve browser partitions. If the host crashes and restarts (§3.1), the tabs reload.
* **[P] Drawing a bot's tab:** it is laid out at the agent's 1280×800 at a scale of 1 (on Windows, `setContentSize` after it is made). It paints at 10 fps while a bot works and nobody watches, with painting stopped while the bot only reads, and at 60 fps while the person watches; a tab no bot has used for a few minutes stops painting. Its frames are CPU bitmaps. GPU shared textures are an optimization for later: only where Chromium composites on the GPU (`app.getGPUFeatureStatus().gpu_compositing`), only once their dropdowns draw, and on Linux only once dmabufs pass the live gate.
* **[P] Screenshots:** a bot's screenshot is the newest painted frame, or `capturePage` while painting is stopped or frames are textures. Both are 1280×800 at a scale of 1, whatever the display.
* **[P] Showing:** the browser view's viewport draws the tab's frames and sends the person's input back: mouse, wheel and keys with `sendInputEvent`, the IME and HTML5 drags over CDP, paste and edit commands as Electron's own, and the page's cursor.
* **[P] A page's own windows:** a window a bot's page opens is offscreen where Electron can make it so, as a cross-site one is. A same-site one can't be (Electron #55565): while the person watches, it opens as a real window; while a bot is alone, it is refused, or its address is reopened as a new offscreen tab without its opener.
* **[P] What a bot's pages may raise:** nothing the user would see. Permissions are denied by default. `window.open` goes through the browser's own handler. File choosers are answered over CDP (`Page.setInterceptFileChooserDialog`). JavaScript dialogs are answered at once (`disableDialogs`), with CDP telling the bot what the page asked; offscreen that is required, since otherwise a dialog brings the tab's hidden window on screen on macOS. `beforeunload` goes through `will-prevent-unload`. Fullscreen, notifications and printing are refused. On macOS a power blocker keeps App Nap off while a bot works.
* **[P] Private addresses** (R13): bot tabs refuse loopback, private (RFC 1918 and ULA), link-local and cloud metadata addresses by default. The check runs at connect time, after DNS, so DNS rebinding can't get round it. A code session's tabs may reach loopback, for local dev servers, but never the metadata address. A per-bot setting to allow the LAN comes later.
* **[P] The proxy** (R14): tabs connect directly at first. A setting then offers three choices: off (direct); the system proxy, including the system's own PAC file but never WPAD discovery; or an explicit http, https or socks proxy.
* **[P] The screen-reader host** (item 93): a 1×1 window, used only for bot tabs made while a screen reader is on (on Windows a 32×32 tool window at opacity 0; on X11 an empty window shape, so no pixel shows and it takes no click; on macOS M1 decides whether it is transparent). A tab a bot works in there has background throttling off and draws at the display's rate, a CDP override holds its page at 1280×800 and a scale factor of 1, and its screenshots are `capturePage` of its view, scaled to 1280×800. The host never takes focus, even when its page asks; passes a click at its point to the window below; stays out of the taskbar, the Dock, Alt-Tab, Mission Control and the Window menu; has a neutral title; and is left out of other apps' screen captures where the OS allows. On Wayland it can show in the window list and its one pixel can take a click; whether GNOME and KDE keep drawing it when covered is a live gate, and the fallback is XWayland. A tab that no bot has used for a few minutes, that plays no sound and that no one watches rests in a never-shown window with throttling on, and goes back to the host before the bot's next command.
* **[P] Winter's headless lessons carry over** (`docs/claude/headless.md`, where a windowless tab shown in the Mac app's panel was fully clickable and laid out to the panel's size): a shown tab is laid out at the view's size, and the agent's own 1280×800 returns when it goes back to headless. A Point from a screenshot taken at another size is refused. While the person holds a tab, the agent's commands on it are refused (Winter's control lease).
* **[P] From another device,** the view streams the tab as video over the link, on its own low-priority stream. The app captures the tab and encodes it with WebCodecs: S7 measured about 2.3 Mbit/s for 30 fps of full motion, and tens of kbit/s for a still page. The codec is H.264 where a hardware encoder exists, else VP8, which measured the same; where no hardware encoder exists, H.264 would mean the software encoder built into Electron, and shipping that raises a patent-licensing question. When the link falls behind, the sender skips to the next keyframe and lowers the bitrate, a design not yet measured on a real link. The codec contract (what the iOS companion decodes with VideoToolbox, H.264 and not VP8, and what Safari and Firefox decode for the web companion) belongs to lane I.
* **[P] Where no app runs** (a server or cloud computer without a display), the browser is Chrome for Testing's headless shell. It is pinned by SHA-256 to the Chromium of the app's Electron, or to the nearest build of the same milestone when that exact build isn't published, and the pin may move ahead of Electron for a security fix. The install fails closed: no pin, no install, and a reused install is checked again. The daemon drives it over the DevTools pipe (no port), with a profile folder per bot. The pipe is a browser-level connection (`Target`, `Browser`, `Storage`), so the CDP allow list sits in the daemon's API here too. On Linux it needs the AppArmor profile, as Electron does, and the server package's dependencies (S7 lists them).
* Until opensky arrives, a bundled plugin's `mcp__moss__Browser` tool drives it through the API, ported from Winter's browser tool over the DevTools protocol.

The limits to plan around:

* **[D] MOSS ships stock Electron, with no patches** (the owner, revision 18, item 94: "stock Electron, wait upstream"). So a same-site window a page opens works only while the person watches (Electron #55565), a page's dialogs are answered at once and never offered to the person, and a watched tab's frames are CPU bitmaps. Fixes go upstream instead.
* Electron has no Widevine, so DRM video sites won't play without the castLabs Electron build, which also needs VMP signing through castLabs' free EVS service.
* Chrome extension support is partial.
* Partitions are per bot, never per site, so sign-ins that hop domains keep their cookies; none mixes with the app's own.
